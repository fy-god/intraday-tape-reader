```text
provider_ts_raw
receive_time
process_monotonic
source_epoch
```

### 2.3 `IT-P1-INDEX-CURRENT-001` — P1，新确认控制流缺陷：指数仍可绕过 current-only 合同

个股 current-only 已修，但指数是另一条路径。

`Engine.poll_once()` 先：

```python
idx_admitted = self.state.update(idx_quotes, now) if idx_quotes else {}
```

但 `spirit_index.evaluate()` 不消费 `idx_admitted`；它遍历整个累计状态：

```python
candidates = {}
for code, q in (getattr(ctx.state, "quotes", None) or {}).items():
    if q is not None and is_index_quote(q):
        candidates[code] = q
```

固定源码：

https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/rules/spirit_index.py

同时 `_fetch_indices()` 明确设计为失败后 `return []` 且“不影响个股”，不会删除上一轮 index cache。

所以：

```text
R1：指数有返回 -> state.quotes 保存 index
R2：指数请求失败/少返回 -> idx_admitted_this_round 为空
R2：spirit_index 仍从 state.quotes 取 R1 index
```

本轮机制探针构造了保留的 5 分钟历史和旧 index quote：`idx_admitted_this_round=[]`，但缓存 index 仍成为 candidates，历史跨度 290s，旧点位相对起点 +1.0 点 / 2.56bp，按当前阈值谓词仍可命中。

这不是完整 repo 集成运行，所以证据等级是**静态调用链 + 控制流机制复现**，下一轮本地 Agent 必须补真正 `Engine -> SpiritIndexRule` 红测。

**影响**：`spirit_index` 默认关闭，因此本轮定为 P1，不升级 P0；但启用时它违反用户明确要求的“指数也不能绕过本轮有效观测”。可能重评估上一轮指数运动，甚至在当前指数源已失败时仍生成旧事件候选。

**修法**：不要在 `spirit_index` 内自行扫描累计 `state.quotes`。统一把 `current_by_code` / `admitted_current` 作为本轮事实源，其中可包含 index；普通个股规则仍只接股票 Snapshot，指数规则从 `ctx.observation.current_indexes` 或等价只读 current view 消费。必须保留历史 window，但 current quote 必须来自当前轮。

### 2.4 Observation Ledger v1 的四个开放语义错误

#### `IT-P2-OBS-002`：时间拒绝与 `unknown_missing` 双计

当前：

```python
admitted = self.state.update(quotes, now)
returned = dict(admitted)
...
unknown_missing = tuple(c for c in self._codes if c not in returned)
```

因此 provider 已返回、但 future/ooo 被拒绝的 code 同时落入：

```text
future_rejected/out_of_order_rejected
+
unknown_missing
```

这违背“缺失桶互斥”的含义。

#### `IT-P2-OBS-003`：`admitted` 混合时间准入与业务筛选

股票计数用 `len(eligible)`（时间准入 + filters），指数用 `len(idx_admitted)`（仅时间准入），却相加进同一个 `admitted`。因此该字段不能作为统一时间质量分母。

#### `IT-P2-OBS-004`：失败轮复用上一成功 observation

抓取异常路径调用 `set_poll_stats(... observation=None)`；Store 仅在 observation 非 None 时更新 `_observation`。`live_session` 每轮再读 Store “最近一轮 observation”。结果：Round N 失败时可能把 Round N-1 的健康账本复制到本轮样本，而且没有 `round_id`/`observed_at` 来证明陈旧。

#### `IT-P2-OBS-005`：provider 返回 zero-price 对象被记成“没返回”

Tencent parser 明确保留 `price<=0` 行用于表示停牌/不可用状态；EngineState 在准入前 `if q.price <= 0: continue`，最终 `unknown_missing` 又基于 admitted 求补集，所以 provider 实际返回的 zero-price object 被错标 missing。

本轮 truth-table 对这些口径做了互斥性验证，future/ooo 的双计和 zero-price 的误标均按当前公式必然出现。正确 ledger 必须**先计 provider object，再经过质量与业务 gate**。

### 2.5 `IT-P0-001` — P0，未修：14:57–15:00 仍属于 CONTINUOUS

## 3. 主改造：Observation Truth Contract v2

本轮不建议继续在 `RoundObservationSet` 上增加几个计数字段，而应把事实链拆清楚，再统一规则/模型消费。

### 3.1 目标与非目标

**目标**：一轮内每个 code 从请求、provider 返回、source/time provenance、质量准入、业务筛选、规则可评估、规则结果到输出都能唯一解释；规则与模型只能消费同一个 `admitted_current` 真相源。

**非目标**：不在本轮改变告警阈值、不用神经网络“学会忽略脏数据”、不把 provider 时间猜成逐笔成交时间、不把 synthetic PR AUC 当实盘收益。

### 3.2 建议对象

```python
@dataclass(frozen=True)
class RawObservation:
    code: str
    quote: Quote
    source: str
    source_epoch: int
    provider_ts: datetime | None
    time_role: Literal["provider_update", "last_trade", "unknown"]
    received_at: datetime
    received_mono_ns: int

@dataclass(frozen=True)
class ObservationDecision:
    code: str
    source: str
    source_epoch: int
    status: Literal[
        "admitted_time", "future_rejected", "out_of_order_rejected",
        "explicit_unavailable", "rejected_quality", "unknown_missing"
    ]
    reason: str = ""

@dataclass
class RoundObservationSet:
    round_id: int
    observed_at: datetime
    status: Literal["ok", "partial", "fetch_error"]
    requested_codes: tuple[str, ...]
    provider_objects: dict[str, RawObservation]
    decisions: tuple[ObservationDecision, ...]
    admitted_current: dict[str, Quote]
    rule_eligible: dict[str, Quote]
    current_indexes: dict[str, Quote]
```

### 3.3 水位线与 source epoch

```text
watermark_key = (code, source_epoch, time_role)
```

水位线只负责排序合同：每次 accepted observation 无条件推进，包括同价同量。

```python
if comparable_time_role:
    prev = accepted_watermark.get(key)
    if prev is not None and event_ts < prev:
        reject(out_of_order)
        continue

accepted_watermark[key] = event_ts
```

切 source 后生成新 epoch。新 epoch 第一份 provider time 不与旧源 provider time 比较。若 `time_role=unknown`，要预先定义保守策略；不能一边 `provider_time=False`，一边又默默拿 `Quote.ts` 当强排序键。

### 3.4 Ledger 机械恒等式

同一 requested universe 下，至少要求：

```text
requested
=
provider_objects
+ unknown_missing
```

provider objects 再分：

```text
provider_objects
=
admitted_time
+ future_rejected
+ out_of_order_rejected
+ explicit_unavailable
+ rejected_quality
```

股票侧：

```text
admitted_time_stock
=
rule_eligible
+ filter_rejected
```

规则侧按 rule 单独：

```text
rule_eligible
=
hit
+ evaluated_no_hit
+ unavailable_capability
+ rule_specific_rejected
```

不能把 stock 的业务过滤和 index 的纯时间准入相加后仍叫一个 `admitted`。

### 3.5 指数 current-only

保留指数 history，但 current candidate 必须来自：

```text
current_indexes = admitted_current ∩ index_codes
```

`spirit_index` 不能再扫描整个 `state.quotes`。这样才真正兑现“股票和指数共用同一准入合同”。

### 3.6 兼容与回退

- 冻结 `Quote`/`Source.snapshots()` 公共签名，先用 sidecar，不强拆 v1 外部接口。
- `RoundObservationSet.as_dict()` 继续只输出有界汇总，不把全市场逐股对象塞 API。
- 逐 code provenance 留在内部/离线 trace，可按计数/样本摘要暴露。
- 新合同以 shadow 记账先跑；只有账本恒等式、红绿回退和长跑稳定后才替换旧统计。
- 回退只关新消费路径，保留 v2 trace，不能把已知脏数据重新解释为正常。

## 6. 研究主线：`EXP-IT-CAP-004-source-epoch-warmup-routing`

### 6.1 为什么做这个实验

上一轮 4-provider-style synthetic 中，provider-specialist 总体较好，但单个 source-switch 邻域里 universal-intersection 曾略高。因此本轮没有增加网络，而是验证一个更具体的问题：

> source switch 后短暂只用 universal common-feature 模型，过 K 个 5 秒槽再切回 specialist，是否更稳？

### 6.2 预登记选择

只在 dedicated synthetic dev stress set 选 K：

```text
K ∈ {0,1,3,6,12}
objective = 0.5 * overall PR AUC + 0.5 * near-switch-12 PR AUC
```

结果：

| K | warmup | Overall PR | Near-switch PR | Objective |
|---:|---:|---:|---:|---:|
| **0** | **0s** | **0.68253** | **0.68675** | **0.68464** |
| 1 | 5s | 0.68234 | 0.68511 | 0.68373 |
| 3 | 15s | 0.68162 | 0.67858 | 0.68010 |
| 6 | 30s | 0.68126 | 0.67309 | 0.67718 |
| 12 | 60s | 0.68104 | 0.67115 | 0.67610 |

所以 **K=0** 胜出，即：这次数据不支持“source switch 后额外 universal warm-up”。该假设被淘汰，不能为了架构看起来高级继续加状态机。

### 6.3 4 个 fresh lockbox

固定 K=0 后，再用 4 组未参与 K 选择的 synthetic lockbox：
