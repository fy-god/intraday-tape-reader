# 2. 新确认错误

## 2.1 IT-P1-008 —— SSE 断线重连后缺少“补账”机制，事件可以永久缺失

### 位置

固定源码：`e6ed352...`

- `src/arad/store.py`：`AlertStore.subscribe()`、`add_alert()`、`recent_alerts()`
- `src/arad/server/web.py`：`DashboardHandler._route_stream()`、`_sse_events()`、`_sse_event()`
- `src/arad/server/dashboard.html`：`connect()`、`loadRecentAlerts()`、`loadSpirit()`、失活检测

关键代码：

```python
# store.py
def subscribe(self) -> queue.Queue:
    q = queue.Queue(maxsize=200)
    self._subs.add(q)
    return q
```

新订阅只得到一个**空的新队列**，不会自动从 `AlertStore._alerts` 回放断线区间。

```python
# web.py
def _sse_event(name, data):
    out = [f"event: {safe_name}"]
    ...
    out.append(f"data: {line}")
```

SSE 帧没有 `id:`，服务端也没有读取 `Last-Event-ID`。

前端：

```javascript
function connect(){
  var es = new EventSource("/api/stream");
  es.addEventListener("open", function(){ touch(); });
  ...
  es.addEventListener("error", function(){
    setConn(false, "连接异常·重连中");
  });
}
```

重连 `open` 只 `touch()`，没有调用：

```javascript
loadRecentAlerts();
loadSpirit();
```

而 10 秒失活检测调用的是：

```javascript
refreshAll();
```

`refreshAll()` 只拉 `status/quotes/watchlist/charts`，也**不补 alerts/spirit**。只有页面首次启动和 `visibilitychange -> visible` 时才补历史。

更值得注意的是，前端 `pushSpirit()` 的注释写着：

```javascript
/* 去重：SSE 重连会重放，靠 key 去重 */
```

但服务端当前并不会在重连时重放，所以注释描述的可靠性语义与实际实现不一致。

### 触发反例

1. 页面保持可见，SSE 正常收到告警 `A100`；
2. 网络抖动 3 秒，浏览器 EventSource 进入自动重连；
3. 断线期间引擎产生 `A101...A110`，`AlertStore` 正常保存且通知其他在线客户端；
4. 原连接被清理；浏览器自动建新连接；
5. 新连接对应新的空订阅队列；
6. `open` 不拉 `/api/alerts` / `/api/spirit`；
7. 后续从 `A111` 开始继续实时显示。

结果：`A101...A110` 在这个仍保持打开的浏览器里**永久缺失**，除非用户之后切换标签页触发 `visibilitychange`、刷新页面，或其他流程恰好手动补历史。

### 影响

- 属于“连接恢复但内容不完整”的静默错误，比直接断网更难发现；
- `SSE connected=true`、tick 正常，并不能证明告警没有漏；
- 对短线异动看板，几秒断线恰好可能覆盖高密度告警区间；
- `/api/alerts` 默认内存环仅保留有限条，晚补也不一定能覆盖长断线；
- `alert` 与 `spirit` 是同一逻辑告警的两种展示形状，二者如果分别恢复还可能产生 UI 不一致。

### 规范依据

当前实现其实没有必要自行发明一套完全私有的断点续传语义。WHATWG SSE 标准已经定义了 `id:` 与重连时的 `Last-Event-ID`；MDN 也明确说明 `id` 会设置 `EventSource` 的 last event ID，`retry` 只负责重连等待时间。

- WHATWG HTML Standard — Server-sent events: <https://html.spec.whatwg.org/multipage/server-sent-events.html>
- MDN — Using server-sent events: <https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events>

当前服务端只写 `retry: 3000`，等于只用了“什么时候重连”，没有使用“从哪里继续”。

### 修复方案

分两层，先补最小正确性，再做可靠协议。

#### A. 最小修复：前端每次 SSE `open` 都补一次 REST 历史

```javascript
es.addEventListener("open", function(){
  touch();
  loadRecentAlerts();
  loadSpirit();
});
```

再加一个 2~3 秒节流，避免频繁抖动时重复拉取。现有 `key` 去重可以吸收重叠数据。

这能修复“小于 AlertStore 保留窗口”的普通断线，但不是最终方案，因为长断线超过环形历史容量仍然会无声丢失。

#### B. 完整修复：单调 `event_seq` + resumable event ledger

建议把逻辑告警拥有一个全局单调序列：

```text
seq=1001 alert key=...
seq=1002 alert key=...
...
```

`AlertStore` 增加：

```python
self._event_seq: int
self._event_log: deque[EventRecord]
```

每个逻辑 alert 写入时分配 `seq`，`/api/alerts` 支持：

```text
GET /api/alerts?after_seq=1000
```

返回至少：

```json
{
  "items": [...],
  "oldest_seq": 950,
  "latest_seq": 1100,
  "cursor_too_old": false
}
```

若请求游标已经早于环形历史最早项，不允许假装补齐成功，必须明确：

```json
{"cursor_too_old": true, "oldest_seq": 1200}
```

SSE 同时加入 `id:`。由于当前一个逻辑 alert 会展开成 `alert` + `spirit` 两个 wire event，不能粗暴地在第一条 `alert` 上就把该逻辑 seq 标成“已完整交付”，否则恰好在 `alert` 与 `spirit` 之间断线时会跳过 `spirit`。较稳妥的两种方案：

1. 让前端只消费一个带完整展示字段的逻辑 alert，减少双事件；或
2. 给逻辑事件建立显式 cursor，重连后允许重复整个逻辑事件，继续靠 `key` 幂等去重。

第一版更推荐 2：兼容当前接口，重复比静默漏更安全。

### 回归验收

1. 连接收到 `seq=100` 后强制断开；断线期间生成 20 条；重连后最终客户端集合必须包含 `101..120`，`missing=0`。
2. 同一个 alert 因重放出现两次 wire message，客户端按 key 合并后只能显示一次。
3. 断线期间产生数量超过服务端保留窗口时，必须得到显式 `cursor_too_old/gap`，不能返回“看似成功但少数据”。
4. 新连接从未持有 cursor 时仍按当前实时模式工作。

## 2.2 IT-P1-009 —— 慢客户端队列满时会静默丢最旧事件，且当前监控无法发现

### 位置

`src/arad/store.py::AlertStore.broadcast()`：

```python
for q in subs:
    try:
        q.put_nowait({"event": event, "data": data})
    except queue.Full:
        try:
            q.get_nowait()      # 丢最旧
            q.put_nowait({"event": event, "data": data})
        except Exception:
            pass
```

每个订阅队列固定：

```python
queue.Queue(maxsize=200)
```

设计目标“不能让慢客户端拖死行情引擎”完全合理；错误不在 drop 本身，而在于：**drop 后没有任何可观测痕迹和恢复协议**。

### 本轮最小机制复现

本轮在分析环境用与仓库完全同构的 `Queue(maxsize=200) + full 时 get oldest + put newest` 算法推入 250 个连续序号事件，结果：

```text
dropped = 50
queue_len = 200
oldest_surviving_seq = 50
newest_surviving_seq = 249
```

这是对算法性质的最小复现，**不是导入仓库执行 pytest，也不是实盘测试**。

### 为什么现有 soak 会漏掉这个故障

`tools/live_session.py::StreamProbe` 当前只统计：

```text
connected
stalled
events_total
events_by_type
error
```

`evaluate_health()` 对 SSE 的判据是：

```python
connected and not stalled and events > 0
```

所以一个客户端即使因为反压丢了 50 条，只要还持续收到后续 tick/alert，仍会被判为 SSE 健康。

现有 `tests/test_server_web.py` 已覆盖：

- SSE header；
- alert 能送达；
- heartbeat；
- 多客户端；
- RST/FIN/timeout 后 unsubscribe；
- shutdown 清理；

这些测试很有价值，但没有覆盖：

- queue overflow；
- drop 计数；
- gap 标记；
- 重连补账；
- `Last-Event-ID`；
- 生产端 alert 数与客户端最终应用数的守恒关系。

### 影响

- 慢浏览器、后台标签页、Wi-Fi 抖动或 socket 写阻塞都可能让队列积压；
- 服务端不会 OOM，也不会断流，因此运维表象反而“很健康”；
- 丢的是最旧项，用户最终看到的是“最新消息不断滚动”，很难凭肉眼察觉中间缺段；
- 一旦拿它做“真实盘中测试 0 SSE 故障”的证据，会高估交付完整性。

### 修复方案

不要把“永不阻塞引擎”改回阻塞模型；应把**丢失变成显式、可恢复状态**。

建议把裸 `queue.Queue` 改成：

```python
@dataclass
class SubscriberState:
    queue: queue.Queue
    dropped_total: int = 0
    first_dropped_seq: int | None = None
    last_dropped_seq: int | None = None
```

当 queue full 时：

1. 仍然 drop oldest，保证引擎不阻塞；
2. `dropped_total += 1`；
3. 记录被丢 seq 范围；
4. SSE 线程下一次有机会写 socket 时先发送 `event: gap`；
5. 前端收到 gap 后用 `after_seq` 回补；
6. 如果回补游标已超出 retained ring，明确展示“存在不可恢复缺口”，不要伪装完整。

同时在 `/api/status` 或专门 health 字段公开：

```text
sse_subscribers
sse_queue_depth_max
sse_drop_total
sse_gap_total
sse_replay_total
```

### 回归验收

- 人工建立一个不消费的 subscriber，推 250 条：引擎不阻塞；`drop_total==50`；gap 范围准确。
- 客户端恢复消费后，通过 replay 最终 `missing_after_reconcile == 0`（前提：数据仍在 retention ring）。
- ring 已覆盖时 `missing` 可以不为 0，但必须 `unrecoverable_gap > 0`，不可静默。
- 正常快速客户端 `drop_total==0`。

## 2.3 IT-P2-ACK-001 —— `_acked` 超阈值后的裁剪不是“保留最近项”

### 位置

`src/arad/store.py::AlertStore.ack()`：

```python
self._acked.add(str(key))
if len(self._acked) > 5000:
    self._acked = set(list(self._acked)[-2000:])
```

### 机制

`_acked` 是 `set`。集合的迭代顺序不表达“最近 ack 的时间顺序”。

因此 `list(self._acked)[-2000:]` 不是“最新 2000 个”，只是当前 set 迭代顺序里的后 2000 个。

### 影响

- 达到 5001 个已读 key 后，刚刚点击“已读”的某条记录可能被随机裁掉；
- `recent_alerts()` 会重新把它显示成 `acked=false`；
- 不影响行情规则/通知，但会造成前端状态反复，属于 P2 一致性错误。

### 修复

最简单的是利用 Python dict 的插入顺序：

```python
self._acked: dict[str, None] = {}

self._acked.pop(key, None)
self._acked[key] = None
if len(self._acked) > 5000:
    while len(self._acked) > 2000:
        self._acked.pop(next(iter(self._acked)))
```

如果希望同一个 key 再次 ack 算“刷新最近时间”，上面的 `pop + reinsert` 正好满足。

### 验收

依次 ack `k0..k5000`，裁剪后必须：

- 最新 `k3001..k5000` 全部保留；
- 最老项被确定性移除；
- 重复 ack `k4000` 后它成为最新项；
- 多线程并发下仍由原有 `RLock` 保护。

# 3. 详细改进方案：把 Web 交付从“活着”升级为“可证明完整”

当前架构其实已经天然适合做两种不同可靠性语义：

1. `tick/quotes/watchlist`：**latest-value**，旧帧没有必要补，允许丢中间帧；
2. `alert/spirit`：**event-log**，不能无声缺段，至少要能检测缺段并在 retention 内回补。

建议不要把二者都塞进同一种可靠性要求。

## 3.1 事件账本字段

为逻辑 alert 增加：

```text
seq            单调递增逻辑序号
key            既有幂等键
generated_at   引擎生成时间
stored_at      AlertStore 入库时间
kind
```

前端维护：

```text
last_seq_applied
seen_keys
replay_count
gap_count
```

## 3.2 明确“交付守恒量”

每次 soak 报告至少应能回答：

```text
G = 本阶段 store 新生成的逻辑 alert 数
R = REST/SSE 最终能恢复到客户端的唯一 alert 数
M = 明确不可恢复的 gap 数
D = 客户端去重掉的重复数
```

在 retention 足够且无明确不可恢复 gap 时，应满足：

```text
G == R
M == 0
```

有故障注入时，允许 wire 层重复，但最终 UI model 按 key/seq 合并后不得漏。

## 3.3 `live_session.py` 增强

当前 `StreamProbe` 只数 `event:` 名称。建议增加：

```text
first_seq
last_seq
unique_alert_seq
sequence_gaps
reconnects
replay_events
server_drop_total_start/end
```

测试工具还应主动做一次“受控断开”：

1. 建连接；
2. 收到若干事件；
3. 主动断开；
4. 在测试 store 中产生一段 alert；
5. 重连；
6. 检查最终逻辑序列完整。

真实市场 soak 不需要人为制造错误，但离线集成测试必须覆盖。

# 4. 本轮待验证新点子

## IDEA-IT-010 —— Resumable Alert Ledger（可恢复告警账本）

**问题机制**：当前 `AlertStore` 是“最近 N 条历史 + 每连接临时队列”，两者之间没有 cursor 关系。

**与现有实现差异**：不是把队列从 200 扩成 1000，而是给逻辑告警一个稳定 seq，使“漏没漏”第一次变成可计算问题。

**实现位置**：

- `src/arad/store.py`：event_seq / event ring / after_seq 查询；
- `src/arad/server/web.py`：SSE `id`、`Last-Event-ID` 或明确 replay endpoint；
- `dashboard.html`：维护 last_seq，gap 后 catch-up；
- `tools/live_session.py`：序列守恒审计。

**初始参数（仅实验起点）**：event ring 先保留 5000 条或 30 分钟二者较大者；最终容量根据真实告警 burst 分布确定，不把 5000 当最优值。

**收益假设**：短断网/页面后台恢复后不漏告警；更重要的是，若真的漏，系统能明确告诉用户。

**失败淘汰条件**：若引入 seq/replay 后 p95 poll 延迟显著回归，或 event ring 增长不可界定，则需要把账本从主引擎锁中拆出去；不能为了可靠性拖慢行情主循环。

## IDEA-IT-011 —— Lossy State / Loss-aware Event 双平面

**问题机制**：行情 tick 与告警事件对“丢一条”的含义完全不同。

**方案**：

- quotes/tick：继续 latest-value，旧帧直接覆盖，追求低延迟；
- alert/spirit：进入可恢复 event ledger，追求可检测完整性；
- 不为每个 tick 做持久重放，避免把可靠性成本施加到高频状态流。

**对照实验**：

A. 当前模型；B. 双平面。

同时测：

```text
poll p50/p95/p99
engine lock hold time
SSE queue drop/gap
客户端最终 missing alerts
内存上界
```

**淘汰条件**：B 如果不能把告警静默漏失降为 0/显式 gap，同时明显恶化主轮询尾延迟，则方案不通过。

## IDEA-IT-012 —— Delivery SLO Dashboard（交付完整性 SLO）

不要再只显示“连接正常”。建议状态区新增：

```text
server_last_seq
client_last_seq
lag
reconnects
dropped
replayed
unrecoverable_gap
```

**价值假设**：把“用户感觉今天少了几条”变成可观测指标。它不提高信号预测能力，但能显著提高系统作为盘中工具的可信度。

**淘汰条件**：如果这些指标无法从真实端到端链条采集，只是在服务端自报自证，则不算完成，必须至少含一个真实客户端探针。

# 5. 最小实验矩阵与验收

| 实验 | 故障注入 | 必须观察 | 验收条件 |
|---|---|---|---|
| E1 重连补账 | SSE 断开期间生成 20 条 | 客户端最终 seq/key 集合 | retention 内 missing=0 |
| E2 慢客户端 | 200 容量队列快速推 250 条 | drop/gap/replay | 50 条 drop 被显式计数，补账后 missing=0 |
| E3 超出 retention | 断开到旧 cursor 被覆盖 | API/SSE gap 状态 | 必须显式 `cursor_too_old`，不得假装完整 |
| E4 多客户端 | 快客户端 + 极慢客户端 | 两客户端各自 gap | 慢客户端丢失不影响快客户端；各自有独立计数 |
| E5 双事件幂等 | alert/spirit 间断线重放 | UI 行数/seen key | 可重复 wire，UI 不重复逻辑告警 |
| E6 ack 裁剪 | 连续 ack 5001 个 key | 最新已读集合 | 最新 2000 确定性保留 |
| E7 soak 守恒 | 正常真实盘中 | G/R/M/D | 无明确 gap 时 G=R，不能只看 connected/stalled |
