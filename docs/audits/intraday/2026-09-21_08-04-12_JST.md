## 3. `IT-P1-EVAL-PUBLISH-001`：P0-0 真实质量标签仍被分母阻塞

当前 `VolumeBurstRule` 的顺序仍是：候选命中 → 规则内排序/`max_per_round` → `mark_published()` → 把 Alert 返回 Engine。随后 Engine 才执行 ignore、`AlertBus.accept()` 的 key 去重/cooldown，只有通过的 Alert 才进入 `fresh`，再 `store.add_alert()` 并交给通知器。

因此现有 `SignalEvalStats.published` 的真实语义不是“已经发布/交付”，而是：

```text
rule_selected
```

这一点不能靠改字段注释解决。未来 T+5/T+30 标签如果从当前 `published` 取事件，仍会把被 cooldown/dedupe 吞掉、从未进入 Store 的候选算成“已发布事件”。

### 应拆的阶段

```text
hit_candidate
→ rule_selected
→ bus_accepted
→ committed
→ delivery_attempted
→ delivery_sent / delivery_skipped / delivery_failed
→ client_received
→ client_applied
→ future_label_known
```

第一阶段未来收益代理标签必须从 `committed` 开始；用户可见交付质量再进一步按 `delivery_sent/client_received` 分层。

## 4. 本轮新 P1：Notifier 的返回值被 Engine 丢弃

### 4.1 源码合同与 Engine 行为冲突

`notifiers/base.py` 明确规定：

```python
def send(alert) -> bool: ...       # 返回是否成功，绝不抛异常
def send_digest(alerts) -> bool: ...
```

内置 Webhook 也严格遵守：网络异常、HTTP 4xx/5xx、业务错误最终返回 `False`，并在内部吞异常；成功返回 `True`。

但 Engine 当前 `_dispatch_many()` 只是：

```python
if callable(digest):
    digest(alerts)       # 返回值完全没接
else:
    n.send(a)            # 返回值也没接
```

只有真的抛异常才进入 Engine 的 except/fallback。对内置 notifier 来说，正常失败路径**按协议就是 False 而不是异常**，所以 Engine 对失败没有统一可见状态。

### 4.2 本轮机制探针

固定 3 条 committed alerts，分别用四种 notifier：

1. `send_digest=True` 且真的产生 side effect；
2. `send_digest=False`，没有发送；
3. `send_digest=True`，但没有 side effect（模拟 disabled / severity skip 的现行语义）；
4. 真抛异常。

当前 Engine 只能对第 4 种看见异常。对 1/2/3 都没有阶段状态；特别是第 2 种**明确失败但 Engine 不知道**，第 1 与第 3 又同为 True，却一个真的发了、一个实际上跳过。

产物：`notification_result_probe.json`。

### 4.3 为什么不能只“检查 bool”

因为内置 notifier 目前在这些场景也返回 True：

```text
enabled=False
severity < min_severity
dry_run / policy skip（不同实现）
```

所以 `True` 不等于 `sent`。

需要 typed result，而不是一个 bool：

```text
sent
skipped_disabled
skipped_severity
skipped_dry_run
failed
```

并带：channel、mode(single/digest)、event_ids、attempts、reason、开始/结束时刻。

### 4.4 不应盲目把 digest False 自动降级成逐条发送

泛化 Notifier 可能在失败返回前已经产生部分副作用，未知第三方 notifier 也未必幂等。Engine 第一阶段应该**如实记录失败**，让 notifier 自己负责其内部已定义的 retry；若以后要做 digest→single fallback，必须配稳定 `delivery_id/event_id` 和明确幂等策略。

## 5. `IT-P1-NOTIFY-RESULT-002`：投递阶段本身需要“跳过”状态

当前 notifier 的 bool 同时承载：

```text
True = 发送成功
True = disabled，根本没发
True = severity 不够，根本没发
False = 尝试过但失败
```

所以即使 Engine 从今天开始保存 bool，也无法回答：

> 这条 committed alert 是“用户渠道成功送达”，还是“策略配置决定不发”？

正确阶段不变量应该是：

```text
对每个 committed event × channel：
    sent + skipped + failed = delivery_decisions
```

而不是：

```text
True = sent
```

这个区分也关系未来质量研究：信号预测价值应该以 committed 为分母；“用户真正看到没看到”才按 delivery/client 维度单独分析，不能把渠道过滤反过来污染模型标签。

## 6. `IT-P1-ALERT-IDENTITY-001`：没有显式 signal_id/event_id

当前 `Alert` 序列化包含 `key/kind/code/name/ts/price/pct/title/detail/severity/metrics`，但没有明确的：

```text
signal_id
event_id
```

`key` 是去重/时间桶语义，`kind` 又不足以区分所有 signal（例如多类短线精灵共用 `AlertKind.UNUSUAL`）；依靠 title 文案或 `metrics.pattern` 拼装研究身份会产生版本漂移。

### 建议

- `signal_id`：规则语义的稳定 ID，例如 `volume_burst`、`spirit_order.institution_buy`；
- `event_id`：在 `bus_accepted` 后、Store commit 前生成的稳定提交事件 ID；
- `rule_candidate_id`：如确实需要对账规则候选，可另建 sidecar，不等同 committed event。

`event_id` 应贯穿 Store、notifier delivery ledger、SSE/client receipt 和 T+5/T+30 标签表。

## 8. 主改造：Alert Truth Contract v2

Observation Truth Contract 已经解决了越来越多“数据到底是什么”的问题；现在需要把同样的纪律延伸到告警交付链。

建议：

```text
admitted_current
    ↓
signal evaluability
    ↓
hit_candidate
    ↓
rule_selected
    ↓
AlertBus accepted
    ↓
committed(event_id)
    ↓
DeliveryDecision(channel)
    ├─ sent
    ├─ skipped_disabled
    ├─ skipped_severity
    ├─ skipped_dry_run
    └─ failed
    ↓
client_received / client_applied
    ↓
future_label(event_id, known_at)
```

### 冻结不变量

```text
rule_selected <= hit_candidate
bus_accepted <= rule_selected
committed <= bus_accepted

每个 committed event × channel：
sent + skipped + failed = delivery_decisions

所有 T+5/T+30 标签：
event_id 必须引用 committed event
```

### 兼容策略

- 旧 `SignalEvalStats.published` 先 deprecated 并重命名/解释为 `rule_selected`；不要突然把同名字段改成另一层语义而让旧报告混在一起。
- 内置 notifier 迁移 typed `NotificationResult`；第三方 legacy bool 通过适配器进入 `legacy_true/failed`，其中 `legacy_true` **不得**直接认证为 physical sent。
- Store committed 独立于外部 notifier 成败；通知失败不能让主行情循环失败，也不能把 committed event 删除。

本轮候选 schema 已落：`alert_truth_contract_v2.json`。

## 9. 其余开放主线

### 9.1 per-code provenance / capability
`RuleContext.provides(key)` 仍是整轮 source capability。要做 soft-partial 混源必须先变成等价于：

```text
(route, code)
→ source
→ source_epoch
→ advertised capability
→ observed field availability
```

再允许 `ctx.provides(code, key)`。

### 9.2 soft-partial targeted fallback
主源不抛异常、只少返回一部分 code，当前仍视为成功。正确顺序依旧是 provenance/capability 完成后，只对 `unknown_missing` 做有界补洞，不能对 explicit unavailable/quality reject 无限切源。

### 9.3 ObservationInterval
accepted watermark 已不再等同 history tail，但 history 仍只在价/累计量变化时追加。仍需用 `first_observed_at/last_observed_at/source_epoch` 表达“平价但持续收到新鲜 observation”。

### 9.4 SSE durable delivery
Store subscriber queue 仍是 `maxsize=200`；满后丢最旧再放最新，没有 cursor/gap 告知客户端。`_series` 主体 dict 也仍有容量治理问题。这些属于 `client_received/applied` 阶段，不能用 notifier 修复替代。

### 9.5 次新股 6–10 日
N/C 只覆盖前五日。`min_list_days=11` 在 universe list_date 元数据不可用时仍需权威本地 listing-date cache；不得用“程序第一次见到日期”冒充上市日。
