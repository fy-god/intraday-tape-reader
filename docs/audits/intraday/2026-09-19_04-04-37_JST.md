## 二、错误证据与修复要求

以下均针对固定提交 `f695102f8794b0b235d5f6ebf24564520d663ad8`，不是对未来版本的自动判定。历史已有问题沿用原 ID；本轮新增问题采用新的稳定 ID。

### 1. IT-P0-003：旧股票进入本轮快照，绕过下游断线间隔保护

**状态：未修；原审计已做片段复现。**

位置：`engine.py::EngineState.update`、`Engine.poll_once`；`rules/spirit_order.py::_drop_stale`、`_check_trades`。证据：[引擎][engine]、[过滤器][filters]、[盘口规则][spirit_order]。

关键代码：

```python
eligible = {
    c: q for c, q in self.state.quotes.items()
    if self.filters.accept(q, now.date()) and c not in self.ignore
}
snap = Snapshot(
    ts=now,
    seq=self.state.seq,
    quotes={c: self.state.quotes[c] for c in self.watchlist
            if c in self.state.quotes},
)
snap.quotes.update(eligible)
```

这里遍历累计缓存 `state.quotes`，不是本轮成功返回且通过质量校验的集合；过滤器没有新鲜度判断。

反例一：第一轮 A、B 有效；第二轮只返回 B。原本通过粗筛的 A 仍在缓存，下一份 Snapshot 仍可能包含 A。

反例二：有效行情后收到零价。`update()` 遇到 `price <= 0` 直接跳过，没有把旧缓存改成当前不可用。原探针中，收到零价后缓存价格仍为旧的 10.0。

下游后果：盘口规则每次处理快照都会先执行：

```python
self._prev[code] = (outer, inner, amount, volume, now_epoch)
```

然后才用前一条记录时间判断 max_gap；`_drop_stale()` 又只在代码不属于 snap.quotes 时移除旧缓存。因此旧 A 被不断塞进快照，会刷新“上一轮时间”。

原 `CASE-18` 的门控结果：

| 项目 | 结果 |
|---|---:|
| 真正两次新观测的间隔 | 180 秒 |
| 中间旧缓存重复处理频率 | 5 秒 |
| 差分保护看到的间隔 | 5 秒 |
| 外盘累计增量 | 7,850 手 |
| 间隔与增量门控 | 通过，进入后续阈值判断 |

该探针没有执行完整告警构造，不能写成已经发出某条机构告警；它证明的是上游伪造连续性会破坏下游已有的长间隔保护。

影响：部分股票缺失或失效时可能继续参与规则；恢复后长区间累计量可能被当作短区间增量。

修改：分离 `admitted_current` 与 `cache_latest`。规则只消费本轮有效观测；旧缓存仅用于明确标旧的展示。盘口 `_prev` 仅由新准入观测更新。

回归：A 缺失不得进入本轮股票规则；有效→零价不得继续按旧价报；180 秒恢复必须识别真实缺口，只建立新差分基线。

### 2. IT-P0-002：事件时间不约束状态，窗口读取未来点

**状态：未修；乱序及窗口边界已做片段复现。**

位置：`EngineState.update/window`，参见 [引擎][engine]。

```python
h.append((ep, q.price, q.volume_lots))
...
if q.ts is not None and q.ts > now:
    pass

# window 仅有下界
return [p for p in h if p[0] >= cutoff]
```

状态使用传入的轮询时间入历史。提供商时间比较发生在写入后，且不拦截。查询缺少 `p[0] <= now_epoch`。

| 反例 | 当前片段结果 | 应有行为 |
|---|---|---|
| 先收到新价格 10，再收到事件时间更早的 10.5 | 旧包覆盖现价，算出约 +5% | 旧事件不回滚当前状态 |
| 已有 t+10，查询截止为 t+5 | 返回未来点 | 严格限制到截止时刻 |
| 共享状态跨日写入新开盘价 | day_open 仍保留旧值 | 明确日状态重置及消费合同 |

跨日片段不能扩大为全部规则跨日失效：spirit_order 已有 `_reset_day()`，应保留保护。

兼容性边界：naive/aware 混用可能在状态已写入后抛 TypeError。v1 契约明确约定北京时间 naive，故这不是默认部署必然出现的错误，而是时区迁移必须贯通上下游的证据。参见 [冻结契约][contract]、[规则上下文][rule_base]。

修改：任何状态变更前归一化时间并准入；分开提供商、接收、处理时间；窗口加上界；市场时区显式使用 Asia/Shanghai，不依赖宿主机。

回归：乱序不改变现价，回拨不读未来，不同宿主时区同一瞬间结果一致，校验失败无部分写入。

### 3. IT-P1-WINDOW-001：压缩新鲜横盘观测后漏掉突发涨幅

**状态：本轮新增；已做片段复现及局部候选对照。**

位置：`EngineState.update/window/price_change`、`TickSurgeRule._covered`。参见 [引擎][engine]、[急拉急跌规则][tick_surge]。

当前仅价格或累计量变化时追加历史；覆盖判断仅检查历史最早一点是否足够早，可能出现 `_covered=True`，但窗口缺起点，`price_change=None`。

固定输入：

```text
t=0,5,10,...,60 秒：每次均有新鲜观测，价格 10.0，累计量 100 手。
t=65 秒：新鲜观测，价格 10.3，累计量 101 手。
```

| 指标 | 当前值变更压缩 | 局部候选：保留新鲜观测 |
|---|---:|---:|
| 保存点数 | 2 | 14 |
| 当前实现的覆盖判断 | True | — |
| 60 秒窗口涨跌幅 | None | 约 +3% |

旧机制仅剩 t=0 与 t=65；窗口下界 t=5 排除前一点后只剩单点。

这不意味着重复包全部保存。必须区分相同旧包重复到达，和价格不变但确实获得新有效观测。负控制：持续新鲜恒价，候选为 0；仅 t=0、t=65 两条且中间没有观测，候选为 None，没有无限前填。

影响：正常横盘后的短时价格变化可能缺少窗口起点，特征漏算。

修改：先用可审查的有效观测环作为基准，再考虑保留覆盖证据和锚点的压缩；规定锚点时间容差与最大内部缺口。

回归：上述输入约 +3%；真缺口仍判不足；同秒不同内容不能简单当重复全丢。

局限：候选原型未解决同秒修订、完整连续性令牌、所有规则接入与生产恢复，不能部署；特征算出 3% 不等于已经证明规则事件召回改善。

### 4. IT-P1-006：股票池修复残留——分页截断仍冒充完整

**状态：部分修复，继续开放；残留已做片段复现。**

位置：`EastmoneySource.universe`、`Engine._universe_meta_of/refresh_universe`。参见 [东财源][eastmoney]、[引擎][engine]。

显式分页失败时当前实现会标记不完整，引擎也已有部分结果保护。但仍有：

```python
pages = min(self.max_pages, -(-total // self.page_size))
...
complete = bool(total > 0) and not failed
```

complete 没检查是否被 max_pages 截断。

原探针使用真实方法控制流、替身分页：`total=300, page_size=100, max_pages=2`，两页成功。结果：

```json
{"complete":true,"expected_total":300,"returned":200,
 "pages_requested":2,"reason":"已按总数翻完"}
```

标为完整的结果会被引擎立即采用，从而绕过不完整结果不能缩小旧池的保护。元数据缺失时 `_universe_meta_of` 另有 `complete=True` 默认值。

影响：分页上限较小、总量增长或元数据缺失时可能缩水但记刷新成功，扫描变快不能当作性能进步。

修改：分开必需页数、请求页数、失败页数、截断、原始总数、过滤及去重；完整性三态 true/false/unknown，未知不默认完整。

回归：300/100/2 必须不完整，不覆盖原 300 只；完整三页正常采用；显式第二页失败的保护不回归。

### 5. IT-P1-SOURCE-EMPTY-001：未知空返回被记为成功

## 三、主改造方案：有效观测驱动，而不是缓存驱动

### 1. 目标与非目标

目标：消除旧包、缺失、换源伪造连续性；保留横盘窗口覆盖；使采集覆盖及降级可解释；逻辑告警可补账、去重、对账。

非目标：新增选股策略、证明机构身份、恢复没有的逐笔数据、认证长期 KDJ，或承诺每轮更快。

```text
原始响应
→ 字段存在性与单位
→ 身份、时间与来源连续性
→ 本轮观测准入
→ 有界窗口与规则状态
→ 逻辑事件账本
→ SSE恢复与前端幂等展示
```

### 2. 新包装合同，保留 v1 接口

冻结契约要求保留现有字段和签名，第一步不全面替换 Quote/Snapshot。新增包装层及版本化接口：

| 对象 | 最少字段 |
|---|---|
| ObservationEnvelope | 交易所/代码、provider、来源epoch、字段/单位版本、原始时间、时间字段角色、UTC事件时间、接收时间、单调处理时间、内容指纹、字段存在性、能力集合、原Quote |
| BatchResult | request_id、route、请求/返回/缺失代码、实际供数方、尝试数、完整性三态、必需/请求/失败页数、截断、原始总数、过滤和去重数 |
| ObservationDecision | observation_id、接受/拒绝/隔离、reason、phase、成员版本、连续性版本 |
| EventRecord | logical_event_id、event_seq、incident_id、rule_version、证据观测ID、quality_flags、提交状态 |

先确认提供商时间字段是最后成交时间还是行情发布时间。最后成交时间不能机械当整份快照新鲜度，接收时间也不能填回去冒充提供商时间。

同秒同指纹可判重复；同秒内容变化处理修订语义，不全丢，也不伪造新的事件秒数。

### 3. 时间、窗口与差分合同

内部 UTC aware 与单调耗时，市场阶段 Asia/Shanghai。兼容 v1 输出北京时间 naive，但转换 epoch 统一经显式函数。RuleContext 当前直接 .timestamp() 也必须接线。

窗口：

```text
R(t,W) = 100 * (P(t) / P_anchor(t-W) - 1)
```

锚点来自有效观测，距左边界不超过容差；内部缺口不超限；所有点不得晚于 t。

累计量差分仅在同一连续性分段：

```text
交易日 × 交易阶段 × 来源epoch × 单位版本 × 能力版本
```

跨段或负增量输出差分不可用及原因，不以 max(0, delta) 把异常伪装成正常零量。

### 4. 规则状态和交付

至少区分 WARMUP/ARMED/FIRED/COOLDOWN/UNKNOWN。冷却到期不等于行情恢复。缺失、停牌、换源不能伪造恢复边沿；保留现有迟滞和日重置。

一件逻辑事件一个 ID。先只合并有明确同义关系的价格异动，触板、炸板、回封仍是不同跃迁。

账本可用标准库 sqlite3；必要状态与事件提交建立事务关系。SSE v2 优先一逻辑帧携完整展示字段，避免 alert/spirit 两帧中间断线。客户端区分接收与应用到两个面板；重播不重复声音或真实通知。

### 5. 起始配置、迁移与回退

以下仅是待验证起点，不是供应商服务保证，也没有写入实际运行配置：

```yaml

```

先同输入影子计算，正确性通过再切规则输入，最后启用账本/交付协议。新增配置必须有消费者和测试。独立开关回退，保留原始数据和新账本，不做破坏性降级。关闭恢复协议必须明确显示仅实时、不保证补齐。
