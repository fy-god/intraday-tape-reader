## §3 `IT-P2-CALL-DETAILED-TYPE-ERROR-ABORTS-FAILOVER-004`（**已确认错误**）

**文件/函数/行**：`src/arad/engine.py:591 def call_detailed`，关键行 **`:650`**
（`:628-645` 是逐源 `try`，`:649-650` 在 `try` **之外**）。

```python
624         last_exc: Exception | None = None
625         for i in order:
626             src = self.sources[i]
627             name = str(getattr(src, "name", "?"))
628             try:
629                 detailed = getattr(src, "snapshots_detailed", None)
630                 if callable(detailed):
631                     out = detailed(codes, route=route)
...
642             except Exception as exc:  # noqa: BLE001 - 逐个后备源尝试
643                 last_exc = exc
644                 log.warning("数据源 %s.snapshots_detailed 失败: %s", name, exc)
645                 continue
646             # ⚠ 原子绑定：source 以**实际返回数据的源**为准。

650                 out = out._replace(source=name)      # <-- 在 try 之外
```

**触发条件 / 反例**：某个源**正常返回但类型不对**（第三方源、半迁移源、返回 `dict`/`None`/旧版
`Quote` 列表）。此时 `:631` 成功返回，`:642` 的 `except` 不触发，于是 `:650` 抛
`AttributeError`，**穿透 for 循环**，`last_exc` 也没被设置，`_bump/_switch` 记账**全部跳过**。

**机制**：把「校验/改写返回值」放在「捕获源异常的 try」之外 ⇒ 源返回**错类型**这条路径
既不被当作源失败、也不被当成编程错误，而是**静默摧毁 failover 语义**。

**影响**：一个返回错类型的源会**阻断健康备用源**，整条路由直接向上抛错。
`call_detailed` 目前**生产调用点 = 0**（见 §6），所以**当前线上影响 = 0**；
一旦 WP03 接线，这会让「热备」在最不该失效的时候失效。

**修复建议**：把 `:646-650` 的原子绑定放进 `try` 内（或加一层只包裹绑定的 `try/except`
并 `continue`），并显式校验 `isinstance(out, SnapshotFetchResult)`；同时把
`out.route != route` 一并纳入同一处校验（见 §7）。

**验收测试**：一个「主源返回错类型 + 健康备用源」的用例必须断言
**备用源被调用**且最终返回备用源数据；并配一个「主源抛异常」对照，证明两条路径行为一致。

**我自己的可控实验（阳性 + 阴性对照对）**：

| 臂 | 构造 | 实测 | 期望 | 符合 |
|---|---|---|---|---|
| **阳性** | 主源返回 `dict` + 健康备用 | `AttributeError: 'dict' object has no attribute '_replace'`（栈顶 `engine.py:650`）；`primary=1 backup=0` | 中断、备用未被尝试 | ✔ |
| 阴性 A | 主源**抛异常** + 健康备用 | 返回备用源数据，`source=good`；`primary=1 backup=1` | 应 failover | ✔ |
| 阴性 B | 主源类型正确 | 返回主源数据；`backup=0` | 不 failover | ✔ |

阴性 A 证明**循环本身是好的**，因此阳性臂的失败**只能**归因于 `:650` 的位置。
