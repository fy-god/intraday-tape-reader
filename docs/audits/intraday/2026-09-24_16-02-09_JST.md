# 1. 本轮最高价值新问题：Sina fallback 会在发 HTTP 之前把部分指数改成另一只证券

新稳定 ID：

### `IT-P1-SINA-INDEX-PREFIX-LOSS-SILENT-WRONG-INSTRUMENT-012`
**P1 latent / production-reachable when index feature is enabled and Sina serves the index route.**

这是比上一轮 route-time diagnostic collision 更靠前、也更严重的根因。

Engine 对指数配置采取的是正确的从严策略：
- `poll.index_codes` **必须带 sh/sz/bj 前缀**；
- 裸 `000001` 会被拒，因为无法区分“上证指数”和“平安银行”；
- `_fetch_indices()` 把带前缀的 `self.index_codes` 原样交给 SourceManager。

默认 5 个指数：
```text
sh000001
sz399001
sz399006
sh000300
sh000688
```

默认行情链：
```text
Tencent primary
Sina fallback
```

但是 `SinaSource.snapshots()` 的第一步：

```python
wanted = _norm_codes(codes)
```

而 `_norm_code()` 明确：

```python
"sh000001" -> "000001"
```

随后 `_fetch_bulk()`：

```python
prefixed = [f"{guess_prefix(c)}{c}" for c in codes]
```

`models.guess_prefix()` 自己的 docstring 已经明确警告：

> **只对个股可靠。指数必须由调用方显式给前缀；`000001` 会被推成 `sz000001`（平安银行），而 `sh000001` 才是上证指数。**

所以真实调用链成为：

```text
配置 / Engine 请求：
sh000001

Sina _norm_code：
000001

guess_prefix：
sz

真实 HTTP：
...list=sz000001
```

也就是说系统要的是**上证指数**，发给 Sina 的却是**平安银行**。

这不是解析后才混淆，而是在 HTTP 请求构造阶段就已经拿错证券。

# 2. 默认 5 个 index_codes 中，Sina 当前有 3 个会改错交易所前缀

本轮固定算法矩阵：

| 配置指数 | Sina 去前缀后 | 当前重新猜出的 wire symbol | 是否正确 |
|---|---|---|---|
| `sh000001` | `000001` | `sz000001` | **错** |
| `sz399001` | `399001` | `sz399001` | 对 |
| `sz399006` | `399006` | `sz399006` | 对 |
| `sh000300` | `000300` | `sz000300` | **错** |
| `sh000688` | `000688` | `sz000688` | **错** |

所以默认配置在 Sina 服务 index route 时：

```text
错误 wire symbol = 3 / 5
```

这个 3/5 是**确定性配置/代码合同计数**，不是实盘故障率。

其中最危险的是 `sh000001 -> sz000001`：
- `sz000001` 是一个真实、正常交易的股票身份；
- 请求不会必然报错或返回空；
- parser 可以得到一个看起来完全正常的 `Quote(code="000001", name="平安银行")`。

因此这是：

> **silent wrong instrument，而不是普通 missing。**

# 3. 为什么这会比“指数缺失”更危险：当前 legacy snapshots 会把错证券当成功结果收下

`SinaSource.snapshots()` 在解析完成后做：

```python
wanted_set = set(wanted)
out = _dedupe(q for q in quotes if q.code in wanted_set)
```

而 `wanted` 此时已经是：

```text
000001
```

错误请求 `sz000001` 返回的平安银行 Quote 也是：

```text
q.code = 000001
```

所以它会**通过 wanted_set 过滤**。

因此系统不能靠：
- 返回条数；
- HTTP 成功；
- wanted-set filter；
来识别这次拿错证券。

这条链可以表现为：

```text
requested index count = 5
returned count 看起来正常
Source health 看起来正常
但 sh000001 这一身份实际被 sz000001 替代
```

这正是“看起来比 missing 更健康，事实反而更错”的故障形态。

# 4. 更重要：已经实现的 `SnapshotFetchResult` / `call_detailed` 也不会自动治好它

不能说：
> WP07 接 `call_detailed` 后 exact raw truth 会自动修复此问题。

Sina 的 `snapshots_detailed()` **同样先调用 `_norm_codes(codes)`**，然后 `_fetch_bulk_detailed()` 同样用：

```python
guess_prefix(c)
```

构造 URL。

而 `parse_response_detailed()` 对 requested identity 也通过 `_norm_code` 归一成裸码。

所以对 `sh000001`：

```text
R:
000001

实际 wire:
sz000001

P:
000001

Q:
000001
```

这套机械恒等甚至可能全部成立。

于是 detailed outcome 可能非常自信地告诉下游：

```text
requested = 1
returned = 1
admitted = 1
identity_holds = True
```

但它证明的是：

> **错误证券 sz000001 的内部集合代数很自洽。**

并没有证明：

> 调用方要求的 sh000001 被正确获取。

因此这条必须在 **Source 身份轴** 修，而不能留给 RoundObservation 补。
