**触发条件/反例（我亲自跑真实函数，非手写复刻）**
用冻结树内**真实的** `summarize_rounds` → `finalize_metrics` → `evaluate_health`：

```text

    capability_unavailable_total   = 20
    capability_unavailable_rounds  = 20
    capability_unavailable_ratio   = 1.0
真实按 code 可评估比例 = 4999/5000 = 99.9800%

    healthy   = False
    exit_code = 1
    fail 项   = ['data', 'capability', 'sse', 'memory']
    capability 检查：
        ok    = False
        level = fail
        detail= 20/20 轮出现'能力缺失导致规则无法评估'（比例 100%），累计不可评估标的 20 个；
```

**机制**：分母是「**出现任意一个 code 能力缺失的轮数 / 有账本的轮数**」，
而不是「**不可评估的 code 数 / 被考察的 code 数**」。
`unavailable_codes` 是所有 rule 写入的**代码集合并集**，`> 0` 即把整轮标记为"不可评估轮"。
任何一轮哪怕 5000 只里只坏 1 只，该轮就进分子 → 20 轮全中 → ratio = 1.0 → 撞上
`unavailable_fail_ratio = 1.0` → 判红，并配上「整类规则一次都没被评估过」的文案。

这不是阈值高低，而是**分母错误**：round-level「有没有任意一个缺失」不能替代
code-level evaluable coverage。soak 的健康结论会被这条**系统性误红**污染，
而它是后续 capability mask / provider specialist / targeted fallback 的**分母来源**。

**修复建议**（与 `00:14` 报告 §3.4 一致，此处给出更小落地面）
新增 per-signal evaluability 统计（`considered / hard_evaluable / blocked_capability /
advisory_missing / evaluated_no_hit / hit_candidates / published`），
健康判定改用 `evaluable_coverage(signal) = hard_evaluable_codes / considered_codes`；
`unavailable_capability` 只保留**诊断**语义，不再作为「整类规则未被评估」的真值。

**验收测试**（真实红测，我已用真实函数验证该反例可构造）
- 5000 code 中 1 code blocked、连续 20 轮 → **不得**被判 `evaluable_coverage = 0`；

## S1. 【证伪失败 → 原声称成立】`IT-P1-CAPABILITY-003` 的「硬阻断 vs 可跳过」混名

`00:14` 报告 §3.3 声称：`VolumeBurstRule` 把**两种相反语义**记成**同一个状态名**：
- 缺 `turnover` → **硬阻断**（被 `min_turnover` 拦掉，永远出不了 Alert）；
- 缺 `volume_ratio` → **可跳过**（门槛被跳过，**仍可能出 Alert**）。

**这不是一句静态断言，是可执行反例。我用真实 `VolumeBurstRule` 构造三组对照**：

```text
(A) 缺 turnover（provides('turnover')=False, q.turnover=0.0 占位）
      出 Alert = 0 条        <- 硬阻断
      ObservationDecision: status=unavailable_capability reason=turnover_not_provided
      unavailable_codes = {'600001'}

(B) 缺 volume_ratio（provides('volume_ratio')=False, q.volume_ratio=0.0 占位）
      出 Alert = 1 条        <- 仍然命中！
      ObservationDecision: status=unavailable_capability reason=volume_ratio_not_provided
      unavailable_codes = {'600001'}

(C) 对照组：两者都提供、vr 低于门槛
      出 Alert = 0 条        <- 被量比门槛正常拦住

判定：
  (A) 硬阻断            = True
  (B) 仍可评估/命中      = True
  (A).status == (B).status == 'unavailable_capability'  = True
  >>> 同一状态名承载两种相反语义 = True
```

**结论：证伪失败，原声称成立且得到了可执行证据。**
`unavailable_capability` 这一个名字同时承载 `blocking_missing`（真不能评估）与
`advisory_skipped`（缺一个当前语义允许跳过的条件，**但仍能出 Alert**）——
这正是它污染 soak capability health 的机制（与 §3.1 的分母错误叠加）。

**旁证（源码）**：`volume_burst.py:167-170` 记账**之后仍走**
`if min_turnover > 0.0 and float(q.turnover) < min_turnover: continue`（→ 硬阻断）；
而 `:177-181` 记账后走的是 `if vr_thr > 0.0 and vr > 0.0 and vr < vr_thr: continue` ——
`vr == 0.0` 时 `vr > 0.0` 为**假**，门槛被**跳过**（→ 可跳过）。两者逐字一致。

> **我的失败尝试我保留在案**：第一版脚本 §[3] 得到 **(B) 出 Alert = 0 条**，

## S2. 【证伪失败 → 修复确实有效】尝试**打破** `e729c1f` 的修复

### S2.1 攻击「回滚会不会把**已发出**的告警状态也回滚 → 下一轮重复报？」

```text
第 5 轮: 0 条 -> []
```
