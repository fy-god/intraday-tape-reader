## 1. 缺陷本体（已确认错误）

**编号**：`IT-P1-SINA-INDEX-PREFIX-LOSS-SILENT-WRONG-INSTRUMENT-012`
**位置**：`src/arad/sources/sina.py` — `_fetch_bulk()`（原 `:571`）、
`snapshots()`（原 `:471`）、`snapshots_detailed()`（原 `:576`）、
`_fetch_bulk_detailed()`（原 `:615`）

### 1.1 触发条件

任何一次**带显式交易所前缀**的请求 —— 即 `poll.index_codes`
（出厂配置 `["sh000001", "sz399001", "sz399006", "sh000300", "sh000688"]`）。
`engine._load_index_codes()` 本身就**只接受带前缀**的写法，所以这是常态路径。

### 1.2 机制

旧代码两步都错，而且**互相掩盖**：

```python
# 第一步：剥掉调用方给的前缀
wanted = _norm_codes(codes)          # "sh000001" -> "000001"

# 第二步：用只对个股可靠的规则重新猜前缀
prefixed = [f"{guess_prefix(c)}{c}" for c in codes]   # "000001" -> "sz000001"
```

关键在于 `guess_prefix` 的 **docstring 自己就写着**：

> ⚠ 本函数**只对个股可靠**。指数必须由调用方显式给出前缀：
> `000001` 会被推成 `sz000001`（平安银行），而 `sh000001` 才是上证指数。

—— 而调用方给的那个前缀，**恰恰在上一行被 `_norm_codes` 剥掉了**。
于是"必须由调用方显式给出前缀"这条要求，在代码里被**自己**破坏了。

### 1.3 实测（`$env:TEMP\r12b_sina_e2e.py`，走真实 `snapshots()`）

```
实际发出的 wire 符号: sz000001,sz399001,sz399006,sz000300,sz000688

  sh000001   -> sz000001      <<< 抓错证券
  sz399001   -> sz399001      OK
  sz399006   -> sz399006      OK
  sh000300   -> sz000300      <<< 抓错证券
  sh000688   -> sz000688      <<< 抓错证券

  默认 5 个 index_codes 中，3/5 被改成错误交易所
```

### 1.4 影响（为什么比 missing 严重）

**这不是"少了一只"—— 这是"拿错了"。**

`sz000001` 是**真实存在的股票**（平安银行）。旧 `snapshots()` 的过滤条件是：

```python
wanted_set = set(wanted)                        # 裸码 {"000001", ...}
out = _dedupe(q for q in quotes if q.code in wanted_set)
```

`wanted_set` 恰好是**裸码**，而 `sz000001` 解析出的 `q.code` 也是裸码
`000001` —— **在集合里**。所以：

> 请求上证指数 → 拿到平安银行的行情 → **通过过滤，记为成功**。

调用方得到一个字段齐全、数值合理、时间戳正常的 `Quote`，
**只是它是另一个证券**。missing 至少是可见的（账上有洞）；
这个是**静默的错误数据**。

### 1.5 第二重表现：detailed 路径的 "exact but wrong"

`snapshots_detailed()` 用同一套 normalization，且 R/P/Q 三轴**全用裸码**：

```python
req = normalize_request(requested, normalize=_norm_code)   # 裸码
raw_keys.append(code.zfill(6))                             # 裸码
quotes = parse_response(text, seq)                         # 全量，不过滤
```

三轴**机械自洽** ⇒ 即使抓的是 `sz000001`，`identity_holds()` 也会返回 `True`
—— 产出**看起来精确、实际是错误证券**的假精确。
这比第一重更危险：第一重至少 `Quote.name` 是"平安银行"，
第二重连账本都在替这个错误背书。

### 1.6 bug 类归属

这是本仓库 **bug 类 (g)「同一语义在两个时点/两个轴上分别推断」的第三例**
（前两例：腾讯 `idx_set` 由调用方写法推断、`time_age` 按裸码覆盖）。
身份在这里被推断了**两次**（剥前缀一次、猜前缀一次），**两次都可以错**。

## 2. 修复

**核心原则**：**前缀是调用方拥有的事实，只能搬运，不能重猜。**

### 2.1 新增三个工具函数（`sina.py`）

| 函数 | 职责 |
|---|---|
| `_split_prefix(spec)` | `"sh000001"` → `("sh","000001")`；无前缀 → `("","000001")`。**不丢信息** |
| `_wire_symbol(spec)` | 有前缀→原样保留；无前缀→退回 `guess_prefix`（个股场景） |
| `_wire_symbols(codes)` | 批量 + 去重，`snapshots*` 的唯一入口 |

`_norm_code` / `_norm_codes` **保留不动**（大量既有测试与 `parse_universe`
依赖它们），但 docstring 加了警告：指数路径不得经此构造 wire 符号。

### 2.2 三处调用点

1. `snapshots()`：`wanted = _wire_symbols(codes)`（原来是 `_norm_codes`）。
2. `_fetch_bulk()`：不再重猜；并且**按带前缀的完整符号过滤响应** ——
   这是第二道修复，旧代码在这里也漏（过滤键是裸码）。
3. `snapshots_detailed()` / `_fetch_bulk_detailed()` /
   `parse_response_detailed()`：wire 符号保留前缀；新增 `wire_symbols`
   参数用于**严格过滤**；账本轴 R/P/Q 保持裸码（与 `outcome._key_of`
   同轴，否则会造出 phantom missing）。

### 2.3 两轴分工（刻意的设计）

```
账本轴 R/P/Q  = 裸码     ← 与 outcome._key_of(quote) 同域，可比、可回归
过滤轴        = 完整符号  ← 与 wire 同域，精确、能区分 sh000001/sz000001
```

**不把 `Quote.code` 改成带前缀**是权衡后的决定：那会牵动 `board_of`、
`engine._load_index_codes`、`spirit_index.is_index_quote` 与
`state.quotes` 的键，爆炸半径大得多。当前缺陷（抓错证券）用两轴分工
**已经修掉**；`Quote.code` 带前缀那条作为独立项留在 §6。

## 5. 我自己犯的四个错（如实记录）

1. **`guess_prefix` 调用少传参数** —— 第一版诊断脚本写
   `guess_prefix(bare)`，实际签名是单参但语义不同，输出
   `rebuild sz` 让我一度以为"连 sz399001 都错了"。**先怀疑自己的探针**。
2. **手搓 payload 只有 6 字段** —— `MIN_FIELDS=32`，三条"阳性对照"
   全被 parser 丢掉，报 `assert 0 == 1`。看着像"产品拒绝一切"。
   改用既有 `bulk_body()` 构造器后立刻绿。**又是"探针没穿过被测路径"（D15）**。
3. **RB-S2 的锚点打在错误的函数上** —— 我把 `if strict:` 当作
   `_fetch_bulk` 的代码，实际它在 `parse_response_detailed` 里，
   而目标测试走的是 `snapshots()` → `_fetch_bulk`，**根本没碰到那个函数**
   → 牙"没咬"（rc=0）。**D15 第四次犯**。改正锚点后 rc=1。
4. **回退脚本把整个文件重写成 CRLF** —— `Path.read_text()/write_text()`
   做 universal-newline 转换，导致 sha256 前后不一致
   （`7df7bee9eb02` vs `e46ef84a4f3d`）。改成按 bytes 读写后一致。
   **差一点就把一个假"源码未复原"当成真结论写进报告。**

第 3 条和第 4 条都是"验证工具自身的错"，不是产品的错 ——
但它们都会**制造假结论**，所以照实写出来。

## 7. 未决项（诚实边界）

### 7.1 本轮**没有**解决

* **`Quote.code` 对指数不带前缀**：账本轴仍是裸码。`sh000001` 与
  `sz000001` 在账本上**仍不可区分**（只能靠 `Quote.name` / `board`）。
  本轮修的是"不抓错"，**不是**"账本能分辨"。这是一条独立项。
* **`call_detailed` 生产调用点仍为 0**：`engine._fetch_indices()`（`:1066`）
  仍走 legacy `call("snapshots", ...)`。**WP04 未做。**
* **Sina 是默认兜底源**（`fallback: ["sina"]`）：本轮只修了 Sina，
  **其他源是否有同一类"剥前缀再重猜"的模式未逐一审计**。
* **腾讯 `snapshots()` / `snapshots_detailed()` 的 `idx_set`** 仍由
  "调用方是否写了显式前缀"推断 —— 同一 bug 类的第一例，未动。

### 7.2 用户真正要的东西

**`spirit_*` 仍然 `enabled: false`。用户要的"盘中盯盘"仍然没有跑起来。**

本轮修的是一个**真实会抓错证券**的缺陷 —— 它确实会让盯盘拿到错误数据
（如果 `spirit_index` 被打开的话）。但：

* 真实 Precision / Recall / 漏事件率 / **仍然 `unavailable`**
* 交易收益 / **仍然 `unavailable`**
* 修复缺陷 ≠ 用户收到有用告警

**本轮模型真正增量提升 = 0。** 修复的是程序正确性，不是模型能力。

## 9. 三条可证伪的研究想法

1. **`guess_prefix` 应当被删除或改名。** 它的存在本身在邀请误用
   （本轮就是）。可证伪预测：若把它的名字改成
   `guess_prefix_for_stock_only` 并强制调用方传 `role`，
   同类缺陷在后续 5 轮内不再出现。
2. **"完整符号过滤"应当成为 `Source` 协议的一部分。** 可证伪预测：
   其余源（腾讯/东财）里至少还有 **1 处**按裸码过滤带前缀请求的响应。
   验证方式：对每个源构造"请求 sh000001、响应 sz000001"的探针。
3. **账本轴与过滤轴的分工是暂时的。** 可证伪预测：若 `Quote.code`
   长期不带前缀，`IT-P2-TIME-DIAGNOSTIC-ROUTE-COLLISION-010` 会在
   其他入口以新形式复发（因为裸码碰撞的根因没消除）。
