## 1. 本轮结论摘要

`6997487` 的 `IT-P1-DELIVERY-LEDGER-002` 修复**不重开**：最新本地 Agent 已独立复现修复前 `6/66=9.1%`，修复后真实 `Replay + Engine + Store` 为 `66/66`，逐 signal `committed` 与 Store 实数逐条相等。这是真进展。

但当前最大的瓶颈已经转移到**两个分母**：

1. **Universe denominator（最优先）**：当前 round `coverage=returned/requested` 的 `requested` 只来自已经决定好的 `_codes`。如果 `_codes` 自身已经是部分股票池，round coverage 可以 100%，而真实全市场 active coverage 只有约 69%。引擎其实已经保存 `transport_expected_total/raw_unique_codes/usable_coverage/complete`，但这些事实没有进入 Store/status/live-session health。于是“没报警”仍然无法区分“没有事件”与“根本没扫到”。
2. **Delivery denominator**：新的交付分母自增仍包在裸 `try/except: pass`；门禁又用 `max(total-named,0)`。账本坏掉时可能假绿，且运营面只看到最近一轮，不是 session 累计；长跑工具也仍只聚合旧 `signal_evaluability` 交付数字。

本轮新增一个辅助问题：`/api/status["universe"]` 目前是 `len(state.quotes)`，这是 latest-cache cardinality，不是 active scan universe；它还可能包含指数和已不在 active `_codes` 的旧缓存。因此即使未来把“universe 数字”显示出来，也不能直接把这个字段当扫描分母。

本轮优先实验 `EXP-IT-COV-001-denominator-decomposition` 实际完成：在固定软件场景 `expected=5913, active=4100, requested=4100, returned=4100` 下，现有 round coverage 是 **100%**（健康），但 active/end-to-end coverage 只有 **69.34%**。这只证明分母合同，不代表任何真实市场覆盖率。

## 4. `IT-P1-UNIVERSE-COVERAGE-001`：当前最严重的是“分母已经被截断后，round coverage 仍可全绿”

固定 SHA 中，Eastmoney universe 已经正确拆出：`transport_expected_total / raw_unique_codes / usable_quotes / transport_complete / usable_coverage`。这说明**上游真值已经存在**。

Engine 也把最近一次采用/候选股票池的 meta 保存在 `_universe_meta`。但 `poll_once()` 的 RoundObservationSet 使用：

```python
req_stocks = len(self._codes)
requested = req_stocks + index_requested
coverage = returned / requested
```

也就是说 round coverage 回答的是：“我决定扫描的这些代码，本轮回来多少？”

它**不回答**：“我应该扫描的市场代码里，到底有多少进入 active scan？”

这两个问题必须分开。

### 本轮实际合同实验

| 场景 | expected | active/requested | returned | round coverage | active market coverage | end-to-end returned |
|---|---:|---:|---:|---:|---:|---:|
| full-near-healthy | 5913 | 5913 | 5908 | 99.92% | 100.00% | 99.92% |
| partial-all-returned | 5913 | 4100 | 4100 | **100.00%** | **69.34%** | **69.34%** |
| partial-near-perfect | 5913 | 4100 | 4096 | **99.90%** | **69.34%** | **69.27%** |
| expected unknown | unknown | 4100 | 4100 | **100.00%** | **unknown** | **unknown** |

现有 live-session 的 coverage 门禁只看 round coverage，所以后 3 种里至少前两种会被读成“覆盖健康”；expected unknown 也不能被伪造成 full。

这就是为何 **P0-0（真实 T+5/T+30 质量标签）不能在全项目层面直接解锁**：如果扫描范围本身缺 30%，你只能评价“已扫到且 committed 的事件”，不能声称全市场漏事件率或 Recall。

## 5. `IT-P2-UNIVERSE-STATUS-CACHE-001`：当前 `/api/status.universe` 不是 active universe

`AlertStore.status()` 当前：

```python
quotes = state.quotes
"universe": len(quotes)
```

而 `state.quotes` 是**所有最近准入过的 latest cache**：

- 个股 `state.update(... route=stocks)` 会写；
- 指数 `state.update(... route=index)` 也会写；
- `EngineState.prune()` 会删 history / last_price / watermark / time evidence，**没有删除 `state.quotes`**。

所以：

```text
status.universe
≠ len(engine._codes)
```

并且在某些状态下可以：

```text
active stocks = 2
latest-cache stocks = 2
latest-cache indices = 1
status.universe = 3
```

或者 active pool 发生变化后，旧 cache 继续留着。

这个字段最多只能叫 `latest_quote_cache_size`，不能拿去做 Universe Coverage Gate。

## 6. `IT-P1-DELIVERY-FALSE-GREEN-001`：当前门禁仍可“账本坏了但 PASS”

固定 SHA：

```python
try:
    observation.committed_alerts_total += len(fresh)
except Exception:
    pass
```

而对账输出：

```python
missing = max(total - named, 0)
```

本轮按当前公式跑 4 个机制病例：

| 病例 | total | named | signed_ratio | unsigned gate | 当前结果 |
|---|---:|---:|---:|---:|---|
| 正常 | 66 | 66 | 1.0 | 0 | PASS |
| 分母自增被吞 | 0 | 66 | None | **0** | **假绿** |
| total 少算 | 1 | 3 | **3.0** | **0** | **假绿** |
| sidecar 少算 | 3 | 1 | 0.333 | 2 | 可能假红 |

正确合同不是继续 clamp，而是显式检查：

```text
0 <= named <= total
accounting_errors == 0
```

只要 `named > total`、账本更新异常、ratio > 1，都必须 `accounting_status = inconsistent`，而不是 PASS。

## 7. `IT-P1-DELIVERY-GATE-PERROUND-001` + `IT-P1-SOAK-LEDGER-BLIND-001`

RoundObservationSet 是**逐轮对象**；Store 每轮用新的 `as_dict()` 覆盖最近 observation。

所以真实 361 轮累计 `66/66=1.0`，不代表 `/api/status.observation.delivery_accounting` 在会话末尾也会显示 1.0。若末轮 0 告警，它自然是：

```text
committed_alerts_total = 0
signed_ratio = None
```

这不是“数学错”，而是**字段层级没命名清楚**。

下一版必须至少拆：

```text
delivery_last_round
delivery_session
```

与此同时，`tools/live_session.py` 的 observation marker/value 白名单仍然只到 `signal_evaluability`，没有 `signal_delivery` / `delivery_accounting`；汇总还在从旧 eval 账本累加 `ev_committed`。因此 soak 对新 Delivery Ledger 仍然盲。

## 9. 主改造：Universe Truth Contract v1

### 目标

让“市场应该有多少 → provider 给了多少 → 可用多少 → 实际扫描多少 → 本轮返回多少 → 时间准入多少”成为一条单一事实链。

### 非目标

- 不改变交易规则阈值；
- 不增加持续抓取；
- 不为了提高 coverage 购买数据；
- 不把 unknown expected_total 当 100%；
- 不用 delivery coverage 替代 universe coverage。

### Schema

建议新增一个有界对象：

```text
UniverseTruth
  refresh_id
  observed_at
  source
  mode = full / partial / retained_previous / watchlist / unknown
  expected_total
  raw_unique_codes
  usable_quotes
  active_scan_codes
  transport_complete
  transport_coverage
  usable_coverage
  active_coverage
  reason
  candidate_was_applied
```

RoundObservationSet 只引用：

```text
universe_refresh_id
active_scan_codes
round_requested_stock_codes
round_returned_stock_codes
```

### 关键恒等式/边界

```text
transport_coverage = raw_unique_codes / expected_total
usable_coverage    = usable_quotes / expected_total
active_coverage    = active_scan_codes / expected_total
round_coverage     = round_returned / round_requested
```

只有 `expected_total` 已知时前三者可计算；未知必须 `None/not_measured`。

`round_coverage` 不能冒充 `active_coverage`。

### 状态转移

```text
unknown -> full
unknown -> partial_degraded
full -> full
full -> partial_candidate_rejected (继续使用旧 full)
partial -> full
any -> watchlist_fallback
```

必须同时暴露 `candidate universe` 与 `active universe`，否则“源端这次只有 4100，但系统仍保留上一次 5563”也无法解释。

### 起始 health 配置

先用保守的、可配置起点：

```text
active_coverage:
  warn < 0.95
  fail < 0.90
unknown expected_total:
  warn/not_measured，不得绿色认证
transport_complete=false:
  至少 warn
```

这只是初始运维阈值，不是统计认证标准；真实盘中数据积累后再校准。

### 兼容/迁移

保留旧 `status["universe"]` 一版，但标 deprecated，并把它改成 `active_scan_codes`；另加 `latest_quote_cache_size` 与 `universe_truth`，避免前端/脚本继续把 cache size 当 active scan。

## 16. 最终判断

`6997487` 真正修复了“交付账本只覆盖 9.1%”的问题；这一点应保留，不应从零重报。

现在项目最应该解决的是：

```text
市场应该有多少
→ provider 实际给了多少
→ 可用多少
→ active scan 到底多少
→ 本轮请求/返回/准入多少
→ signal 是否可评估
→ Alert 是否 committed
→ 通知是否 sent
→ client 是否 applied
→ future label
```

目前后半段的 Delivery Ledger 已经向前走了一步，但**最前面的 Universe 分母仍不在运营事实链里**。如果这一层不闭合，系统可以在只扫描部分市场时仍显示 round coverage 100%，那么任何“没报警”“漏事件率”“全市场 Recall”都没有可靠分母。

因此下一阶段优先级是：**Universe Truth Contract > Delivery 账本自检/session 化 > event_id/notifier truth > per-code provenance/soft-partial > 真实标签与模型。**
