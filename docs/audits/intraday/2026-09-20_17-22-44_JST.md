## 1. `IT-P1-TIME-ROLE-001/002/003` — source-epoch / time-role 时间合同（P1-最高，已修 + 验牙）

### 1.1 文件 / 函数 / 行号（修复前）

- `src/arad/engine.py:56-60` `accepted_watermark: dict[str, float]`（**只有 code，无来源**）
- `src/arad/engine.py:169-173` 乱序判定 `if wm is not None and q_ep < wm: reject`
- `src/arad/engine.py:190` `accepted_watermark[q.code] = max(wm, q_ep)`
- `src/arad/engine.py:209-210` `if q_ep > ep: return True, ep, ""`（轻微超前夹到 now）
- `src/arad/engine.py:211` `return True, q_ep, ""`（**无陈旧下限**）
- `src/arad/capabilities.py:93/98/103` 三家 `provider_time=False`

### 1.2 触发条件

**跨源切换**：主源连续失败达阈值，`SourceManager` 改由备用源供数
（`engine.py:355` `self._serving[route] = i`）。

### 1.3 机制与影响

**001 —— 水位线跨源共享，新鲜报价被静默丢弃。**
`accepted_watermark` 是 `code -> timestamp`，**不含来源**。A 源先接受
`10:30:40`；供数切到 B 源、B 首包 `10:30:05` —— 按事件时间它比水位线旧，
于是被当"乱序"拒绝。但 B 的时间轴是**另一个 epoch 的起点**，不是倒退。

**002 —— 轻微超前的 provider ts 被静默改写成本地 now。**
`q_ep > ep` 时返回 `(True, ep, "")`，把 provider 时间换成接收时间，原值丢失。
与三家 `provider_time=False` 叠加后，**任何跨源时间比较都无意义**。

**003 —— 首见码无陈旧下限。**
`_admit_time` 最后一行无条件接受任何早于 now 的 ts。首见码喂 `now-3天` 照样准入
—— 跨源切换（新码首现）时可能把数天前的价格当新鲜行情。

### 1.4 复现证据（修复前，本机真实执行）

```text
A 源 ts=10:30:40 -> admitted=['600000']  watermark 是否 ==10:30:40: True
B 源 ts=10:30:05 -> admitted=[]          stats={'t_reject:out_of_order': 1}
                    quotes.price 仍是 10.0（B 的 10.5 丢了）

首见码 ts=3天前  -> admitted=['999999']  【被接受】

轻微超前 ts=now+2s -> 入库 history 时间戳 == now（原始 ts 丢失）
                      provider_ts_raw 属性: 不存在
```

> **构造用例的陷阱（我自己先栽了一次）**：`ts` 必须是**已发生**的时间。
> 若用 `now+40s`，它会被 `_admit_time` 夹到 `now`，水位线停在 `now`，
> B 的 `now+5s` 也被夹到 `now` —— 两者相等而放行，**缺陷被掩盖**。
> 我第一版探针正是这么错的，改正后才复现出来。

### 1.5 修法

1. **水位线按实际 serving source 分段**（`EngineState.begin_source_epoch()`）。
   供数源一变就开新 epoch，新 epoch 的**水位线清空重算** —— 跨 epoch 不互相
   否决，epoch **之内**的真实乱序照拒。
   必须用 `serving_of(ROUTE_STOCKS)` 而不是 `SourceManager.current`：热备期间
   由备用源实际供数，`current` 还是主源，按它分段会把两个 epoch 混成一段。
2. **epoch 标签用「名字#下标」**，不是只用名字：配置里两个源重名时，只用名字会
   让切换前后标签相同、`begin_source_epoch` 判为幂等而不重置水位线，
   跨源误杀原样回来（已单独加测试与验牙）。
3. **A→B→A 是三个 epoch**：存标签而非布尔，同一来源重复上报**幂等**。
4. **保留 provider 原始 ts**：新增 `provider_ts_raw`。入库仍用夹过的 `q_ep`
   —— 那是**既有且被测试固定**的契约（`test_engine_time_admission.py:113`
   断言 `h[-1][0] == EP`），本轮**不擅自**改动它，只是额外留痕。
5. **`effective_event_time` 与 `received_at` 分开**，跨源比较才有依据。
6. **首见码加保守陈旧下限** `STALE_TOLERANCE_SECONDS = 4h`。只对**首见码**生效
   （`first_seen=` 参数在准入前取），已有水位线的码不走这条，避免与 epoch 内
   乱序判定互相干扰。**4 小时**是有意的保守值：A 股冷门股可能几十分钟才成交一次，
   它的 `ts` 表示"最后成交时间"，下限设成几分钟会把正常冷门股全部误杀。
7. `prune()` 一并回收三张新表，避免长时间运行无界增长。

### 2.2 机制

## 7. 三条可证伪的研究想法

### RF-01【程序修复】时间语义必须有可执行的合同守卫

- **假设**：`provider_time=False` 与三家 parser 照常填 `ts` 并存了多轮，是因为
  **没有任何东西检查"声明的能力"与"实际取值"是否一致**。本轮
  `tests/test_source_time_contract.py` 把合同的 `provider_field` 绑到真实解析位置，
  这类漂移从此会立刻变红。
- **证伪条件**：若该守卫在未来 3 轮内一次都没抓到真实漂移，或抓到的全是误报，
  则它只是仪式、不值得维护。
- **可执行动作**：把同一手法推广到 `capabilities.py` 的其余声明位
  （`float_cap`、`turnover`、`volume_ratio`）。

### RF-02【任务定义调整】"陈旧"应当有真实判定，而不是保守兜底

- **假设**：本轮把陈旧下限设成 4 小时是**权宜**，因为三家 `role=unknown`，
  无法判断"这个 ts 表示什么"。一旦 `source_time_contract` 拿到权威证据
  （例如确认某字段确为 snapshot publish time），下限就能按源分别设定并大幅收紧。
- **证伪条件**：若按源分别设定后，真实语料上误杀率（正常报价被判陈旧）**不降**，
  说明"保守 4 小时"已经是合理终态，不值得继续投入。
- **性质**：这是**任务定义**问题 —— "多旧算陈旧"取决于 provider 语义，
  本轮**未决定**，只把"该路径此前不存在"这一事实写进了字段注释与合同。

### RF-03【模型真正增量提升】时间可信度应作为特征而非硬门控

- **假设**：本轮把 `provider_ts_raw` 与 `effective_event_time` 分开留痕后，
  **首次**可以量化"provider 时间与本地时钟的偏差分布"。把
  `provider_ts - received_at` 作为特征输入模型，可让模型学到"该源此刻时间是否
  可信"，从而在真实数据上提升 PR AUC。
- **证伪条件**：真实语料上相对 base 提升 < 0.005，或该特征在 family permutation
  中重要性排名后 50%。
- **前提**：依赖真实多日语料，当前 `blocked`。
