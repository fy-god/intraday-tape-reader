## 0. 本轮新增结论

在不重复上一份报告 `IT-P0-001 ~ IT-P2-003` 的前提下，本轮确认两个新的、会改变告警语义的问题：

1. **`Engine.poll_once()` 的规则候选来自长期累计的 `state.quotes`，不是本轮真实返回的 quotes。** 只要某只股票在一个“整体请求成功”的轮次里被数据源漏掉、解析跳过，或者已经从新股票池移除，它的旧 Quote 仍可能继续进入规则。现有代码只处理“整个 snapshots 调用抛异常”时不跑规则，没有处理“成功但部分代码缺失”的 stale code。
2. **“上市 11 天后就可以按普通涨跌停规则计算”的工程近似不是交易制度语义。** `min_list_days` 按自然日计算，数据缺失时直接放行；而 `Quote.limit_up_price` 在数据源未给真实限价时无条件按板块比例推算。当前上交所/深交所规则下，IPO 股票前 5 个**交易日**不设普通涨跌幅限制；长假、缺上市日字段或特殊重新上市/退市整理场景都可能让当前 fallback 人工造出一个并不存在的“涨停价/跌停价”。

本轮优先级：先修 `IT-P0-003`，再修 `IT-P1-005`。它们比新增新规则更重要，因为二者都会让正确写出的规则在错误观测集/错误市场制度上运行。

# 2. P0 新问题：当前轮缺失代码仍可能拿上一轮旧 Quote 跑规则

## IT-P0-003：`state.quotes` 是累计缓存，但 `eligible` 被当作“本轮快照”使用

### 2.1 固定源码证据

固定提交：`f8dcbdd80c7b647df7e8ef7d28a59e2a91a0922b`

`src/arad/engine.py::EngineState.update()`：

```python
for q in quotes:
    ...
    self.quotes[q.code] = q
```

这里是“收到谁就覆盖谁”，**没有删除本轮没返回的旧 code**。

`src/arad/engine.py::Engine.poll_once()` 随后构造规则候选：

```python
self.state.update(quotes, now)

eligible = {
    c: q for c, q in self.state.quotes.items()
    if self.filters.accept(q, now.date()) and c not in self.ignore
}
...
snap = Snapshot(
    ts=now,
    seq=self.state.seq,
    quotes={c: self.state.quotes[c] for c in self.watchlist if c in self.state.quotes},
)
snap.quotes.update(eligible)
```

关键点：`eligible` 遍历的是**历史累计 `self.state.quotes`**，不是本轮 `quotes`。

`src/arad/filters.py::Filters.accept()` 只看停牌、代码、板块、价格、成交额、ST、上市天数；它不检查：

```text
本轮是否真的返回该 code
quote.ts 是否属于本轮
quote.seq 是否为当前 round
```

### 2.2 为什么“请求成功”不等于“代码覆盖完整”

`src/arad/sources/tencent.py::TencentSource.snapshots()` 的确保证“任一 chunk 网络异常则整次抛 `SourceError`”，这是好的；但同一个成功 HTTP body 中，`parse_response()` 会跳过：

- 字段不足的行；
- 无法解析 `price/prev_close` 的行；
- 没有匹配正则的行。

最终：

```python
merged = {}
for batch in results:
    for q in batch:
        merged[q.code] = q
return list(merged.values())
```

**没有校验 `len(merged)` 是否覆盖 requested codes，也没有返回 missing code 集合。** Sina 同样会跳过空 payload、字段不足和无行情行。

因此“整个 call 没抛异常”完全可能对应“本轮少了一些代码”。

### 2.3 确定性反例

离线即可构造：

```text
round 1 requested = [A, B]
source returns      [A@10.00, B@20.00]
state.quotes        = {A:10, B:20}

round 2 requested = [A, B]
HTTP/parse 整体成功，但 B 的响应行字段不足，被 parse_response 跳过
source returns      [A@10.20]
state.quotes        = {A:10.20, B:20.00(old)}

eligible 遍历 state.quotes
=> A 和 B 都进入 Snapshot
=> 规则在 round 2 仍可针对 B 求值
```

更严重的第二条路径：股票池刷新后 `B` 已不在 `_codes` 中，但 `state.quotes` 没有随 universe refresh 删除 B；`eligible` 仍遍历旧 B。`state.prune()` 当前只删除 `history/last_price/first_seen`，并不删除 `quotes/day_open/universe`；而因为 B 先被旧 Quote 判为 eligible，它还会重新进入 `keep`，历史甚至可能永远得不到 prune。

### 2.4 影响

这不是普通“延迟一轮”问题：

- `wide_amplitude`、高开低走、低开高走等只依赖当前 Quote 字段的规则可能对旧 B 继续告警；
- 涨跌停状态机可能把旧价格与新的 `now`/状态跃迁组合；
- 当前 `IT-P0-002` 又没有真正做 event-time freshness，旧 Quote 不会因为年龄被中心门控；
- 全市场扫描时，数据源“少回几十只”比整轮抛异常更可能长期不被察觉，因为 poll latency / source health 仍可能显示正常。

### 2.5 修复方案：把“当前观测”和“历史状态”物理分开

**不要清空历史状态；只把规则的 current snapshot 改成当前轮真实观测。**

建议最小实现：

```python
round_quotes = {q.code: q for q in quotes}
if idx_quotes:
    round_index_quotes = {q.code: q for q in idx_quotes}

state.update(round_quotes.values(), now)       # 历史可继续累计

eligible = {
    c: q for c, q in round_quotes.items()      # 注意：不再扫 state.quotes
    if filters.accept(q, now.date()) and c not in ignore
}

snap = Snapshot(ts=now, seq=state.seq, quotes=eligible)
```

watchlist 也不能从旧 `state.quotes` 强行塞回本轮；watchlist 某 code 本轮缺失，应明确记 `missing_current_round`，而不是展示旧价参与规则。

进一步把数据源返回类型从 `list[Quote]` 升级为：

```python
@dataclass
class SnapshotBatch:
    source: str
    source_epoch: int
    requested: tuple[str, ...]
    quotes: dict[str, Quote]
    missing: tuple[str, ...]
    received_at: datetime
    event_ts_min: datetime | None
    event_ts_max: datetime | None
```

### 2.6 覆盖率门控

只做到“本轮缺谁就不评谁”还不够。若 5563 只请求只回来 3800 只，系统应该标记 degraded，而不是静默当正常轮次。

建议新增：

```text
coverage = returned_valid_codes / requested_codes
missing_current_round_total
coverage_p50 / p95 (也可按 round 输出当前值)
```

起始工程策略（阈值待实测校准，不声称最优）：

- coverage >= 99%：正常；
- 95% <= coverage < 99%：degraded，规则只评当前有数据的代码，并显示数据质量告警；
- coverage < 95%：尝试备用源或整轮规则冻结，避免“半市场静默缺失”。

阈值应通过真实多日日志再定，不能把上述数字写死成“最优”。

### 2.7 回归测试

新增集成测试 `test_partial_success_does_not_reuse_stale_quote`：

```text
round1 FakeSource -> A,B
round2 FakeSource -> A only，且不抛异常
StubRule(code=B)
预期 round2 = 0 alert，B 不在 snap.quotes
```

再加 universe-remove 场景：

```text
round1 codes=[A,B]
刷新后 codes=[A]
下一轮只返回 A
断言 B 不在 current snapshot / eligible / 新规则输出
```

这两个测试比单纯断言 `state.quotes` 内容更重要，因为允许历史 cache 留着；必须保证**规则输入不再把 cache 当 current observation**。

# 3. P1 新问题：无涨跌停期间可能被 fallback 人工造出“涨停价”

## IT-P1-005：`min_list_days` 是自然日，`limit_up_price` fallback 不知道 no-limit regime

### 3.1 固定源码证据

`config/settings.yaml`：

```yaml
filters:
  # 上市天数少于该值的新股不告警（避免无涨跌幅限制的新股噪声）
  min_list_days: 11
```

`src/arad/filters.py::_too_new()`：

```python
return (today - d).days < self.min_list_days
```

这是**自然日**。

同一个函数在没有 `list_date` 时：

```python
if not raw:
    return False
```

也就是**上市日期缺失时 fail-open，直接允许进入规则**。源码注释也说明只有东财股票池提供 list_date；新浪 fallback 时新股过滤会失效。

`src/arad/models.py::Quote.limit_up_price`：

```python
if self.limit_up and self.limit_up > 0:
    return self.limit_up
return round(self.prev_close * (1 + limit_rate_of(self.code, self.name)), 2)
```

所以数据源没给真实涨停价时，就按主板10%、双创20%、北交所30%、主板ST5%推算。

而 `src/arad/sources/sina.py` 明确说明：

```text
新浪不提供涨停价/跌停价 -> limit_up=0, limit_down=0
```

### 3.2 与当前交易制度的冲突

截至本轮核验的上交所/深交所官方规则：

- 上交所关于全面注册制交易机制说明：主板新股上市后前 5 个交易日不设涨跌幅限制；科创板官方交易机制同样是前 5 个交易日不设普通涨跌幅限制。
- 深交所现行交易规则 3.3.15 明确，IPO 股票前 5 个交易日不适用涨跌幅限制；另有重新上市、退市整理期首日等特殊情形。

官方来源：

- SSE: https://english.sse.com.cn/news/newsrelease/c/5715812.shtml
- SSE STAR: https://english.sse.com.cn/start/trading/mechanism/
- SZSE Trading Rules（英文译本 2024）：https://www.szse.cn/English/rules/siteRule/P020240911598586572526.pdf

### 3.3 反例

假设某 IPO 在国庆长假前不久上市：

```text
上市后已经过去 11 个自然日
但真正完成的交易日 < 5 个
```

当前 `Filters._too_new()` 会因为 `calendar days >= 11` 放行。

若此时主行情切到新浪（或其他未提供 actual limit price 的源）：

```text
Quote.limit_up = 0
Quote.limit_up_price -> prev_close * 1.10 / 1.20 / 1.30
```

系统会制造一个交易所当天并不存在的普通“涨停价”，`limit_board` 随后可以产生假的触板/封板/炸板语义。

另一个更直接的场景：universe 从新浪取得，`list_date` 缺失 -> 新股过滤直接放行。

### 3.4 修复方案：把涨跌停制度做成显式 `PriceLimitRegime`

不要继续用 `min_list_days` 间接猜市场制度。

建议：

```python
@dataclass(frozen=True)
class PriceLimitRegime:
    mode: Literal["limited", "unlimited", "unknown"]
    rate: float | None
    source: str                 # exchange_calendar / source_explicit / derived
    reason: str                 # normal / ipo_first5 / relisted / delisting_day1 ...
```

判定顺序：

1. 数据源明确给出有效 `limit_up/limit_down`：可直接使用，但仍记录来源；
2. 独立证券主数据 + 交易日历知道“IPO 前5交易日 / 重新上市首日 / 特殊无涨跌停情形” -> `unlimited`；
3. 能确定处于普通限制制度 -> 才允许按板块/ST比例派生；
4. 上市日期/交易状态不足以判断 -> `unknown`，**limit_board fail-closed（跳过这只）**，不要猜一个限价。

`min_list_days` 可以继续作为用户层“过滤新股噪声”的策略配置，但不能兼任交易制度判定器。

### 3.5 回归验收

至少四组：

| 场景 | 预期 |
|---|---|
| IPO 第1~5交易日，source limit=0 | `regime=unlimited`，limit_board 不运行 |
| 第6交易日普通主板，source limit=0 | 可按10%派生 |
| 长假跨越 11+自然日但交易日<5 | 仍是 `unlimited` |
| list_date / regime 不可知 | `unknown`，limit_board 跳过并计数，不人工猜限价 |

并单独覆盖重新上市/退市整理等特殊日，不要把所有异常场景都塞进“新股11天”。

# 4. P2 深化：当前 `SourceManager` 只表达“哪个源成功”，没有表达“这一轮数据是否足够好”

这不是一个新的独立 bug ID，而是对上轮 `IT-P1-001 + IDEA-IT-001` 的具体化。

目前 `SourceManager.call()` 的成功条件基本是“方法没有抛异常”。但对实时快照，应该至少分三层：

```text
Transport OK        HTTP/解析过程无异常
Coverage OK         requested codes 的有效覆盖达到门槛
Semantic OK         本规则所需字段能力齐全、event time新鲜
```

所以建议把 failover 从“异常驱动”升级为“质量驱动”：

```text
current source fetch
    ↓
SnapshotBatch(coverage, missing, capabilities, age)
    ↓
质量足够 -> 规则
质量不足但备用源适配同语义 -> fallback
备用源字段降级 -> 仅允许兼容规则继续，其他规则冻结
```

这能同时解决：

- `IT-P0-003` 的 partial success；
- `IT-P1-001` 的 Tencent/Sina 能力切换；
- `IT-P0-002` 的 stale/out-of-order；
- 数据源“接口在线但字段退化”的灰色故障。

## IDEA-IT-004：Current-Round Observation Barrier

### 机制

规则的“当前状态”必须只由本轮真实观测决定；长期 cache 只服务历史窗口与展示，不得冒充当前 tick。

### 实现位置

`Engine.poll_once()` / `EngineState`。

引入：

```text
round_id
seen_codes_this_round
missing_codes_this_round
coverage
```

规则入口只接收 `RoundSnapshot.quotes`；历史窗口仍可从 `EngineState.history` 读。

### 对照

A：当前 `state.quotes -> eligible`

B：`round_quotes -> eligible`

用同一离线脚本注入 1%、5%、20% 随机代码缺失和 universe remove/rejoin。

比较：

- stale-code alerts；
- 真正有 current quote 的告警保留率；
- degraded round 比例；
- 不同 missing rate 下的规则稳定性。

### 淘汰条件

如果实现仍需要每条规则自行检查 “seen this round”，说明 barrier 放错层，应回到 Engine 统一生成 current snapshot，不能把负担下推给规则。

## IDEA-IT-005：Price-Limit Regime Service

### 机制

涨跌停规则不是单纯 `board -> rate`，还依赖上市/重新上市/特殊交易阶段。

### 实现

新增只读服务：

```text
SecurityMaster + TradingCalendar -> PriceLimitRegime(code, trade_date)
```

输入至少：上市日、板块、ST状态（当日有效）、特殊交易状态；输出 `limited/unlimited/unknown` 与 rate。

### 数据需求

- 可靠交易日历；
- point-in-time 股票状态；
- 数据源实际限价字段作为交叉校验。

### 验证

抽样最近多批新股/科创/创业板/主板/ST，比较：

```text
regime 推导价 vs 主行情 actual limit price
```

普通限制日必须逐日一致；无涨跌停日必须不派生价格。

### 淘汰条件

如果拿不到 point-in-time 证券状态，宁可把 `limit_board` 在 regime unknown 时禁用，也不要保留一个看起来完整但会在特殊交易日造假限价的服务。

## IDEA-IT-006：Severity-3 二源轻量交叉确认（仅价格类）

### 机制

高严重度告警（封板、极端急拉等）数量远小于全市场轮询。与其每轮双源抓全市场，可以只在 severity=3 候选出现时，用第二公开源对**同一只股票**做一次短超时确认。

### 与已有 failover 的差异

现有 fallback 解决“主源请求失败”；这里解决“主源成功但单个 symbol 数据异常/陈旧”。

### 起始实现

只适用于双方都能可靠给出的价格类字段：

```text
primary candidate
  ↓
secondary fetch 1 code, timeout <= 1s
  ↓
abs(P1/P2 - 1) <= epsilon 且 timestamp age 可接受
  ↓
confirmed / source_disagreement / secondary_unavailable
```

不用于 `outer/inner`、L5 盘口或“机构”类，因为 Sina 不具备等价字段。

建议初始 `epsilon` 以 1~2 个最小价位单位或 5bp 做**候选参数**，随后用多日双源日志校准；不能未经数据就固定成真理。

### 对照与淘汰

比较 5 个交易日：

- severity-3 总数；
- source disagreement 数；
- 确认额外延迟 p50/p95；
- 被二源否决后事后证明主源确有异常的比例。

若额外延迟明显影响用户价值，而双源分歧极少且几乎都是第二源更旧，则不用于阻断，只保留 `confidence badge`；不要为了“更稳”牺牲实时性。
