## 2. WP01 — 关闭 `IT-P0-002-R2`，但不要用错误的跨源水位线

### 问题

当前乱序守卫依赖 `history[-1][0]`，而 history 只在价格/累计量变化时 append。被准入的同价同量快照不会推进 history 水位线，因此“比最新已接纳事件时间旧、但比最后 append 点新”的迟到报价仍可进入 cache 和规则。

### 先写红测

至少增加：

- R1 t0 `10.0/100`；R2 t+60 `10.0/100`；R3 t+30 `9.8/110`。R3 必须被拒，cache/last_price 保持 10.0，规则 Snapshot 无该票，`out_of_order_rejected==1`。
- 连续 3 次同价同量后送旧价。
- 相同事件时间的合法修订不得因为 `<`/`<=` 写错被无条件拒绝。
- 股票与指数分别覆盖。
- source 切换后不得把新来源因时间语义/基准不同误判为旧包。

### 实现要求

不得再复用 history append 点做准入水位线。建议新增“最新已接纳事件水位线”，但必须与 `source_epoch` / `time_role` 一起设计：

```text
(code, source_epoch, time_role) -> last_accepted_event_time
```

至少在来源切换时重建/warm-up；不允许 Tencent 的水位线直接约束 Sina/Eastmoney。

先完成第 3 节的时间角色核验，再决定哪些 source 可以用 provider timestamp 做严格乱序门控。未知时间角色时优先使用 receive-time 连续性并保守记录诊断，不要把不确定字段当权威 snapshot time。

### 回退验牙

修绿后局部恢复 `history[-1][0]` 守卫，上述红测必须再次失败；还原后全绿。保存 `red.log / green.log / rollback-tooth.log`。

## 4. WP03 — 重构 Observation Ledger，关闭 `IT-P2-OBS-002/003/004/005`

当前一个 `admitted`/`returned` 标量混了多层语义。必须拆层：

```text
requested
provider_objects            # provider 确实返回了代码对象，不论价是否>0
returned_positive           # 解析后正价可用对象
admitted_time               # 时间准入
rule_eligible               # 再经过 filters/ignore
unknown_missing             # requested - provider_objects
explicit_unavailable / rejected_quality
future_rejected
out_of_order_rejected
filter_rejected
```

股票和指数建议分列，至少让总账可机械对账。

### 必测反例

1. 请求 A/B/C；provider 返回 A 正常、B far-future、C 完全没返回：`unknown_missing=[C]`，B 只能在 future_rejected，不能双计。
2. provider 返回 Z 但 price=0：Z 不能叫 `unknown_missing`。根据真实 source 语义进入 `explicit_unavailable` 或 `rejected_quality`。
3. 正价 0.01 被 Filters 拦：`admitted_time=1`、`rule_eligible=0`、`filter_rejected=1`。
4. index 缺失也必须进入总账，不能 requested 包含指数但 missing 只遍历股票。
5. provider 整轮异常：Store 必须写新的 `round_id/status=fetch_error/observed_at`，不得继续展示上一成功轮而无 stale 标记。

### 不变量

至少机器检查：

```text
provider_objects + unknown_missing == requested       # 同一请求口径
admitted_time + time/quality rejects == returned_positive（按定义核对）
rule_eligible + filter_rejected == admitted_time（股票口径）
```

若某类无法形成严格 partition，必须解释重叠原因，不靠注释假定。

## 5. WP04 — targeted fallback 前先解决 per-code capability/provenance

`SourceManager.call()` 目前整批 fallback，因此一轮只有一个 serving source，`RuleContext.capabilities` 用单一 capability 还能成立。

先设计并测试：

```text

```


或等价 per-code metadata；不要先实现 mixed-source 合并、之后才发现所有规则都按错误的全局 capability 判断。

随后再实现 requested/returned `unknown_missing` 的**定向补洞**：只补 unknown_missing，不重抓整个 universe；合法停牌/明确 unavailable 不无限 fallback。保留 IT-P1-007 route-specific fail accounting。
