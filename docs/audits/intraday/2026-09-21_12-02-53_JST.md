## 2. 先更正最新本地 Agent 报告的一处范围：`str/int` fail-open 是事实，但当前产品可达性未被证明

最新本地 Agent 正确证明了：

```python
_as_date("2025-03-10") -> None
_as_date(20250310)     -> None
st_limit_rate_on(...)  -> 0.10
```

这说明函数对不支持类型会静默 fail-open，**函数行为本身确实有缺陷**。

但本轮重新沿真实产品路径核对后，需要收紧“可达性”表述：

1. `Quote.ts` 的数据模型是 `datetime | None`。
2. Tencent `_parse_ts()` 返回 `datetime | None`，解析异常返回 `None`；不会返回 `str/int`。
3. replay 给 `Quote.ts` 的是 timeline 中的 `datetime`。
4. `server/web.coerce_ts()` 虽然会从字符串解析时间，但该代码段是在把 JSON 行重建为 **`Alert.ts`** 供 feed 展示，并不是构造 `Quote.ts`，因此不能作为 ST `Quote.trade_date` 的可达证据。

因此应拆成：

- **已确认可达**：`datetime` / `None`；
- **已确认函数鲁棒性问题、当前生产可达性未证实**：`str` / `int`。

这项更正很重要：否则本地 Agent 可能为了“修 str/int”去扩大 `_as_date` 接受面，反而把数据边界变得更模糊。

本轮机制矩阵已落盘 `market_rule_date_provenance_probe.json`。

## 3. 新的统一根因：`IT-P1-LIMIT-PROVENANCE-001`（P1，新增）

### 3.1 现象

当前 `Quote.limit_up_price` / `limit_down_price` 的优先级是：

```python
if self.limit_up > 0:
    return self.limit_up
...
return prev_close * (1 + date_aware_rate)
```

这对**provider 明确返回的交易所限价**是合理的：例如 Tencent 真实字段存在时，应优先信明确限价。

但 replay 也把自己**本地推导**出来的 `limit_up/limit_down` 填进同一字段：

```python
rate = stock.limit_rate()              # 当前没传 replay day
limit_up = start_price * (1 + rate)
...
Quote(..., limit_up=limit_up, limit_down=limit_down, ts=ts)
```

于是两个完全不同的语义被压进同一个槽：

```text
Quote.limit_up
= provider_explicit_authoritative
或
= local_replay_derived
```

而 `Quote.limit_up_price` 无法区分，都会无条件提前返回。

### 3.2 为什么这比“只补 when 参数”更重要

给 `ScriptedStock.limit_rate(when)` 补日期可以修复**当前这次** 2026-07-06 制度变更。

但如果未来再发生制度变化，或者其他本地构造路径预填了旧制度限价，仍可能再次绕过日期感知逻辑。

真正应冻结的合同是：

```text
provider 显式限价
    → 可作为 authoritative explicit value

本地/回放推导限价
    → 不能伪装成 provider explicit
    → 应保留 provenance 或不写入 Quote.limit_up/down
```

### 3.3 最小兼容修法

推荐最小改动：

1. `ScriptedStock.limit_rate(when)` 显式接 replay 日期；
2. `build_script()` 用 replay 日期算局部 `limit_up/limit_down`，只用于生成/夹住 synthetic 价格和封单剧本；
3. replay 生成 `Quote` 时**不要**把本地推导值塞进 `Quote.limit_up/down`，保留 `0.0`，让 `Quote.limit_up_price` 根据 `Quote.ts` 走日期感知 fallback；
4. 若产品必须保留 replay 预置限价，则新增 sidecar/字段 `limit_source = provider_explicit | local_derived | unknown`，只有 `provider_explicit` 允许 unconditional short-circuit。

这能保留 Tencent 明确限价值的优先级，同时不让 synthetic/local derived value 冒充 provider authority。

固定主板 ST、昨收 10.00：

| replay day | 当前 replay 旧值 | 日期感知正确值 |

| 2025-03-10 | 11.00 | **10.50** |
| 2026-07-05 | 11.00 | **10.50** |
| 2026-07-06 | 11.00 | 11.00 |

因此历史 replay 前制度阶段仍然会漏掉真实 5% 封板。

本轮不把它和 `str/int` 直接归成“同一行代码根因”；更精确的分层是：


A+B 是当前 replay 真实可达故障；C 是应修的边界合同，但当前内置 Quote 生产路径只证实 `datetime|None`。

## 5. `None` 日期应如何处理：不要再把 provider timestamp 与市场规则交易日绑死

这里还有一个架构要点。

此前 `source_time_contract.json` 已明确：Tencent/Sina/Eastmoney 的 provider `Quote.ts` 语义仍是 `unknown`，只允许在 source epoch 内做 ordering，不能把它当权威 freshness 时间。

同理，**市场制度所需的“交易日”也不应该依赖 provider timestamp 的语义角色**。

规则求值上下文本身已有：

```python
RuleContext.now
Snapshot.ts
```

它们来自 Engine/replay 的决策时钟，是“本轮属于哪个交易日”的更直接证据。

因此长期更稳的 Market Rule Contract 应是：

```text
decision_trade_date
= replay clock / engine evaluation clock

provider_ts_raw
= 行情来源的时间证据，仅用于来源对账/排序政策
```

不要让：

```text
provider ts role unknown
```

继续承担：

```text
交易制度版本选择
```

的唯一职责。

### 建议策略

- 实盘：`decision_trade_date = ctx.now.date()`；
- replay：`decision_trade_date = replay timeline date`；
- provider 明确 limit_up/down：仍可优先采用，但必须记录其 provenance；
- provider 未给限价：按 `decision_trade_date` 本地推导；
- 日期证据缺失：显式 advisory / unknown，不得悄悄写成“现行制度已确认”。

这比简单扩大 `_as_date` 能接受的类型更稳。

## 7. Alert Truth Contract 继续开放；本轮补了一个统计层反例

当前开放项维持：

- `IT-P1-EVAL-PUBLISH-001`：rule 内 `published` 实际仍是 `rule_selected`；
- `IT-P1-NOTIFY-RESULT-001/002`：Engine 丢 bool，且 bool 不能区分 sent 与 skipped；
- `IT-P1-ALERT-IDENTITY-001`：无稳定 `signal_id/event_id`。

本轮没有重复 notifier 机制探针，而是验证这对研究统计有什么后果。

### `EXP-IT-LABEL-002-event-denominator`

构造 250 个独立 synthetic 事件簇，每个簇含 1 个 committed event、1–20 个高度相关的 rule-selected 重复命中。

结果：

```text
independent event clusters = 250
rule_selected rows         = 2671
行数膨胀倍数                = 10.684×

naive IID SE(rule_selected) = 0.000176
cluster-level SE(committed) = 0.000592

naive / cluster SE          = 0.298
```

也就是说在这个软件统计反例里，若把同一事件簇的重复 `rule_selected` 当独立样本，名义标准误只有 cluster-level 的约 30%，会产生明显“伪样本量”。

这**不是市场模型成绩**，只证明用户要求的“事件簇不能当独立行”是必要的。

因此 future-label 研究必须从：

```text
committed event_id
```

开始，再按 symbol/day/event cluster 做 block/group bootstrap。

## 9. 本轮主改造：Market Rule & Limit Provenance Contract v1

### 目标
保证历史 replay、实时 fallback、未来制度变更和研究标签使用同一套可追溯市场规则身份。

### 非目标
- 不改变交易策略阈值；
- 不修改远端产品代码；
- 不宣称真实命中率提升；
- 不把 provider timestamp 强行认定为交易日语义。

### 合同

```text
DecisionClock
  decision_ts
  trade_date
  mode = live | replay

QuoteTimeEvidence
  provider_ts_raw
  received_at
  provider_time_role

LimitEvidence
  limit_up
  limit_down
  source = provider_explicit | local_derived | absent

MarketRuleEvidence
  market_rule_version
  trade_date_known
```

### 优先级

```text
provider_explicit validated limit
    >
date-aware local derivation using DecisionClock.trade_date
    >
unknown / unavailable
```

禁止：

```text
local_derived limit
→ 写入 explicit 槽
→ 绕过 date-aware calculation
```

### 迁移

第一阶段无需破坏 `Quote` 公共 schema：

- replay 不写 locally-derived `limit_up/down`；
- 给 committed alert metrics/sidecar 写 `market_rule_version` 与 `limit_source`；
- 后续若多处需要，再正式增加 typed provenance。

### 回退

若候选改造出现回归，恢复 replay 的显式字段写入即可；红测必须重新暴露 2025-03-10 `11.00 != 10.50`，作为“回退验牙”。
