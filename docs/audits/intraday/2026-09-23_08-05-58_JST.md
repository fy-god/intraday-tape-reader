# 3. 反例一：直接给 complete 路径加 shrink guard，会把已经修好的“新股进入”重新修坏

直接使用仓库已有的 exact fixture：

```text
previous active   = 5913
raw market member = 5923
new member        = 10
current-unusable old members = 370
usable Quote      = 5553
true removals     = 0
```

四种策略：

| 策略 | active | 老有效成员丢失 | 新成员进入 | exact membership |
|---|---:|---:|---:|---|
| 当前 usable replacement | 5553 | 370 | 10 | 否 |
| **naive complete shrink guard** | **5913** | 0 | **0** | **否** |
| `prev ∪ usable` | 5923 | 0 | 10 | 是（仅本 fixture） |
| **transport membership replacement** | **5923** | **0** | **10** | **是** |

为什么 shrink guard 会失败：

```text
usable candidate = 5553
prev active       = 5913

5553 < 5913
→ reject whole refresh
```

于是：
- 370 个老停牌成员保住了；
- 但 10 个真实新增成员也全部进不来。

这会直接回归当前已有：

`TestNewListingsEnterPoolDespiteInvalidRows.test_new_listings_enter_pool`

所保护的旧问题。

所以 complete-path shrink guard 最多是：

> “宁可不更新，也不要错误大缩水”的临时 fail-safe。

它不是 Membership Truth。

# 4. 反例二：`prev ∪ usable` 看似完美，但会永久保留真实退市/移除成员

为了证明 union 也不是最终答案，本轮构造一个完全确定的 membership state：

```text
previous members = 100
真实移除/退市     = 5
真实新增          = 10

正确 raw membership
= 100 - 5 + 10
= 105

其中当前不可用   = 20
usable Quote      = 85
```

结果：

| 策略 | active | 丢有效成员 | 错保真实移除 | 新成员进入 | exact |
|---|---:|---:|---:|---:|---|
| 当前 usable replacement | 85 | 20 | 0 | 10 | 否 |
| complete shrink guard | 100 | 0 | **5** | **0** | 否 |
| `prev ∪ usable` | **110** | 0 | **5** | 10 | 否 |
| **raw transport replacement** | **105** | 0 | 0 | 10 | **是** |

因此 union 的结构性问题是：

```text
它只能加，不能正确删。
```

如果某证券真的退出 market membership：

```text
prev ∪ usable
```

会把它作为 stale member 永久保留，直到另一个额外机制来清理。

这会把当前“停牌被误删”的缺陷，换成：

> “退市/移除成员永远不删”。

所以最终合同必须是：

```text
active scan membership
=
本次可信 transport membership
```

而不是：
- usable Quote；
- previous-size guard；
- previous union。

# 6. 本轮新增一个非常关键的实施约束：Membership 不能只存 code，否则会把 `list_date` 再弄丢一次

这是本轮相对上一版 Membership Contract 最重要的设计收紧。

Eastmoney raw clist 行里：

```text
f12 = code
f14 = name
f26 = list_date
```

这几个字段并不依赖当前价格是否有效。

但是当前 `_quote_of()` 顺序是：

```python
code = ...
name = ...

price = f2
prev_close = f18

if price invalid or prev_close invalid:
    return None

...
Quote(... list_date=_list_date_of(f26))
```

因此停牌/价格无效行虽然有：

```text
code + name + list_date
```

却在构造 Quote 前就返回。

当前 `ClistPage.codes` 只保存 code，没有保存 `name / f26`。

Engine 又只从：

```text
state.universe 的 usable Quote
```

重建：

```text
filters.list_dates
```

而 `filters.min_list_days` 默认是 **11 天**。

更关键的是 Eastmoney 后续 snapshots 使用的 `ULIST_FIELDS` **没有 f26**。

这意味着如果 Membership 修复只做：

```text
“把 raw code 放进 _codes”
```

那么某个当前不可用的新股恢复交易后：
- snapshot 确实能抓到；
- 但 exact `list_date` 已经没了；
- ulist snapshot 又不会补 f26。

Filters 的 fallback 是名称前缀 `N/C`：
- `N`：首日；
- `C`：第 2–5 日。

而 `min_list_days=11` 还覆盖第 6–10 日。

所以一个**只修 code、不修 membership metadata**的方案，可能引入新的回归：

> day 6–10 的新股因为 exact list_date 丢失而绕过 11 天过滤。

因此新合同不允许：

```text
Universe membership = list[str]
```

作为最终接口。

必须至少有：

```text
UniverseMember(
  code,
  name,
  board,
  list_date,
  source
)
```

并且这些字段在 Quote 不可用时仍能存在。

对应本轮本地产物：`membership_metadata_guard.json`。



这正好把四层事实彻底拆开：


完整合同见本轮本地产物：`universe_membership_truth_contract_v2.json`。
