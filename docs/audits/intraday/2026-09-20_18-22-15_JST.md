同一场景在 020f2bb 旧代码上实跑：returned=5543  complete=True            <-- 旧判 True

停牌比例不是编造：`docs/NOTES_tencent.md:100` 记录真实全市场实测
「5908 只里 **358 只停牌**」= **6.06%**，约在第 C 例的口径上。

> **口径声明（不夸大）**：我手上唯一的真实 clist 抓包
> `fixtures/raw/eastmoney_clist_p1.txt`（100 行、total=5913）**恰好 0 行带 `"-"`**。
> 所以"东财 clist 路径上停牌行必然出现"是**由契约（`DATA_CONTRACT.md:189`）与

> 但**机制本身不依赖该比例**：只要全市场任意一只票返回 `"-"`，判据即翻假。

**机制**：`complete` 是引擎是否**采纳**该股票池的门控（`engine.py:703`），
但它的判据把"传输/池规模"与"解析后可用条数"混为一谈，于是**契约要求的正常丢弃
被误判成传输缩水**。

**影响（本机实跑，真实 `Engine.refresh_universe()`）**：

```text

A) 冷启动、无停牌        : complete=True   采纳 5913
B) 冷启动、约 6% 停牌    : complete=False  采纳 5543（池子少 370 只）
C) 现有池 5913、约 6% 停牌: complete=False  refresh 返回 0 -> 池子不变
D) 现有池 5913、约 0.2% 停牌: complete=False refresh 返回 0 -> 池子不变
```

`C`/`D` 的引擎日志实录：

```text

（缺 12 行，覆盖 99.8%）），继续尝试后续来源
所有来源都只给出部分股票池；eastmoney 仅 5901 只 < 现有 5913 只，保留现有股票池以免缩小扫描范围
```

**最严重的可测后果：新股永不入池。** 构造"全市场 5913 + 10 只新上市 + 约 6% 停牌"：

```text
feed total = 5923（含 10 只新上市）   停牌 ~6.25%
parsed returned = 5553   shortfall = 370   complete = False
refresh_universe() = 0
NEW listings now in pool = []      -> 新股采纳 0/10
```

即：**只要市场里有停牌股，股票池刷新就永久走 partial 分支；而 partial 分支又有
"不得小于现有池"的保护，于是全市场规模增长（新股上市）永远进不来**，
且用户侧只看到一行 WARNING 日志，没有任何看板信号。

**修复建议**：把两个口径拆开，不要用一个布尔承担两件事：

1. `transport_complete = bool(total > 0) and not failed and not truncated`（原义）；
2. `usable_coverage = len(out) / expected_total`（新增，诊断用）；
3. 采纳门控应看 `transport_complete`；行数缩水另走**独立**判据，
   且必须能区分"服务端真的少给行"与"解析按契约丢弃"——
   在 `parse_clist` 侧统计 `dropped_invalid` 并上抛，用
   `expected_total - dropped_invalid` 作可比基准。

**验收测试**：
1. 全市场含 `f2="-"` 的停牌行、每页足额、无失败页、未截断 →
   断言 `transport_complete is True`（当前为 False，红）；
2. 同一场景断言 `usable_coverage < 1.0` 且 `complete` 不受其影响；
3. 每页只回 10 行（真缩水）→ 断言 `complete is False`（保住 16:25 已修的轴）；
4. 全市场增长（新增上市码）叠加停牌 → 断言新股最终**在**池中。

**影响**：平价期间的**持续时长不可测**；首见时刻被合并丢掉，窗口起点晚于真实起点。

**修复建议**：区分"变化采样窗口"与"观测账本"；需要时长的规则读观测账本。

**验收测试**：断言平价观测推进"最后观测时刻"，以及窗口起点等于真实首见。

## 6. 三条有依据的研究／改进想法

### RF-01【程序修复】用"分母一致性"守卫自动发现本次这类判据错误

- **依据**：§2.1 的根因是 `len(out)`（post-parse）与 `expected_total`（transport）
  两个分母被写进同一个比较式。这类错误在代码里可机械识别：任何
  `complete`/`valid`/`ok` 布尔若同时引用"原始计数"与"过滤后计数"，即告警。
- **可执行动作**：`tools/check_denominator_consistency.py`——对可疑布尔取其
  AST 依赖的变量，追溯各自是否经过 filter/parse/dedupe（`_dedupe`、
  `parse_clist`、`_quote_of`、`drop`、`filter`）。
- **证伪条件**：若它对仓库现有全部判据只报误报、或漏掉 §2.1 这一形态，则规则无效。

### RF-02【任务定义变更】把"请求"与"想要"在账本里彻底分开

- **依据**：§2.5/§2.6 显示 `requested` 由配置生成而非真实 dispatch，
  于是 `coverage` 的分母是一个"意图"而不是"事实"。
- **假设**：若每个 route（stocks / index）各自记录
  `wanted / dispatched / returned / usable`，则 OBS-008 与 OBS-009 会同时消失，
  且 `coverage` 首次具备可解释性。
- **证伪条件**：若按 route 拆分后，真实（非合成）语料上 `coverage` 的
  轮间波动与拆分前无显著差异，则拆分只增加复杂度而无诊断价值。

### RF-03【真实模型增益】停牌/不可用模式作为"该不该告警"的特征

- **依据**：`docs/NOTES_tencent.md:100` 实测真实全市场 **6.06% 停牌**，
  且 §2.10 修完后逐 (code, field, reason) 的不可评估明细**首次可用**。
- **假设**：把"该标的当前缺哪些字段 / 是否停牌"作为特征输入，
  可能提升真实数据上的 PR AUC——因为**数据可用性本身与是否值得告警相关**。
- **证伪条件**：真实多日语料上相对 base 提升 < 0.005，或缺失模式在
  family permutation 中重要性排名后 50%。
- **前提**：依赖真实多日连续语料，当前 `blocked_no_mounted_multiday_continuous_corpus`；
