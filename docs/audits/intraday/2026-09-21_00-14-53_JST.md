## 3. `IT-P1-CAPABILITY-003`：当前 capability health 的分母与语义都不对

### 3.1 当前实现到底统计了什么

`RoundObservationSet.unavailable_capability` 当前定义为：

```python
return len(self.unavailable_codes)
```

其中 `unavailable_codes` 是所有 rule 写入的**代码集合并集**，并不是某条规则的“不可评估代码数”，更不是“整类规则不可评估”。

`tools/live_session.py` 随后按轮统计：

```text
只要 unavailable_capability > 0
=> unavailable_rounds += 1

capability_unavailable_ratio
= unavailable_rounds / rounds_with_observation
```

健康判定默认 `unavailable_fail_ratio = 1.0`，并把 100% 的 round ratio 解释成：

> “整类规则在这整场 soak 里一次都没被评估过”。

这个推论不成立。它最多说明：**每一轮至少有一个 code 被某个规则记录过 capability missing**。

### 3.2 本轮机制反例：每轮只坏 1 / 5000，也会被判 whole-class FAIL

本轮按当前聚合公式构造：

```text
20 rounds
每轮 requested codes = 5000
每轮 unavailable codes = 1
```

真实的“按 code 粗略可评估比例”仍约为：

```text
4999 / 5000 = 99.98%
```

但当前 health 得到：

```text
unavailable_rounds = 20
observation_rounds = 20
ratio = 1.0
level = FAIL
```

也就是 **99.98% 标的可评估的场景，被文案解释成“整类规则一次都没评估过”**。

这不是阈值高低的小问题，而是分母错了：round-level “有没有任意一个缺失”不能替代 code/signal-level evaluable coverage。

### 3.3 更严重：`unavailable_capability` 甚至不总表示“不可评估”

`VolumeBurstRule` 对换手率与量比采用了两种不同语义：

- 缺 `turnover`：先记 `unavailable_capability`，然后 `q.turnover=0` 会被默认 `min_turnover=0.5%` 门槛拦掉 —— 这是**硬阻断**。
- 缺 `volume_ratio`：同样记 `unavailable_capability`，但当占位 `vr=0` 时，代码的 `vr > 0 and vr < threshold` 为假，量比门槛被跳过；如果速度、金额、涨跌幅等后续条件成立，**规则仍然可以正常出 Alert**。

所以现在同一个状态名：

```text
unavailable_capability
```

同时承载：

```text
blocking_missing       真正不能评估
advisory_skipped       缺一个当前语义允许跳过的条件，但仍可评估/命中
```

这会直接污染 soak 的 capability health。

### 3.4 修复方向

不能继续只加一个全局计数。需要新增**Signal Evaluability Contract**：

```text
signal_key
  volume_burst
  spirit_order:big_buy
  spirit_order:institution_buy
  ...

considered_codes
hard_evaluable_codes
blocked_capability_codes
advisory_missing_codes
evaluated_no_hit_codes
hit_candidate_codes
published_alerts
```

有界持久化只保存计数 + 少量样本；逐 code 状态可以在本轮内临时存在。

健康判定应该依据：

```text
evaluable_coverage(signal)
= hard_evaluable_codes / considered_codes
```

而不是“有 unavailable 的轮数 / 总轮数”。只有某条启用 signal 在整场 soak 中 `evaluable_coverage≈0`，才有资格输出“整类规则没有被验证”。

## 4. `IT-P1-CAPABILITY-004`：`spirit_order` 在 fallback 下仍是 capability blind

### 4.1 三源能力与当前规则消费方式

当前 capability table 声明：

| source | L1 | L5 | outer/inner | turnover | volume_ratio |
|---|---:|---:|---:|---:|---:|
| Tencent | ✓ | ✓ | ✓ | ✓ | ✓ |
| Sina | ✓ | ✗ | ✗ | ✗ | ✗ |
| Eastmoney | ✗ | ✗ | ✗ | ✓ | ✓ |

Sina parser 确实填了：

```text
bid1 / ask1
bid_vol / ask_vol
```

但没有填：

```text
bid_vols / ask_vols
```

而 `spirit_order._best_order()` 只遍历 `q.bid_vols / q.ask_vols`。它虽然给“价格”提供了 `fallback_px`，却没有给“数量”提供 L1 fallback。

这造成一个非常具体的合同断裂：

> capability table 说 Sina 有 `depth_l1=True`，但 `institution_buy / institution_sell` 的实现实际上无法消费这份 L1。

### 4.2 8 个 pattern 在当前实现下的实际能力矩阵

`spirit_order` 的 8 个 pattern：

- `big_buy / big_sell / institution_eat / institution_vomit`：依赖 `outer_inner` 增量；
- `institution_buy / institution_sell`：语义上只需要单档 L1，但当前实现遍历五档 tuple；
- `big_bid_wall / big_ask_wall`：明确要求 `q.has_depth`，即真实 L5。

按**当前实现**而不是 capability 声明推导：

| source | capability 声明看起来可支持 | 当前实现实际 hard-evaluable |
|---|---:|---:|
| Tencent | 8 / 8 | **8 / 8** |
| Sina | 2 / 8 | **0 / 8** |
| Eastmoney | 0 / 8 | **0 / 8** |

Sina 的 2 条差额正是 `institution_buy / institution_sell`：有 L1 量，但实现没有拿 `bid_vol/ask_vol` 当单档数量使用。

### 4.3 更隐蔽：完全失效时 Observation Ledger 也不一定知道

`SpiritOrderRule` 当前没有调用：

```text
ctx.provides(...)
ObservationDecision(...)
```

所以在 Sina / Eastmoney 服务期间，上述 pattern 因字段能力不足而不可能命中时，`unavailable_capability` 仍可能完全没有记录。

如果 `volume_burst` 关闭、或者没有走到它的 capability mark 分支，live-session 的 capability health 可以显示“没有能力缺失”，但 `spirit_order` 实际整类 signal 已经不可评估。

这与项目 README 的目标直接冲突：系统已经明确承诺“不假装拿得到拿不到的数据”，那么“不具备能力”就不能继续表现为普通的 `0 alerts`。

### 4.4 修法

第一步，不急着混源：先把每个 pattern 的硬需求显式化。

建议：

```text
spirit_order:big_buy           requires outer_inner
spirit_order:big_sell          requires outer_inner
spirit_order:institution_eat   requires outer_inner
spirit_order:institution_vomit requires outer_inner
spirit_order:institution_buy   requires depth_l1
spirit_order:institution_sell  requires depth_l1
spirit_order:big_bid_wall      requires depth_l5
spirit_order:big_ask_wall      requires depth_l5
```

对 Sina 的 L1 两条，`_best_order()` 应在五档 tuple 为空时，用 `bid_vol/ask_vol + bid1/ask1` 构造一个单档候选；这符合“机构买单/卖单是单档挂单”的规则定义。对 outer/inner 或 L5 缺失的 pattern，必须记录 `blocked_capability`，不要静默当 `evaluated_no_hit`。

## 5. `IT-P1-CAPABILITY-002`：未来 targeted fallback 的真正前置仍未完成

`RuleContext.provides()` 当前签名仍是：

```python
ctx.provides(key)
```

而 `Engine.poll_once()` 的 `capabilities` 仍从 **stocks route 最近 serving source** 取一份 round-global 声明，再整份塞给 `RuleContext`。

现在还没有 mixed-source，所以这尚未直接制造当前生产错判；但 `IT-P1-SOURCE-EMPTY-001` 的下一步是针对 soft-partial 只补缺失代码，一旦实现：

```text
A -> Tencent
B -> Sina
```

同一 Snapshot 里不同 code 的能力立即不同：

```text
A: turnover/L5/outer_inner = yes
B: turnover/L5/outer_inner = no
```

一份 `ctx.capabilities` 无法正确描述这两个 code。

因此顺序必须固定：

```text
per-code provenance/capabilities
    ↓
per-signal evaluability
    ↓
requested-vs-returned reconciliation
    ↓
targeted fallback
```

不能先做 mixed-source，再补 capability。

建议兼容扩展：

```python
ctx.capabilities_for(code)
ctx.provides(code, key)
```

旧 `ctx.provides(key)` 可暂时保留为 single-source compatibility view。

## 6. `IT-P1-SOURCE-EMPTY-001` 仍然成立

`SourceManager.call()` 当前失败语义仍是：



## 7. `IT-P1-WINDOW-001` 仍未被 accepted watermark 修掉


## 8. 新增 P2：`IT-P2-OBS-STATUS-001`

`AlertStore` 已经有 `observation_seq`，`live_session` 也正确地在每轮 poll 前后比较 seq：本轮没有新 observation 时，不会拿上一轮账冒充本轮。这一点已经修得比早期版本好。

但 `/api/status` 仍直接返回：


```text

observation_observed_at

```

因此外部 API 消费者如果没有像 `live_session` 一样直接访问 Python Store 属性，就无法可靠区分：



## 10. 主改造：Per-code / Per-signal Evaluability Contract

建议从当前 Observation Truth Contract 再加一层：

```text
raw provider batch
    ↓
per-code provenance
    source / source_epoch / received_at / provider_ts_raw
    ↓
time & quality admission
    ↓
admitted_current
    ↓
per-code capabilities
    ↓
per-signal evaluability
    blocking / advisory-skipped / evaluable
    ↓
rule evaluation
    evaluated_no_hit / hit_candidate
    ↓
policy truncation + cooldown
    ↓
published alert
```

建议新增有界统计对象（名称可调整）：

```python
SignalEvalStats(
    signal_key,
    considered,
    evaluable,
    blocked_capability,
    advisory_missing,
    evaluated_no_hit,
    hit_candidates,
    published,
    reasons,
    blocked_sample,
)
```

SpiritOrder 必须按 pattern 统计，不能只统计 `rule=spirit_order`，因为 8 个 pattern 的能力需求不同。

### 机械不变量

```text
evaluable + blocked_capability = considered

evaluated_no_hit + hit_candidates = evaluable

published <= hit_candidates
```

`max_per_round` / AlertBus cooldown 的截断应发生在 `hit_candidates` 之后，不能让“命中了但被策略限流”被统计成“没命中”。
