### 2.1 修复本身在 `Quote` 路径上是**正确**的

### 2.2 但 replay 路径**结构性地**绕过它

`src/arad/models.py`：

```python

L350      return self.limit_up                              # ← 直接返回预置值

L354               * (1 + limit_rate_of(self.code, self.name, self.trade_date)), 2)
```

**机制**：`L349-350` 只要 `limit_up > 0` 就**提前返回**，`L354` 那行**日期感知的重算永远不会被执行**。
而 replay 在 `L361` **总是**把算好的 `limit_up` 塞进 `Quote`。

### 2.3 反例（本机真实执行，端到端）

同一只主板 ST 股、同一 `start_price=10.00`，只因回放日不同：

```text

    Quote.ts              = 2025-03-10 09:30:00
    Quote.trade_date      = 2025-03-10
    Quote.limit_up        = 11.0    ← replay 预置
    Quote.limit_up_price  = 11.0    ← 规则真正消费的值
    正确的 limit_up       = 10.5
    与当日真实制度一致？  False

--- 回放日 = 2026-09-16（post，真板率 10%）---
    Quote.limit_up_price  = 11.0
    正确的 limit_up       = 11.0
    与当日真实制度一致？  True
```

**规则级后果**（`limit_board` 真实消费该值）：

```python
limit_board.py:115   up = self._limit_up_price(q)
limit_board.py:155   def _limit_up_price(q): return float(q.limit_up_price)
```

实测：

```text
Quote(price=10.50, prev_close=10.00) 于 2025-03-10
    当日真实 5% 涨停价 = 10.50
    Quote.limit_up_price = 11.0     ← 10% 带宽，错
    is_at_limit_up()     = False    ← 应为 True
    距（错误的）上限仍有 -4.55%
```

即：**在 2026-07-06 之前的回放里，一只真实封在 5% 涨停价上的主板 ST 股不会被识别为「贴板」**。

### 2.4 影响面（如实说明边界）

- **实盘当日不受影响**：今天是 2026-09-21，`CURRENT == 0.10`，而 `when=None` 也返回 `0.10`，两者一致。
- **仅三条件同时成立时出错**：① 历史回放；② 走 `replay.py` 预置 `limit_up`；③ 回放日在 2026-07-06 之前。
- **未计数**：我没有真实多日连续 ST 语料，**未统计**受影响的真实 ST 股票数/告警条数 → 该数字标 `未计数`，不编造。
- **`default_universe()` 当前不含任何 ST 股票**（见 §3.3），所以**默认参数下这条路径今天打不到**；
  但它对**用户传入自定义 `ScriptedStock`** 立即成立，且这正是该修复 commit 自己写进 docstring
  要求保持 5% 的场景（`models.py:45-47`）。

### 2.5 修复建议

1. `ScriptedStock` 增加 `day`/`trade_date`（或 `limit_rate(when)` 接受回放日），
   `replay.py:160` 改为 `limit_rate_of(self.code, self.name, when)`。
2. 更稳的根治：`Quote.limit_up_price` 的**预置值优先级**需明确 —— 若 `limit_up > 0` 但 `trade_date`
   落在旧制度区间，应**不信任**预置值（或至少让 `replay` 不预置，交由 `Quote` 自算）。
   当前「预置即真理」的语义把制度变更的判定权交给了**最不了解交易日的那一层**。
3. 让 `default_universe` 真的包含一只主板 ST（见 §3.3），否则该路径在默认配置下永远不被测试覆盖。

## 8. 有依据的研究/改进想法（依据均来自本轮证据）

1. **把「制度生效日」变成一等公民，而不是散落在计算点。**
   依据：§2.2 的两个 `limit_rate_of` 调用点，一个传 `trade_date`（`models.py:354`）、
   一个不传（`replay.py:160`），于是同一只 ST 股在同一份代码里得到两个板率。
   建议把 `trade_date` 提成 `Snapshot` 级字段并按回放日注入，
   让「算板率」这件事只有**一个**入口，缺失日期时**抛错**而不是静默取现行制度
   （当前的 `when=None -> CURRENT` 是一个**静默 fail-open**：我把 `ts` 设为 `None`/`str`/`int`
   三种情况，2025 年的 ST 股都返回了 10%）。
2. **默认股票池应当覆盖它自己文档承诺的每一个制度分支。**
   依据：§3.3 —— docstring 承诺覆盖 ST，实测 0 只；而 §2 的缺陷恰好落在「ST + 历史回放」这个交集上。
   建议给 `default_universe` 加一只主板 ST 与一只 `*ST`，并把「池子覆盖了哪些制度分支」
   做成一条自检断言（这是**零成本**地让 §2 的缺陷在 CI 里变红的手段）。
3. **Notifier 的 `bool` 语义需要升级为三态账本。**
   依据：§4 —— 内置 notifier 在 disabled/severity-skip 时返回 `True`，
   而 `_dispatch_many` 又完全丢弃返回值。「没发」与「发了」在账本上不可区分，
   使得任何「漏报率」都无法计算。建议返回值改为 `sent / skipped / failed` 三态
   并在 `SignalEvalStats` 里单列 `notified`，把「规则选出」与「真正投递」分开计数
   ——这同时会解除 `IT-P1-EVAL-PUBLISH-001` 的分母争议。
