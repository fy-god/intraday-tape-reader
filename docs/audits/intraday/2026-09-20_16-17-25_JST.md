## 3. `IT-P1-TIME-ROLE-001`：现在的 watermark 仍然不是来源隔离的

固定源码：
[`src/arad/engine.py@020f2bb`](https://github.com/fy-god/intraday-tape-reader/blob/020f2bb5f45a50bb3367ea631654702b37b3aab9/src/arad/engine.py)

当前字段仍是：

```python
accepted_watermark: dict[str, float] = field(default_factory=dict)
```

而 `update()` 里：

```python
wm = self.accepted_watermark.get(q.code)
if wm is not None and q_ep < wm:
    ... reject ...

...
self.accepted_watermark[q.code] = q_ep if wm is None else max(wm, q_ep)
```

也就是排序域只有：

```text
code
```

没有：

```text
source
route
source_epoch
time_role
```

### 3.1 本轮最小机制反例

本轮重新执行机制探针：

```text
source A:
  code=600000, event_ts=10:00:40
  accepted -> watermark=10:00:40

下一轮实际供数切到 source B:
  code=600000, event_ts=10:00:05
```

当前 code-only watermark：

```text
10:00:05 < 10:00:40
→ reject
```

候选 `(code, source_epoch, time_role)` 分段后：

```text
B 的首条 observation
→ 建立新 epoch watermark
→ 不和 A 的时间值直接比较

B epoch 内再来 10:00:01
→ 正确 reject
```

机制探针文件：`engine_contract_probe_v7.json`，SHA256
`5584dc0a489c67841e5b66fd0aef25d8b1eee107bc66068f7eb431000c0e0e76`。

这是**机制测试**，不是在声称真实 Tencent/Sina 固定相差 35 秒。source offset 是反例输入。

### 3.2 为什么不能直接把 source 名塞进 key 就结束

`SourceManager.call()` 当前热备语义是：主源本轮失败、备用源成功时，`serving_of(route)` 会指向备用源；连续达到阈值才正式把 `idx` 提升。也就是说 source 实际供数可以在 formal primary 改变前就切换。

因此建议 `source_epoch` 不是“主源名字”本身，而是：

```text
per route:
只要实际 serving source 与上一成功轮不同
→ epoch += 1
```

A→B→A 应得到三个 epoch，而不是重新复用最早 A 的 ordering 状态。

### 3.3 `time_role` 仍不能猜

三家 parser 都会填写 `Quote.ts`：

- Tencent：字段 30 解析 `%Y%m%d%H%M%S`；
- Sina：字段 30/31 合并日期、时间；
- Eastmoney：`f124` 转换成 naive datetime。

但当前 `SourceCapabilities` 对三家全部声明 `provider_time=False`。因此代码当前同时表达：

```text
“这个 source 没有可信 provider_time capability”
```

和：

```text
“只要 Quote.ts 非空，就用它做严格 ordering”
```

这两个合同冲突。

本轮额外查到的社区资料只能说明：
- Tencent 字段 30 常被描述为“数据更新时间”；
- Sina 30/31 是响应日期与时间；
- Eastmoney f124 被社区映射为“时间戳”。

这些都不是交易所/数据商正式字段规范，不能据此认证它究竟是 snapshot publish time、last trade time 还是其他 update time。

因此下一版 `source_time_contract.json` 必须允许：

```text
snapshot_update_time
last_trade_time
unknown
```

在证据不足时保持 `unknown`。

## 4. `IT-P1-TIME-ROLE-002/003`：时间信息还存在两个独立问题

### 4.1 轻微 future 被静默改写

当前 `_admit_time()`：

```python
if q_ep > ep + FUTURE_TOLERANCE_SECONDS:
    return False, q_ep, "future"
if q_ep > ep:
    return True, ep, ""
```

因此 provider 原始时间若只比 receive time 超前 45 秒：

```text
provider_ts_raw = 10:00:45
received_at     = 10:00:00
effective_ts    = 10:00:00
```

原始时间在 State/history 层消失。

这会让后续审计无法区分：

```text
provider 时钟轻微超前
```

与：

```text
这个 observation 本来就没有 provider time
```

修复不是简单取消 clamp，而是 sidecar 保留：

```text
provider_ts_raw
effective_event_time
received_at
clamped=true/false
```

### 4.2 首见码没有 stale 下限

当前 `_admit_time()` 的最后分支对任何过去时间：

```python
return True, q_ep, ""
```

只要该 code 还没有 watermark，`now-3days` 也会被接受。

本轮机制探针再次确认：

```text
now = 2026-09-20 10:00:00
provider_ts = 2026-09-17 10:00:00
age = 259200s
current_admit_time_accepts = true
```

但 stale 多少秒应该拒绝**不能拍脑袋定值**。必须先确认 provider time role，再按 role 决定：

- 若是 snapshot update time，可设 freshness 上限；
- 若是 last trade time，停牌/低成交股票可能天然很旧，不能直接当 snapshot 陈旧；
- 若 unknown，先记录与观察，strict ordering 不应依赖它。

## 5. `IT-P2-OBS-008`：没有实际请求指数，却把它计入 coverage 分母

这是本轮新增的、直接由当前代码和默认配置推出的账本错误。

`_fetch_indices()` 明确：

```python
if not self.index_codes or not self._wants_indices:
    return []
```

而 `build_rules()` 只加载 `enabled=true` 规则。默认配置中：

```yaml
poll:
  index_codes:
    [sh000001, sz399001, sz399006, sh000300, sh000688]

rules:
  spirit_index:
    enabled: false
```

所以默认运行时：

```text
_wants_indices = false
index 网络请求 = 根本没有发
```

但是 `poll_once()` 构造 Observation 时仍然：

```python
requested = req_stocks + len(self.index_codes)
index_requested = len(self.index_codes)
```

也就是说“配置过”被记成“本轮实际请求过”。

### 5.1 反例

本轮探针固定：

```text
实际 stock request = 100
实际 stock return  = 100
配置 index codes    = 5
spirit_index disabled
实际 index request  = false
```

当前 ledger：

```text
requested=105
returned=100
coverage=95.238%
```

真实本轮网络覆盖应是：

```text
requested=100
returned=100
coverage=100%
```

默认全市场约 5563 个股票时，这个偏差较小，约 0.09 个百分点；但如果全市场源失败、退到 10 只 watchlist，这个错误会把“10/10 全返回”显示成“10/15=66.7%”。

### 5.2 修法

`requested` 必须来自**真实 dispatch**，不是配置：

```text
stock_route_started
index_route_started
```

分别记录。

只有 `_fetch_indices()` 真的调用 `SourceManager.call(..., route=ROUTE_INDEX)` 时：

```text
index_requested = len(actual_index_request_codes)
```

否则必须为 0。

## 7. `IT-P1-INDEX-CURRENT-001`：指数 current-only 仍然没有闭合

当前 `_fetch_indices()` 失败时只记录日志并返回 `[]`，不会拖垮股票链。

但是 `SpiritIndexRule.evaluate()` 仍然从累计状态读取：

```python
for code, q in (getattr(ctx.state, "quotes", None) or {}).items():
    if q is not None and is_index_quote(q):
        candidates[code] = q
```

引擎还明确写着：

```text
指数不进 snap.quotes
spirit_index 从 ctx.state.quotes 自取
```

所以：

```text
R1:
指数成功返回 -> state.quotes 缓存指数

R2:
index 请求失败 -> idx_admitted={}
但 state.quotes 还留 R1 指数

SpiritIndexRule:
仍把 R1 的 index quote 当本轮 current candidate
```

这一条在默认配置下 `spirit_index.enabled=false`，所以不是默认运行路径；但一旦用户启用指数精灵，它就重新引入了和早期 `IT-P0-003` 同类型的“累计缓存冒充 current”问题。

正确修法：

```text
保留 index history
但规则 candidate 必须来自本轮 current index view
```

可以给 `RuleContext` 增加非冻结 sidecar：

```python
current_indices: dict[str, Quote]
```

或统一放入 `RoundObservationSet` 的 runtime-only current view。

## 8. `IT-P1-COMPLETE-001`：当前错误成立，但上一报告的“直接比 len(out)”修法需要修正

当前 Eastmoney `universe()`：

```python
out = _dedupe(quotes)
complete = bool(total > 0) and not failed and not truncated

_last_universe = {
    ...
    "expected_total": expected_total,
    "returned": len(out),
}
```

`returned` 只是诊断，`complete` 不消费它。这就是 13:39 报告已经独立复现的“每页缩水仍 complete=True”。

但这里有一个很重要的修法细节：

`out` 是**经过 `_quote_of()` 解析和质量过滤之后的可用 Quote**。

`_quote_of()` 会丢：

```text
缺 code
f2/f18 无效
price <= 0
prev_close <= 0
```

所以：

```text
expected_total
```

是 transport/API universe 口径，而：

```text
len(out)
```

是 usable parsed quote 口径。

它们不能天然要求完全相等。

### 8.1 三个机制案例

本轮新增 `completeness_contract_probe_v7.json`：

#### Case A：真的缩水

```text
expected_total=100
raw unique codes=10
usable quotes=10

transport_complete=false
```

#### Case B：传输完整，但有 5 个无效/不可用 Quote

```text
expected_total=100
raw unique codes=100
usable quotes=95

transport_complete=true
usable_coverage=95%
```

如果修成：

```python
complete = len(out) >= expected_total
```

反而会把这个 transport-complete 情况误判为不完整。

#### Case C：行数够，但重复 code

```text
expected_total=100
raw rows=100
raw unique codes=90
usable quotes=90
```

按 raw row count 也不能证明完整。

### 8.2 正确合同

Eastmoney pagination 应同时记录：

```text
raw_rows
raw_unique_codes
usable_quotes
expected_total
required_pages
pages_requested
pages_failed
truncated
```

建议：

```text
transport_complete =
    total_known
    and not failed
    and not truncated
    and raw_unique_codes >= expected_total
```

`usable_coverage` 则另外定义：

```text
usable_quotes / raw_unique_codes
```

若真实 API 存在 total 漂移或允许少量差异，容差必须先通过真实多日抓取统计后冻结；不能现在随便设一个 1% 或 5%。

这同时修正 13:39 报告里“直接把 `len(out)` 与 expected_total 挂钩”的过度简化建议。

## 9. Observation Truth Contract v3：本轮主改造

### 9.1 目标

把以下概念从同一个 `Quote/list/count` 中拆开：

```text
配置了什么
真正发出了什么请求
provider 返回了什么原始对象
解析出什么
时间准入了什么
质量拒绝了什么
业务过滤了什么
规则真正能评估什么
```

### 9.2 推荐对象

```python
@dataclass(frozen=True)
class RawBatchResult:
    route: str
    request_id: str
    source: str
    source_epoch: int
    requested_codes: tuple[str, ...]
    provider_object_codes: tuple[str, ...]
    raw_rows: int
    raw_unique_codes: int
    received_at: datetime
```

```python
@dataclass(frozen=True)
class TimeEvidence:
    provider_ts_raw: datetime | None
    provider_time_role: str   # snapshot_update_time / last_trade_time / unknown
    received_at: datetime
    effective_event_time: datetime
    clamped: bool
```

```python
@dataclass(frozen=True)
class ObservationDecision:
    code: str
    route: str
    source: str
    source_epoch: int
    status: str
    reason: str
    time: TimeEvidence
```

```python
@dataclass
class RoundObservationSet:
    round_id: int
    observed_at: datetime
    status: str

    stock_route_started: bool
    index_route_started: bool

    requested_codes: tuple[str, ...]
    provider_object_codes: tuple[str, ...]

    admitted_time_codes: tuple[str, ...]
    rule_eligible_codes: tuple[str, ...]

    unknown_missing_codes: tuple[str, ...]
    explicit_unavailable_codes: tuple[str, ...]
    future_rejected_codes: tuple[str, ...]
    stale_rejected_codes: tuple[str, ...]
    out_of_order_rejected_codes: tuple[str, ...]
    filter_rejected_codes: tuple[str, ...]

    decisions: tuple[ObservationDecision, ...]
```

### 9.3 source epoch

每个 route 保存：

```text
last_serving_source
epoch_id
```

实际 serving source 发生变化：

```text
epoch_id += 1
```

即使还没达到 formal primary promotion 阈值，也要新建 epoch。

watermark：

```text
(route, source_epoch, code, time_role)
    -> last_accepted_event_time
```

不要跨 epoch 比 provider time。

### 9.4 time role 策略

建议起步规则：

- `snapshot_update_time`：可以参与同 source epoch 内 ordering/freshness；
- `last_trade_time`：不能当 snapshot arrival ordering；保留作“最后成交年龄”特征；
- `unknown`：原始值保留为 evidence，但 strict ordering 以 receive/sequence 为主，不把未认证 timestamp 当硬真值。

### 9.5 必须成立的机械不变量

只要 route 真发起：

```text
requested_codes
=
provider_object_codes
∪ unknown_missing_codes
```

## 10. 研究推进：`EXP-IT-CAP-004-disagreement-and-blend`

### 10.1 为什么本轮不重新训练

上一轮已经保存了 4 组 synthetic lockbox 共 77,271 行逐样本预测，包含：

```text
base_full
capmask_global
specialist_route
universal_intersection
```

真实多日行情仍未挂载。

本轮如果把相同 synthetic 数据重新 fit 一遍，只会增加训练次数，不增加信息。因此本轮围绕一个新问题做**post-hoc 机制诊断**：

> global capmask 与 provider-specialist 分歧很大时，是否应该 abstain，或者把两者融合？

证据等级：`posthoc_synthetic_diagnostic_on_existing_lockboxes`。不是独立锁箱，也不是实盘验证。

### 10.2 总体基线

77,271 行：

| 模型 | PR AUC | ROC AUC | Brier |
|---|---:|---:|---:|
| base | 0.68531 | 0.65738 | 0.23010 |
| capmask | 0.69451 | 0.66807 | 0.22695 |
| specialist | **0.70022** | **0.67473** | **0.22528** |
| universal | 0.67305 | 0.64549 | 0.23238 |

近 source switch（<=12 tick，8,658 行）：

```text
capmask PR     0.67577
specialist PR  0.69356
```

### 10.3 分歧并不是“越大越不可信”

定义：

```text
D = |specialist_score - capmask_score|
```

若只保留 `D <= 0.03`：

```text
coverage = 62.54%
specialist PR = 0.70308
```

相对完整 specialist：

```text
PR 0.70022 -> 0.70308
仅 +0.00286
但丢掉 37.46% coverage
```

`D <= 0.05`：

```text
coverage = 82.28%
PR = 0.70035
```

几乎没有增量。

更重要的是高分歧区：

```text
D > 0.08
n = 4,178

capmask PR     = 0.64747
specialist PR  = 0.70668
```

也就是说，在这套 synthetic 生成器里，大分歧区域反而是 specialist 相对 capmask **最有价值**的区域之一。

因此：

> **拒绝“模型分歧大就 abstain”这个规则。**

### 10.4 简单双模型 blend 也不值得增加复杂度

固定：

```text
blend = alpha * specialist + (1-alpha) * capmask
alpha = 0, .25, .5, .75, 1
```

4 个既有 lockbox 平均：

```text
alpha=0.75:
mean PR = 0.7002487

alpha=1.00 specialist:
mean PR = 0.7002152
```

PR 差：

```text
+0.0000335
```

几乎为零。

同时 specialist 自身的平均 ROC/Brier/LogLoss 更好。

所以当前研究决策：

```text
不增加 blend
不增加 disagreement-abstention
保留 provider-specialist 作为真实数据候选
```

这是一项**负结果**，有助于阻止 shadow 方案继续膨胀。

## 15. 本轮结论

工程层当前最重要的判断是：

> **“accepted watermark”不能继续只是 code→timestamp；Observation Ledger 也不能把配置、真实请求、provider object、时间准入和业务可评估性混在同一组计数里。**

下一阶段应把 `source_epoch + time_role + actual route dispatch + per-code current view` 做成统一事实链。

研究层的新判断是：

> **不增加 disagreement-abstention，不增加 capmask/specialist blend。** 在现有 synthetic 逐样本结果里，模型分歧大的区域并不等于 specialist 不可信；简单融合的平均 PR 增量只有约 0.00003，不足以支付复杂度。provider-specialist 继续只作为真实数据候选。
