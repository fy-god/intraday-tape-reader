## 0. 本轮新增结论

在不重复上一轮 `IT-P0-003`（旧 Quote 混入当前轮）和 `IT-P1-005`（无涨跌停制度 fallback）细节的前提下，本轮确认两个新的工程正确性问题，并把此前分散的“源切换 / stale / partial-success”问题收敛成一个可落地的数据质量层方案：

1. **`SinaSource.universe()` 会在第 2 页及以后失败时返回已经抓到的部分股票池；`Engine.refresh_universe()` 又把“任意非空结果”当完整全市场，直接替换上一轮股票池。** 这会在短暂分页故障时把 5000+ 只的全市场扫描静默缩成前若干页，造成系统性漏报，而且不会触发下一 universe source。
2. **`SourceManager` 只有一个全局 `fails` 计数，不区分“全市场股票快照”“指数小请求”等不同路由。** 当主源对大批股票请求失败、备用源顶上后，同一轮一个很小的指数请求若主源成功，会立刻把 `fails` 清零；于是正式切换阈值可能永远达不到，系统长期处在“每轮先失败一次、再备用源成功”的抖动状态，同时 `health()[active]` 仍把主源显示为 active。
3. 这两件事与上一轮的 `IT-P0-003`、基线审计的 `IT-P1-001` 本质上是同一个根因：**`Source` 只返回 `list[Quote]`，调用链没有“本轮实际由谁提供、请求多少、返回多少、是否完整、能力有哪些、事件时间范围是什么”的质量元数据。** 下一版最值得先做的不是新增规则，而是加一个向后兼容的 `ObservationQuality / CallMeta` 层。

本轮优先级：`IT-P1-006` > `IT-P1-007` > `IT-P2-004`。前两项先通过离线 FakeSource 回归固定行为，再实现统一质量层。

# 2. P1 新问题：分页失败的“半个股票池”会被当成完整全市场

## IT-P1-006：`SinaSource.universe()` partial success + `refresh_universe()` non-empty acceptance

### 2.1 固定源码证据

固定提交：`f8dcbdd80c7b647df7e8ef7d28a59e2a91a0922b`

`src/arad/sources/sina.py::SinaSource.universe()`：

```python
for page in range(1, pages + 1):
    try:
        raw = self._request(url)
    except SourceError:
        if page == 1:
            raise
        self._stats["pages_failed"] += 1
        self._stats["last_err"] = f"universe 第 {page} 页失败"
        break
    ...
    out.extend(fresh)

return out
```

语义是：

- 第 1 页失败：抛异常；
- 第 2 页及以后失败：**保留前面已拿到的结果，break 后返回 partial list**。

这对“尽量拿到东西”本身合理，但调用端需要知道这是 partial。

`src/arad/engine.py::Engine.refresh_universe()` 当前逻辑：

```python
quotes = src.universe()
if not quotes:
    continue
codes = self._record_universe(quotes)
if codes:
    self._codes_raw = codes
    self._codes_pinned = False
    self._universe_refreshed_at = time.time()
    return len(codes)
```

只判断“非空”，**没有 completeness / pages_failed / expected_total / count-drift 门控**，也不会因为 partial 去尝试下一个 universe source。

已有 `tests/test_engine.py` 覆盖了：

- 第一个 universe source 整体抛异常时会尝试下一个；
- 所有来源都失败时保留旧股票池；
- 空股票池时可降级 watchlist。

但当前测试没有覆盖“来源返回非空 partial result”这一条中间状态。

### 2.2 确定性反例

假设上一轮：

```text
旧 universe = 5563 只
```

30 分钟后刷新，东财本轮失败，进入 Sina。Sina：

```text
page 1..20 成功 -> 2000 只
page 21 网络异常 -> pages_failed += 1, break
return 2000 quotes
```

`Engine.refresh_universe()` 看到 2000 条非空，直接：

```text
_codes_raw: 5563 -> 2000
刷新时间重置
return 2000
```

结果：

- 约 3500 只股票接下来不再被请求快照；
- 由于本轮被视为“刷新成功”，不会继续尝试下一个 universe source；
- 至少等到下一次 universe TTL 才可能恢复；
- status 里只会看到 universe count 下降，若没有专门告警，属于“系统在运行但覆盖率腰斩”。

当前 `IT-P0-003` 尚未修时还会产生更复杂的混合状态：`_codes` 已缩小，但 `state.quotes` 里可能仍保留旧代码并被当 current 参与规则；一旦 `IT-P0-003` 修好，这个问题会更纯粹地表现为**漏报 / 覆盖率下降**。

### 2.3 影响范围

这不是单只股票误差，而是**全市场覆盖率错误**：

- 所有依赖全市场池的异动检测都可能漏掉未抓到的后续页面；
- 实盘性能指标会“变快”，但其实是因为扫描股票少了；若只看 poll_ms 反而可能误判系统性能改善；
- 当 partial pool 恰好偏向按代码排序前部，样本分布会变化，规则命中率/告警数也会出现结构性偏移；
- 现有 README 的 4800/5563 规模性能不能用于证明这种 partial-refresh 情况下仍保持全市场覆盖。

### 2.4 修复方案

#### A. 第一阶段：先把 partial 与 complete 区分开

因为 `docs/DATA_CONTRACT.md` 冻结了 `Source.universe() -> list[Quote]` 的公开签名，不建议第一步就破坏协议。可向后兼容地增加内部元数据，例如：

```python
@dataclass(frozen=True)
class CallMeta:
    source: str
    method: str
    request_class: str
    complete: bool
    requested_count: int | None
    returned_count: int
    pages_completed: int | None = None
    pages_failed: int = 0
    expected_total: int | None = None
    elapsed_ms: int = 0
```

实现方式可以是：

- `SinaSource.last_call_meta`；或
- `SourceManager.call_with_meta()` 包装原来的 `call()`，保留老 `call()`；
- 不改 Quote / Snapshot 冻结字段。

Sina 中只要出现第 2+ 页异常，就明确：

```text
complete = False
pages_failed > 0
```

#### B. Engine 接受策略

`refresh_universe()` 不能再“非空即采用”。建议：

```text
complete == True
  -> 可以候选为新 universe

complete == False
  -> 不覆盖旧完整 universe
  -> 尝试下一 universe source
  -> 若全部来源都 partial/失败，保留旧池并进入 degraded
```

对于没有显式 completeness 能力的旧 source，先标 `unknown`，不要自动冒充 `complete`；可通过一个兼容策略逐步迁移。

#### C. count sanity 只做二级保护，不替代 completeness

可以再记录：

```text
new_count / old_count
jaccard(old_codes, new_codes)
added / removed
```

但不能简单写死“少于 95% 一律拒绝”，因为真实上市/退市、数据源节点变更也会改变集合。count/jaccard 更适合作为 `WARN / quarantine`，首要判断仍是 source 自己能否证明本次分页完整。

### 2.5 回归测试

新增 `test_partial_universe_does_not_replace_complete_pool`：

```text

source1 returns 1800 codes + meta.complete=False
source2 returns 5001 codes + meta.complete=True

期望：
- 必须继续调用 source2
- 最终 _codes = source2 的 5001
- 1800 partial 绝不成为正式池
```

新增 `test_all_partial_universe_keeps_previous_pool`：

```text

source1 partial=1800
source2 partial=3000

期望：
- 保留 existing 5000
- status/degraded reason 明确为 universe_incomplete
- 不伪装“刷新成功 3000只”
```

另加“旧池为空”的 bootstrap 场景：若只能拿 partial，是否临时以 partial 运行应做**显式 degraded 策略**，不能与完整池使用同一状态名。建议先降级 watchlist + 报警，避免把 partial 当“全市场”。

# 3. P1 新问题：全局 fail counter 会被同轮不同请求重置，导致正式切换永远达不到阈值

## IT-P1-007：`SourceManager.fails` 没有按请求路由/负载类型隔离

### 3.1 固定源码证据

`src/arad/engine.py::SourceManager.call()`：

```python
if i == self.idx:
    self.fails = 0
else:
    self.fails += 1
    if self.fails >= self.threshold:
        self.idx = i
        self.fails = 0
```

也就是说，**当前主源只要任意一次调用成功，就把全局 `fails` 清零**。

而 `Engine.poll_once()` 同一轮可能先后调用：

```python
quotes = self.sources.call("snapshots", list(self._codes))   # 数千只个股
...
idx_quotes = self._fetch_indices()
# _fetch_indices() -> self.sources.call("snapshots", index_codes)  # 少数指数
```

这两个请求：

- 方法名相同，都是 `snapshots`；
- 请求负载完全不同：数千股票 vs 几个指数；
- 却共用同一个 `fails`。

`SourceManager.health()` 最后只按 `self.current` 标记 `active`，没有记录本轮股票快照实际上由备用源服务过。

### 3.2 确定性反例

假设：

- primary Tencent 对“5000只股票的大请求”当前网络环境经常失败；
- backup Sina 能成功；
- Tencent 对 `sh000001` 等 3~5 个指数的小请求却能成功；
- `failover_threshold=3`；
- 启用了需要指数的规则。

每轮：

```text
A. stocks snapshots:
   Tencent fail -> Sina success
   fails: 0 -> 1

B. index snapshots:
   Tencent success (仍是 current primary)
   fails: 1 -> 0
```

下一轮重复。

结果：

- 业务上“全市场股票路由”连续每轮都依赖 Sina；
- `fails` 却永远到不了 3；
- `current` 永远还是 Tencent；
- 每轮都白付一次大请求失败延迟；
- `health()` 的 `active=True` 仍指向 Tencent，不能回答“本轮股票数据实际由谁提供”。

这会进一步放大基线审计的 `IT-P1-001`：源身份/能力在轮内可能来回变化，但累计量差分规则不知道 source epoch。

### 3.3 影响

主要是**可用性 + provenance + 规则一致性**，不是单纯性能：

1. 延迟：每轮先等 primary 大请求失败，再走 backup；长期 p95/p99 被放大。
2. 数据能力：股票本轮可能来自 Sina（无内外盘/五档能力），指数却来自 Tencent；单一 `active source` 无法描述真实状态。
3. `spirit_order` 等依赖累计字段的规则更容易处于“这一轮 backup、下一轮 primary”的反复 rebaseline 风险。
4. 运维误判：`health()[active]` 可能显示 primary active，但最重要的全市场 stocks route 实际一直由 backup 提供。

### 3.4 修复方案：按 route 维护 failover 状态

不建议继续把一个整数补丁式扩展。至少区分：

```text
snapshots:stocks
snapshots:indices
universe
```

内部状态：

```python
@dataclass
class RouteState:
    primary_idx: int
    consecutive_primary_failures: int
    last_served_idx: int | None
    source_epoch: int
    last_switch_at: float | None
```

`SourceManager.call()` 增加内部 `request_class`（对旧调用可默认 `generic`），或由 Engine 使用：

```python
call("snapshots", codes, request_class="stocks")
call("snapshots", index_codes, request_class="indices")
```

然后：

- stocks route 的 primary success/failure 只影响 stocks；
- indices route 不得把 stocks failure counter 清零；
- 返回/记录 `served_source` 与 `source_epoch`；
- status 同时显示 `configured_primary` 与 `last_served_source_by_route`，不要只有一个 `active`。

如果不想立即支持“不同 route 有不同 current source”，最小修法也应做到：**只有与导致 fallback 相同的 request_class 成功，才清零其 failure streak。**

### 3.5 回归测试

构造一个离线 source：

```python
class SizeSensitivePrimary:
    snapshots(codes):
        if len(codes) > 10: raise SourceError
        return success
```

backup 始终成功。

连续 3 轮：

```text
call stocks(100 codes) -> primary fail, backup success
call indices(1 code)   -> primary success
```

验收：

- `stocks` 的 failure streak 应为 1,2,3，而不是每轮回到 0；
- 达阈值后 stocks route 进入 backup / circuit-open；
- index route 可继续 primary；
- status 能同时看到 stocks last_served=backup、indices last_served=primary。

现有 `tests/test_engine.py::test_source_manager_failover()` 与 `test_source_manager_recovers_counter_on_success()` 都是连续调用同一 `universe()` route，不能覆盖这种交错请求反例。

# 4. P2 根因：当前冻结 Source 协议无法表达“质量”和“来源身份”

## IT-P2-004：`list[Quote]` 只表达数据，不表达本轮数据是否可信/完整

`docs/DATA_CONTRACT.md` 与 `src/arad/sources/base.py` 的冻结接口是：

```python
def universe(self) -> list[Quote]
def snapshots(self, codes: list[str]) -> list[Quote]
def health(self) -> dict
```

这个接口可以表示：

- 有哪些 Quote；

但无法直接表示：

- 请求了多少个代码；
- 返回多少个；
- 哪些 code 缺失；
- 是否 partial success；
- 实际 serving source；
- source epoch；
- 该源是否具备 `outer/inner/depth/limit_price` 能力；
- event_ts 范围 / quote age；
- universe 分页是否完整。

因此最近三轮审计发现的问题会反复在各层补丁化出现：

```text
IT-P0-002 event time freshness
IT-P0-003 current-round coverage
IT-P1-001 source switch + cumulative delta
IT-P1-006 universe partial completeness
IT-P1-007 route-specific serving source
```

它们应当收敛到一个统一的数据质量层，而不是每个 rule 单独猜。

### 4.1 向后兼容设计

不修改冻结的 Quote / Snapshot 字段，也可以先在 Engine/SourceManager 内部增加：

```python
@dataclass(frozen=True)
class ObservationQuality:
    request_class: str
    configured_source: str
    served_source: str
    source_epoch: int
    requested: int | None
    returned: int
    missing_codes: tuple[str, ...]
    complete: bool | None
    capabilities: frozenset[str]
    event_ts_min: datetime | None
    event_ts_max: datetime | None
    received_at: datetime
    latency_ms: int
    flags: tuple[str, ...]
```

规则不需要看到全部字段。Engine 在进入 rules 前先做统一门控：

```text
coverage / freshness / source-epoch / capability
                   ↓
          可评估的 current quotes
                   ↓
               Snapshot
```

对 `spirit_order` 这种特殊规则，RuleContext 可以提供只读质量视图：

```text
ctx.quality.capabilities
ctx.quality.source_epoch
```

当 `source_epoch` 变化或缺 `outer_inner` 能力：只更新 baseline，不发 trade-class alert。

# 5. 详细优化方案：先建数据质量层，再优化规则阈值

## 阶段 A：Current-round + Universe 两条完整性契约

### A1. Snapshot coverage

每轮记录：

```text
requested_codes
returned_valid_codes
missing_codes
coverage_ratio
served_source
source_epoch
```

规则输入只用 `returned_valid_codes`，不从 `state.quotes` 补旧值；这落实上一轮 `IT-P0-003`。

### A2. Universe completeness

每次 universe refresh 记录：

```text
complete / partial / unknown
pages_completed / pages_failed
old_count / new_count
added / removed
jaccard
```

只有 complete 才能替换一个已有的 complete pool。partial 只能：

- 尝试下一来源；
- 或显式 degraded bootstrap；
- 绝不能静默覆盖完整旧池。

## 阶段 B：route-specific failover + capability

路由至少拆：

```text
stocks_snapshot
indices_snapshot
universe
```

每路独立：failure streak、last served、latency、source epoch。

capability 不根据“字段是不是 0”猜，直接由 adapter 声明。例如：

```text
Tencent: price, amount, depth, outer_inner, float_cap, limit_price, event_ts
Sina:    price, amount, depth, event_ts   # 以真实 parser 能力为准
```

注意这里的具体 capability 表必须以各 adapter 当前实现逐项核对后冻结，不能只照 README 写。

## 阶段 C：规则质量门控

例：

```text
price-only rules:
  require fresh_price

order-book rules:
  require depth + current_round

trade-delta rules:
  require outer_inner + same source_epoch + monotonic cumulative fields

limit-board rules:
  require PriceLimitRegime=limited + current price
```

这样数据源切换时不再“所有规则一刀切”；有能力的规则继续工作，无能力的规则明确 skip。

## 阶段 D：监控/看板

status 至少显示：

```text
stocks coverage
universe completeness
stocks served source
indices served source
stale/out_of_order counts
capability-degraded rule count
```

否则系统“有进程 / 有 HTTP 200”不等于业务健康。

# 6. 本轮新研究点子（均为待验证工程假设）

## IDEA-IT-007：Observation Quality Envelope

### 机制

把“数据值”和“这份数据能不能用于某类规则”分开。一次 source call 产生：

```text
quotes + quality envelope
```

而不是让规则通过 `0.0`、空字段、旧 cache 去猜。

### 相较已有实现

当前 `Quote` 只带值；`SourceManager.health()` 是源级健康，不是本轮请求级质量。新方案是**request-level provenance**。

### 最小实现

先只做 6 个字段：

```text
request_class
served_source
source_epoch
requested_count
returned_count
complete
```

完成 `IT-P0-003 / IT-P1-006 / IT-P1-007` 后再扩 event_ts/capabilities。

### 评价

不是看“告警更多”，而是看：

- stale reuse = 0；
- partial universe overwrite = 0；
- source-switch 后第一轮 trade-delta false alert = 0；
- degraded 状态可观测率 = 100%。

### 淘汰条件

如果实现后仍需要每个规则自己维护一套来源/完整性判断，说明 envelope 抽象边界错误，应退回重构而不是继续加字段。

## IDEA-IT-008：Universe Shrink Quarantine

### 机制

即使 source 声称 complete，极端的 universe 大幅缩小也值得进入短暂 quarantine，而不是立即替换。

记录：

```text
removed_ratio
jaccard(old,new)
source_complete_flag
```

若 source_complete=True 但集合突变异常：

1. 立刻用第二来源做一次低频确认；
2. 未确认前继续沿用旧 pool，但对已确认停牌/退市状态按现有规则处理；
3. 记录 `universe_change_pending`。

### 为什么不是写死 95%

真实 universe 会自然变化，且不同数据源覆盖定义可能不同。阈值必须用多日真实日志估计正常日变化分布，再选告警线；本报告不把 95% 当最优参数。

### 对照实验

离线注入：

- 5000 -> 4997 complete：应正常接受；
- 5000 -> 1800 partial：必须拒绝；
- 5000 -> 1800 complete 但第二源仍 4998：应 quarantine 并拒绝首源异常结果。

### 淘汰条件

如果真实多日日志显示正常源间 universe 定义差异过大，以至于 Jaccard/removed_ratio 无法稳定区分故障与正常差异，则只保留 source explicit completeness，不做集合异常门控。

## IDEA-IT-009：Route-specific Circuit Breaker

### 机制

全市场大请求和指数小请求的失败概率不同，不该共享一个 fail counter。

为 `stocks_snapshot / indices_snapshot / universe` 各维护：

```text
closed -> open -> half-open
failure streak
cooldown
last served source
```

stocks 连续失败达阈值后短时间直接走 backup；cooldown 后用一小批股票做 half-open probe，成功再恢复 primary。

### 相较已有实现

当前每轮股票大请求都会重新尝试 primary；任何同轮 current-source 成功又会全局清零。新方案避免 repeated-failure latency 和 route 相互污染。

### 初始参数

沿用当前 `failover_threshold=3` 作为第一版，不声称最优；circuit cooldown 可从 30~60 秒做两个预注册对照。

### 验收

构造 primary 对大请求 100% fail、对 1-code request 100% success：

- 3 次 stocks fail 后必须 open stocks circuit；
- 后续 stocks 不应每轮重复付 primary 失败延迟；
- indices 仍可 primary；
- 切回 primary 前 trade-delta 规则必须 rebaseline。

### 淘汰条件

若真实日志显示 primary 故障绝大多数是一次性瞬态，circuit breaker 反而显著增加 backup 使用和恢复延迟，则保留 route-specific accounting，但取消 open/half-open，退回更简单的路由计数。
