## §5 1–3 条有证据、可证伪的研究想法

### 想法 1〔**程序修复**（审计工具侧）〕：给"修复前后对照"设一条**不可绕过**的基准
* **证据**：本轮 R3 的 "6 → 0 → 5" 中，0 **在父提交上不可复现**（§1.1），
  而 6 与 5 分别来自不同 `--minutes`。若当时有一条"父提交必须实跑一次同命令并落盘"
  的强制步骤，这个数字不会被写成那样。
* **可证伪做法**：在 `docs/audits/` 侧加一个脚本，
  对同一命令在 `HEAD^` 与 `HEAD` 各跑一次，把原始 stdout 落盘并比较**类型分布行**；
  若两行相同（如本轮），脚本直接输出 `NO_BEHAVIOUR_CHANGE_DETECTED`，
  禁止报告中出现"修复前 N 条"这类未落盘的端点。
* **判定**：若加了这个门禁，本轮 R3 会被标成"机制成立、父提交无可见影响"，
  而不是"功能消失 → 修复"。**可证伪**：拿历史报告回放，看有多少"修复前 N"缺少落盘证据。

### 想法 2〔**任务定义调整**〕：把"告警是否有效"的验收从"发了多少条"改成**覆盖率分母必须闭合**
* **证据**：本轮测得 `Σcommitted == Σ带 signal_id 告警` **恒真但不覆盖 90.9% 的告警**（§1.2）。
  一个恒真的等式不能当验收判据。
* **可证伪做法**：把判据改为 `Σcommitted == 真实告警总数`（当前 6 vs 66，**必然红**），
  并把 `无 signal_id 告警数` 作为一等指标暴露到 `/api/status`。
  然后每轮只看这个数是否下降。
* **判定**：这是一个**会立刻失败**的门禁——正是它的价值。当前它红，说明覆盖缺口真实存在。

### 想法 3〔**真实模型增益：无**〕：本轮没有任何模型层面的改进
* 本轮是**告警交付链路与制度日期**的审计，不涉及预测模型。
  `signal_id` / 三级账本 / ST 日期感知都属**可观测性与正确性**，不是 alpha。
* **明确结论**：`真实模型增益 = 0`，且**不应**把"账本更细"当作模型进步来汇报。
