## 1. 新发现（P1）`IT-P2-TENCENT-NAME-BLIND-REQUEST-KEY-REGRESSION-002`

**文件 / 函数 / 行**
- `src/arad/sources/tencent.py:479` —— 请求侧判据
  `if prefix and sym in idx_set and looks_like_index(sym, "", c): return sym`
- `src/arad/sources/tencent.py:448` —— **raw 侧**判据
  `if symbol in idx_set and looks_like_index(symbol, name, code): return symbol`
- `src/arad/models.py:241` —— `if "指数" in nm or "成指" in nm: return True`
  （**名称是"它是不是指数"的合法证据之一**）

**机制（两轴不对称）**
`_key`（raw 侧）**拿得到 provider 给的中文名称**，`_req_key`（请求侧）
**被固定传空串**（提交 `4648b1c` 的注释自述："请求侧没有 name，传空串即走
'名称缺失一律按股票'的既有消歧规则"）。
于是**当某符号只有名称能证明它是指数时**：
- raw 轴 → 带前缀符号（`sh000009`）
- 请求轴 → 裸码（`000009`）
- 交集恒空 → `P=Q=∅` → 报「请求的 symbol missing + 返回了未请求代码」

**触发条件 / 反例（控制对照实测，非构造）**
同一 payload、同一注入 fetcher、PRE/POST 成对跑（`fetcher` 注入点
`tencent.py:682`，实测每次仅调用 1 次，**全程未出网**）：

```text
symbol     name           in INDEX_CODES  lli(name)  lli("")  PRE    POST   REGRESSION
sh000009   上证380指数      否              True       False    True   False  ← 是
sh000001   上证指数         是              True       True     True   True   否
sz399001   深证成指         否(399段)       True       True     True   True   否
sh600000   浦发银行         否              False      False    False  True   否
sz000001   平安银行         是(sz)          False      False    False  True   否
sh000300   沪深300指数      是              True       True     True   True   否
sh000905   中证500指数      是              True       True     True   True   否
```

`sh000009`（上证380）逐轴明细：
```text
PRE    R=['sh000009']  P=['sh000009']  missing=[]           unexp=[]             admitted=1   ← 正确
POST   R=['000009']    P=[]            missing=['000009']   unexp=['sh000009']   admitted=0   ← 坏了
```
`sh000009` **不在** `INDEX_CODES`（= `{000001,000010,000016,000300,000688,000852,000905}`）、
也不以 `399` 开头，因此**只有名称**能判定它是指数 —— 恰恰是这个盲点。

**影响**
- **当前暴露面**：随包配置 `config/settings.yaml` 的 `index_codes` 为
  `["sh000001","sz399001","sz399006","sh000300","sh000688"]`，
  我实测这 5 个**全部**在 `lli("")` 下也为 True → **随包配置暴露 5/5 安全**。
- **风险面**：`_load_index_codes`（`engine.py:882-896`）允许用户自行添加指数；
  任何"不在 `INDEX_CODES` 且非 399 段"的上证系列指数（如 `sh000009`）
  被加入即**每一次取数都报假 missing + 假 unexpected**，
  且因为 `raw_presence_known=True`（exact 路径），这个假账**会被当成精确账**。
- **与主报告的关系**：RED 2 修的正是"两轴不同轴"，本回归是**同一条 bug 类的反向实例**
  —— 修了 `prefix` 这个代理，却又引入了"空名称"这个新代理。

**修复建议**
请求侧**不得**丢名称信息。两个可行方向：
1. `snapshots_detailed` 在拿到响应后，用 **raw 侧已经确认的指数集合**回填请求轴
   （即 `_req_key` 改为"若该 sym 在本次 raw 里被判为指数，则用带前缀形式"），
   使请求轴与 raw 轴**同源**而非各自推断；或
2. `_req_key` 采用与 `_key` **同一份**判据的**保守超集**：
   `prefix and sym in idx_set and (looks_like_index(sym,"",c) or sym in idx_set)`
   —— 但更干净的做法是**两轴共用同一个 `_key` 函数**，从结构上消灭"两处推断"。

**验收测试**（必须配对照，否则是 `zzz2` 的空断言）
1. `sh000009` + 真实名称 → 断言 `missing==[] and unexpected==[] and admitted==1`；
2. **阳性对照**：`sh000001` / `sz399001` / `sh000300` 仍取带前缀身份（不得被"修过头"）；
3. **阴性对照**：`sh600000` / `sz000001` 仍取裸码（RED 2 不得复发）；
4. 断言 `_req_key` 与 `_key` 对**同一 (symbol,name)** 返回同一结果（同轴不变量）。

**为什么定 P1 而非 P2**：RED 2 本身是云端评的 P2；但本回归会让**正常取数**在
`exact` 路径上产生**假精确账**，直接污染 `unknown_missing` 与
`unexpected_raw_keys` 两个终局桶，且用户加一个指数即可触发。

## 2. 新发现（P1）`IT-P2-LEGACY-FALLBACK-PHANTOM-MISSING-003`

**文件 / 函数 / 行**
- `src/arad/engine.py:637-641` —— legacy 退化的 `build_outcome` 调用，
  第 639 行 `normalized_request=tuple(str(c) for c in codes)` 用的是**调用方原样字符串**
- `src/arad/sources/outcome.py:368` —— `q_in_req = [x for x in q_list if _key_of(x) in req]`
  （Q 必须与 R 相交）
- `src/arad/sources/tencent.py:318` —— legacy parser `code = symbol[2:]`（**裸码**）

**机制**：legacy 源没有 raw 证据，`build_outcome` 用 Quote 投影当 P 的下界。
但 Quote 的 `code` 是**裸码**，而 `normalized_request` 原样保留了调用方的
**带前缀**字符串 → `_key_of(quote) in req` 恒假 → **Q 被清空**，
随后 `missing` 报该码缺席。**来源明明正常返回了它。**

**触发条件 / 反例（实测，含阳性对照）**
探针先证明 parser 真的返回了行情（1 条、裸码），再测 outcome：
```text
parser 正控: sh600000 -> 1 条, codes=['600000']     （非空 = 探针有判别力）
parser 正控: sh000001 -> 1 条, codes=['000001']

request=['sh600000']  R=['sh600000']  Q=0  missing=['sh600000']  prov=quote_projection_legacy  ← 假 missing
request=['600000']    R=['600000']    Q=1  missing=[]            prov=quote_projection_legacy  ← 正确（对照）
request=['sh000001']  R=['sh000001']  Q=0  missing=['sh000001']  prov=quote_projection_legacy  ← 假 missing
```
**注意**：我第一版探针用了一个返回**带前缀 code** 的假源，那让 Q 恰好命中 R，
于是得到"无缺陷"的**假绿**。真实 parser 发裸码（`tencent.py:318`），
换成真 parser 后缺陷才现形。这是 `zzzz2` 的第二次。

**影响**
- **当前暴露面 = 0**：随包 `sources.primary=tencent`、
  `fallback=["sina"]`，而 tencent/sina/eastmoney **三个内置源都已定义
  `snapshots_detailed`**（实测 `git grep`），故都走 exact 分支，**不进** legacy 分支。
- **风险面**：`call_detailed` 一旦被 WP03 接进 `poll_once`，
  任何**第三方源**（没有 `snapshots_detailed`）都会走 legacy 分支；
  而 `_load_index_codes` 要求指数**必须带前缀**（`engine.py:883` 文档明说裸码会被丢弃），
  于是**每一轮指数取数**经第三方源都会得到 phantom missing。
- 与刚修好的 `IT-P2-TENCENT-...-KEY-AXIS-001` 是**同一条 bug 类**（两处各自推断同一身份）

**修复建议**
legacy 分支必须让 `normalized_request` 与 Quote 的 `code` **同轴**：
1. 用与各源 parser 一致的规范化函数（裸码轴）构造 `normalized_request`；或
2. 先取到 quotes，再**用 quotes 的实际 code 轴**反推 R（并保留原始请求用于报告），
   即"先看数据长什么样，再决定身份轴"；或
3. `build_outcome` 增加一个 `identity_axis="bare"` 显式参数，
   由 legacy 调用方声明"我这批身份是裸码轴"，避免再次靠猜。

**验收测试**：legacy 源（无 `snapshots_detailed`）请求 `["sh600000"]`、
返回 1 条 `code="600000"` 的 Quote → 断言 `unknown_missing==[] and len(quotes)==1`；
**对照**：真缺席时应仍报 missing（不得把缺陷修成"永远不报 missing"）。
