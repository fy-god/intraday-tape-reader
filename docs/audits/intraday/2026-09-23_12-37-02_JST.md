# 2. 本轮新 P1：同一个“raw row 已返回但行情不可用”状态，会因 serving source 不同落进不同账本桶

新稳定 ID：

### `IT-P1-SNAPSHOT-OUTCOME-SOURCE-SEMANTICS-DRIFT-001`
**P1 · fixed-SHA 源码确认 + deterministic mechanism；本轮没有 repo-import execution**

固定业务状态：

```text
requested = 600001

provider raw response:
明确包含 600001
但当前价格/昨收不可用或非正
```

三个 built-in source 的当前解析行为不同。

## Tencent

`parse_response()` 的合同明确写：

```text
price <= 0 / prev_close <= 0
（停牌）
仍保留 Quote
```

因此：

```text
raw row present
→ Quote(code=600001, price<=0)
→ Engine quality_bad
→ rejected_quality = {600001}
→ unknown_missing = {}
```

这与 `RoundObservationSet` 的定义一致。

## Sina

`parse_response()` 当前：

```python
price = ...
prev_close = ...

if price <= 0 or prev_close <= 0:
    continue
```

所以同一个：

```text
raw row present but unusable
```

在进入 Engine 前已经消失。

Engine 只能看到：

```text
requested 600001
Quote output 没 600001
```

最终：

```text
rejected_quality = {}
unknown_missing = {600001}
```

也就是把：

> raw response 明明返回了

错误记成：

> provider 完全没返回。

## Eastmoney

Eastmoney `_quote_of()` 同样在价格/昨收无效时返回 `None`；`parse_ulist()` / `snapshots()` 目前只对外给 `list[Quote]`。

因此如果 Eastmoney 被配置成 stock snapshots source，也会发生和 Sina 一样的 collapse。

# 3. 这个 P1 不只是“不同 parser 风格”，因为默认系统会真实在 Tencent 和 Sina 间切换

默认 stock source chain 就是：

```text
Tencent
↓ failover
Sina
```

而 SourceManager 的 route-aware failover 会真实改变 serving source。

因此相同 market state：

```text
600001 raw-present, suspended/unusable
```

可能仅仅因为：

```text
stock route serving source:
Tencent → Sina
```

就让 observation ledger 从：

```text
rejected_quality
```

变成：

```text
unknown_missing
```

市场事实没有变，网络是否“完全缺这个 code”的事实也没有变，变的只是 parser/source。

这会直接污染：
- provider missing rate；
- round coverage/质量归因；
- SourceManager soft-empty 判断；
- 后续 H 家族“质量/缺失/来源变化”研究因子；
- source-switch 分组验证。

如果研究模型以后把：

```text
unknown_missing
```

当质量特征，它甚至可能学习：

```text
现在 serving source 是 Sina
```

而不是学习市场本身的数据质量。

本轮机制产物：

`snapshot_cross_source_semantics_probe.json`

与：

`snapshot_source_semantics_matrix.csv`。

# 5. 本轮主改造：Snapshot Outcome Contract v4 必须是 source-agnostic

建议统一结果：

```text
SnapshotFetchResult
    route
    source
    requested_keys
    raw_presence_known
    raw_returned_requested_keys
    quotes
    rejected_quality_keys
    unexpected_raw_keys
    duplicate_raw_keys
    raw_rows
    provenance
```

其中最关键的不是字段数量，而是**集合语义**。

定义：

```text
R = caller 实际请求的规范化 unique identity set

P = raw response 中实际看见的 identity
    与 R 的交集

Q = 可形成 usable Quote 的 identity
    与 R 的交集
```

则：

```text
returned
= |P|

rejected_quality
= P - Q
  （时间拒绝仍留给 Engine 后续单独分账）

unknown_missing
= R - P

unexpected_raw
= raw_seen - R
```

而不是：

```text
returned = raw row 数
```

也不是：

```text
returned = 所有 raw unique code 数
```

# 6. 本轮新增 P2 设计护栏：详细 raw outcome 如果不做 requested-set 交集，也会制造新假账

新稳定 ID：

### `IT-P2-SNAPSHOT-RAW-SET-ALGEBRA-001`
**P2 · deterministic mechanism / design guard**

Eastmoney 当前代码自己已经注明：

> 服务端可能回带未请求的行，所以最终 Quote 输出要按 wanted_set 过滤。

因此 future detailed raw result 必须同样遵守 caller request identity。

固定：

```text
requested:
600001
600002
600003

raw rows:
600001 invalid
600001 duplicate invalid
600002 valid
600999 unexpected valid

usable quotes:
600002
600999
```

正确账：

```text
R = {600001,600002,600003}

P = raw ∩ R
  = {600001,600002}

Q = usable ∩ R
  = {600002}

returned          = 2
rejected_quality  = {600001}
unknown_missing   = {600003}

unexpected_raw    = {600999}
duplicate_raw     = {600001}
```

机械恒等式：

```text
requested 3
=
admitted 1
+ quality 1
+ missing 1
```

两种错误实现：

### 错误 A：直接把 raw row count 当 returned

```text
returned = 4
requested = 3
```

立刻越界。

### 错误 B：用未过滤的 raw unique count

```text
raw unique = 3
requested  = 3
```

表面看 coverage=100%，但请求的：

```text
600003
```

其实没回来，只是被不相关的：

```text
600999
```

“补齐”了分子。

所以 Detailed Outcome 必须从第一版就把：

```text
unexpected
duplicate
```

作为诊断，而不能在迁移后再补。

本轮产物：
`snapshot_raw_set_algebra_probe.json`。

# 7. 三个 source 都可以不增加 HTTP 请求就实现 exact raw presence

这是本轮对 Agent 工单最重要的实现约束。

## Tencent

现有正则：

```text

```

在任何 numeric quality parse 之前就已经给出 symbol。

所以 detailed parser 可以先记录：

```text
raw identity
```

再决定是否能构造 Quote。

当前 `price<=0` 已经保留；真正新增价值主要是：
- 字段不足；
- price/prev_close 不能解析；
- 其它导致 Quote 不产生但 symbol 已知的行。

## Sina

现有 `LINE_RE` 同样先得到：

```text

```

然后才：
- 判断字段长度；
- 解析 price；
- `price<=0 / prev_close<=0` 时 continue。

所以 Sina 也可以**零额外网络请求**保留 raw presence。

而且这条最关键，因为 Sina 是默认 stock fallback。

## Eastmoney

# 8. Legacy / partial rollout 不能伪装成 exact

如果某个 source 暂时没有 detailed adapter，候选结果必须明确：

```text
raw_presence_known = False

provenance =
quote_projection_legacy
```

而不是：

```text
raw_returned_codes = quote codes

```

因为后一种写法会把：

```text

```

```text

```

也就是说，在 raw presence 未知时：

```text

```

不能继续被对外声称为**精确 provider absence**。

最优方案仍然是：

> 三个内置 stock source 同一产品 diff 内都完成 exact adapter。

因为三家当前都有不增加额外 HTTP 的实现路径。

# 9. Source identity/provenance 要与结果原子绑定

当前 SourceManager：

```text

→ 返回 bare method output

→ 另外存到 _serving[route]
```

这个设计对普通 Quote list 尚可。

```text

```

这不是本轮单独列 P1 的 bug，而是 v4 合同必须提前避免的接口风险。

# 10. `IT-P1-SOURCE-EMPTY-001` 的修复条件现在可以定义得更精确

当前 SourceManager 仍然是：

```text
exception
→ 尝试 backup

正常 return []
→ 视为成功
→ backup 不调用
```

所以这个 P1 继续开放。

但在没有 Snapshot Detailed Outcome 之前，直接把：

```text
quotes == []
```

定义为 source failure 会误伤另一种场景：

```text
raw response 明明有很多 requested code
只是全部 Quote quality unusable
```

正确 soft-empty 候选条件应该是：

```text
requested set 非空
AND raw_presence_known == True
AND raw_returned_requested_keys == ∅
```

这时才能说：

> 对本次非空请求，provider raw response 中一个 requested code 都没出现。

相反：

```text
raw_returned_requested_keys 非空
quotes 为空
```

是质量问题，不应因为 Quote usability 差就盲目切源。

因此顺序继续保持：

```text
Snapshot Outcome
→ Observation Ledger
→ Membership
→ Source soft-empty
```

## 最终判断

12:11 把优先级从 Membership 提前到 Snapshot Raw Outcome 是对的。

本轮进一步证明：

> **Snapshot Raw Outcome 不能只是 Eastmoney 的特殊补丁，它必须是整个 stock source chain 的统一合同。**

因为默认系统真的会：

```text
Tencent primary
→ Sina fallback
```

而当前同一个：

```text
raw row 已返回
但行情值不可用
```

在 Tencent 可以是：

```text
rejected_quality
```

在 Sina 却变成：

```text
unknown_missing
```

只要 source 切换，数据质量标签的语义就变。

所以现在正确链条必须是：

```text
Requested Identity Set
        ↓
Source Raw Outcome
        ↓
Quote Usability
        ↓
Observation Ledger
        ↓
Active Membership
        ↓
Source Failover / Quality Factors
        ↓
Research Labels / Models
```

下一轮真正有价值的成果不是再写一版设计，而是让 Tencent/Sina/Eastmoney 三条内置 source 都通过同一组 raw-presence RED/GREEN/rollback，然后再进入 Membership 5923/5553 产品修复。
