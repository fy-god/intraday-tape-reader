## 3. `IT-P0-002-R2`：时间准入水位线仍依赖“最后一次 history append”

### 3.1 当前代码

当前乱序判断：

```python
h = self.history.get(q.code)
if h and q_ep < h[-1][0]:
    ...
    continue
```

而 history 只有价格或累计成交量变化才追加：

```python
if prev is None or prev != q.price or not h or h[-1][2] != q.volume_lots:
    h.append((q_ep, q.price, q.volume_lots))
self.last_price[q.code] = q.price
admitted[q.code] = q
```

固定源码：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/engine.py#L145-L177>

### 3.2 本轮独立机制复现

固定三轮：

```text
R1 t+0   price=10.0 volume=100
R2 t+60  price=10.0 volume=100   # 被准入，但同价同量，不追加 history
R3 t+30  price=9.8  volume=110   # 事件时间旧于已经接受的 t+60
```

当前控制流得到：

```json
{
  "history": [[t0,10.0,100],[t30,9.8,110]],
  "latest": 9.8,
  "round3_admitted": ["600000"],
  "out_of_order": 0
}
```

也就是说，R2 已经是“最新被接受事件”，但因为 history 没 append，水位线仍停在 t0；R3 的 t+30 大于 t0，于是错误通过。

候选机制改为**独立 accepted watermark**后，同一输入：

```json
{
  "history": [[t0,10.0,100]],
  "latest": 10.0,
  "round3_admitted": [],
  "out_of_order": 1,
  "watermark": "t+60"
}
```

所以 05:30 本地 Agent 的 R2 结论得到本轮第二套独立机制证据支持。

### 3.3 不能直接“加一个 last_accepted_ep”就结束

本轮又检查了三家解析器和 capability 合同，发现时间字段本身还有角色不清的问题，见下一节。因此正确修复不是无条件建立一个跨来源永久水位线，而应至少绑定：

```text
(code, source_epoch, time_role) -> last_accepted_event_time
```

来源切换必须 warm-up / 重建水位线，否则不同来源的时间字段角色或滞后可能造成假乱序。

### 3.4 验收

真实 repo 下一轮必须新增：

1. 同价同量 t+60 后送 t+30，必须拒绝；
2. 连续多轮同价同量也推进 accepted watermark；
3. 相同事件时间的合法修订不能被误杀；
4. stock/index 两条路径一致；
5. source switch 不继承错误的旧来源 watermark；
6. 修后做局部回退验牙。

## 4. `IT-P1-TIME-ROLE-001`：三家都声明“不提供 provider_time”，三个 parser 却都写 `Quote.ts`

这是本轮新增的**合同级静态风险**，暂不冒充已复现实盘故障。

Capability 表目前：

```text
Tencent    provider_time=False
Sina       provider_time=False
Eastmoney  provider_time=False
```

固定源码：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/capabilities.py>

但实际 parser：

- Tencent：把类似 `YYYYMMDDHHMMSS` 字段解析成 `Quote.ts`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/sources/tencent.py#L290-L380>
- Sina：用日期+时间字段填 `Quote.ts`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/sources/sina.py#L120-L230>
- Eastmoney：将 `f124` 转为时间并填 `Quote.ts`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/sources/eastmoney.py#L120-L220>

而 `EngineState._admit_time()` 只要 `q.ts is not None` 就把它当事件时间，做 future/乱序准入。

问题不是“字段存在不存在”，而是：

```text
它代表 snapshot发布时间？
最后成交时间？
服务端刷新时间？
还是其他行情时间？
```

如果是 `last_trade_time`，无成交但盘口变化时 timestamp 可能不推进；如果是 source-specific snapshot time，跨源直接比较又可能存在不可比偏移。

因此建议增加：

```text
time_role = snapshot_time | last_trade_time | unknown
source_epoch
```

证据不足就写 `unknown`。不要为了关闭 R2 把三个不明确的时间字段都升级成“权威 snapshot time”。

## 5. Observation Ledger：本轮再确认 4 个口径问题

### 5.1 `IT-P2-OBS-002`：future/ooo 被重复记成 `unknown_missing`

当前 `poll_once()`：

```python
admitted = self.state.update(quotes, now)
returned = dict(admitted)
...
unknown_missing=tuple(c for c in self._codes if c not in returned)
```

但同一段后面 `returned` 计数却是原始正价 provider 对象数。固定源码：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/engine.py#L890-L909>

`RoundObservationSet` 对 `unknown_missing` 的定义又明确是“请求了但本轮没返回”。

本轮反例：请求 A/B/C；provider 返回 A 正常、B far-future、C 完全没返回。

当前：

```text
requested=3
returned=2
admitted=1
unknown_missing=[B,C]
stale_rejected=1
```

B 明明返回了，只是后来被时间门控拒绝，却被同时算作 missing + stale。

候选正确分层：

```text
provider_objects=2
admitted_time=1
unknown_missing=[C]
future_rejected=[B]
```

### 5.2 `IT-P2-OBS-003`：`admitted` 不是纯时间准入口径

当前：

```python
eligible = admitted + filters.accept + ignore
...
admitted = len(eligible) + len(idx_admitted)
```

个股 `admitted` 实际是“时间准入 + 业务粗筛”，指数却只是“时间准入”，同一个标量混了两个层级。

固定价格 `0.01` 的正价个股：

```text
returned=1
时间准入通过=1
filters拒绝=1
当前 observation.admitted=0
future/ooo=0
```

所以代码注释“returned 与 admitted 的差额就是时间拒绝”不成立。

建议拆：

```text
admitted_time
rule_eligible
filter_rejected
```

股票和指数至少分项后再汇总。

### 5.3 `IT-P2-OBS-004`：fetch-error 后 API 留着上一成功轮

正常成功轮 `set_poll_stats(... observation=observation)`；抓取异常路径只传 poll_ms/count/health，没有 observation。

Store 又只在 `observation is not None` 时覆盖 `_observation`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/store.py#L118-L155>

所以：

```text
round1 OK:  requested=50 returned=48 admitted=45
round2 fetch error
```

API 仍可显示 round1 的 `50/48/45`。Observation 自身没有 `round_id/status/observed_at`，下游无法知道它已经陈旧。

下一版失败轮也必须写：

```json
{
  "round_id": 2,
  "status": "fetch_error",
  "requested": 50,
  "returned": 0,
  "admitted_time": 0,
  "observed_at": "..."
}
```

### 5.4 `IT-P2-OBS-005`：provider 返回了 zero-price 对象，却被叫成“没返回”

Tencent parser 明确保留 `price<=0` / `prev_close<=0` 的行，让下游识别停牌/不可用；而 Engine 的原始 returned 统计只计 `q.price>0`，`unknown_missing` 又基于 admitted 集合。

固定输入：请求 Z，provider 确实返回 Z，但 `price=0`。

当前 Observation：

```text
requested=1
returned=0
admitted=0
unknown_missing=[Z]
```

“provider 未返回”是事实错误。正确分层至少应该先记：

```text
provider_objects=1
returned_positive=0
unknown_missing=[]
```

再根据来源语义把 Z 放入 `explicit_unavailable` 或 `rejected_quality`。不能把“对象已返回但质量不可用”和“根本没有响应该代码”混为一类。

这对未来 targeted fallback 很关键：否则系统会对已经拿到但不可用的代码反复补抓，浪费限额并掩盖真正 missing。

## 6. `IT-P1-CAPABILITY-002`：targeted fallback 不能先做，因为当前 capability 只有“整轮一个”

当前 `SourceManager.call()` 对一个整批调用采用一个 source 成功即返回；所以目前 `RuleContext.capabilities` 用一个全局 `SourceCapabilities` 尚能表达“这一轮是谁供数”。

固定代码：
- `SourceManager.call()`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/engine.py#L300-L350>
- `RuleContext.provides()`：<https://github.com/fy-god/intraday-tape-reader/blob/a88094e915340b4eaec534af2826b5ffef68fe0e/src/arad/rules/base.py>

但下一步计划是：主源请求 `[A,B]`，只回 A，备用源只补 B。这样同一 `Snapshot` 中会出现：

```text
A -> Tencent -> turnover/L5/outer_inner available
B -> Sina    -> turnover/L5/outer_inner unavailable
```

如果仍然只有：

```python
ctx.capabilities = one_round_capability
ctx.provides("turnover")
```

那么 A/B 必然至少有一只被错误判断。

因此 targeted fallback 的前置依赖必须是**per-code provenance/capability**：

```text
code -> source
code -> source_epoch
code -> SourceCapabilities
```

规则 API 改成类似：

```python
ctx.provides(code, "turnover")
```

或等价 sidecar。这个问题当前还不是生产 bug，因为 mixed-source 合并尚未实现；但它是 WP03 的明确架构阻断，必须先解决再写定向补洞。

## 8. 其他仍开放的工程问题

### `IT-P1-SOURCE-EMPTY-001`

`SourceManager.call()` 仍然只以“调用是否抛异常”判成功。provider 请求 4800 只、正常返回 4700 只时，没有 requested-vs-returned 合同，不会定向补洞。下一步必须在 per-code provenance 已就绪后再实现，避免 mixed-source capability 错判。

### `IT-P1-WINDOW-001`

history 仍然只在 price/volume 变化时 append，因此“每 5 秒都有新鲜观测但值没变”的覆盖证据消失。accepted watermark 修 R2 不能替代窗口覆盖修复；建议 ObservationInterval 保存 `first_observed_at/last_observed_at/value/source_epoch`。

### `IT-P1-LIMIT-001`

封单状态仍需从“到限价”与“达到合格封单门槛”拆开，避免 `100万 -> 300万` 首次合格被 `prev=sealed` 吞掉。

### `IT-P1-006-R1`

Eastmoney 必须检查 `required_pages > max_pages`，不能“两页都请求成功”就把 200/300 误标 complete。

### `IT-P1-008/009/003`

Store 的 subscriber queue 满时仍静默丢最旧事件；持久游标补账和 `committed -> sent -> received -> applied` 尚未实现。`series` 的主体字典容量问题也继续开放。

## 9. 本轮主改造：Observation Ledger v2 + per-code provenance

本轮建议不再给多个孤立补丁，而把当前上游统一成一份分层事实链：

```text
raw provider batch
       ↓
RawBatchResult
       ↓
per-code source / source_epoch / time_role / capabilities
       ↓
Time & Quality Admission
       ↓
admitted_time
       ↓
Business Filter
       ↓
rule_eligible
       ├── EngineState latest/history
       ├── rule Snapshot
       ├── live coverage ledger
       └── research features / shadow model
```

建议新对象：

```python
RawBatchResult(
    requested_codes,
    provider_objects,        # code -> Quote，即使 price<=0 也表示 provider 回过对象
    source_by_code,
    source_epoch_by_code,
)

ObservationDecision(
    code,
    source,
    source_epoch,
    time_role,
    status,                  # admitted / future / ooo / unavailable / filter_reject / missing
    reason,
)

RoundObservationSet(
    round_id,
    observed_at,
    status,                  # ok / degraded / fetch_error
    requested,
    provider_objects,
    returned_positive,
    admitted_time,
    rule_eligible,
    unknown_missing,
    explicit_unavailable,
    future_rejected,
    out_of_order_rejected,
    filter_rejected,
    per_code_provenance,
)
```

必须机器检查：

```text
provider_objects + unknown_missing == requested            # 同一请求口径
rule_eligible + filter_rejected == admitted_time            # 股票粗筛口径
Snapshot.keys ⊆ rule_eligible/watchlist-current
latest/history 只能消费 admitted_time
```

对于停牌/zero-price，是否进入 `explicit_unavailable` 还是 `rejected_quality` 由 source 语义决定，不能只靠 `price==0` 猜。

失败轮也必须有新 round identity，不能沿用上一成功轮账本。

迁移建议：先以 sidecar 方式新增 v2 字段，不破坏冻结 `Quote`；旧 status 字段保留一版兼容，新增 v2 后让 live_session 同时对账，稳定后再移除含混标量。

回退：关闭 v2 consumer 仍可走旧规则，但审计页面必须标“legacy observation semantics”，不能静默把旧字段继续称作完整覆盖。

## 10. 新研究实验：`EXP-IT-CAP-003-synthetic-specialist-routing`

上一轮 synthetic 结果提示 explicit capability mask 比全特征 base 在 provider shift 下更稳。本轮没有重新做大搜索，而是检验一个更具体的机制假设：

> 不同 provider 能提供的因子集合不同；用 provider-specific HGB specialist 是否比一个 global capability-mask HGB 更稳健？

### 10.1 选择防火墙

- 特征 schema 在新 lockbox 生成前，根据当前源码 capability 合同固定；
- HGB 超参沿用旧 tune：`max_iter=80, learning_rate=0.04, max_leaf_nodes=15, l2=0.1`；
- v5 lockbox seeds 在读取 v5 成绩前固定；
- v5 没有重新调参；
- 全部是 synthetic，不是实股。

Schema：

```text
Tencent specialist:     35 factors
Sina specialist:        28 factors（公共因子 + 可用 L1/microprice 子集）
Eastmoney specialist:   23 factors（无盘口家族）
Universal intersection: 23 factors
Global capmask:         35 factors + 8 family masks
```

### 10.2 新主 lockbox

```text

provider_shift_seed 9202029
30 synthetic symbols
5 artificial days
19,248 candidates
positive rate 0.48239

```

### 10.3 总体结果

| 模型 | ROC AUC | PR AUC | LogLoss | Brier |
|---|---:|---:|---:|---:|
| Full-feature base | 0.6470 | 0.6454 | 0.6533 | 0.2308 |
| Global capability-mask | 0.6617 | 0.6577 | 0.6474 | 0.2280 |

| Universal intersection | 0.6402 | 0.6373 | 0.6587 | 0.2334 |

主 lockbox 中 specialist 相对 capmask：`PR AUC +0.00694`。

### 10.4 按 provider

| Provider | Base PR | CapMask PR | Specialist PR | Universal PR |
|---|---:|---:|---:|---:|
| Tencent | 0.6668 | 0.6654 | **0.6682** | 0.6373 |
| Sina | 0.5894 | 0.6398 | **0.6622** | 0.6420 |

Synthetic 机制上，specialist 的增量主要来自缺失盘口能力更严重的 Sina/Eastmoney。

### 10.5 source-switch 邻域反而显示另一个问题

在 provider 切换后约 7 个 synthetic ticks 的 near-switch slice：

```text

Specialist PR 0.6592
Universal  PR 0.6637
```

Universal intersection 在这个局部略高于 specialist。这说明 source transition 本身可能需要“warm-up / continuity reset / transition fallback”，不能简单把整轮路由到 specialist 就认为问题结束。

### 10.6 额外 3 个全新 lockbox

完全相同模型/配置，不重新训练调参，另外跑三组新 seed：

| Lockbox | Specialist - CapMask PR | Specialist - Base PR |
|---|---:|---:|
| 1 | +0.00615 | +0.01204 |
| 2 | +0.00793 | +0.01581 |
| 3 | +0.00986 | +0.02225 |

三组 specialist-capmask 平均：`+0.00798 PR AUC`；加上主 lockbox，共 4 个 synthetic lockbox 方向一致。

这只能把 specialist routing 从“一个点子”升级成“值得真实数据验证的机制假设”，不能升级成部署结论。

### 10.7 aggressive abstention 不值得在 synthetic 上直接采用

| 策略 | Coverage | PR AUC |
|---|---:|---:|
| 全部 provider | 100% | 0.6646 |
| 不用 Eastmoney | 93.68% | 0.6666 |
| 只用 Tencent | 75.68% | 0.6682 |

丢掉约 6.3% coverage 只换约 +0.0019 PR；只用 Tencent 损失约 24.3% coverage 只换约 +0.0035 PR。当前没有依据采用激进 abstention。

真实阶段必须同时报告 coverage，不能只展示过滤后剩余样本的 Precision/PR。

### 10.8 研究推理微基准

batch=1024、100 次：

| 模型 | p50 ms | p95 ms | p99 ms |

Specialist 尾延迟更高，当前脚本还包含 pandas/multi-model branching 成本。这不是生产 E2E 延迟；真实 shadow 接入前必须用服务实际 feature tensor 和批处理方式重测。

## 14. 本轮最终判断

产品 `a88094e` 是实质进展：`IT-P0-002-R1` 的明显绕过路径和 Observation 可观测性主干已经改善，不能反复否定。

但目前最重要的事实链还没有闭合：

```text
provider返回了什么
→ 这个对象是什么状态
→ 时间字段扮演什么角色
→ 是否被时间准入
→ 是否被业务过滤
→ 实际来自哪个source/epoch
→ 规则是否有能力评估
→ 模型能使用哪些因子
```

现在这些层仍被 `returned/admitted/unknown_missing` 少数几个标量压在一起，导致 R2 水位线、missing 双计、zero-price 假 missing、失败轮陈旧账，以及未来 mixed-source capability 错判。

因此下一轮工程主线应优先把 **accepted watermark + time role/source epoch + Observation Ledger v2 + per-code provenance** 做成一个统一合同，而不是继续往规则层补判断。

研究方面，本轮 4 个 synthetic lockbox 都显示 provider-specialist HGB 相对 global capability-mask 有同方向小幅增量，但 aggressive abstention 的覆盖损失远大于质量收益，source-switch 邻域又显示 universal feature subset 仍可能更稳。最合理的下一步是：**真实数据一到位，只做固定三模型的严格 time-forward/provider/unseen-stock 验证，不扩大网络、不增加搜索预算。**
