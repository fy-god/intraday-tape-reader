```python
quotes = self.sources.call("snapshots", list(self._codes), route=ROUTE_STOCKS)

    q.code for q in raw_stock + raw_idx if q.price <= 0
```

# 3. 本轮新增 P2：`SnapshotFetchResult.coverage` 与 `RoundObservationSet.coverage` 同名但不是同一个量

稳定 ID：

### `IT-P2-SNAPSHOT-OUTCOME-COVERAGE-SEMANTIC-COLLISION-001`
**P2 · 新确认 · WP02 集成前必须修。**

当前 source outcome：

```python
coverage =
len(quotes) / len(requested_keys)
```

也就是：

\[
C_{usable} = |Q|/|R|
\]

但当前 `RoundObservationSet.coverage()`：

```python
returned / requested
```

而 `returned` 的文档明确定义为 provider raw returned，所以是：

\[
C_{raw} = |P|/|R|
\]

这两个量不能共用一个模糊名字。

### 本轮反例

请求 3 只：

```text
R = 3
P = 3   # 三只 raw 全回来
Q = 1   # 两只质量不可用
```

则：

```text
SnapshotFetchResult.coverage = 1/3 = 33.3%
RoundObservationSet.coverage = 3/3 = 100%
```

两者都“正确”，但回答的问题不同：

```text
33.3% = usability
100%  = raw return completeness
```

如果 WP02 直接把：

```text
outcome.coverage
```

接到现有 health 的 `coverage`，就会把：
> provider 全部返回、只是质量差

重新读成：
> provider 只返回三分之一

这正是整个 Snapshot Outcome Contract 想消灭的语义塌缩。

### 修法

正式拆名：

```text
raw_return_coverage = |P| / |R|
usable_coverage     = |Q| / |R|
```

Engine：
- `RoundObservationSet.returned = |P|`
- `RoundObservationSet.coverage()` 继续是 raw return coverage
- usable coverage 单独导出，不覆盖旧 `coverage` 语义

本轮产物：
`coverage_semantic_collision_matrix.csv`。

# 4. 本轮新增 P2：Tencent detailed 对“显式带前缀的股票”会发生 identity 轴错位

稳定 ID：

### `IT-P2-TENCENT-DETAILED-EXPLICIT-STOCK-KEY-AXIS-001`
**P2 · 新确认 · source v4 API 级 bug；默认 Engine 当前主要用裸股票码，因此暂不升 P1。**

Tencent detailed 的当前流程：

```python
norm = _norm_specs(codes)
idx_set = {sym for sym, explicit in norm if explicit}
```

也就是说：
> 任何显式写了 sh/sz/bj 前缀的请求，都先进入 `idx_set`。

随后 raw identity `_key(symbol, name)`：
- 只有 `looks_like_index(...)` 真的是指数时才保留前缀；
- 普通股票仍变成裸 6 位 code。

但 request identity `_req_key(raw)`：
```python
if prefix and sym in idx_set:
    return sym
```
并没有再次确认它真的是指数。

### 反例

请求：

```text
sh600000
```

它是浦发银行，不是指数。

当前 detailed key 可能变成：

```text
R requested key = sh600000
raw key         = 600000
Quote.code      = 600000
```

于是：

```text
P = empty
Q = empty
unknown_missing = sh600000
unexpected_raw  = 600000
```

也就是 provider 明明正常返回，detailed outcome 却可以报：
> 请求的股票 missing，另外返回了一个未请求代码。

当前测试覆盖：
- 裸股票 code；
- 显式前缀指数 + 裸股票；
但没有锁：
- **显式前缀普通股票**。

### 修法

Tencent 的 `_req_key` 必须与 raw `_key` 用同一份“是否真指数”判据。

更简单的设计：
- stocks route：股票 identity 一律裸 6 位；
- index route：指数 identity 明确带前缀；
不要用“显式写了前缀”作为“它是指数”的代理。

# 5. 本轮新增 P2：`merge_outcomes()` 可以让同一 code 同时属于 admitted 与 rejected_quality

稳定 ID：

### `IT-P2-SNAPSHOT-MERGE-TERMINAL-OVERLAP-001`
**P2 · 新确认 · WP02 前必须修。**

当前 `merge_outcomes()` 的前半段其实能构造正确的全局：

```text
P = union(raw_present)
Q = dedup(usable quotes)
```

并调用 `build_outcome()` 得到正确：

```text
quality = P - Q
```

但最后又做：

```python
return out._replace(
    rejected_quality_keys=frozenset(quality),  # 这里的 quality 是各 part quality 的并集
    ...
)
```

这会重新覆盖掉全局正确终态。

### 本轮反例

同一 code `600001`：

```text
part A:
raw present
Quote invalid
=> quality={600001}

part B:
raw present
Quote valid
=> admitted={600001}
```

全局正确语义：

```text
P={600001}
Q={600001}

quality = P-Q = empty
admitted = {600001}
duplicate_raw = {600001}
```

当前 merge 的 per-part quality union：

```text
quality={600001}
```

于是最终出现：

```text
admitted ∩ rejected_quality = {600001}
```

终态桶不再互斥，`identity_holds()` 也会失败。

### 可达性说明

正常 chunk 请求集合通常不重叠，所以暂不升 P1。

但代码和测试已经明确承认：
- provider 可能回带未请求 code；
- merge 需要检测跨批次 duplicate。

因此“同一 raw identity 出现在多个 part”本来就是被设计允许/诊断的输入，不能让终态集合在这种情况下自相矛盾。

### 修法

终态 `rejected_quality` 在全局 merge 后重新计算：

```text
merged_quality = merged_P - merged_Q
```

而：
- duplicate
- unexpected

才适合直接并集保存为诊断集合。

本轮产物：
`merge_terminal_overlap_probe.json`。

# 6. Main 改造：Snapshot Outcome → Round Attribution Integration Contract v2

本轮主改造不是再重写 source parser。

Source 层已经有了足够好的原料。

现在应冻结下面这条链：

```text
Requested identities R
↓
Raw-present identities P
↓
Usable Quote identities Q
↓
Time admission
↓
Disjoint Round terminal attribution
```

### 6.1 SourceManager 必须原子返回实际 serving source + outcome

不能先：

```text
call() 返回结果
```

然后在另一个时点读取：

```text
serving_of(route)
```

去猜这批结果来自谁。

建议：

```text
call_detailed(...)
→ (SnapshotFetchResult, serving_source/index)
```

或让 result 自己带真实 source，Manager 只负责 failover。

### 6.2 Normal / Empty 只能有一个 attribution helper

禁止继续：

```text
normal path 一套账
empty path 另一套账
```

建议：

```text
_build_round_attribution(stock_result, index_result, state_admission_deltas)
```

统一生成：
- admitted
- exact missing
- quality
- future
- out-of-order
- unattributed

### 6.3 legacy / unknown raw presence

若：

```text
raw_presence_known=False
```

则：

```text
R - known terminal facts
```

进入：

```text
unattributed_requested
```

而不是 exact `unknown_missing`。

内置 Tencent/Sina/Eastmoney 的目标是：

```text
raw_presence_known=True
unattributed=0
```

### 6.4 terminal invariant

最终要求：

\[
R=
A \dot\cup M \dot\cup Q_b \dot\cup F \dot\cup O \dot\cup U
\]

其中：
- A admitted
- M exact raw missing
- Q_b quality rejected
- F future
- O out-of-order
- U unattributed

### 6.5 coverage

严格分：

```text
raw_return_coverage = |P|/|R|
usable_coverage     = |Q|/|R|
```

现有 health 的“数据返回覆盖率”继续消费 raw_return coverage。

## 最终判断

19:05 产品轮已经真正完成了一个重要前置：

> 三家 Source 终于都能表达 exact raw presence。

但是它刻意没有接进 Engine，所以**线上账本语义还没有改变**。

现在最危险的不是“继续没接线”本身，而是：

> 如果下一轮直接把新对象接进去，而不先处理 coverage 双语义、Tencent key-axis 和 merge terminal overlap，会把新合同在集成阶段重新破坏。

```text
Source v4 contract self-consistency
↓
SourceManager detailed serving truth
↓
Engine unified Round Attribution
↓
live-session exact missing/unattributed
↓
Membership
↓
Soft-empty failover
↓
Research
```

这一层闭合之前，模型继续保持 0 是合理的。
