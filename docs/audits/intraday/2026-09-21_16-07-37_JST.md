## 1. 本轮最高价值结论

最新本地 Agent 正确量化出一个严重缺口：真实 replay 共 66 条 committed 告警，只有 6 条有 `signal_id` 并能进入交付账本，60 条不可对账，覆盖率只有 **9.1%**。其源码核对也正确：7 条能发 Alert 的规则中，只有 `volume_burst` 与 `spirit_order` 同时维护 `signal_id + SignalEvalStats`；`limit_board / spirit_index / spirit_price / tick_surge / unusual` 都没有。

但它给出的修法“给 5 条规则补 `signal_id`（各自一行即可）就能让 committed 一级对账生效”按当前 `eba8c4a` 的 Engine 控制流不可成立。

当前 `_mark_stage()` 的硬门禁是：

```python
sig = alert.signal_id
if not sig:
    return

evals = observation.signal_evals
if not isinstance(evals, dict) or sig not in evals:
    return
```

所以 `signal_id` 只是必要条件，不是充分条件。该 signal 还必须已经由规则自己创建在 `observation.signal_evals` 中，Engine 才会记 `bus_accepted / committed`。

当前五条未覆盖规则恰好没有创建这些 evaluability 行。因此只加：

```python
Alert(..., signal_id="limit_board.limit_up_seal")
```

仍然会在 `sig not in observation.signal_evals` 处直接返回，交付覆盖率不会闭合。

本轮将其登记为：

### `IT-P1-DELIVERY-LEDGER-002`

**P1 · 已确认 · 未修。**

也不能让 Engine 在 bus/commit 阶段自动 `eval_stats(sig)` 建行：那会出现 `considered=0 / evaluable=0 / hit_candidates=0 / rule_selected=0 / bus_accepted=1 / committed=1`，直接违反现有机械不变量 `hit_candidates >= rule_selected >= bus_accepted >= committed`，并把“没有做逐 code evaluability 统计”伪装成“0% 可评估”。

根因不是漏填 5 个字段，而是：**可评估性账本与交付账本被错误绑在同一个 registry。**

## 2. 本轮独立实验：`EXP-IT-LEDGER-003`

本轮没有重复训练模型，而是围绕上述结构做可证伪软件合同实验。

### 固定输入

按当前仓库 7 个能发 Alert 的规则模块构造代表 signal：

```text
volume_burst                         已有 evaluability 行
spirit_order.institution_buy         已有 evaluability 行
limit_board.limit_up_seal            无 evaluability 行
spirit_index.index_pull              无 evaluability 行
spirit_price.rocket                  无 evaluability 行
tick_surge.surge                     无 evaluability 行
unusual.reseal                       无 evaluability 行
```

### 四组对照

| 方案 | 结果 |
|---|---|
| 当前 `_mark_stage` + 当前 signal_id | 只有 2/7 模块能记 delivery |
| **仅给另外 5 条规则补 signal_id** | **仍然只有 2/7，完全没改善** |
| Engine 在 delivery 时自动创建 `SignalEvalStats` | 5/5 新行出现 `bus > rule_selected`，不变量破坏 |
| **独立 `SignalDeliveryStats` registry** | 7/7 全部闭合，delivery 不变量 0 违规 |

因此 signal_id-only 修法已被本轮机制实验直接证伪。

### 120,000 事件 property stress

固定 seed `20260921`：

```text
40 个 signal
120,000 个 rule-selected 软件事件
只有 9 个 signal 假设具备 evaluability instrumentation
40 个 signal 全部进入独立 delivery registry
```

结果：

```text
delivery invariant 运行中违规 = 0
最终违规                         = 0
evaluability registry 大小        = 9（没有被 Engine delivery 自动扩成 40）
delivery-only signal              = 31
```

这证明至少在机械合同层面，交付覆盖可以扩到所有 signal，而不需要伪造 evaluability 分母。它不是市场准确率实验。

## 3. 为什么当前测试会让 9.1% 覆盖合法通过

当前 `tests/test_replay_capability_ledger.py` 的逻辑是：只把 `signal_id` 非空的 Store 告警计入 `tagged`，然后断言 `sum(tagged.values()) == committed_total`，并且明确 `assert untagged > 0`。

所以当前门禁只证明“已经进入 SignalEvalStats 的那一小部分告警内部自洽”，不能证明“所有真正 committed 的第一方告警都有交付事实”。最新本地 Agent 的 `6 == 6` 就是内部自洽；同时 60/66 条真实 committed 告警完全没进入等式。

下一版必须拆成两层门禁：

```text
A. evaluability ledger 自己闭合
B. delivery ledger 覆盖全部第一方 committed Alert
```

两者不能再共用“有无 SignalEvalStats 行”作为准入条件。

## 4. 主改造：Alert Truth Contract v3 —— evaluability 与 delivery 分账

### `SignalEvalStats`：规则所有

继续只回答：

```text
considered
evaluable
blocked_capability
advisory_missing
evaluated_no_hit
hit_candidates
```

只有真正定义逐 code evaluability 的规则才写它。

### `SignalDeliveryStats`：Engine 所有

建议独立 sidecar：

```python
@dataclass
class SignalDeliveryStats:
    rule_selected: int = 0
    global_ignored: int = 0
    bus_accepted: int = 0
    committed: int = 0
```

Engine 对所有带稳定 `signal_id` 的第一方 Alert 统一记：

```text
rule.evaluate 返回 valid Alert -> rule_selected
全局 ignore                    -> global_ignored
AlertBus.accept True           -> bus_accepted
Store.add_alert                -> committed
```

若保留 global ignore，则机械关系是：

```text
bus_accepted <= rule_selected - global_ignored
committed <= bus_accepted
```

### `rule_selected` 为什么应由 Engine 统一记

对 Engine 而言有一个统一、不会猜的边界：**规则真正返回的 Alert，就是 rule-selected output。** 这避免每条规则重复写同一阶段又再次发生“某规则忘记维护交付账本”。

`volume_burst / spirit_order` 现有 `SignalEvalStats.rule_selected/bus_accepted/committed` 可在迁移期保留作交叉核验；对已 instrument signal 强制两套计数相等，稳定后再决定是否移除重复字段。

### 稳定 signal ID

另外五条第一方规则已有足够机器语义：`limit_board/spirit_index/spirit_price/unusual` 都有 `metrics.pattern`，`tick_surge` 有方向 kind。规则应显式赋值，例如：

```text
limit_board.limit_up_seal
limit_board.open_limit_up
spirit_index.index_pull
spirit_price.rocket
unusual.reseal
tick_surge.surge
tick_surge.plunge
```

不得从 title 反推。

### 全局门禁

```text
first_party_committed_without_signal_id == 0

delivery_accounting_coverage
= committed_with_signal_id / committed_first_party_total
= 1.0

sum(delivery_stats.committed)
= Store 本轮第一方 committed Alert 数
```

缺少 evaluability 统计必须表示 `not_instrumented/not_measured`，不能表示 0% evaluable。

## 6. Alert identity / notifier 仍开放

当前 `Alert` 已有稳定 `signal_id`，但没有 durable `event_id`。`Alert.key` 含时间桶，服务于 dedupe/cooldown，不适合作为跨 Store / notifier / SSE / future label 的主键。

`_dispatch_many()` 仍直接调用 `send_digest()` / `send()` 而丢弃返回值，只在抛异常时记录 error。继续维持：

- `IT-P1-NOTIFY-RESULT-001`：Engine 丢弃 notifier 结果；
- `IT-P1-NOTIFY-RESULT-002`：bool 不足以区分 sent / skipped / failed；
- `IT-P1-ALERT-IDENTITY-001`：signal_id 已有，event_id 未完成。

推荐后续 typed terminal result：`sent / skipped_disabled / skipped_severity / skipped_dry_run / failed / legacy_true_unknown`，并挂到 `event_id × channel`。

## 14. 本轮结论

`eba8c4a` 已经把“某个 signal 自己的 hit → selected → bus → committed”链条做对了一大步；但交付事实仍依赖 evaluability registry 是否存在，所以它现在是“2 条规则的严格账本”，不是“全项目的交付账本”。

最新本地 Agent 找到 9.1% 覆盖缺口非常重要；本轮进一步证明，它建议的“一行 signal_id 修五条规则”不足以解决，因为 Engine 会在 `sig not in observation.signal_evals` 处继续丢掉这五条。

下一阶段应把 `per-code evaluability` 与 `per-alert delivery` 拆成两套可连接但不互相伪造的真值源。等全体 committed Alert 都有稳定 `signal_id/event_id`，并且 universe coverage 能被认证以后，再开始全项目 T+5/T+30 与模型优化，研究结论才有可信分母。
