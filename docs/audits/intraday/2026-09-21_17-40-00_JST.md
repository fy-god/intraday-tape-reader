## 3. 【已确认错误 · P1 · 本轮新发现】新门禁是"逐轮"的，运营面读到的是最后一轮

### 文件/函数/行
- `src/arad/engine.py:1323` — `observation.committed_alerts_total += len(fresh)`
- `src/arad/capabilities.py:824-834` — `delivery_accounting` 的导出
- `src/arad/store.py:156` — `self._observation = as_dict()`（**每轮覆盖**）
- `src/arad/store.py:320` — `status()["observation"] = observation`

### 触发条件 / 反例（实测）
361 轮真实回放（`D:\ccc\_sched\work\asr_h16_perround.py`）：

```
rounds                                 = 361
SUM over rounds committed_alerts_total  = 66      <-- 累计真值
SUM over rounds named committed         = 66
cumulative ratio                        = 1.0

LAST round committed_alerts_total       = 0
LAST round named committed              = 0
LAST round signals in ledger            = 0

rounds with 0 committed                 = 305 / 361
rounds with >=1 committed               = 56 / 361

store.observation["delivery_accounting"]
  = {'committed_alerts_total': 0, 'committed_with_signal_id': 0,
     'signed_ratio': None, 'first_party_committed_without_signal_id': 0}
```

### 机制
`RoundObservationSet` 是**逐轮**对象，`poll_once` 每轮新建；`store.set_poll_stats(observation=obs)` 每轮把 `obs.as_dict()` **覆盖**写进同一个 `self._observation`。因此 `delivery_accounting` 永远只描述**最后一轮**。`committed_alerts_total` 在整个仓库里**只有 `engine.py:1323` 一个写入点**，而 `store.py` / `web.py` / `cli.py` 对它 **0 命中** —— **没有任何累计计数器能到达运营面**。

### 影响
1. **门禁在会话结束时几乎必然读 `None`**：305/361 轮是 0 条告警，最后一轮落在"0 条"上的概率很高。`None` 的语义是 `not_measured`，会被误读成"没测过/无数据"，而真实语义是"**本会话交付 66/66，完全合规**"。
2. **告警稀疏时门禁静默**：只在"某轮恰好有告警"的那 56 轮里才显示有意义的值；而那 56 轮的 `signed_ratio` 也可能因为其它 alert 的 signal_id 缺失而掉下来，**但下一轮就被 0/0 覆盖成 `None`，异常窗口只存在一轮**。一个只存在一轮的告警无法被人看见。
3. **`first_party_committed_without_signal_id` 同理**：它现在读 0 不是因为"全合规被持续证明"，而是因为**最后一轮没有告警**。真正的违规如果发生，会在下一轮被静默覆盖。

### 修复建议
把交付账本的**累计**与**逐轮**分开，并让累计值可达 `status()`：
- 在 `AlertStore` 上维护会话级累计（`committed_alerts_total_session` / `committed_with_signal_id_session`），在 `set_poll_stats` 里按**增量**累加，而不是覆盖；
- 或让 `Engine` 持有跨轮累加器，并在 `status()` 中同时导出 `delivery_accounting_last_round` 与 `delivery_accounting_session`，**两个字段名字必须不同**，避免消费方再把"末轮"当"会话"；
- 关键：`signed_ratio_session` 应基于会话累计，且**当累计分母为 0 时返回 `None` 而不是 1.0**（保留现有的诚实语义）。

### 验收测试
在真实 Replay 上跑 N 轮，构造**最后一轮 0 条告警**的场景，断言：
```
status()["delivery_accounting_session"]["signed_ratio"] == 1.0
status()["delivery_accounting_last_round"]["signed_ratio"] is None
```
并断言两者**不是同一个字段**。再构造"某轮有 1 条无 signal_id 的告警"，断言会话累计 `signed_ratio < 1.0` 且**在后续轮次不会被覆盖回 1.0**。

numerator (real named)     = 3
raw total - named          = -2   ->  max(-2, 0) = 0   <-- PASS

**(4) 假红（FALSE RED）** —— 让"分子标记"抛异常：
```

```
**结论：分子侧异常会让门禁把**无辜规则**报成违规**，而告警本身全部合规。

### 机制
`engine.py:1322-1325` 的设计意图是"**可观测性不能打断告警主链路**"（该注释在 `:1358` 明确写出），这个意图是对的。问题是它用了**裸 `pass`**：**吞掉异常却不记账**。全仓库实测**没有任何吞异常计数器**：

### 影响
