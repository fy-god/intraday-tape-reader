## 2. 新 P1：Eastmoney UList 在进入 Engine 前已把“raw 返回但不可用”和“provider 完全没返回”合并

`RoundObservationSet` 的固定合同非常明确：

```text
unknown_missing   = 请求了，但 provider 本轮完全没返回
rejected_quality  = provider 返回了，但质量不可用
future/ooo        = provider 返回了，但时间条件拒绝
```

已有机械恒等式测试：

```text
stock_requested
= admitted_stock
+ unknown_missing
+ rejected_quality
+ future
+ out_of_order
```

且 missing / quality / time 三类互斥。

然而 Eastmoney snapshot 路径是：

```text
ULIST raw response
→ parse_ulist()
→ parse_clist(...)
→ parse_clist_page(...).quotes
→ list[Quote]
→ Engine
```

`_quote_of()` 先解析 `f12` code，再读取 `f2/f18`；若价格/昨收无效就 `return None`。因此原始响应里即使 code row 已经存在，只要当前字段不能构成 Quote，它在 source 边界前就完全消失。

Engine 后面：

```python
raw_codes = {q.code for q in raw_stock if q.price > 0}
```

实际得到的是 **post-parser Quote presence**，而不是 raw provider presence。于是它无法区分：

```text
A. provider 返回了 code row，但 row 当前质量不可用
B. provider 根本没返回 code
```

这与 `unknown_missing` 注释/测试宣称的语义不一致。

## 6. `coverage_active=1` 不应被人为视为假绿

固定源码自己定义：

```text
C_transport = raw_unique_codes / expected_total
C_usable    = usable_quotes / expected_total
C_active    = active_scan_codes / expected_total
C_round     = round_returned / round_requested
```

如果 Membership 修复后系统明确把全部 transport members 都安排进入 active schedule，那么 `C_active=100%` 是正确答案。`C_transport` 与 `C_active` 数值相等，不代表语义被合并。

不可用 member 的事实应该继续体现在：

```text
C_usable
rejected_quality
provider_missing
C_round
```

如果为了让旧 `C_active` 继续保持 93.75% 而故意把当前不可用的真实 market members 排除出 active scan，反而会重新引入 Membership P1 本体。

因此下一轮 Agent 的明确纪律是：**按定义修指标，不按旧数字修指标。**

## 8. “370 个 code 保证没 raw row / 纯开销”没有被现有证据证明

09:05 真实三臂用的是 fake source 的 `list[Quote]` 输出，因此只能证明“Engine 没收到 Quote”，不能证明真实 Eastmoney HTTP raw response 没 code row。固定产品 `parse_ulist -> parse_clist -> page.quotes` 正好会在 source 内丢掉 raw-invalid row，所以当前接口本身无法回答这个问题。

同样，多出的轮询至少承担恢复交易检测功能；在没有真实 batch/latency 实验前，不应称“纯开销”。

算术上，现有 fixture：

```text
usable fast set = 5553
all members     = 5923
BULK_LIMIT      = 50
```

得到：

```text
ceil(5553/50) = 112 batches / 5s
ceil(5923/50) = 119 batches / 5s
增加 7 batches ≈ 6.25% batch-count
```

这是请求批次数算术，不是延迟实测。

正确性完成后如成本过高，可独立比较 unavailable-member probe 15/30/60/120/300 秒等频率；必须实测 p50/p95/p99、CPU/RSS、网络错误和恢复发现延迟后再选策略。

## 12. Source soft-empty 现在有更安全的修法入口

`IT-P1-SOURCE-EMPTY-001` 仍开放。`SourceManager.call()` 当前只有 exception 才 fallback，正常返回 `[]` 会被当成成功。

在 Quote-only 协议下，直接定义 `[] = source failure` 很危险，因为“raw response 有 code、但全部 Quote 当前不可用”也会得到空 Quote 列表。

SnapshotFetchResult 完成后可以更安全地区分：

```text
requested nonempty
raw_returned_codes == 0
→ soft-empty candidate，可尝试 backup

raw_returned_codes 非空
usable_quotes == 0
→ source 有响应，只是质量不可用，不应盲目切源
```

所以 Snapshot Outcome P1 会同时为 SourceManager failover 提供可靠触发依据。

```text
raw UList row
```

```text
Snapshot Raw Outcome
```
