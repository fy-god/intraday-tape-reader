# 1. 先纠正一个定性：global source promotion 是当前“被测试固定的产品行为”，不能继续直接报成隐藏 P1

最新 09:27 本地审计把：

`IT-P1-SOURCE-MANAGER-GLOBAL-IDX-BREAKS-ROUTE-ISOLATION-008`

继续列为 P1。

代码机制本身没有争议：`SourceManager` 的失败计数和 `serving_of` 按 route 分账，但正式首选仍是全局 `self.idx`；任一路由达到 threshold 会：

```python
self.idx = i
self._fails.clear()
```

因此 stocks 达阈值后，下一次 index 会优先从新的 global source 开始。

但是当前仓库测试明确把这个行为写成期望：

```python
# 第 3 轮切换发生在个股请求之后，此时 backup 已是主源，
# 指数请求直接由 backup 服务 —— 所以是 2 次而非 3 次。
# 这恰好说明切换真的生效了。
assert primary.served == [1, 1]
```

所以当前证据应分两层：

1. **机制事实**：cross-route global promotion 确实存在；
2. **缺陷定性**：当前 executable product test 明确要求该行为，因此在没有产品策略变更前，它不能再被称作“测试遗漏的隐藏 bug”。

真正剩余的是：

### `IT-P2-SOURCE-PROMOTION-POLICY-DOC-CONFLICT-009`

EngineState 的时间合同仍写：
> stocks / index 是两条独立流，各有自己的 serving source 与切源时机。

这与 SourceManager 的 global promotion 口径不完全一致，需要文档/策略统一。

**本轮不要求 Agent 顺手把 global promotion 改成 route-specific。**
如需改变，必须单独做产品策略变更与回归。

# 2. 本轮新发现：时间水位线按 route 分开了，但时间诊断 map 仍按裸 code 共用

新稳定 ID：

### `IT-P2-TIME-DIAGNOSTIC-ROUTE-COLLISION-010`
**P2 当前风险 / P1 级 WP07 前置。**

`EngineState` 已经正确把这些关键准入状态按 `(route, code)` 分账：

```python
accepted_watermark_by_route: dict[tuple[str, str], float]
seen_in_epoch: dict[tuple[str, str], bool]
source_epochs: dict[str, str]
source_names: dict[str, str]
stale_diagnosed: dict[str, int]
```

代码注释甚至明确指出：
> `000001` 既可能是股票平安银行，也可能是上证指数，route 必须参与 key。

但紧接着的诊断 map 仍是：

```python
provider_ts_raw: dict[str, float]
effective_event_time: dict[str, float]
received_at: dict[str, float]
time_age_seconds: dict[str, float]
```

只按裸 code 存。

`poll_once` 的更新顺序又固定为：

```python
idx_admitted = state.update(idx_quotes, ..., route=ROUTE_INDEX)
admitted = state.update(quotes, ..., route=ROUTE_STOCKS)
```

所以后一条 stocks 更新可以覆盖前一条 index 的诊断。

这不是纯理论：当前 Sina legacy parser 对行情响应直接：

```python
code = m.group(1)[2:]
```

去掉 `sh/sz/bj` 前缀，因此如果 Sina 服务 index route，`sh000001` 可进入 `EngineState` 为裸 `000001`；股票 route 里平安银行同样是 `000001`。

## 固定机制反例

同一轮：

```text
index 000001:
provider age = 900s
=> stale_diagnosed["index"] += 1
=> time_age_seconds["000001"] = 900

随后 stock 000001:
provider age = 0s
=> time_age_seconds["000001"] = 0
```

本轮末尾 `_stale_codes` 又用：

```python
self.state.time_age_seconds.get(q.code, 0.0)
```

判断 stale code。

于是可出现：

```text
provider_stale_by_route["index"] = 1
但 provider_stale_diagnosed_codes 不含 000001
```

即**route 计数说“指数有陈旧包”，code 诊断集合却说“没有”**。

反向场景中，stock 的 stale 值也可以覆盖成“这个裸 code 看起来两条 route 都 stale”。

当前三家 source 的 `freshness_allowed=false`，所以这不等于当前硬时间准入已跨 route 失效；真正 hard admission 的 watermark 已经 route-keyed。

当前影响主要在：
- stale/age 诊断；
- provider/effective/received timestamp provenance；
- soak/研究质量因子；
- 下一步 per-route health 的可解释性。

本轮机制产物：
`route_time_diagnostic_collision_matrix.csv`。

# 3. 第二个新发现：future / out-of-order 当前只能拿到全局总数，无法恢复到具体 route

新稳定 ID：

### `IT-P2-TIME-REJECT-ROUTE-ATTRIBUTION-011`
**P2 当前 / P1 级 WP07 前置。**

`EngineState.update(route=...)` 最终只返回：

```python
dict[str, Quote]   # admitted
```

但被拒绝的 future / out-of-order 只写到全局：

```python
self.stats["t_reject:future"]
self.stats["t_reject:out_of_order"]
```

`poll_once` 的做法是：

```python
_t0_future = global_counter
_t0_ooo = global_counter

update(index)
update(stocks)

future_rej = global_after - _t0_future
ooo_rej = global_after - _t0_ooo
```

所以当前 RoundObservation 只能得到：

```text
本轮一共 future 几条
本轮一共 ooo 几条
```

不能知道：
- future 属于 index 还是 stocks；
- ooo 属于 index 还是 stocks；
- 具体是哪一个 identity。

## 本轮不可逆反例

场景 A：

```text
index future = 1
stock ooo = 1
```

场景 B：

```text
index ooo = 1
stock future = 1
```

两者最终 aggregate 完全相同：

```text
future_rejected = 1
out_of_order_rejected = 1
```

因此**从当前 aggregate 结果数学上无法反推出 route truth**。

这意味着上一轮提出的 `Per-Route Round Observation` 不能只在 `poll_once` 外面包一层 schema。

如果 WP07 想写：

```text
routes["index"].future_rejected
routes["stocks"].out_of_order_rejected
```

当前 State API 根本没有足够信息。

本轮产物：
`route_time_reject_attribution_matrix.csv`。

# 4. 主改造升级：Route Admission Result Contract v1

> **RouteObservation 必须由 `SnapshotFetchResult + StateUpdateResult` 两份 route-local truth 构建。**

不能从 global stats 反推。

建议新增：

```text
StateUpdateResult
  route
  admitted
  rejected_future
  rejected_out_of_order
  stale_diagnosed
```

同时把这些诊断改为 `(route, code)`：

```text
provider_ts_raw_by_route
effective_event_time_by_route
received_at_by_route
time_age_seconds_by_route
```

这样事实链变成：

```text
SnapshotFetchResult
  R / P / Q / source
        ↓
StateUpdateResult
  admitted / future / ooo / stale
        ↓
RouteObservation
        ↓
Round compatibility aggregate
```

而不是：

```text
两个 route update
→ 全局 stats 加总
→ 事后猜每条 route 到底发生了什么
```

`time_age_seconds["600000"]`

## 最终判断

上一轮已经确定 WP07 需要 per-route RoundObservation。

本轮继续往上游追了一层，发现：

> **当前 State 层本身还不能提供精确的 per-route 时间拒绝与时间诊断事实。**

水位线已经 route-aware，但：
- provider/effective/received/age 诊断仍是 code-only；
- future/ooo 原因仍只有 global counters。

所以现在正确的实施链应该是：

```text
SnapshotFetchResult
        ↓
Route-local StateUpdateResult
        ↓
Per-Route RoundObservation
        ↓
Per-Route Health / Provenance
        ↓
Compatibility Aggregate
```

先把这一层做成机械可对账的事实，再做 Membership、soft-empty 和研究模型。
