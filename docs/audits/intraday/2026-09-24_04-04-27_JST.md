# 2. P1 已确认：`call_detailed` 返回错类型会穿透 failover

稳定 ID：

### `IT-P2-CALL-DETAILED-TYPE-ERROR-ABORTS-FAILOVER-004`
**当前严重度：P1。**

固定源码 `SourceManager.call_detailed()`：

```python
try:
    detailed = getattr(src, "snapshots_detailed", None)
    ...
    out = detailed(...)
except Exception:
    continue

# 已离开 try
if getattr(out, "source", "") != name:
    out = out._replace(source=name)
```

最新独立审计真实三臂结果：
- 主源返回 `dict` + 健康备用：`AttributeError` 穿透，`backup.calls=0`；
- 主源抛异常 + 健康备用：正常 failover，`backup.calls=1`；
- 正确类型主源：正常主源返回。

所以根因不是“循环 failover 整体坏了”，而是：

> **返回值合同校验位于 per-source try 外。**

修复必须把：
1. 类型校验；
2. source 绑定；
3. route 校验；
都放到 per-source try 内。错类型是 source contract failure，必须允许尝试 backup。

当前 `call_detailed` 生产调用点仍为 0，所以**当前线上直接暴露为 0**；但它是 WP03 接线前的硬门。

# 4. 本轮新增 P1 candidate：路由分账，但“正式主源”仍是一个全局 `idx`

稳定 ID：

### `IT-P1-SOURCE-MANAGER-GLOBAL-IDX-BREAKS-ROUTE-ISOLATION-008`
**P1 candidate · 本轮 mechanism confirmed · 需要仓库 RED 冻结产品策略后再正式定案。**

这条是本轮新推进。

当前 SourceManager 已经做了：
- `_fails[route]`
- `_serving[route]`

CHANGELOG 与 EngineState 也明确写：
> 个股与指数是两个独立数据流，各有自己的 serving source 与切源时机。

但是“preferred/current source”仍然只有一个：

```python
self.idx = 0
```

任一 route 达到 threshold 后：

```python
self.idx = i
self._fails.clear()
```

这会同时改变**所有 route 下一次调用的第一选择源**，并清掉其它 route 的失败计数。

### 本轮 deterministic mechanism

条件：

```text
threshold = 2

primary:
  stocks = fail
  index  = healthy

backup:
  stocks = healthy
  index  = healthy
```

执行：

```text
stocks #1
→ backup 服务
→ global idx 仍 primary
→ fails[stocks] = 1

stocks #2
→ backup 服务
→ threshold 达到
→ global idx = backup
→ fails 全清

index #1
→ index 自己从未失败
→ 但 order 先试 global idx = backup
→ backup 直接服务 index
→ 健康 primary index 根本没被调用
```

镜像场景（index 触发阈值、stocks 健康）同样成立。

因此“失败计数按 route 分开”并不等于“正式 source 选择按 route 隔离”。

### 影响

如果 route independence 是产品当前文档的真实合同，那么这会：
- stock-only degradation 静默改变 index provider；
- index `serving_of(route)` 随之变化；
- Engine 会为 index 开新 source epoch，即使 index 自身没有失败；
- 可能产生额外延迟、能力差异与 provider 语义切换；
- `_fails.clear()` 还会抹掉其它 route 的独立失败历史。

这条是**当前生产 `call()` 也具备的机制**，不依赖未来 WP03。

### 为什么先写 P1 candidate，而不是直接判已确认 P1

代码行为已明确；但产品尚缺一个明确策略测试：

```text
正式切换究竟是“全局 provider promotion”
还是“route-specific promotion”？
```

现有注释/时间状态合同偏向后者，但必须由产品测试冻结，避免审计者替产品设计。

下一本地 Agent 必须先写 RED：

```text
stocks 达阈值
index 零失败

期望 index 下一次仍先试原 primary
```

若产品明确选择 global promotion，则必须反向：
- 写测试固定全球切换；
- 修改“各 route 各有切源时机”的文档/注释；
- 解释为何 route-specific counters 仍合理。

本轮机制产物：
`source_manager_route_isolation_matrix.csv` / `source_manager_route_isolation_probe.json`。

# 5. P2：`result.source` 被 Manager 绑定，但 `result.route` 未校验

稳定 ID：

### `IT-P2-CALL-DETAILED-ROUTE-MISBIND-006`

当前：

```text
Manager accounting route = caller route
```

但 `SnapshotFetchResult.route` 若被第三方/半迁移源错误填成别的 route，Manager 不检查。

于是理论上可形成：

```text
_fails/_serving 记 stocks
returned outcome.route 写 index
```

三个 built-in source 当前都按传入 route 构造结果，仓内没有当前触发，所以保持 P2。

修复原则：
- `source` 是 Manager 可安全强制绑定的实际 producer identity；
- `route` 是 caller-owned contract，若返回不一致，建议当 source contract failure 进入 failover，而不是静默掩盖一个可能已经按错误 route 解析过的数据。

与 wrong-type 一起在同一个 validation try 内收口。

# 6. 主改造：Pre-WP03 Failover + Identity Gate v2

下一轮不能直接进入 Engine WP03。

必须先闭合四件事：

### 6.1 Result contract validation

每个 source attempt 内顺序固定：

```text
fetch detailed
→ isinstance(SnapshotFetchResult)
→ bind/validate actual source
→ validate caller route
→ Manager route accounting
→ return
```

任何 contract failure：
`continue backup`。

### 6.2 Identity 单一角色源

- stocks route：裸 6 位；
- index route：带前缀；
- mixed helper：显式 per-request role。

禁止 request/raw 两边独立推断角色。

### 6.3 Route promotion policy

推荐候选：

```text
preferred_by_route[route] = source_idx
```

达到 threshold：
- 只更新该 route preferred；
- 只清该 route fail counter；
- `serving_routes` 与 `preferred_routes` 分开。

为了兼容，可以保留 `idx` 给无显式 route 的 legacy 调用。

若产品坚持全局 promotion，则必须以测试与文档明确，而不能一边写 route independence、一边由全局 idx 隐式决定。

### 6.4 WP03 coverage 边界

新生产代码只允许显式使用：
- `raw_return_coverage`
- `usable_coverage`

不得消费 deprecated generic `coverage`。

完整候选合同：
`pre_wp03_failover_identity_gate_v2.json`。

## 12. 本轮结论

本轮没有新产品代码，最有价值的进展不是再重复 7/7 identity，而是发现：

> **项目已经把“失败计数”按 route 拆开，但“正式首选源”仍是一个全局 idx。**

这与 EngineState 自己写的“个股与指数是两个独立数据流、各有自己的切源时机”存在直接合同张力。

所以 WP03 之前的真正 gate 现在是：

```text
identity truth
+ detailed result validation
+ route promotion policy
```

三者都冻结后，exact raw truth 才能安全接进在线 RoundObservation。

模型训练继续为 0 是合理的。
