## 4. 最高优先级错误证据

### 4.1 `IT-P0-002`：事件时间没有形成写前门控，窗口没有右边界

固定源码：[`src/arad/engine.py@3477820`](https://github.com/fy-god/intraday-tape-reader/blob/34778204dee41575697357f5d2e20a40aad3bc9d/src/arad/engine.py)。

`EngineState.window()` 当前只检查下界：

```python
cutoff = now_epoch - float(seconds)
return [p for p in h if p[0] >= cutoff]
```

没有 `p[0] <= now_epoch`。`EngineState.update()` 又先用调用方 `now.timestamp()` 写 state/history，最后才出现：

```python
if q.ts is not None and q.ts > now:
    pass
```

这个 `pass` 对前面已经写入的状态没有任何门控作用。

本轮机制探针把历史写成 `(100,10)`、`(110,11)`，查询 `now=105, W=10`，当前逻辑返回两个点，包含**未来 110 秒的样本**；正确窗口只能返回 100 秒点。本轮还没有完整 checkout，因此证据等级是“固定源码 + 同控制流机制复现”，不是“真实模块 pytest 已红”。

根因不是一个漏写的 `<=` 而已，而是系统没有统一 `provider_event_time / received_at / process_monotonic` 质量合同。建议先在 Observation admission 层完成时间角色判定和写前拒绝，再让窗口加严格上界。回归必须覆盖：future、out-of-order、同秒修订、provider ts 缺失、宿主机时区差异、回放时钟。

### 4.2 `IT-P1-SOURCE-EMPTY-001`：三家 source 都缺 requested-vs-returned 合同

Tencent 在某个 chunk 的 HTTP/parse 过程只要不抛异常，就把解析出的 Quote 列表作为该 chunk 成功；Sina 和 Eastmoney 同样会在“成功响应但少一只代码”的情况下返回剩余列表。它们对**批次异常**已有处理，但没有统一的：

```text
requested_codes
returned_codes
explicit_unavailable
unknown_missing
```

上层 `SourceManager.call()` 又是“没有抛异常即成功”，于是：

```text
requested = [A, B]
primary returns = [A]
backup could return = [A, B]
```

当前路径会返回 `[A]`，备用源调用次数为 0，并把主源本路由失败计数清零。本轮机制探针已经复现这个分支。

这正是下一步最应先做的主改造：不是简单“少一只就整批失败”，而是把**明确停牌/无行情**与**未知缺失**分开；只对 unknown missing 有界补洞并记录 provenance/source_epoch。

### 4.3 `IT-P1-WINDOW-001`：横盘越久，突然跳变反而可能算不出窗口涨幅

`EngineState.update()` 只在价格或累计量变化时 append history。重复旧包确实不应堆点，但“新鲜快照、值恰好不变”也被一并压掉。

本轮固定反例：`t=0,5,...60` 每 5 秒都得到新鲜 `price=10, volume=100`；`t=65` 得到 `10.3,101`。当前 history 只保留 `(0,10,100)` 与 `(65,10.3,101)`。查询 60 秒窗口时 cutoff=5，`t=0` 被剔除，窗口只有一个点，因此 `price_change=None`，而真实可观测路径是约 +3%。

主方案不是把所有重复值无限保存，而是引入 `ObservationInterval(first_observed_at,last_observed_at,value,source_epoch)`：连续新鲜但不变的观测延长 `last_observed_at`；真正断线则不会延长，所以不会无限前填。

### 4.4 `IT-P1-LIMIT-001`：封单从不合格变合格时首次合格封板可永久漏掉

固定源码：[`src/arad/rules/limit_board.py@3477820`](https://github.com/fy-god/intraday-tape-reader/blob/34778204dee41575697357f5d2e20a40aad3bc9d/src/arad/rules/limit_board.py)。

当前 `at_limit` 分支先执行：

```python
self._state[tag] = "sealed"
if prev == "sealed":
    return None
return self._make_seal(...)
```

而 `_make_seal()` 之后才检查：

```python
if self.min_seal_wan > 0 and seal_wan < self.min_seal_wan:
    return None
```

所以第一轮价格在涨停、封单 100 万、门槛 200 万时：状态先变 `sealed`，但不告警；第二轮封单升到 300 万时，`prev == sealed`，直接返回 None。本轮探针输出 `[None, None]`，正确语义应是 `[None, "seal"]`。

修复应把价格状态与资格状态拆开，例如 `at_limit_unqualified -> sealed_qualified`，只在**首次跨过资格门槛**时发 seal；跌停侧镜像测试必须一起补。

### 4.5 `IT-P1-006-R1`：Eastmoney 达到 `max_pages` 上限仍可能宣布完整

固定源码 `EastmoneySource.universe()`：

```python
pages = min(self.max_pages, ceil(total / page_size))
...
complete = bool(total > 0) and not failed
```

假设 `total=300, page_size=100, max_pages=2`，实际需要 3 页，但只请求 2 页；若两页都成功，当前仍得到 `complete=True`。本轮机制探针复现 `required_pages=3, pages_requested=2, complete_current=true`。

1.0.2 对 `IT-P1-006` 已做了重要修复，尤其 Sina “翻满上限仍未到底”已经识别为 incomplete；本问题是**Eastmoney 分支的残留**，不应把整个旧修复否定掉。修复条件应至少加入：

```python
required_pages = ceil(total / page_size)
truncated = required_pages > max_pages
complete = total > 0 and not failed and not truncated
```

### 4.6 `IT-P0-001`：14:57–15:00 仍被视作连续竞价

当前 `session.py` 把 `13:00 <= t < 15:00` 全部返回 `AFTERNOON`，而 `AFTERNOON` 属于 `CONTINUOUS`。代码注释本身又写了 14:57–15:00 是收盘集合竞价，内部语义自相矛盾。

本轮同时复核交易所公开规则：上海证券交易所股票连续竞价下午时段为 13:00–14:57，收盘集合竞价为 14:57–15:00；深圳证券交易所公开投资者页面同样给出该边界。官方资料：
- SSE Trading Hours: https://english.sse.com.cn/start/trading/schedule/
- SZSE Trading Overview: https://investor.szse.cn/English/services/trading/tradOverview/index.html

本轮机制边界结果：14:56:59=afternoon、14:57:00=afternoon、14:59:59=afternoon、15:00=post；14:57 起前两项不符合连续竞价语义。

## 5. 监控本身仍看不到 soft-partial：`IT-P2-OBS-001`

`tools/live_session.py::_soak_loop()` 当前逐轮记录：

```python
quotes=len(state.quotes)
universe=len(engine._codes)
```

`state.quotes` 是累计最近值缓存，`_codes` 是期望扫描池，都不是“本轮成功返回且通过质量门控的股票数”。固定反例：universe=4800、累计 cache=4800、本轮实际只回 4500，当前 soak 仍可打印“池4800 / 行情4800”，真实本轮覆盖只有 93.75%。

所以此前真实 12 分钟 soak 的 144 轮、接口/SSE/延迟数据仍是有价值的历史运行证据，但它不能证明每一轮每一只股票都取得了新的有效快照。下一版 round sample 必须补 `requested/returned/admitted/unknown_missing/stale_rejected/out_of_order_rejected/source_mix`。

## 6. 仍开放的可靠性交付问题

`AlertStore.broadcast()` 对 maxsize=200 的订阅队列满时直接丢最旧项，然后写入新项，没有 gap/event cursor；这意味着慢客户端可以不知道自己漏了数据。`record_tick()` 有 `_series_codes` 的 120 长度 deque，但 `_series` dict 新增 code 后没有同步删除被 deque 淘汰的旧 code，主体 key 数长期仍可增长。SSE 当前也没有一个持久 committed→sent→received→applied 的恢复账本。这些本轮未做浏览器 E2E，继续保持开放，不冒称已复现真实漏报率。

另外，Tencent TLS 在证书错误时默认允许退到 `CERT_NONE`（可通过 `ARAD_ALLOW_INSECURE_TLS=0` 禁用）。这属于明确的安全/完整性风险；不可信网络环境下应默认关闭或把该配置显式化，而不是把行情可用性放在证书校验之前。

## 7. 本轮本地研发：35 因子、五类模型和因果性检查

### 7.1 数据与 TaskSpec

真实多日连续训练数据在本轮沙箱**不可用**。仓库可读 fixture 中包括 `fixtures/raw/eastmoney_trends2_600000.txt`，它是单只股票、单个交易日的分钟趋势样本；另有 Tencent/Sina/Eastmoney 少量 raw fixtures。这些不足以支持 30 股票×20 日、5 秒时序模型训练，因此真实训练状态是 `blocked_real_data`。

为了实际验证研究代码链而不是停在设计文档，本轮生成了明确标记为 `synthetic_fixture` 的数据：30 symbols × 20 business days × 220 ticks × 5s，共 132,000 行；已知候选 79,069。时间切分按整交易日：12 日 train、3 日 tune、2 日 calib、3 日 test，不跨日窗口。

冻结任务仅是“候选事件 180 秒 observed-path 持续性 shadow 评分”：方向调整后的 180 秒末收益 >15bp 且期间最大逆向幅度 >-25bp 为正；随访不足/跨 session/缺失为 unknown。它不是可成交收益标签，也不是 H504 长期牛股标签。

### 7.2 35 个因子，8 个家族

本轮实际生成 35 个候选因子：

| 家族 | 内容 | 数量 |
|---|---|---:|
| A | 多尺度 log-return、速度、加速度 | 8 |
| B | volume/amount rate、past-only zscore | 5 |
| C | spread、1/3/5档 imbalance、top3 pressure | 5 |
| D | microprice-mid 偏离、micro/mid return | 3 |
| E | imbalance rolling mean / persistence | 4 |
| F | VWAP 偏离、变化、保持 | 3 |
| G | market return、个股残差/残差加速度 | 3 |
| H | quality、gap、depth missing、source switch | 4 |

关键公式包括：

\[
r_W(t)=\log(P_t/P_{t-W})
\]

\[
I_k(t)=\frac{\sum_{i=1}^k BidSize_i-\sum_{i=1}^k AskSize_i}{\sum_{i=1}^k BidSize_i+\sum_{i=1}^k AskSize_i}
\]

\[
MicroPrice=\frac{Ask_1\cdot BidSize_1+Bid_1\cdot AskSize_1}{BidSize_1+AskSize_1}
\]

训练预处理参数只从 train 拟合。为检验因果性，本轮额外做了 50 次“把决策时刻之后全部原始 price/volume/book/quality 字段大幅扰动，再重算当前时刻全部 35 因子”的 future-perturbation 检查；**50/50 当前时刻因子完全不变**。这只证明本轮 synthetic factor 实现没有从未来行取值，不代表它们已经正确映射到真实供应商字段。

### 7.3 模型闭环实际运行

所有训练均在 CPU 沙箱运行，线程上限 4，没有 GPU。首次单体研发脚本因为环境没有 pyarrow/fastparquet，在 `to_parquet` 处失败；本轮**没有安装依赖**，改用 pickle。之后两个单体流程因会话时限超时，保留已落盘的数据/因子中间产物，最终拆分为 `train_models.py` 并成功完成。失败试验没有删除或伪装成成功。

成功训练脚本完成 Rule baseline、Logistic、HistGradientBoosting、MLP、causal TCN 的 `fit -> checkpoint -> reload -> predict -> evaluate`。checkpoint 重载最大预测差：Logistic=0、HGB=0、MLP=0、TCN=0。

成功训练进程 `/usr/bin/time -v`：wall 15.54s，CPU 167%，Max RSS 821,516 KB（约 802 MiB），socket messages sent/received=0。这是 synthetic pipeline 的脚本成本，不是生产引擎成本。

| 标签置换负控制 | 11,726 | 0.5181 | 0.5533 | 0.6918 | 0.2493 | 接近随机，管线没有明显“标签仍可被轻易恢复”的异常 |

这些值**不能拿来声称真实行情模型命中率**。尤其 TCN 只构造出 train 425 / tune 125 / test 213 条 128-step 序列，而且只训练 2 epoch，用途只是验证 causal conv、mask、checkpoint/reload 和推理链。当前证据反而说明：在真实数据到位前，**不要扩大神经网络**；先让 HGB/简单模型成为可复现的影子基准。

### 7.5 因子消融

HGB 同配置 synthetic 消融：

| 组合 | 特征数 | ROC AUC | PR AUC |
|---|---:|---:|---:|
| A price only | 8 | 0.6527 | 0.6882 |
| A+B price/volume | 13 | 0.6516 | 0.6890 |
| A..F microstructure | 28 | 0.6629 | 0.7082 |
| full no quality | 31 | **0.6652** | **0.7096** |
| quality only | 4 | 0.5009 | 0.5412 |
| full | 35 | **0.6652** | **0.7096** |

在这个 synthetic fixture 中，H 质量特征没有增量（full 与 no-quality 相同），quality-only 接近随机。这是一个有用的负结果：后续真实数据实验必须保留 quality-only 对照，避免模型只是“识别供应商故障”。

### 7.6 因子调试与粗筛继续实际运行

本轮随后又执行了 10 个**只看 tune 指标**的粗筛配置：Logistic `C={0.05,0.2,1,5}`；HGB `max_leaf_nodes={7,15,31} × learning_rate={0.04,0.08}`，其余固定。搜索没有用 test 选择参数。

Synthetic tune 最优 HGB 为：`max_leaf_nodes=15, learning_rate=0.04, max_iter=80, l2=0.1`，tune PR AUC 0.6976。由于之前 smoke 已经看过同一 test 区域，随后 test 输出被明确标为 `descriptive_prior_smoke_already_inspected`，不能再称未见最终测试；描述值 ROC AUC 0.6707、PR AUC 0.7140。

选定 HGB 后做 3 个 expanding walk-forward synthetic 折，ROC AUC 分别 0.6929 / 0.6806 / 0.6620，PR AUC 0.6943 / 0.7011 / 0.6795。再以 seeds 17/29/43 在固定 tune 上跑，PR AUC 0.6976 / 0.6949 / 0.6953。说明 synthetic 生成机制下 HGB 结果不是只靠一个 seed，但仍然**不构成真实市场泛化证据**。

## 8. 主改造方案：Round Observation Contract + Research Shadow v1

### 8.1 目标

把“source 无异常返回”改成“本轮每只股票的观测质量有明确定义”，统一解决 soft-partial、时间错误、source 切换和窗口连续性；在这个工程合同之上，再做因子/模型 shadow 排序。模型绝不能绕过 admission，把被工程层拒绝的旧包重新变成有效行情。

### 8.2 内部 schema

建议保持既有 v1 `Source.snapshots()->list[Quote]` 对外签名，新增内部包装：

```python
@dataclass(frozen=True)
class BatchResult:
    request_id: str
    route: str
    requested: tuple[str, ...]
    returned: dict[str, Quote]
    explicit_unavailable: frozenset[str]
    unknown_missing: frozenset[str]
    source: str
    source_epoch: str
    completeness: Literal["complete", "partial", "unknown"]
    elapsed_ms: int

@dataclass(frozen=True)
class ObservationDecision:
    code: str
    source: str
    source_epoch: str
    provider_ts: datetime | None
    received_at: datetime
    process_mono_ns: int
    decision: Literal["admit", "reject", "quarantine"]
    reason: str

@dataclass
class RoundObservationSet:
    requested: set[str]
    admitted_current: dict[str, Quote]
    unknown_missing: set[str]
    stale_rejected: set[str]
    out_of_order_rejected: set[str]
    source_mix: dict[str, int]
```

规则层不变量：

```text
Snapshot_t == admitted_current_t
latest_cache != current observations
```

### 8.3 时间与连续性

内部统一比较 canonical event time / received time，任何 future/out-of-order 判断在 state 写入**之前**完成；window 定义必须满足：

```text
now-W <= point.ts <= now
```

累计量差分只允许同 `trading_day × session_segment × source_epoch × unit/capability_version`；跨 segment 第一条只 warm-up。

对值不变但持续新鲜的快照使用 interval history：

```python
ObservationInterval(
    first_observed_at,
    last_observed_at,
    price,
    cum_volume,
    source_epoch,
)
```

值不变则延伸 `last_observed_at`；没有新鲜快照则不延伸，从而同时保留横盘 anchor 与真实断线。

### 8.4 研究 shadow

研究模型输入只能来自 `admitted_current` 和严格过去窗口。第一阶段保持原规则发布完全不变：

```text
rule candidates -> shadow feature/model score -> offline compare
```

模型失败、缺字段、延迟超预算时直接 `shadow_score=unavailable`，不能阻断原规则，更不能触发真实通知。真实标签到位前只做 observed-path research，不做交易收益声明。
