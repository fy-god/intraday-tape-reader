### 🔴 D1 `IT-P1-SUITE-TIMING-ASSERTION-NONDETERMINISTIC-001` — 已确认错误

**文件/函数/行**
`tests/test_rule_limit_board.py:1175 def test_performance_1000_stocks()`，断言在 **`:1212`**：

**触发条件/反例**

- 第 1 次整套 → `1 failed, 1801 passed`，exit **1**，报 `214.3ms`
- 第 2、3 次整套 → `1802 passed`，exit **0**

**机制**
断言的判据是**墙钟耗时上界 `0.2s`**，而实测值贴着阈值（214.3ms 对 200ms 阈值，超出仅 **7.2%**）。它度量的是**当时机器的调度/负载**，不是代码正确性。我另做了隔离与负载对照（见 §3 未复现项），证明它不是简单的"CPU 满载"型不稳，但**整套运行时温度/GC/并发足以让它跨过 7% 的余量**。

**影响**
1. **本仓库唯一的整套门是非确定性的**：CI/审计里"红了"不能推断代码错，"绿了"不能推断代码对。
2. 我实测到它在**同一棵树**上给出两种结论，所以**任何以"整套 pytest 全绿"为依据的通过声明都不可信**（这正是我要在本轮之后避免的引用方式）。
3. 受影响样本：整套 1802 个测试的**红旗信号价值**全部被这一条削弱；单独看，只有 1 个测试真正不稳。

**修复建议**（三选一，按优先级）
- (a) **推荐**：把墙钟上界改为宽松的**回归警戒**（如 `elapsed < 2.0`），把精确性能基准移到 `pytest.mark.benchmark` 之类的**非门控**标记里；性能本来就该有专门基准，不该塞进门控断言。
- (b) 保留 0.2s 但**重试/取多轮中位数**（例如 5 次取中位），并显式标注"性能测试，允许抖动"。
- (c) 若坚持门控，则**必须**同时记录并断言机器基线（如同机跑一个固定空转基准），否则阈值本身没有可比性。

**验收测试**
对同一棵树连续运行整套 ≥3 次，**结论必须一致**；且失败率应为 0（当前实测：3 次中 1 次红，失败率 33%）。等价的可执行判据：`for i in 1..3; do pytest -q; done` 全部 exit 0。
