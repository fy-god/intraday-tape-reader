确实接通时才有意义）我已满足 —— 阳性对照**在同一套装置**上立刻变红。
两条合起来的含义是：

> 任何后续"修法"（包括把两轴都改错的）都会**绿灯通过**。

**M6 顺带暴露的第二个未检测破坏**：M6 下 `raw_returned_requested_keys`（账本键）
与 `Quote.code` **不再一致**：

sh000001  账本键=['sh000001'] Quote.code=['sh000001'] ALIGNED=True

而 M6 让 `_key` 独走 → 账本键与真实行情键错位，**同样零测试覆盖**。

**由此得出的验收要求（比我补遗二/三写的更严）**：

1. 对名称唯一定身份的指数（如 `sh000922`）→ `missing==[] and unexpected==[] and admitted==1`；
2. `_key`(raw 账本) 与 `parse_response:334` 的 `out_code` **逐字节一致**；
3. 两轴判据的**输入**相同（不是判据"形状"相同）。
再加一条**变异测试**：把判据输入改成空串必须让测试变红（否则等于没测）。

## 3. 更正我的"两轴"表述：实为**三处**身份判据

补遗一/二我一直说"两轴分叉"。核对代码后，判据其实有**三处**：

```text
tencent.py:333  parse_response   is_index = symbol in idx_set and looks_like_index(symbol, name, code)
                                 -> 决定 Quote.code（行情键）, 输入 = 真名
tencent.py:448  _key (raw 账本)   looks_like_index(symbol, name, code)
                                 -> 决定账本键,            输入 = 真名
tencent.py:479  _req_key (请求)   looks_like_index(sym, "", c)
                                 -> 决定请求键 R,          输入 = 空串
```
`:479` 的补丁把**判据形状**对齐了 `:448`，但**没有对齐输入**（`:448` 有真名、`:479` 传空串），
并且 `:333` 这第三处必须与 `:448` 保持**逐字节一致**（否则 §1 的账本错位）。
**准确的描述是**：`tencent.py` 里"同一个身份判定"被实现了**三次**，
其中一次（`:479`）的输入与另外两次不同 —— 这正是本仓库反复出现的
"同一语义实现多次"bug 类（`build_outcome` 的 docstring 自己就点名过这一类）。
