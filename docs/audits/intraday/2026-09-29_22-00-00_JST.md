### 1.1 `IT-P1-ADMIT-REASON-STALE-SILENT-DROP-016`【确认 · 已修】

**文件/函数/行号**：`src/arad/engine.py`
· 生产：`EngineState._admit_time()` 原 `:461`
· 消费：`EngineState.update_detailed()` 原 `:356-361`

```python
# 生产（:461）
if first_seen and freshness_allowed and q_ep < ep - STALE_TOLERANCE_SECONDS:
    return False, q_ep, "stale"          # ← 第三种原因

# 消费（:359-361）
if why == "future":
    ...
elif why == "out_of_order":
    ...
# ← 没有 else，没有 stale 分支
```

**触发条件**：某源的 `freshness_allowed=True`（合同允许判新鲜度）
且收到本 route 本 epoch 的**首见**陈旧包。

**机制**：`why` 是**自由字符串**，生产者能返回三个值
（`future` / `out_of_order` / `stale`），消费者只分派两个。
`stale` 会写全局计数 `t_reject:stale`，然后**两个 if 都不匹配、静默跌落** ——
route-local 归属（`rejected_future` / `rejected_out_of_order`）
**贡献 0**。

**为什么这是真缺陷而不是理论**：
- **可达**：两个**既有**测试就走到它 ——
  `test_source_epoch_time_contract.py::test_stale_packet_rejected_when_source_is_trusted`
  与 `test_source_epoch_route.py::test_stale_rejected_per_route_epoch_when_freshness_trusted`
  都把 `TIME_POLICY["tencent"]["freshness_allowed"]` 置 True。
- **我独立核实过**：`git show HEAD:src/arad/engine.py` 确认 `:461` 返回
  `"stale"`，`:359-361` 无 else 分支。**不是转述**。

**影响**：这是 bug 类 **(d)「默认分支 = 假绿出口」**——不是"没数据"，
而是**有数据、算出来了、然后掉进没有覆盖的分支**。账面看是
"本条 route 没有时间拒绝"，实际是"拒绝了但归错了桶"。
派生的后果：一次 failover 后陈旧包被硬拒却不计入任何 route 桶，
下游无法区分"这条链路干净"与"这条链路的拒绝没被记账"。

> ⚠ **云端任务书的判断是错的**。任务书（与我的原始 brief）隐含
> "`stale` 不可达"。**实测可达**。这是一次**下调/更正**。

**修复**（`src/arad/engine.py` + `src/arad/capabilities.py`）：
- 新增 `class AdmitReason(str, Enum)`：`FUTURE` / `OUT_OF_ORDER` /
  `STALE` / `NO_REJECT`，单点声明；派生闭集
  `ADMIT_REJECT_STATS_KEYS`（仅**拒绝**类，不含 NO_REJECT）。
- `_admit_time` 返回类型 `tuple[bool, float, str]` → `tuple[bool, float, AdmitReason]`。
- 分派改为**穷尽**且 `else: raise` —— 未知值不再静默。
- `StateUpdateResult` 新增 `rejected_stale: int = 0`（加法式，默认 0，
  既有字段与 JSON 键**字节不变**）。
- `RoundObservationSet` 新增 `stale_hard_rejected`（**不叫**
  `stale_rejected` —— 那个名字是已弃用属性，意思是"陈旧**诊断**"，
  复用会把"诊断"与"拒绝"两条互斥曲线重新合并，正是
  IT-P1-OBS-010 修掉的那个 bug）。
- 消除 `:508` 手写第二遍的 `"t_reject:out_of_order"` 字面量，
  改为 `AdmitReason.OUT_OF_ORDER.stats_key`（bug 类 b：同一语义两份实现）。

**⚠ 一个差点酿成事故的陷阱（`str, Enum` 不改变 `str()`）**

实测（修复前后对照）：

```
str(AdmitReason.FUTURE)   == 'AdmitReason.FUTURE'   ← 若不处理
f"{AdmitReason.FUTURE}"   == 'AdmitReason.FUTURE'   ← 若不处理
't_reject:' + AdmitReason.FUTURE == 't_reject:future'   ← 拼接反而是对的
```

也就是说 `f"t_reject:{why}"` 会静默产出
`t_reject:AdmitReason.FUTURE` —— **这正是本任务要保护的仪表盘匹配键**。
修复：绑定 `__str__ = str.__str__` 与 `__format__ = str.__format__`。
**我独立复核**（不走转述）：

```
str(R)   = 'future'          f-string = 'future'
plus     = 't_reject:future' %s       = 'future'
.value   = 'future'          =='future' = True
typo AdmitReason('furure') -> ValueError ✅
```

**验收测试**：`tests/test_admit_reason_vocabulary.py`（**28 条**）
- `test_implementation_can_only_return_declared_reasons`
- `test_positive_control_stale_is_classified_as_stale_not_silently_dropped`
- `ADMIT_REJECT_STATS_KEYS == {"t_reject:future","t_reject:out_of_order","t_reject:stale"}`（含字节级 `.encode()` 比较）
- `str(m) == f"{m}" == m.value`
- `AdmitReason(typo)` 抛 `ValueError`
- 生产路径：`{k for k in stats if k.startswith("t_reject:")} <= ADMIT_REJECT_STATS_KEYS`

### 1.2 `IT-P1-SOAK-RAW-PRESENCE-GRADE-BLIND-001`【确认 · 已修】

**文件/函数/行号**：`tools/live_session.py`（观测工具层）
· 消费点原 `:356-359`

```python
missing = obs.get("unknown_missing")
out["unknown_missing"] = len(missing) if isinstance(...) else 0
quality = obs.get("rejected_quality")
out["rejected_quality"] = len(quality) if isinstance(...) else 0
```

**机制**：上一轮我把 `raw_presence_known_by_route: dict[str, bool]` 加进了
`RoundObservationSet`（`capabilities.py:564` / `as_dict()` `:949`），
引擎也在两个分支里填了它。但**没有任何消费者读它** ——
`live_session` 照旧把 `unknown_missing` / `rejected_quality` 当**硬事实**
计数上报。

后果：当某条 route 的 presence 是**投影反推**（`False`）时，
报告仍以与精确数据**同等的权威**呈现这些数字。而
`raw_presence_known_by_route[route] is False` 的语义恰恰是
"分不清 provider 没返回 还是 返回了但数值不可用"。

**这正是我自己上一轮犯的 bug 类 (c)「数据算了、判决层零读者」**，
以及 (e)「证据子集自称全程」——我加了字段却没接读者，
等于把"修好了"留在测试里。

**修复**（`tools/live_session.py`）：
- 逐轮读取 `raw_presence_known_by_route`，产出**三态**：
  - `exact` —— 全部 route 都有精确 raw presence 证据
  - `mixed` —— 部分 route 精确、部分投影（**点名** `raw_presence_projected_routes`）
  - `not_measured` —— 键**整体缺失**（旧轮次 / legacy 源）
- 单步诚实旗标 `raw_presence_exact_all_routes`。
- 保留原始数字（可回溯），但降级旗标**相邻可见**，不再同级呈现。

**我独立复核三态**（走真实 `make_round_sample`，非转述）：

```
True,True        state='exact'         all_exact=True   projected=[]
False,True       state='mixed'         all_exact=False  projected=['stocks']
ABSENT (键缺失)   state='not_measured'  all_exact=False  projected=[]
三态互不相同: True      ★ ABSENT 未被当成 exact: True
```

**第三态是这条修复里最关键的性质**：键缺失**不得**静默当成 `True`。
否则"没测"会变成"测了且很好" —— 又一种假绿出口。实测 fail-closed ✅。

**验收测试**：`tests/test_live_session_raw_presence_grade.py`（**22 条**）

### 1.3 `IT-P1-006-R1-R2` Eastmoney 无 total 分支 `truncated` 恒 False【确认 · 已修】

**文件/函数/行号**：`src/arad/sources/eastmoney.py` · `universe()` · 原 `:499-502`

```python
else:
    pages_requested = self.max_pages      # ← 只写这个
                                          # ← truncated 从不赋值
reason = "接口未返回总数，只能顺序探测，无法确认是否翻完"
```

**背景**：云端任务书把 `IT-P1-006-R1`（Eastmoney `max_pages` 截断仍标
complete）列为**待独立复核**，因为上轮修复只覆盖有 total 的路径。

**我的复核结论（分两半，都要说清）**：

**① 安全性没有漏。** `truncated` 只在 `if total > 0` 分支被赋值；
无 total 分支不写它。但 `transport_complete` 在无 total 时**恒为
`False`**（"没有基准就证明不了完整"，fail-closed）。实测三场景全 False ✅。

**② 但诊断字段说谎。** 当 `for` 循环**跑满 `max_pages` 且末页仍有代码行**
（= 传输层明明还有数据，我们却因页数上限停了），`for...else` 只写了
`pages_requested`，**`truncated` 保持 `False`**，reason 还写成
"无法确认是否翻完" —— 可我们**恰恰有证据**证明被截断。

**实测（修前）**：

```
场景 1（无 total + 翻满 max_pages 仍未到底）
  请求页: [1,2,3,4,5]   pages_requested = 5
  transport_complete = False   ✅ 安全正确
  truncated = False            ❌ 与事实相反
  reason = "接口未返回总数，只能顺序探测，无法确认是否翻完"   ❌ 我们其实知道
```

**影响**：不是漏报不完整，而是**误诊**。下游会把"被 `max_pages` 卡住"
读成"接口不返回总数"，从而去调**错的旋钮**（去查 API 而不是调
`max_pages`）。这是 bug 类 (g)「同一语义在两个时点/两个轴上分别推断」——
"是否被页数截断"在两条分支上被各自推断了一次，只有一条真的推断。

> 诚实分级：这是**诊断正确性**缺陷，**不是**安全漏洞。我按诊断缺陷报。

**修复**：`for...else` 里补 `truncated = True`；reason 拆成两支，
区分"**确证**被页数上限截断"与"顺序探测已到底，但无基准仍无法证明完整"。

**实测（修后，四场景）**：

```
no_total_exhausted_maxpages  truncated=True   transport_complete=False  ✅
no_total_reached_end         truncated=False  transport_complete=False  ✅
total_truncated              truncated=True   transport_complete=False  ✅
total_fully_fetched          truncated=False  transport_complete=True   ✅
```

**验收测试**：`tests/test_eastmoney_no_total_truncation_diag.py`（**8 条**）
含**阳性对照** `test_no_total_reaching_the_end_is_not_marked_truncated`
（防"永远报截断"这种反向假数据）与
`test_total_branch_fully_fetched_is_complete`（防假阴性）。

## 3. 独立复核：把"疑似缺陷"降级

**R2 原始怀疑**：`call`（`engine.py:665`）与 `call_detailed`（`:709`）
各写了一份 failover + 失败计数逻辑。修只落在 `call_detailed`（WP03 的
try 边界），`call` 那份从未审计。若两者**耗尽路径**语义不同，
同一件事在两条链路上会有不同后果。

**我写了 4 条路径探针（真实代码，非推理）**：

| 路径 | call | call_detailed | 一致 |
|---|---|---|---|
| 单源全失败（耗尽） | `idx=0 fails=1` | `idx=0 fails=1` | ✅ |
| 单源 threshold=1 | `idx=0 fails=1` | `idx=0 fails=1` | ✅ |
| 双源全失败 ×3 轮 | `idx=1` | `idx=1` | ✅ |
| 尾源成功（i≠idx 记账） | 第2轮起 `idx=1 fails=0` | 同 | ✅ |

**结论：行为完全一致** → **不是已确认缺陷**，降级为 bug 类 (b) 的
**潜在**风险（两份手写逻辑**迟早**会漂移）。诚实下调，不虚报战功。
