## 1. 已确认错误（全部已在真实行情上复现并修复）

### 1.1 `IT-P1-NEWLIST-001` · 新股没有涨跌幅限制，却被套上 ±10%

| 项 | 内容 |
|---|---|
| **文件/行** | `src/arad/models.py:231-240`（`limit_up_price` / `limit_down_price`） |
| **触发** | 真实行情中出现名称冠 `C` 的次新股：`601091 C沈鼓` |
| **机制** | `limit_rate_of()` 只按板块返回 ±10%/±20%。2023 全面注册制后**新股上市前 5 个交易日不设涨跌幅限制**，但代码不知道这件事 |
| **影响** | `601091` 当日 **+177.74%**、现价 57.77，却算出 `limit_up=22.88`、`limit_down=18.72`。`limit_board` 拿这套**根本不存在于该股**的阈值做状态机判定，产出告警「**打开跌停 +208.60%**」；同轮该股还同时报「低开高走 +285.1%」，**自相矛盾**。同轮 `688837 C信诺维`（+34.46%）同样越界 |
| **修复** | 无约束时 `limit_up_price`/`limit_down_price` 返回 **`0.0`**（语义＝"没有这个约束"）。配套 `has_price_limit` / `is_new_listing` / `is_at_limit_up` / `is_at_limit_down`。`limit_rate_of` **保持纯板块/ST 语义不变**（有测试钉住） |
| **验收** | 修复后重跑真实全市场：601091/688837 **零告警**；`600000` 照常放行。回退 `models.py` → **9 条 AssertionError 真验牙** |

**为什么用 `0.0` 而不是某个假比例**：`limit_rate_of` 返回的是**比例**，
而"无限制"不是一个比例。硬塞 `0.0` 或 `1.0` 都会被下游当成真阈值。
`0.0` 是一个**哨兵值**，含义是"这个约束不存在"，下游一律 `if limit > 0` 处理
（`limit_board._check_side:189`、`limit_board.evaluate:117`、`unusual.py:282`
三处**本来就**是这么写的，所以修复后语义天然自洽）。

**最容易写错的地方**：`q.price >= q.limit_up_price` 在 `limit_up_price == 0.0`
时**恒真**。所以提供了 `is_at_limit_up()` 作为唯一正确入口，并写测试钉住。

### 1.2 `IT-P1-NEWLIST-002` · 新股过滤第二层缺失，`min_list_days` 静默失效

| 项 | 内容 |
|---|---|
| **文件/行** | `src/arad/filters.py:41-56`（`_too_new`）、`:58-74`（`accept`） |
| **触发** | 默认配置 `filters.min_list_days = 11`，走腾讯链路 |
| **机制** | 该配置**完全不生效**。`list_dates` 只有**东财**股票池提供，而东财在本机被 IP 封禁（`RemoteDisconnected: Remote end closed connection without response`），实际走腾讯 —— `list_date` 是空串。`engine.py:985` 自己已注明"该字段为空、新股过滤自动失效"，而 `_too_new` 遵循"数据缺失时放行、不误杀"的约定，**两层防线同时不存在** |
| **影响** | C沈鼓/C信诺维 畅通进入**全部**规则，产出「巨震 326.5%」等。新股无涨跌幅限制，"巨震"是**制度性必然**而非有用信号，只会淹没真异动 |
| **修复** | `_too_new` 增加**第二层**：无精确上市日时退回**名称前缀**（`N`＝首日、`C`＝第 2~5 日）。判据收紧到"首字母 N/C 且第二字符是**中文**" |
| **验收** | 实测 5564 只真实行情里符合该形态者**恰好 2 只、零假阳性**；`TCL科技`/`NVIDIA概念`/`CPU概念` 均不被误伤。回退 `filters.py` → **7 条 AssertionError，零结构性** |

`min_list_days <= 0` 时两层都关 —— 用户显式关闭的功能**不能**被偷偷强制。

### 1.3 `IT-P1-REPLAY-DETERMINISM-001` · 回放确定性承诺是假的

| 项 | 内容 |
|---|---|
| **文件/行** | `src/arad/replay.py:374`（`generate_script` 里的 `hash(s.code)`） |
| **触发** | 修完上面两个后，`selftest` 告警数从 69 变 70 |
| **机制** | 文档承诺「同 seed + 同参数字节级可复现」，但用 `hash(s.code)` 播种。CPython 对 `str` 的 `hash()` 按 `PYTHONHASHSEED` **每进程随机化**（抵御哈希碰撞 DoS） |
| **影响** | 三进程（seed=42）实测数据指纹 `8ba5542d…` / `4d73762d…` / `95a79558…` **互不相同**。`selftest` 告警数在 **68/69/71 之间漂移**，**不能当回归判据**；历次报告里"selftest N 条告警"全都**不是**稳定不变量 |
| **修复** | 改用 SHA-256 派生的稳定种子 `_stable_code_seed` |
| **验收** | 修复后 6 次连跑**全部 68 条**、跨进程指纹一致。固定 `PYTHONHASHSEED=0` 后三进程一致 → **根因确证**。回退 `replay.py` → **3 条 AssertionError，零结构性** |

**发现路径值得记录**：我没有把"69→70"当噪声放过，而是逐条对比 → 两次都 69
→ 再连跑 6 次 → 发现 68/69/71 都在出现 → 才定位到 `hash()`。
这正是上一轮"改完就宣布完成"教训的反面。

## 6. 诚实声明：这**不等于**用户明天能收到有用告警

用户的核心诉求是**盯盘**，不是让测试变绿。必须说清：

1. **本轮修的是"会不会报错"，不是"报得准不准"。**
   601091 那类假告警确实消失了，但**真告警的正确率完全未测**。
2. **`spirit_*` 三条规则默认仍是 `enabled: false`**（`config/settings.yaml:188/223/257`）。
   配置注释的原话是「建议先在真实行情里观察命中质量再打开」。**我还没有
   足够证据建议打开** —— 见 §7。
3. **真实 Precision / Recall / 漏报率 / 交易收益 依然是 `unavailable`。**
   没有任何标注数据（"这只票当时到底该不该报"），所以无法计算。
   **我不提供任何编造的数字。**
4. **盯盘要真正可用，还差**：连续竞价时段的实测（09:30 后）、
   以及"报出来的告警里有多少是有价值的"这件事的**人工标注**。

## 7. 研究想法（附造假条件）

### 想法 A：用「事后收益」给告警打标签，量化 Precision

- **做法**：记录每条告警的 `(code, ts, price)`，T+5/T+30 分钟后取真实价格，
  算"告警后是否继续同向移动"。不需要人工标注，能自动产出 Precision 代理指标。
- **能回答**：`spirit_order` 的 20 条/轮 里有多少是噪声 —— 这正是配置注释
  说"要先观察命中质量"的那件事。
- **造假条件（falsify）**：若告警后 T+5 的收益分布与**随机抽样时点**的收益分布
  **无显著差异**，则该信号无预测价值，应当默认关闭或重调阈值。
- **明确区分**：这是**任务定义调整**（从"会不会报错"转向"报得准不准"），
  不是模型增量。

### 想法 B：验证 `max_per_round=20` 是否在**系统性丢弃**高价值告警

- **观察**：真实全市场里 `limit_board` 每轮恰好卡在 20 条（其 `max_per_round=20`），
  而同一轮 `unusual` 报了 35 条 → 说明**大量候选被截断**。
- **待查**：被截断的候选里有没有比留下的更紧急的？截断按 `(-severity, -|pct|)` 排序，
  但"封单额 1 亿"与"封单额 1734 万"被同等对待。
- **造假条件**：若被截断候选与保留候选的 severity/|pct| 分布在统计上无差别，
  则截断是"随机丢"，`max_per_round` 的排序键需要改。
- **这是产品意图问题**（P0，`NEXT_STEPS.md` 已记）：`max_per_round`
  到底是硬性限流，还是"宁可少报也不报错"？
