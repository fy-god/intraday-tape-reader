### 1.1 `IT-P1-EVAL-PUBLISH-001`：交付账本只有一级，overcount 24× 〔**已确认 · 已修复**〕

* **文件/函数/行号**
  * `src/arad/capabilities.py:214` `SignalEvalStats.published`（旧字段）
  * `src/arad/capabilities.py:450` `mark_published()`（旧实现）
  * `src/arad/engine.py:1292` `AlertBus.accept()` 调用点、`:1302` `store.add_alert()` 调用点
  * `src/arad/rules/volume_burst.py:344`、`src/arad/rules/spirit_order.py:741`（规则内记账点）
* **触发条件**：同一标的在 `cooldown_seconds` 窗口内**每轮都满足**判据
  （例如持续放量的票，5 秒一轮、cooldown=600 秒）。
* **机制**：旧账本只有一个 `published`，且它在**规则内部**、
  `max_per_round` 截断之后**立刻**写入。那时告警**还没**经过
  ①`AlertBus.accept()` 的 key 去重与 cooldown、②`store.add_alert()`。
  于是被 cooldown 丢掉的候选也被计成"已发布"。
* **影响**：**不是"数字不好看"**。若拿旧 `published` 当"已发布事件"的
  分母去给事后收益打标签，那 23 条从未交付给任何人的候选会被当成
  真实发生过的告警事件，**标签集从源头就是错的**。
* **机制反例（真实代码端到端复现，非推演）**：

  | 阶段 | 计数 |
  |---|---|
  | 规则选中 `rule_selected` | **24** |
  | 过 `AlertBus` `bus_accepted` | **1** |
  | 真写进 Store `committed` | **1** |
  | overcount 因子 | **24.0×** |

  探针：`$env:TEMP\probe_publish_overcount.py`（真实 Engine + 真实
  `volume_burst` + 真实 `AlertBus` + 真实 Store，24 轮 × 5 秒，
  `cooldown_seconds=600`）。输出 `机械不变量违规: 无` 且
  `rule_selected=24 / bus_accepted=1 / committed=1`。
* **修复**：把单级 `published` 拆成**交付阶段链**
  ```
  hit_candidates >= rule_selected >= bus_accepted >= committed
  ```
  * `capabilities.py`：新增 `rule_selected` / `bus_accepted` / `committed`
    三字段 + `dropped_by_bus` / `committed_ratio` 两个属性；
    `published` 降级为 `rule_selected` 的**兼容别名**（保留旧消费方不炸，
    但不再是交付真值）；`check_invariants()` 增加两条链式断言。
  * `engine.py`：新增 `_mark_stage(observation, alert, stage)`，
    在 `bus.accept()` **之后**记 `bus_accepted`、在 `store.add_alert()`
    **之后**记 `committed`。
  * `models.py`：`Alert` 新增 `signal_id` 字段（**必须由产生它的规则填写**；
    留空表示不参与账本）。为什么不能靠 `title` 或 `cooldown_key` 猜：
    8 个 spirit pattern 共用同一个 `AlertKind`，文案会改，**猜错必然串账**。
  * `tools/live_session.py`：soak 聚合输出三级总量；
    **旧轮样本缺失新键时退回 `published`**（不能退成 0，否则升级当天
    历史报告会被读成"一条都没交付"）。
* **验收测试**：`tests/test_alert_delivery_stages.py`（20 条）
  + `tests/test_live_session_observation.py::TestAlertDeliveryStageAggregation`（3 条）

### 1.2 `IT-P1-EVAL-PUBLISH-001-R1`：记了"不能判"却照样发告警 〔**已确认 · 已修复 · 本轮新发现**〕

* **文件/函数/行号**：`src/arad/rules/volume_burst.py:237-243`（旧）
* **发现方式**：**真实看板端到端对账**（§3）。单元测试与离线 selftest 都没抓到。
* **触发条件**：源**声明**不提供 `turnover`（Sina 情形），但 payload 里
  该值恰好可用（`q.turnover >= min_turnover`）。
* **机制**：旧代码
  ```python
  if min_turnover > 0.0 and not ctx.provides("turnover"):
      self._mark_unavailable(ctx, code, "turnover")
      _mark(obs, "mark_blocked", signal, code, "turnover_not_provided", "turnover")
  if min_turnover > 0.0 and float(q.turnover) < min_turnover:
      continue          # ← 只有数值不达标才跳过
  ```
  第一段**只记账、没有 `continue`**。于是同一票**既被记成"判不了"(blocked)
  又继续往下判并真的发出告警**。
* **影响**：机械不变量 `rule_selected <= hit_candidates` 当场被打破。
  实测：`considered=1 blocked=1 hit_candidates=0 rule_selected=1`。
  **这是既有缺陷** —— 对本轮改动前的 HEAD 跑同一探针同样复现。
* **修复**：**记 blocked 就必须真的跳过该票**（blocked 的语义就是"判不了"）。
  turnover 是本规则的硬依赖，且 Sina 的非零换手率同样是**不可信占位值**
  （`tests/test_capabilities.py::test_capability_is_source_level_not_value_level`
  已钉住"同源下改数值不改变可评估性判定"）。
  兼容性：真实 Sina 送 `turnover=0.0` 占位，旧代码也会在数值门槛处
  `continue`，故**告警集合逐字不变**。
* **验收测试**：`test_blocked_code_must_not_still_emit_an_alert`、
  `test_placeholder_zero_turnover_still_counts_as_blocked`、
  `test_tencent_real_zero_turnover_is_a_business_zero_not_a_gap`

  | `"20250310"` | **0.10** | 0.05 | 0.05 |
  | `20250310` | **0.10** | 0.05 | 0.05 |
  | `date(2025,3,10)` | 0.05 | 0.05 | 0.05 |
  | `None` / `""` / `"garbage"` / epoch | 0.10 | 0.10 | （降级，语义不变）|

* **影响**：当日**无影响**（今天现行制度恰是 10%），但在

  * **附带发现（自我加严）**：`strptime("2025031", "%Y%m%d")` 会**宽松地**
    解析成 `2025-03-01` —— 把 7 位乱码当成合法日期。因此改用正则
    **显式钉住位数**（`_DATE_RE`）再交给 `date()` 校验真实性。

### 3.3 真实看板端到端对账（本轮最关键的一步）

用与 `cli._serve_replay` **完全相同的链路**（同一个 store 既被引擎写、
又被 HTTP 看板读）建真实 Engine + Replay + Store + HTTP 服务，

361/361 轮无遗漏），再用 `Alert.to_dict()["signal_id"]` 对真实告警精确分组：

* **被 AlertBus 去重/冷却丢掉 60 条** —— 这正是旧口径会算成"已发布"的量。
* **我的两次探针错误（如实记录）**：
  1. 第一版把 `/api/alerts` 的返回当列表读（真实形状是 `{"items": [...]}`），

## §7 1–3 条有证据、可证伪的研究想法

### 想法 1〔**程序修复**〕：给"股票池覆盖率"设一条**硬门禁**，覆盖率过低时拒绝出结论

* **证据**：本轮两次真实扫描覆盖率 **73.0%** 与 **83.1%**（`5917` 只全市场）。
  `universe` 变量在 `once` 输出里甚至是 `0`。
* **可证伪预测**：若在 `once` / `soak` / 看板里加一条
  "覆盖率 < 90% 时把本轮标记为 `degraded` 并在结果顶部显著提示"，
  则**任何一次真实扫描**都会立刻暴露"这次只扫了七成市场"，
  而不是让用户把"没报警"读成"市场很平静"。
  反证条件：若真实运行中覆盖率恒 ≥ 95%，
  则该门禁永不触发 —— 说明源端其实稳定，我这个担心不成立。
* **为什么它比别的想法优先**：这是**唯一一个会让用户误读"没报警"**的
  结构性因素，其余都是统计噪声。类别：**程序修复**。

### 想法 2〔**任务定义调整**〕：把"告警是否有效"的验收从"发了多少条"改成"交付账本三级各自的对账"

* **证据**：本轮实测 `rule_selected=66 → bus_accepted=6 → committed=6`。
  也就是说**规则选中的 66 条里，60 条（90.9%）被 AlertBus 去重/冷却丢掉**。
  在旧口径下这 66 条**全都**会被记成"已发布"。
  这意味着一件事：**用条数评价系统有效性，在当前架构下几乎完全是噪声** ——
  真正决定用户收到什么的，是 cooldown 与 `max_per_round` 的配置，而不是规则质量。
* **可证伪预测**：若把验收指标改为"三级分别对账 + 交付率 `committed/hit_candidates`"，
  则调 cooldown 的效果会**立刻可见**（例如 cooldown 600s→60s 应显著抬高
  `committed`），而调规则阈值的效果只在 `hit_candidates` 上体现。
  反证条件：若改 cooldown 后 `committed` 不变，说明瓶颈在别处（如 `max_per_round`
  或 Store 上限），我这个归因就是错的。
* **类别**：**任务定义调整**（不改产品语义，改"什么算成功"）。

### 想法 3〔**模型真正增量提升：无**〕：本轮**没有**任何模型层面的改进

* 诚实声明：`程序修复` = §1 的 7 项；`任务定义调整` = 想法 2（尚未实施）；
  **`模型真正增量提升` = 0**。本轮没碰任何模型、任何预测能力。
* 仍待回答的核心问题（延续上轮）：**真实 Precision / Recall / 漏报率 / 收益**
  依旧 `unavailable`。本报告不编造任何命中率或收益率。
* 附带记录一条**证据链失效**：既有研究 `EXP-IT-CAPABILITY-005` 依赖的
  `predictions_v6.csv` 来源链断裂/继承，结论为 `UNVERIFIABLE`
  （**不是**造假，是**无法验证**）。
