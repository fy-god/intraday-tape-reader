# 2. 主故障链：soft partial → 缓存伪当前 → gap 被洗短 → soak 仍健康

## 2.1 `IT-P1-SOURCE-EMPTY-001`：指定代码源没有请求集合完整性

固定源码：`f695102f8794b0b235d5f6ebf24564520d663ad8`

### 腾讯

源码：<https://github.com/fy-god/intraday-tape-reader/blob/f695102f8794b0b235d5f6ebf24564520d663ad8/src/arad/sources/tencent.py>

关键路径：

```python
raw = self._fetcher(url, headers, self.timeout)
quotes = parse_response(decode_body(raw), seq, index_codes)
return quotes
```

上层只把 future 抛异常记成批次失败；若请求 600 个代码，HTTP 成功但服务端少回一行、解析器因为字段不足/坏价格跳过一行，`snapshots()` 最终可能合法返回 599 个 `Quote`，不会抛错，也不会标明缺失的代码。

### 新浪

源码：<https://github.com/fy-god/intraday-tape-reader/blob/f695102f8794b0b235d5f6ebf24564520d663ad8/src/arad/sources/sina.py>

`_fetch_bulk()` 解析 HTTP 响应后直接返回 Quote 列表；`snapshots()` 最终只做 `wanted_set` 过滤和去重。它对**请求批次抛异常**有处理，但对“请求 600、正常返回 599”没有 requested-vs-returned 质量对象。

### 东财

东财对“某个批次 future 抛 `SourceError`”会让整次 `snapshots()` 失败，这是正确的硬失败路径；但成功批次仍只做过滤、去重后返回。单行解析丢失同样缺少“请求集合覆盖率”的合同。

### SourceManager 放大问题

`SourceManager.call()` 当前以“有没有异常”判断成功：

```python
out = getattr(src, method)(*args)
self._serving[route] = i
if i == self.idx:
    self._fails[route] = 0
return out
```

因此 soft-partial 会：

1. 被记为本路由成功；
2. 清掉主源失败计数；
3. 不尝试备用源；
4. 没有 `missing_codes` 留给上层诊断。

### 固定反例

```text
requested = [A, B]
primary actual return = [A]
backup could return = [A, B]
```

当前控制流：不抛异常 → `SourceManager` 直接接受 `[A]` → backup 不被调用。

机制探针结果：

```text
actual_current_coverage = 1 / 2 = 50%
source_manager_route = success
backup_calls = 0
```

### 修改方法

不要用“列表非空”代表质量。新增不破坏 v1 `Source.snapshots()` 的包装接口：

```python
@dataclass(frozen=True)
class BatchResult:
    requested_codes: tuple[str, ...]
    returned: dict[str, Quote]
    explicit_unavailable: frozenset[str]
    unknown_missing: frozenset[str]
    source: str
    source_epoch: str
    complete: Literal["true", "false", "unknown"]
    elapsed_ms: int
```

`SourceManager.call_with_meta()` 根据 `unknown_missing` 决定是否有界尝试备用源，并保留“主源部分 + 备用源补洞”的 provenance。

**不能**把所有缺行都自动认定网络故障：停牌、退市、供应商明确无行情要进入 `explicit_unavailable`；只有未知缺失才是覆盖缺口。

### 回归

- 请求 `[A,B]`，主源回 `[A]`，备用回 `[B]` → 最终 current-set 包含 A/B，且 provenance 可追踪；
- 两源都缺 B → B 为 `unknown_missing`，不能用上轮 B 冒充本轮 B；
- B 明确停牌 → 不无限重试，状态明确为 unavailable；
- 599/600 的 soft-partial 必须在指标中可见，而不是“成功 600”。

## 2.2 `IT-P0-003`：累积缓存被包装成本轮 Snapshot

源码：<https://github.com/fy-god/intraday-tape-reader/blob/f695102f8794b0b235d5f6ebf24564520d663ad8/src/arad/engine.py>

核心路径：

```python
self.state.update(quotes, now)

eligible = {
    c: q for c, q in self.state.quotes.items()
    if self.filters.accept(q, now.date()) and c not in self.ignore
}

snap = Snapshot(...)
snap.quotes.update(eligible)
```

`state.quotes` 是累计“最近已知值”，不是本轮实际返回集合。因此：

```text
round 1: A,B 均返回
round 2: provider 只返回 A
```

round 2 的 `state.quotes[B]` 仍存在，只要 B 仍通过普通粗筛，它继续进入 `snap.quotes`。

零价路径同样危险：`EngineState.update()` 对 `q.price <= 0` 直接 `continue`，不会把旧缓存 B 明确改成“当前不可用”。

### 与 `spirit_order` 的集成缝隙

仓库已经有很好的规则级保护：`SpiritOrderRule._drop_stale()` 会把**本轮 Snapshot 中不存在**的代码从 `_prev` 删除；测试 `test_stale_code_cache_dropped_between_rounds` 也钉住了该语义。

但生产 Engine 恰好可能继续把 B 放进 Snapshot，于是 `_drop_stale()` 看不到“缺席”。随后 `_check_trades()` 会先执行：

```python
prev = self._prev.get(code)
self._prev[code] = (outer, inner, amount, volume, now_epoch)
```

再检查：

```python
if max_gap > 0 and now_epoch - p_epoch > max_gap:
    return []
```

所以 stale B 每轮被重新处理，会不断把 `_prev` 的时间刷新成当前轮。

### 反例：180 秒真实缺口被看成 5 秒

```text
10:00:00 B 最后一次真实观测
10:00:05 ~ 10:02:55 B 持续缺失，但缓存 B 每 5 秒进入 Snapshot
10:03:00 B 真正恢复，累计外盘明显增加
```

真实观测间隔：180 秒；`spirit_order` 的 `max_gap_seconds` 默认 120 秒，本应跳过差分。

由于旧缓存每 5 秒刷新 `_prev` 时间，恢复轮看到的 `p_epoch` 可能只有 5 秒前，长缺口保护被“洗短”。机制探针：`real_gap=180s`、`seen_gap=5s`，当前 gate 会继续进入差分阈值判断。

这说明旧缓存问题不只是“看板显示旧价”，还会破坏已有的差分安全阀。

### 修改方法

Engine 内明确分三层：

```text
latest_cache        # 最近已知值，只用于展示/诊断
round_observations  # 本轮实际返回且解析成功的观测
admitted_current    # 本轮通过时钟/质量/成员资格门控的观测
```

规则的 `Snapshot` **只**来自 `admitted_current`。旧值若用于看板必须带 `age/stale/current=false`，不能混入业务规则。

## 2.3 `IT-P2-OBS-001`：当前 live soak 看不见 soft-partial

源码：<https://github.com/fy-god/intraday-tape-reader/blob/f695102f8794b0b235d5f6ebf24564520d663ad8/tools/live_session.py>

`_soak_loop()` 当前逐轮记录：


其中：

# 3. `IT-P0-002` + `IT-P1-WINDOW-001`：时钟与窗口证据必须一起修

## 3.1 历史窗口能读到“未来点”

当前 `EngineState.window()`：

```python
cutoff = now_epoch - seconds
return [p for p in h if p[0] >= cutoff]
```

函数文档声称返回 `[now-seconds, now]`，实际只有下界，没有 `p[0] <= now_epoch`。

固定反例：历史含 `t=100` 与 `t=110`，查询 `now=105, seconds=20`，当前路径仍会返回 `t=110`。机制探针确认该点进入结果。

同时 `update()` 以处理时刻 `now.timestamp()` 写历史；`Quote.ts > now` 时只是 `pass`，而且发生在状态已经写入之后，不构成质量门控。

### 修复要求

- 在任何状态变更前统一时间归一化与准入；
- 区分 provider/event time、receive time、process monotonic time；
- `window()` 必须有上下界；
- 乱序旧包不能回滚 current state；
- 时间校验失败不能留下半写状态。

## 3.2 change-only 压缩导致真实横盘后跳变算不出

当前历史只在“价格或累计成交量变化”时 append。固定输入：

```text
t=0,5,10,...,60：每轮都有新鲜观测，price=10.0, volume=100
t=65：新鲜观测，price=10.3, volume=101
```

当前只保留 `(0,10.0,100)` 和 `(65,10.3,101)`。在 t=65 查询 60 秒窗口，cutoff=5，t=0 被排除，只剩 t=65，一个点无法算涨跌，得到 `None`。

但事实上 t=5...60 期间持续存在新鲜的 10.0 观测。这里缺的不是价格，而是“这个值一直被新鲜确认到什么时候”的证据。

### 本轮候选：有效观测区间压缩

不要简单“每 5 秒全存”，而是把连续相同、且均通过准入的观测压成：

```python
@dataclass
class ObservationInterval:
    first_observed_at: float
    last_observed_at: float
    price: float
    cum_volume: float
    source_epoch: str
```

同一连续性段、相同价格/累计量的新鲜观测只延长 `last_observed_at`；值变化或来源连续性变化才新增区间。

上述输入可压成：

```text
[0,60] price=10.0 volume=100
[65,65] price=10.3 volume=101
```

60 秒窗口左边界 5 秒落在第一个 interval 内，因此锚点是 10.0，涨幅约 +3%。

真正断线反例：若第一段只被确认到 t=0，之后直到 t=65 才恢复，则 `last_observed_at=0`，候选必须因 gap 超限拒绝，不能无限前填。

本轮在同一 Python 进程比较：

- current：change-only tuple history；
- candidate：interval-compressed admitted history。

参数：5563 symbols × 60 ticks × 3 reps；每组前 5 tick 不进分位；纯 Python 数据结构操作，不含真实仓库导入/网络/规则/Web。

`_check_side()`：

```python
if at_limit:
    self._state[tag] = "sealed"
    if prev == "sealed":
        return None
    return self._make_seal(...)
```

而 `_make_seal()` 之后才判断封单门槛：

```python
seal_wan = self._seal_amount_wan(q, rising)
if self.min_seal_wan > 0 and seal_wan < self.min_seal_wan:
    return None
```

### 确定反例

默认门槛 200 万：

```text
round 1：price == limit，封单 100 万
  _check_side 先 state = sealed
  _make_seal 因 100 < 200 返回 None

round 2：price 仍 == limit，封单增到 300 万
  prev == sealed
  直接 return None
```

预期是 round1 不报，round2 在“封单首次达到有效阈值”时产生一次封板事件。机制探针当前输出 `[None, None]`，期望 `[None, "seal"]`。

### 为什么现有测试没挡住

仓库测试分别覆盖：

- 封单低于阈值 → 不报；
- 封单高于阈值 → 报；
- 阈值边界；

但每个用例通常新建规则实例，没有覆盖“价格一直贴板、封单从不合格跨到合格”的**跨轮状态转移**。

### 修改建议

把“价格在限价”和“满足有效封板条件”分开：

```text
away
  -> at_limit_unqualified  # 价格到板，但封单不足
  -> sealed_qualified      # 封单首次达标，发 seal
sealed_qualified
  -> sealed_qualified      # 持续达标，不重复
  -> at_limit_unqualified  # 封单退坡（是否立即降级按定义）
  -> broken                # 价格离板
```

涨停与跌停镜像测试。

回归至少包含：100→300 万；300→300 持续不重复；300→100→300 是否允许重新触发要在合同里明确；价格离板后再封回继续保留原有“回封可重报”语义。

# 6. 主改造方案：Round Observation Contract v1

## 6.1 目标

建立从 provider 到 rule 到 soak 的统一“本轮观测”合同，修复以下同根问题：

- soft-partial 被当成功；
- 旧缓存冒充当前行情；
- stale 缺口被下游时间缓存洗短；
- 窗口缺覆盖证据；
- soak 用缓存 key 误当实时覆盖。

## 6.2 非目标

- 不通过此改造新增股票策略；
- 不把快照升级成逐笔数据；
- 不根据外盘增量声称“一笔大单”或机构身份；
- 不改变用户已有信号阈值来掩盖数据质量问题；
- 不以更少告警作为正确性证据。

## 6.3 数据合同

在不破坏冻结 v1 `Quote`/`Source.snapshots()` 公共签名的前提下，新增内部包装：

```python
@dataclass(frozen=True)
class BatchResult:
    request_id: str
    route: str
    source: str
    source_epoch: str
    requested_codes: tuple[str, ...]
    quotes: dict[str, Quote]
    explicit_unavailable: frozenset[str]
    unknown_missing: frozenset[str]
    complete: Literal["true", "false", "unknown"]
    elapsed_ms: int

@dataclass(frozen=True)
class ObservationDecision:
    code: str
    accepted: bool
    reason: str
    provider_ts: datetime | None
    received_at_utc: datetime
    process_mono_ns: int
    source: str
    source_epoch: str

@dataclass(frozen=True)
class RoundObservationSet:
    round_id: int
    requested: frozenset[str]
    admitted: dict[str, Quote]
    rejected: dict[str, str]
    explicit_unavailable: frozenset[str]
    unknown_missing: frozenset[str]
```

`latest_cache` 与 `RoundObservationSet.admitted` 明确分开。

## 6.4 时间合同

内部业务时间统一成明确的市场时间/UTC 转换，不依赖宿主机本地时区；至少维护：

```text
provider/event time
receive wall-clock UTC
process monotonic time
```

任何 freshness/out-of-order 判定在状态写入前完成。

## 6.5 窗口合同

用 interval-compressed admitted observations 保存“值 + 新鲜确认区间”。窗口需要：

1. 左锚点存在；
2. 锚点距离边界不超过容差；
3. 窗口内部最大有效观测 gap 不超过限制；
4. 不读取 `> now` 点；
5. 不跨 source epoch / unit version / trading-session discontinuity 做累计量差分。

窗口涨跌：

\[
R(t,W)=100\left(\frac{P(t)}{P_{anchor}(t-W)}-1\right)
\]

只有覆盖合同成立才返回数值，否则返回不可用原因，而不是静默 `None/0` 混在一起。

## 6.6 状态转移

规则状态建议统一最少语义：

```text
WARMUP -> ARMED -> FIRED -> HOLDING/COOLDOWN -> REARMED
                 \-> UNKNOWN (数据质量断裂)
```

`UNKNOWN` 不得等价于恢复状态；冷却时间到期也不等于市场条件已恢复。

## 6.7 起始配置（仅候选）

```yaml
observation_quality:
  mode: shadow
  max_age_seconds: 15
  max_future_skew_seconds: 2
  max_gap_seconds: 15
  unknown_missing_policy: reject_current
  fallback_fill_unknown_missing: true

window:
  storage_mode: admitted_intervals
  max_anchor_age_seconds: 10
  max_points_per_symbol: 360

coverage:
  warn_below: 0.995
  degraded_below: 0.98
```

这些是影子模式起点，不是已经验证的供应商 SLA。

## 6.8 迁移与回退

先影子计算新 `RoundObservationSet` 与新窗口，不替换生产告警；输出旧/新差异账本。通过固定重放后才切规则输入。发生异常可回到旧规则输入，但**不能**重新把未知缺失标成当前有效数据；至少要保留质量日志，避免“回退=恢复静默错误”。

# 8. 优先实验与备选假设

## EXP-IT-OBS-001 v2 — change-only vs admitted-intervals

### 假设

当前 change-only 历史同时存在两种错误方向：

- 静态/缺失缓存会制造伪连续；
- 新鲜但数值不变的观测被压掉，会丢覆盖证据。

`admitted-intervals` 同时保存“值”和“被新鲜确认到何时”，有机会同时降低两类错误。

### 对照

同一固定输入分别跑：

1. current change-only；
2. save-all-admitted（诊断上界，不作为首选生产方案）；
3. interval-compressed admitted。

矩阵必须含：quiet 横盘、横盘后跳变、真实断线、重复响应、乱序、future point、来源切换、午休、跨日。

### 淘汰条件

候选若出现任一情况就淘汰：

- 真断线被无限前填；
- 同秒合法修订被全部吞掉；
- 跨 source epoch 做累计差；
- active 场景内存/CPU 无法在真实仓库预算内接受；
- 为了通过测试而放松 freshness 阈值。

## 备选 A — Missing-code fill only

只在 SourceManager 做缺码补洞，不改窗口表示。若它能消除绝大多数 stale-current 但仍留 WINDOW-001，则只作为第一阶段，不视作完整解决。

## 备选 B — Full admitted ring

每个有效观测全存，作为正确性 oracle。若 interval 实现复杂或出现边界争议，先用 full ring 建立重放真值，再优化压缩表示。
