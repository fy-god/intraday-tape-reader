## 1. 已确认错误

### 1.1 IT-P1-007 —— 故障转移的失败计数被小额指数请求清零

**位置**

- `src/arad/engine.py:188` `class SourceManager`
- 旧 `SourceManager.call()`：`self.fails` 单个全局计数器
- 调用点：`src/arad/engine.py:519`（指数路由）、`src/arad/engine.py:751`（个股路由）

**触发条件**

一轮 `poll_once()` 会依次发出两类 `snapshots` 请求：先是全市场几千只的个股请求，
再是只含 `index_codes` 那几只的指数请求。只要主源「大请求失败、小额指数请求成功」
（限流/超时按批量走时非常常见），旧实现就会：

1. 个股请求：主源失败 -> 备用源顶上 -> `self.fails += 1`
2. 指数请求：主源成功 -> `self.fails = 0`（**清零**）

**机制**

旧 `call()` 里计数器没有任何「路由」维度：

```python
if i == self.idx:
    self.fails = 0          # 任一路由在主源上成功，就清零全局计数
else:
    self.fails += 1
```

指数请求成功走的就是 `i == self.idx` 分支，于是把个股链路攒下的失败计数一并清掉。

**影响**（严重，且是"静默"型）

- 个股数据**一直由备用源提供**，但 `health()` 里 `h["active"]` 始终指向主源 ——
  看板得出的结论与事实相反。
- `threshold` 永远达不到，**正式切换永不发生**。
- 主源每轮都被白试一次，延迟照付（实测复现中一轮 100 只的请求每次都先打主源）。
- 备用源长期承压却始终是"备用"，主源一旦真的整体挂掉，系统已在错误状态下运行很久。

**复现证据**（修复前，真实代码非 mock；`threshold=3`）

```
轮次   stocks(100)        indices(1)        fails  current
 1    fail->backup       primary ok        1 -> 0     primary
 2    fail->backup       primary ok        1 -> 0     primary
 3    fail->backup       primary ok        1 -> 0     primary
✗ fails 每轮被指数请求清零，current 永远是 primary
  primary 收到的失败大请求次数 = 3（每轮都重试，延迟白付）
  health() 显示: [('primary', True), ('backup', False)]
  -> active 指向 primary，但股票数据其实一直由 backup 提供
```

**修复**

`SourceManager` 的失败计数改为**按路由分账**（`src/arad/engine.py:191-193` 定义
`ROUTE_STOCKS` / `ROUTE_INDEX` / `ROUTE_UNIVERSE`）：

- `self._fails: dict[str, int]`、`self._serving: dict[str, int]` 取代 `self.fails`
- `call(method, *args, route=None)`，缺省 `route = method`（向后兼容，老调用点行为不变）
- `engine.py:519` 指数请求传 `route=ROUTE_INDEX`；`engine.py:751` 个股传 `route=ROUTE_STOCKS`；
  `engine.py:608` 股票池传 `route=ROUTE_UNIVERSE`
- `fails` 保留为**只读属性**（各路由求和），旧测试与看板不受影响
- 新增 `fails_by_route` / `serving_of()` / `route_health()`；`health()` 每条新增
  `serving_routes` 字段，如实反映「谁在真正供数」

**验收测试**（`tests/test_engine.py`）

- `test_source_manager_fails_are_tracked_per_route` —— 用 `SizeSensitivePrimary`
  （`len(codes) > 50` 则失败、小额成功）如实重现真实场景，断言 3 轮后**必须切换**
- `test_route_accounting_keeps_primary_attempts_down` —— 断言切换前主源只被尝试
  `threshold` 次，切换后不再回头试主源大请求
- `test_source_manager_route_specific_counter_isolated` —— 两路由计数互不影响
- `test_source_manager_default_route_is_method_name` —— 缺省按方法名分账（兼容性）
- `test_source_manager_health_reports_serving_routes` —— `serving_routes` 正确

**修复后回归**：5 条全绿；把 `route = route or method` 回退为恒等值（恢复"共用一个
计数器"的旧语义）后，上述 5 条**全部变红** —— 测试确实有牙（见 §5）。

### 1.2 IT-P1-006 —— `universe()` 部分成功 + 只判空，静默缩小股票池

**位置**

- `src/arad/engine.py:588` `refresh_universe()`
- `src/arad/sources/sina.py:375` `SinaSource.universe()`（分页中途失败返回前缀）
- `src/arad/sources/eastmoney.py:314` `EastmoneySource.universe()`（少页同样返回部分）

**触发条件**

新浪 `universe()` 在翻页途中某页失败时，**保留已拿到的部分并正常返回**（这是有意
设计：整轮报废更糟）。东财被限流时也会少几页。此时旧 `refresh_universe()` 只判断
「非空」就采用：

```python
if not quotes:
    continue
codes = self._record_universe(quotes)
if codes:
    self._codes_raw = codes      # 直接覆盖
    ...
    return len(codes)
```

**机制**

「返回条数」与「是否拿全」是两件事，旧代码只有前者。部分结果与完整结果在类型上
完全无法区分：都是 `list[Quote]`，都非空。

**影响**（严重）

- 已有一轮拿到的 **5563 只**完整池，会被下一轮的 **3000 只**部分池**静默覆盖**。
- 丢掉 2563 只股票 —— 这些票**永远不会再产生告警**，而系统**记为"刷新成功"、
  不报任何错**。这是最难发现的一类故障：看板一切正常，只是漏掉一半股票。
- 更糟的是它可能反复发生（每轮都缩一点），且反向无法自愈（部分结果更小 -> 继续缩）。

**复现证据**（修复前，真实代码）

```
完整旧池 5563 -> 被 partial 的 3000 覆盖
✗ 静默丢掉 2563 只股票，且被视为"刷新成功"
```

**修复**

引入**完整性元数据**，三层配合：

1. `SinaSource.universe()`（`sina.py:375-457`）—— 记录 `_last_universe`：
   `complete` / `pages_failed` / `pages_ok` / `pages_requested` / `returned` / `reason`。
   用 `for...else` 区分「翻到空页正常收尾」与「翻满上限被截断」——**后者也是不完整**，
   这种"不是失败的失败"最危险（返回几千只、看着很成功，其实只是全市场的前缀）。
   第 1 页即失败时也写入不完整元数据再抛错。
2. `universe_info()`（`sina.py:459`、`eastmoney.py:366`）—— 契约之外的诊断接口。
3. `Engine.refresh_universe()`（`engine.py:588`）改为：
   - 完整结果立即采用；
   - **不完整结果只作兜底候选，继续往后试**（旧实现会终止链条，后面的完整来源
     永远拿不到机会）；
   - 所有来源都不完整时取**最大**的候选，且**若比现有池更小则拒绝覆盖**并返回 0；
   - 来源未实现 `universe_info`（如腾讯）时按完整处理，不因缺元数据就拒绝。

同时把 `_record_universe` 的代码提取部分抽成**纯函数** `_extract_codes`
（`engine.py:688`）：候选比较阶段不写 `state.universe`，避免被拒绝的部分结果留下痕迹。

**验收测试**（`tests/test_engine.py`、`tests/test_sources_sina.py`）

- `test_universe_partial_result_does_not_shrink_existing_pool` —— 5000 只现有池 +
  3000 只部分结果 -> 必须拒绝并保持 5000
- `test_universe_prefers_complete_over_partial` —— 断言调用序列确实是
  `["sina", "eastmoney"]`（部分结果后继续找完整的）
- `test_universe_partial_smaller_than_complete_earlier_in_chain` —— 兜底取最大候选
- `test_universe_partial_result_is_used_when_it_is_larger` —— 更大时允许采用（可自愈）
- `test_universe_meta_is_recorded_on_success` / `..._without_meta_is_treated_as_complete`
- 新浪侧 5 条：翻到底 -> `complete=True`；中途失败 / 翻满上限 / 首页失败 ->
  `complete=False`；坏一轮后成功要能回到 `complete=True`

**修复后回归**：全绿；把 `if not meta.get("complete", True):` 短路为 `if False:`
（恢复"非空即采用"的旧语义）后 3 条变红；把新浪的
`complete = ended_clean and not failed_pages` 改成 `complete = True` 后另 3 条变红 ——
两侧都有牙（见 §5）。

## 3. 研究想法（可证伪，1–3 条）

1. **指数路由是否也应有独立的「切换」而不仅是独立的计数？**
   本轮只把计数分账，`idx`（主源下标）仍是全局唯一的。若"个股走备用源、指数走主源"
   长期稳定，全局 `idx` 会在个股路由触发切换时把指数路由一起搬走 —— 而指数在主源上
   本来是好的。
   *证伪方式：构造"个股大请求失败、指数小额成功"的主源，跑 3 轮后断言指数路由仍然
   由原主源服务；若被一并搬走，说明需要 per-route 的 `idx`。*
2. **`pages_ok`/`expected_total` 这类完整性指标是否应进入 `/api/status` 看板？**
   目前 `_universe_meta` 只记在引擎内存里，外部看不到。
   *证伪方式：给 `/api/status` 加字段后，构造部分成功场景，断言接口能反映
   `complete=false`；若无法反映，说明该指标对运维不可见、价值有限。*
3. **`threshold` 的默认值 3 是否对"按路由分账"后仍然合理？**
   分账前个股链路几乎永远达不到 3（被清零）；分账后变得容易达到，可能更频繁切换。
   *证伪方式：用真实行情日志回放，对比分账前后一天内的切换次数；若切换过于频繁
   （比如十几次），说明阈值或需要滞回机制。*

## 6. 本轮踩到的坑（如实记录）

1. **我第一版 IT-P1-007 测试没有牙。** 最初用 `FakeSource(fail_times=99)` 做"主源"，
   它对**所有**方法都失败，所以指数请求也失败、计数照样会累加 —— 旧代码在这组数据下
   也能通过。必须用 `SizeSensitivePrimary`（按请求批量大小决定成败）才能如实重现
   "大请求失败、小额指数成功"这一真实场景。**这是本轮最重要的自我纠正。**
2. **两个测试前提是我自己写错的**，不是代码错：
   - `assert primary.served == [1, 1, 1]` —— 第 3 轮切换发生在个股请求之后，
     此时 `backup` 已是主源，指数请求直接由 `backup` 服务，所以是 `[1, 1]`。
     这个"少一次"恰好证明切换真的生效了，已写进注释。
   - `route_specific_counter_isolated` 里用 `FakeSource(fail_times=99)` 当主源，
     它在 `universe` 上也失败，导致 `index` 路由计数也是 1。改成只让
     `snapshots` 失败的 `FailsSnapshots` 才符合测试本意。
3. **`python -m arad selftest` 不是正确入口**，会报
   `No module named arad.__main__`。正确写法是 `python -m arad.cli selftest`
   （README 第 64 行即如此）。
4. **性能类测试前必须先查僵尸 python 进程。** 本机历史上两次因此误判性能回归
   （6–7 个残留进程把 CPU 打满）。本轮跑全量前确认只有 1 个 1MB 的闲置进程。
5. 幂等性提醒：`selftest` 的告警条数**不确定**（68–72），不可引用固定值；
   本轮为 69。
