### 2.1 `IT-P1-WALLCLOCK-BOUND-IS-A-CORRECTNESS-GATE-001`（`已确认错误`，P1，**缺陷类，本轮扩面**）

> **与既有台账的关系**：`LATEST.md:62` 已登记 `IT-P1-SUITE-TIMING-ASSERTION-NONDETERMINISTIC-001`（「同一源码树完整 pytest 3 次出现 1 红 / 2 绿」）。本轮**不新建同类 ID**，而是对**同一条**做两件事：(a) 该 ID 的**「非确定性」措辞本轮未复现**（§2.5-1），予以降级；(b) 其**底层缺陷类**（墙钟上界当正确性门）**由 1 处扩面到 3 处**并给出实测余量。`LATEST.md:81` 的产品自述「默认 pytest 去掉 tight wall-clock correctness gate，性能另跑 benchmark」**与本条修复建议一致**，故这是一个**双方已有共识、尚未落地**的项。

- **文件 / 函数 / 行**（三处，AST 枚举，非目视）：
  - `tests/test_rule_limit_board.py:1212` — `assert elapsed < 0.2, f"evaluate 太慢: {elapsed*1000:.1f}ms"`（在 `:1175 test_performance_1000_stocks`）
  - `tests/test_rule_tick_surge.py:556` — 同一断言形状（在 `:539 test_performance_1000_stocks`）
  - `tests/test_daemon_attribution.py:117` — `assert dt < 3.0, f"child 已死却等了 {dt:.1f}s，应立刻返回"`
- **触发条件 / 反例**：断言左侧是 `time.perf_counter()` 差值，右侧是**与代码正确性无关的绝对墙钟上界**。测量到的耗时取决于当时机器的调度、GC、温度和并发。上一轮已观测到一次 214.3 ms。
- **机制**：性能上界被当作**正确性门**。它与被测代码的正确性**没有任何因果关系**——`evaluate()` 返回的 `800` 条告警数正确与否，与它耗了 30 ms 还是 214 ms 无关。
- **影响**：整套 pytest 的退出码会被一次环境停顿翻转，进而**污染所有以退出码为证据的结论**（包括上一轮自己的 1802/1830 计数）。
- **本轮实测的余量（这才是定级依据）**：

| 断言 | 中位 | 最大（60 样本） | 上界 | 余量 |
|---|---|---|---|---|
| `test_rule_limit_board.py:1212` | **31.566 ms** | 35.060 ms | 200 ms | **6.34x** |
| `test_rule_tick_surge.py:556` | **5.621 ms** | 6.913 ms | 200 ms | **35.58x** |
| `test_daemon_attribution.py:117` | 未计数 | 未计数 | 3000 ms | 未计数 |

- **修复建议**：(a) 把这三处**移出**正确性套件，另设 `-m perf` 标记、默认不选；或 (b) 保留但改为**多轮取中位数**并显式标注「性能测试，允许抖动」；或 (c) 把上界放宽到与中位数成数量级关系（如 `median*10`）。
- **验收测试**：断言套件在**注入一次 250 ms 停顿时仍然绿**（对正确性门而言这是必须的），或明确把这些用例排除在「正确性退出码」之外。

> **对上一轮结论的修正**：上一轮把这**一整条**的 headline 定为「整套 pytest 其实是随机门」，并给出机制「超出仅 7.2%」。以我实测的 6.34x 余量看，**「7.2% 薄余量」这个机制是错的**：214.3 ms 是约 6.8 倍的环境性停顿。**「墙钟不能当正确性门」这个结论成立且被我扩面到 3 处**；但「随机门」这一描述我**未复现**（§3.1）。
