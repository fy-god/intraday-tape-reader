## 3. 本轮新增确认：IT-P1-CAPABILITY-001 — 配置中的 Tencent→Sina failover 会静默让默认启用的 `volume_burst` 失去可评估能力

**级别：P1。状态：本轮新增确认，未修。**

### 3.1 证据链

主配置明确设置：

```yaml
sources:
  primary: tencent
  fallback: [sina]
```

同时 `volume_burst.enabled: true`，默认 `min_turnover: 0.5`。

Tencent parser 会提供 `turnover`、`volume_ratio`、五档、内外盘；Sina parser 则明确把：

```python
turnover=0.0
volume_ratio=0.0
```

作为“源不提供该字段”的占位。`VolumeBurstRule.evaluate()` 对量比做了“缺失时跳过门槛”的特殊处理：

```python
vr = q.volume_ratio
if vr_thr > 0 and vr > 0 and vr < vr_thr:
    continue
```

但换手率没有 capability 语义，直接：

```python
if min_turnover > 0 and q.turnover < min_turnover:
    continue
```

于是同一行情状态下，只要从 Tencent 正式/热备切到 Sina：

```text
Tencent equivalent: turnover=1.2% -> 可继续计算，speed_ratio=6.0
Sina equivalent:    turnover=0.0  -> 在 turnover gate 被静默拒绝
```

本轮 `capability_probe.py` 对同一 market state 的控制流复现结果正是：Tencent/Eastmoney 等效样本通过，Sina 等效样本在 `turnover` 门槛失败。

### 3.2 为什么不是单纯“字段少一点”

这是**默认启用规则的系统性覆盖损失**：SourceManager 可以认为 Sina 调用成功，整体 health 也可以继续正常，而 `volume_burst` 在 Sina 服务期间对所有股票都因 `turnover=0` 被提前过滤。系统不会告诉用户“放量规则当前不可评估”，只会表现为这类告警突然消失。

`spirit_order` 也存在更严重的 capability 差异，但它默认关闭：Tencent 填五档与内外盘；Sina 只有买一/卖一价量，不填五档 tuples 和内外盘；Eastmoney 快照路径连买一/卖一都置 0。`spirit_order` 的五档 wall 明确要求 `q.has_depth`，成交类又依赖 `outer_vol/inner_vol`，所以将来启用时必须有 source capability contract，而不是把 0 当真实业务值。

### 3.3 根因

`Quote` 是冻结业务模型，但当前没有 sidecar 来区分：

```text
numeric zero
vs
field unavailable from provider
```

不同 source 用相同 `float=0.0` 承载两种语义。规则只能猜。

### 3.4 推荐修法

不要直接把冻结的 `Quote.turnover: float` 改成 Optional；优先在 Round Observation Contract 增加 sidecar：

```python
SourceCapabilities(
    turnover: bool,
    volume_ratio: bool,
    depth_l1: bool,
    depth_l5: bool,
    outer_inner: bool,
    float_cap: bool,
    provider_ts: bool,
)

ObservationDecision(
    code,
    source,
    source_epoch,
    capabilities,
    admitted,
    reject_reason,
)
```

规则再声明要求：

```python
VolumeBurstRule.required = {
    'turnover': 'required_if_threshold_enabled',
    'volume_ratio': 'optional_skip_gate',
    'amount': 'required',
    'cum_volume': 'required',
}
```

**第一阶段不要擅自“缺 turnover 就跳过门槛”**，那会改变误报率。先把 `evaluable / unavailable_capability / evaluated_no_hit / hit` 四态显式化，soak 与看板能看到规则覆盖率；之后再用真实数据决定某字段缺失时是关闭规则还是走降级口径。

回归用例至少包含：同一行情对象分别带 Tencent/Sina/Eastmoney capability；断言规则不是静默 `0 alerts`，而是产生明确 `unavailable_capability` 计数；恢复 Tencent 后恢复 evaluable。

## 4. 继续开放的高优先级问题

### IT-P0-002 — future/out-of-order 仍可污染状态

`EngineState.window()` 的文档说返回 `[now-seconds, now]`，实现却只过滤 `p[0] >= cutoff`，没有 `p[0] <= now_epoch`。`EngineState.update()` 又是先把 quote 写进 `quotes/history`，之后遇到 `q.ts > now` 只执行 `pass`。因此“提供商时间质量”仍没有写前准入。

建议下一步不是只补 window 上界，而是把 provider event time / receive time / monotonic process time 放进统一 admission，先判再写。

### IT-P0-001 — 14:57–15:00 仍归入连续竞价

当前 `SessionPhase.AFTERNOON` 覆盖 `13:00-15:00`，且属于 `CONTINUOUS`。SSE 与 SZSE 官方当前股票交易时段均明确：连续竞价下午到 14:57，14:57–15:00 是收盘集合竞价。需要新增/兼容 `CLOSE_AUCTION` 语义并由规则声明是否支持。

### IT-P1-SOURCE-EMPTY-001 — soft-partial 仍无 requested-vs-returned 合同

三家指定代码抓取都可能出现“HTTP 成功但返回代码集合不完整”。没有 `requested/returned/explicit_unavailable/unknown_missing`，上层无法知道需不需要向备用源补洞。

### IT-P1-WINDOW-001 — change-only history 删除“新鲜横盘”证据

只有价格/累计量变化才 append history，会把持续新鲜但数值不变的观测压缩掉；60 秒横盘后 65 秒急跳时，窗口 anchor 可能落在被压缩掉的区间，导致 `price_change=None`。

建议仍采用 `ObservationInterval(first_observed_at,last_observed_at,value,source_epoch)`，而不是无限保存每个重复数值点。

### IT-P1-LIMIT-001 / IT-P1-006-R1 / IT-P2-OBS-001 / SSE 系列

这些问题本轮没有产品代码变化，状态保持开放；下一轮应在真实 checkout 里迁成红测，不再重复同构片段。

## 6. 新训练：capability-dropout HGB

沿用上一轮**已经在旧 tune 选定**的 HGB 超参作为固定基线，不用新锁箱调参：

```text
max_iter=80
learning_rate=0.04
max_leaf_nodes=15
l2_regularization=0.1
```

新增唯一训练变体 `capability-dropout`：只在旧 train 内复制一部分样本，模拟 Sina/Eastmoney 的缺字段模式；20% 复制为 Sina capability、12% 复制为 Eastmoney capability，缺失盘口因子按训练集统计处理并设置 missing-depth 标志。新锁箱从未用于选择或训练。

结果：

| 模型 | 场景 | ROC AUC | PR AUC | LogLoss | Brier |
|---|---|---:|---:|---:|---:|
| base | clean lockbox | 0.6732 | 0.6790 | 0.6418 | 0.2255 |
| base | provider shift | 0.6442 | 0.6479 | 0.6570 | 0.2325 |
| capdrop | clean lockbox | 0.6687 | 0.6758 | 0.6446 | 0.2267 |
| capdrop | provider shift | **0.6605** | **0.6632** | **0.6489** | **0.2287** |

观察：base 在来源能力漂移后 PR AUC 从 0.6790 降到 0.6479（下降 0.0311）；capability-dropout 在 clean 上略退化，但 provider-shift PR AUC 提升到 0.6632，相对 base shift 增加 0.0153。

这是**合成来源漂移实验的正向信号**，不是实盘有效性。它支持下一步在真实数据上保留 capability-aware augmentation 对照，但不能直接部署。

## 7. 负结论一：旧 calib 上的 Platt / Isotonic 在新锁箱反而更差

模型仍由旧 tune 选择，校准器只用旧 calib 拟合。新锁箱结果：

| 场景 | 校准 | LogLoss | Brier | ECE10 |
|---|---|---:|---:|---:|
| clean | raw | 0.6418 | 0.2255 | 0.0218 |
| clean | Platt | 0.6460 | 0.2271 | 0.0437 |
| clean | Isotonic | 0.6532 | 0.2282 | 0.0486 |
| provider shift | raw | 0.6570 | 0.2325 | 0.0218 |
| provider shift | Platt | 0.6676 | 0.2366 | 0.0579 |

结论：**当前 synthetic 条件下不要把 Platt/Isotonic 作为默认改进。** 两者在新锁箱上同时恶化 Brier/ECE；真实数据必须重新独立校准，校准失败就保留 raw score。

## 8. 负结论二：事件阈值策略没有提升事件 Precision，暂不采用

为了避免每 5 秒候选行被当独立事件，本轮按 `symbol/day/direction` 和 60 秒连续间隔聚为事件簇。19,458 个候选行被压成 1,242 个事件簇，说明行级样本依赖非常强，不能把 19k 当 19k 个独立事件。

阈值只在旧 tune 事件簇上选择，得到约 0.407。应用到新锁箱：

- clean：864 个发布事件，Precision 0.4606、Recall 0.6910；
- provider-shift：816 个发布事件，Precision 0.4620、Recall 0.6545。

按反推，事件簇自身正例率约 46.4%，所以这个阈值**没有带来有意义的 Precision 提升**。本轮将其判为淘汰候选，不接 shadow 发布政策；后续只保留 raw score 与 capability 状态。

## 11. 主改造：Capability-aware Round Observation Contract

本轮把主改造从“current-only Snapshot”进一步推进为：

```text
raw provider response
  -> BatchResult(requested/returned/missing)
  -> SourceCapabilities
  -> ObservationDecision(time/source/capability admission)
  -> RoundObservationSet(admitted_current)
  -> feature/rule evaluability
  -> rule/model result + coverage accounting
```

关键 schema：

```python
BatchResult:
    requested_codes
    returned_by_code
    explicit_unavailable
    unknown_missing
    source
    source_epoch

SourceCapabilities:
    turnover
    volume_ratio
    depth_l1
    depth_l5
    outer_inner
    float_cap
    provider_time

RuleEvaluationStatus:
    evaluable
    unavailable_capability
    rejected_quality
    evaluated_no_hit
    hit
```

核心不变量：

1. `Snapshot_t = admitted_current_t`；
2. `numeric 0 != unavailable field`；
3. source 切换时 capability 变化必须进入 observability；
4. source/capability epoch 变化不能直接串接累计量；
5. 研究模型的 feature mask 必须由真实 capability 产生，而不是事后猜缺失。

4. 真实 `dataset_manifest.json`，至少明确可用股票/交易日/采样间隔/字段能力，即使不足 30×20 也必须量化；
5. 真实因子 capability mask；
6. 若真实数据足够，只先跑 HGB base vs capability-dropout，TCN 暂不扩网；
7. committed/sent/received/applied SSE 对账继续推进。

本轮最重要的新结论不是“模型分数又高了一点”，而是：**当前系统缺的不是单一 source failover，而是 source capability failover。数据源调用成功并不等于规则仍有能力评估；工程 observability 与研究 feature mask 必须共享同一份 capability contract。**
