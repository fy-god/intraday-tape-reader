## 0. 结论

项目的工程基础比普通“几条 if 规则”完整得多：三数据源、故障转移、状态窗口、规则去重、SSE 看板、离线 replay、真实盘中短跑记录以及大量回归测试都已经存在。尤其 `spirit_order` 已经明确承认快照增量不是逐笔成交，默认也关闭，这个边界是正确的。

但本轮在固定源码上确认了几类会直接改变告警语义的实质问题：

1. **收盘集合竞价 14:57–15:00 被代码当成连续竞价**，所有 `only_continuous` 规则都有机会在错误市场机制下运行。
2. **行情源自带时间戳虽然被解析，却没有真正参与 freshness / 乱序门控**；`EngineState.update()` 的“未来时间戳忽略”分支实际上只有 `pass`，旧行情仍以当前轮询墙钟写入窗口。
3. **主源/备用源切换会污染依赖累计量差分的状态规则**。默认 Tencent -> Sina 热备时，Sina 没有 `outer_vol/inner_vol`，缓存会被写成 0；下一轮 Tencent 恢复后，全天累计外/内盘可能被当成一个轮询区间增量。
4. **SSE 断线重连没有可靠的增量补账协议**。客户端注释写“重连后补齐”，但 `EventSource.open` 只 `touch()`；服务端订阅队列满时会丢最旧事件，也没有 `event id / Last-Event-ID`。
5. **分时序列字典存在长期增长路径**：`_series_codes` 会淘汰代码，但 `_series` 不同步删除旧代码。
6. 另有两个次级契约错误：`tick_surge.max_per_round=0` 文档说“不限量”，实际最多取 1 条/方向；replay 注入时钟没有贯穿到 `AlertStore.status()`。

这几项优先级高于继续增加新的“短线精灵”规则。先把市场时钟、事件时间、数据源能力与端到端事件账本做对，后面的阈值优化才有意义。

# 2. P0：必须先修的正确性问题

## IT-P0-001：14:57–15:00 收盘集合竞价被误判为连续竞价

### 代码位置

固定提交：`f8dcbdd80c7b647df7e8ef7d28a59e2a91a0922b`

`src/arad/session.py`：`CONTINUOUS`、`TradingCalendar.phase()`。

当前核心逻辑：

```python
CONTINUOUS = (SessionPhase.MORNING, SessionPhase.AFTERNOON)
_T_AFTERNOON_START = time(13, 0)
_T_CLOSE = time(15, 0)
...
if t < _T_CLOSE:
    return SessionPhase.AFTERNOON
```

所以 `14:57:00 <= t < 15:00:00` 会进入 `AFTERNOON`，进而被视为 `CONTINUOUS`。

但上交所、深交所当前官方交易时间都明确：

- 连续竞价：13:00–14:57
- 收盘集合竞价：14:57–15:00

官方来源：

- SSE Trading Hours: https://english.sse.com.cn/start/trading/schedule/
- SZSE Trading Overview: https://www.szse.cn/English/services/trading/tradOverview/

### 触发条件

任意交易日 14:57–15:00，启用了默认 `only_continuous=true` 的规则，例如 `tick_surge`、`spirit_order`、`spirit_price`。

### 影响

集合竞价和连续竞价的成交/委托形成机制不同。把 14:57 后的快照继续输入“急拉”“盘口增量”“加速度”等连续竞价逻辑，会制造语义错误：规则认为是在连续撮合中观测到的速度/主动量变化，实际处在收盘集合竞价阶段。

### 修改方案

不要把 14:57–15:00 粗暴当 POST；建议新增稳定语义：

```python
class SessionPhase(...):
    CLOSE_AUCTION = "close_auction"

CONTINUOUS = (MORNING, AFTERNOON)

13:00 <= t < 14:57 -> AFTERNOON
14:57 <= t < 15:00 -> CLOSE_AUCTION
15:00 <= t          -> POST
```

引擎仍然可以在 `CLOSE_AUCTION` 抓行情、更新状态、展示看板；但 `only_continuous` 规则自动停用。以后如果需要专门的收盘竞价信号，单独声明支持 `CLOSE_AUCTION`，不能偷偷复用连续竞价阈值。

### 回归验收

至少新增边界测试：

| 时间 | 预期 phase | `only_continuous` 规则 |
|---|---|---|
| 14:56:59 | AFTERNOON | 可运行 |
| 14:57:00 | CLOSE_AUCTION | 不运行 |
| 14:59:59 | CLOSE_AUCTION | 不运行 |
| 15:00:00 | POST | 不运行 |

并验证 SSE/SZSE 股票一致。模块顶部“收盘集合竞价（深市）”的旧注释也要同步改掉，上交所股票同样有收盘集合竞价。

## IT-P0-002：行情事件时间没有真正门控，陈旧/乱序行情会被当“现在”写入滑窗

### 代码位置

`src/arad/engine.py`，`EngineState.update()`：

```python
ep = now.timestamp()
...
h.append((ep, q.price, q.volume_lots))
...
if q.ts is not None and q.ts > now:
    pass  # 行情时间戳超前（时钟偏差），忽略
```

`q.ts` 已经由数据源解析：

- Tencent：字段 idx30 `YYYYMMDDHHMMSS`
- Sina：日期字段 + 时间字段
- Eastmoney：`f124`

但 Engine 最终把每条行情的历史时间统一写成**本地轮询时的 `now`**。

### 触发条件

- 数据源缓存返回几秒/几十秒前的旧行情；
- 网络重试后拿到旧响应；
- 数据源时间戳回退；
- 本机时钟与行情时间有偏差；
- 未来时间戳进入代码时，当前 `if ...: pass` 实际没有丢弃这条 Quote。

### 影响

`tick_surge.price_change()`、量能速度、窗口覆盖等全部按 ingestion wall-clock 计算。旧行情一旦被重新盖上“当前时间”，就可能让 60/180/300 秒窗口的速度判断失真；乱序行情也可能造成价格先后关系反转。

这是实时预警系统的核心正确性问题，而不只是日志美观问题。

### 修改方案

在 `Engine.poll_once()` 进入 `state.update()` 前增加统一 freshness gate，不要让每个规则自己处理：

```text
Quote source event_ts
      ↓
统一转换 Asia/Shanghai aware datetime
      ↓
检查 future_skew / age / per-code monotonicity
      ↓
accepted / stale / future / out_of_order
      ↓
只有 accepted 进入状态与规则
```

建议新增配置（起始值只是工程默认，不是已证明最优阈值）：

```yaml
poll:
  max_quote_age_seconds: 15
  max_future_skew_seconds: 3
```

并保存两种时间：

- `event_ts`：数据源行情时间；
- `ingest_ts`：本机收到时间。

窗口规则优先使用 event time；延迟监控使用 `ingest_ts-event_ts`。

同时不要依赖“机器时区刚好是 CST”。`config/settings.yaml` 已写 `Asia/Shanghai`，实现应真正用 `zoneinfo.ZoneInfo("Asia/Shanghai")`，否则部署到 UTC、日本或容器默认时区时，交易时段和 Eastmoney `datetime.fromtimestamp()` 都可能偏移。

### 回归验收

人工离线场景：

1. 当前 10:00:10，输入 `q.ts=09:59:30`，不得作为 10:00:10 新点进入 60 秒急拉窗口。
2. `q.ts` 比上一个同股已接受时间更早，拒绝并计 `out_of_order`。
3. `q.ts=now+10s`，超过 future skew 时拒绝。
4. 改系统环境时区后，同一行情 timestamp 得到相同北京时间 phase。

运行期增加 `quote_age_ms p50/p95/p99`、stale/out_of_order 比率；性能报告必须同时附数据新鲜度，单看 poll_ms 不够。

# 3. P1：高概率造成假告警、漏告警或长期运行问题

## IT-P1-001：主/备用源切换污染累计量差分，可能把全天量当“一轮增量”

### 代码证据

默认配置：

```yaml
sources:
  primary: "tencent"
  fallback: ["sina"]
  failover_threshold: 3
```

`src/arad/engine.py::SourceManager.call()` 会在 Tencent 当前请求失败时直接调用 Sina 返回本轮数据，但没有把“本轮实际由谁提供”传给规则，也没有触发状态重新基线。

`src/arad/rules/spirit_order.py::_check_trades()`：

```python
prev = self._prev.get(code)
self._prev[code] = (outer, inner, amount, volume, now_epoch)
...
if volume < p_volume or outer < p_outer or inner < p_inner:
    return []
...
d_outer = outer - p_outer
```

而 `src/arad/sources/sina.py::parse_response()` 没有 `outer_vol / inner_vol / depth / float_cap` 字段，这些保持 Quote 默认值 0。

### 可构造的确定反例

1. `t0`: Tencent 正常，某股 `outer=120000手`，缓存为 120000。
2. `t1`: Tencent 单轮失败，热备 Sina 成功；Sina `outer=0`。代码先把 `_prev` 写成 0，再发现累计量回退并跳过。
3. `t2`: Tencent 又恢复，真实累计 `outer=120500`；这时相对 `_prev=0`，代码看到 `d_outer=120500手`，可能把几小时累计量当成 5 秒区间量。

`spirit_order` 默认关闭，所以默认配置不会立即触发此错误；一旦用户按照 README 开启，这条路径就存在。

### 修改方案

需要一个**数据源 provenance / capability 契约**，不要靠规则猜字段是否可信。

最小侵入版本：

```text
SourceManager.last_served_source
SourceManager.source_epoch  # 实际服务源变化时 +1
EngineState.source_name/source_epoch/capabilities
```

能力例如：

```text
outer_inner_cumulative
orderbook_l5
float_cap
actual_limit_price
source_event_ts
```

`spirit_order` 只有在 `outer_inner_cumulative=true` 且 `source_epoch` 未变化时才做相邻差分；源变化后第一帧只 re-baseline，不发成交类信号。盘口类也只在 `orderbook_l5=true` 时使用五档语义。

### 回归验收

离线三帧剧本：Tencent -> Sina -> Tencent。第三帧不得出现由 0 基线导致的 `big_buy/institution_eat`。再连续给第二个 Tencent 新帧，只有第二个同源区间的真实增量可以触发。

这个测试必须放在 source failover + spirit_order 集成层，不要只单测各自模块。

## IT-P1-002：SSE 自动重连后没有可靠补账，短时断线可能漏告警

### 代码位置

`src/arad/store.py`：每个订阅者队列 `maxsize=200`，满时**主动丢弃最旧事件**以保护行情线程。

`src/arad/server/dashboard.html::connect()`：

```javascript
es.addEventListener("open", function(){ touch(); });
...
es.addEventListener("error", function(){
  setConn(false, "连接异常·重连中");
});
```

注释写“首屏/重连后补齐历史告警”，但 `open` 回调并没有调用：

```javascript
loadRecentAlerts();
loadSpirit();
```

这两个函数只在页面启动和 `visibilitychange -> visible` 时调用。页面一直可见、EventSource 自动断线重连时，不会主动补回断线期间的历史。

服务端 SSE 也没有输出 `id:`，客户端没有 `Last-Event-ID` 的恢复点。

### 影响

- 短时 SSE 断线期间产生的告警可能只留在 `AlertStore`，不会自动补到可见页面；
- 新订阅是新 queue，只能收到重连后的未来广播；
- 队列溢出时丢旧事件也没有 dropped counter / gap 指示。

README 的一次 12 分钟“未断流”不能证明更长运行或网络抖动下没有丢事件。

### 修改方案

短期修复：`EventSource.open` 在首次连接之后每次重连都调用 `loadRecentAlerts/loadSpirit`，依靠 key 去重。

长期正确方案：AlertStore 给每个服务端事件分配单调 `event_seq`，SSE 发：

```text
id: 123456
event: alert
data: {...}
```

API 提供 `GET /api/events?after_seq=...` 或 alerts 带 seq。客户端保存 `last_seq`；发现 gap 或重连时按 seq 补账。服务端同时暴露 `subscriber_queue_dropped_total`。

### 验收

离线 E2E：

1. 客户端收 seq 1..10；断开；服务端产生 11..25；重连。
2. 最终前端集合必须正好包含 1..25，无重复、无缺号。
3. 人工把 subscriber queue 设小制造 overflow，前端必须检测 gap 并补齐，而不是静默丢失。

## IT-P1-003：分时序列 `_series` 字典没有跟随 120-code 索引淘汰，长期运行会增长

`src/arad/store.py::record_tick()`：

```python
self._series_codes = deque(maxlen=120)
...
if buf is None:
    buf = deque(maxlen=self._series_len)
    self._series[q.code] = buf
    self._series_codes.append(q.code)
```

`deque(maxlen=120)` 自动淘汰的是**代码索引**，但被挤出的 code 没有执行 `self._series.pop(old_code)`。

`record_tick()` 会记录自选 + 本轮 fresh alerts，因此每天出现新的异动股票时，`_series` 的 key 可以长期累积。

### 修改方案

改显式 LRU，不依赖 maxlen 的隐式丢弃：

```python
if code not in _series:
    if len(_series_codes) >= max_codes:
        old = _series_codes.popleft()
        if old not in watchlist_pinned:
            _series.pop(old, None)
    _series_codes.append(code)
```

或者 `OrderedDict`/自建 LRU；watchlist 可单独固定保留。

### 验收

离线依次写入 500 个唯一代码，断言：

- `_series` 上限与配置一致；
- 被淘汰的非 watchlist code 不再占内存；
- watchlist code 始终保留；
- 24h soak 记录 RSS、`len(_series)`、历史点总数，确认达到平台后不随新代码数线性增长。

## IT-P1-004：Tencent TLS 证书失败时默认允许降级为不校验证书

`src/arad/sources/tencent.py` 当前：

```python
ARAD_ALLOW_INSECURE_TLS 默认值 = "1"
...
if SSL error and allowed:
    ssl.CERT_NONE
```

这是显式实现，不是推测。它确实有助于某些 Windows 根证书不完整的机器“能抓到行情”，但代价是行情完整性失去 TLS 身份校验。对实时告警而言，篡改行情不需要盗钱也能制造错误信号。

### 修改方案

默认改为安全失败：`ARAD_ALLOW_INSECURE_TLS=0`；证书问题交给备用源。只有用户明确在可信网络中临时打开不安全回退时才使用，并在 status/README 明确显示 `tls_verified=false`。

验收：模拟证书错误，默认不得进入 unverified context；配置显式 opt-in 时才能进入，并且 health 中可观察到降级状态。

# 4. P2：配置/回放一致性问题

## IT-P2-001：`tick_surge.max_per_round=0` 的实现与注释相反

`src/arad/rules/tick_surge.py` 初始化明确写：

```python
# 0 = 不限量
```

但输出使用：

```python
surges[: max(self.max_per_round, 1)]
plunges[: max(self.max_per_round, 1)]
```

所以 `0` 实际变成每方向 1 条，不是不限量。当前正式配置是 15，因此默认没有触发；但契约错误应修。

正确逻辑：`>0` 才切片，`<=0` 全部保留。回归测试构造 3 个同时命中的 surge，`max_per_round=0` 应返回全部 3 条。

## IT-P2-002：Replay 时钟没有贯穿 Web status

Engine 支持 `now_fn` 注入，回放能把 `Engine.state.session` 设置成模拟时刻。但 `src/arad/store.py::status()` 又重新调用：

```python
phase = self.calendar.phase()
ts = datetime.now()
```

因此真实墙钟休市、回放时间为早盘时，看板状态可能显示“休市”，而规则实际上按早盘运行。

修改：Store 统一使用 `engine.now()` / `state.session`；`snapshot_payload`、状态时间和 series 都要沿用同一个 Clock abstraction。回归测试把墙钟设休市、注入 10:00，所有 API/status/SSE 均应显示 10:00 MORNING。

# 6. 详细优化路线

## 阶段 A：先建立“数据质量层”，再跑规则

新增中心化 `QuoteQualityGate`，输入所有源 Quote，输出：

```text
accepted quote
source_name / source_epoch
capabilities
source_event_ts / ingest_ts / age_ms
freshness_status
counter_reset_status
```

规则不再直接假设每个 Quote 都具备相同语义。

### 建议能力矩阵

| capability | Tencent | Sina | Eastmoney |
|---|---:|---:|---:|
| price/OHLC/volume/amount | 是 | 是 | 是 |
| source timestamp | 是 | 是 | 是 |
| outer/inner cumulative | 是 | 否 | 否/当前未映射 |
| level-5 orderbook | 是 | 否 | 否 |
| float cap | 是 | 否 | 是 |
| actual limit price | 是 | 否 | 否 |

能力必须来自 adapter 明示，不靠 `0.0` 猜“是真 0 还是没有这个字段”。

## 阶段 B：状态机按 source epoch 和 session phase 重置

至少为状态规则提供：

```text
on_new_trading_day
on_source_epoch_change
on_market_phase_change
on_universe_gap/rejoin
```

尤其是累计计数差分：任何 source change、counter regression、超 gap 后第一帧都只 re-baseline。

## 阶段 C：告警分成 RawEvent 与 UserNotification

目前多个规则可能观察同一行情波动。建议不要通过“建议关掉某个规则”解决所有重复，而是保留原始事件，增加事件聚合层：

```text
RawEvent: tick_surge / rocket / volume_burst / limit_touch ...
                 ↓
同 code + direction + 10~20s 时间簇
                 ↓
CompositeEvent
                 ↓
一条用户通知，附 corroborating_signals
```

这样既不会刷屏，也不会丢掉“急拉 + 放量 + 临近涨停”这类多证据结构。raw event 全部保留用于事后分析。

## 阶段 D：端到端事件 ledger

给每个服务端事件单调 sequence；记录：

- generated_seq
- stored_seq
- broadcast_seq
- client_last_seq（客户端本地）
- subscriber_drop_count

这能把“144 轮 SSE 没断”升级成真正可对账的“服务端生成多少、前端最终收到多少”。

# 7. 三个待验证新点子

以下全部是**研究/工程假设，不是已证明提升**。

## IDEA-IT-001：Source Epoch + Capability-Aware Rules

### 机制

当前 failover 把“可用性”与“字段语义”混为一谈。备用源能给价格，不代表能给外盘、内盘、五档、市值或真实涨停价。

### 与现有实现差异

现有规则检查数值是否为 0；新方案检查“源明确声明是否支持字段”。

### 实现

EngineState 增加：

```text
source_name
source_epoch
capability_set
```

每个规则声明 `required_capabilities`。缺能力时不是把 0 当真实值，而是明确 `SKIP_UNSUPPORTED` 并统计。

### 验证

用 Tencent/Sina/Eastmoney 三源离线矩阵重放相同股票路径，验证：

- 价格规则可以跨源运行；
- outer/inner 与 L5 规则在缺能力源自动冻结；
- 源切换后的第一帧不产生差分事件。

### 淘汰条件

如果 capability 层增加复杂度，却仍需每个规则写大量源特判，说明抽象失败，应退回 adapter 统一“可用字段 + missing mask”的更简单设计。

---

## IDEA-IT-002：Event-Time Watermark + Data Quality Score

### 机制

实时预警最重要的不只是“接口返回快”，还要知道这条行情本身有多旧。5 秒轮询拿到 30 秒旧行情，poll latency 仍然很好看。

### 实现

每轮维护：

```text
age_ms = ingest_ts - source_event_ts
source_lag_p50/p95/p99
stale_share
out_of_order_share
missing_share
```

生成一个独立 `data_quality` 状态。低质量时规则可以：

- 停止发高等级告警；
- 在前端明确显示“数据降级”；
- 恢复后先预热窗口再发信号。

### 对照实验

对同一离线行情注入 0/3/10/30 秒延迟与乱序，比较原引擎和 watermark 引擎的告警数量、假急拉/急跌数量、恢复时间。

### 淘汰条件

如果真实盘中多日 `source_event_ts` 本身不稳定到不可用于 freshness，则保留 ingest-time 但必须通过源级 heartbeat / response-age 另做健康判定，不能假装 event time可靠。

---

## IDEA-IT-003：把“机构吃货”改造成可定义的“区间主动流激增”分数

### 机制

项目没有逐笔成交，因此无法从公开快照可靠判断“单笔大单”或“机构身份”。与其继续把 5 秒区间聚合量映射为拟人化身份，不如直接建模**它真正观测到的量**。

定义起始版本：

```text
buy_rate = Δouter_shares / Δt
sell_rate = Δinner_shares / Δt
net_rate = (Δouter_shares - Δinner_shares) / Δt
float_norm = net_rate / float_shares
```

再按同一股票/流动性桶的历史同分钟分布做 robust z-score：

```text
z_flow = (float_norm - median_clock_bucket) / MAD_clock_bucket
```

名称直接叫“区间主动买入激增/主动卖出激增”，不声称机构身份。

### 数据需求

需要保存多日真实快照增量以及 event/source 时间。若未来能合法取得一小段 Level-2 数据，可把它作为外部标注集验证 snapshot proxy 与真实逐笔主动大单的相关性，但不是本方案运行的前提。

### 对照

同一真实盘中 replay：

A. 当前绝对阈值 `50万股/100万元/流通盘比例`

B. 区间 rate + time-of-day robust z

比较：

- 每股每天告警数与市场时段分布；
- 不同市值/成交活跃度桶的告警偏置；
- 未来 30/60/180 秒方向延续率（只作描述性标签）；
- 多日稳定性与 source-switch 假信号率。

### 淘汰条件

若 B 在多日/多流动性桶中不能降低时段和规模偏置，也不能改善短时后验稳定性，则不要保留复杂归一化，回到更简单透明的区间量阈值。
