## 3. `IT-P1-COMPLETE-001-R1`：当前最直接的默认路径功能回归

当前 `EastmoneySource.universe()` 仍然：

```python
out = _dedupe(quotes)
shortfall = expected_total - len(out)  # len(out) 是 post-parse usable Quote
complete = bool(total > 0) and not failed and not truncated and shortfall == 0
```

而 `parse_clist()` 会按数据合同丢弃 `price<=0`、`prev_close<=0`、`"-"` 等不可用行。于是：

- `expected_total` 是 transport/universe 层总数；
- `len(out)` 是 parse/quality 层可用 Quote 数。

这两个分母不能直接比较。

18:22 JST 冻结树真实复现已经证明：约 6% 停牌情形下，分页完全健康也会被判 `complete=False`；已有全市场池又会因为“partial 不得比现有池小”而拒绝覆盖，新增 10 只股票实测采纳 `0/10`。当前 `eastmoney.py` blob 与该冻结树一致，因此本轮不重复造 synthetic 来冒充新证据，而是把它提升为下一轮第一批产品修复。

### 终态设计

不要再用一个 `complete` 混 transport 与 usable：

```text
transport_expected_total
raw_rows
raw_unique_codes
transport_complete

usable_quotes
dropped_invalid
usable_coverage
```

建议兼容期：

```python
meta["complete"] = meta["transport_complete"]  # 保留旧引擎门控
```

真正 transport completeness 以**分页/失败/截断 + raw unique code coverage**判断；`usable_coverage` 只做质量诊断，不能让正常停牌行把全市场 transport 判成 partial。

### 必须有的红测

1. `raw_unique_codes == expected_total`，其中 6% 行按契约 parse 为不可用 → `transport_complete=True`；
2. raw 每页真的缩水 → `transport_complete=False`；
3. raw 行数够但 code 重复导致 unique code 不足 → `transport_complete=False`；
4. 现有池 + 新上市代码 + 正常不可用行 → 新代码可进入池；
5. 回退旧 `shortfall == 0` 判据后上述 1/4 必须重新变红。

## 4. `IT-P1-TIME-ROLE-004`：stock/index 两条 route 与一个全局 epoch 不相容

`SourceManager` 已经正确地把 `ROUTE_STOCKS` 和 `ROUTE_INDEX` 分开记 serving source；但是 `EngineState` 只有：

```python
source_epoch: str
accepted_watermark: dict[code, timestamp]
```

而 `poll_once()` 只做：

```python
serving_idx = self.sources.serving_of(ROUTE_STOCKS)
self.state.begin_source_epoch(f"{stock_source}#{idx}")

idx_admitted = self.state.update(idx_quotes, now)
admitted     = self.state.update(quotes, now)
```

这导致两个方向相反的错误。

### 反例 A：index route 自己切源，stocks 不切

```text
R1 stock serving = Tencent
R1 index serving = Tencent
sh000001 watermark = 100

R2 stock serving 仍 Tencent
R2 index serving 切 Sina
Sina 首包事件时间 = 70
```

Engine 不开新 epoch，因为它只看 `ROUTE_STOCKS`。结果 index 新 source 的第一包被旧 index watermark 当 out-of-order 拒绝。

本轮机制复现：`new_index_source_first_packet_admitted = false`，`out_of_order_rejects = 1`。

### 反例 B：stocks 切源，index 没切

```text
R1 stock/index 都 Tencent
index watermark = 100

R2 stocks 切 Sina
index 仍 Tencent
```

`begin_source_epoch("sina#1")` 会把**所有 code** 的 watermark 清空，包括指数。随后同一个 index source 的较旧事件时间 `80` 被错误接受，latest index 从 3900 倒退到 3890。

本轮机制复现：`older_same_index_source_packet_admitted = true`。

### 修法

epoch 至少要按 route 隔离：

```text
route_epoch[ROUTE_STOCKS]
route_epoch[ROUTE_INDEX]

accepted_watermark[(route, code)]
```

`begin_source_epoch(route, source_tag)` 只清/重置该 route 的 ordering 状态。长期更稳妥的是生成单调 epoch token：

```text
stocks:tencent#0:epoch17
index:tencent#0:epoch4
```

A→B→A 必须是三个 epoch，不能复用旧 A 的水位线。

## 5. `IT-P1-TIME-ROLE-003-R1`：陈旧下限没有按 source epoch 重置

当前 stale 判定只在：

```python
first_seen = q.code not in self.first_seen
```

时生效。

但 `begin_source_epoch()` 只清：

```python
accepted_watermark.clear()
```

不会清 `first_seen`。

因此：

```text
Source A:
600000 @ now-10s
→ admitted
→ first_seen 已含 600000

切 Source B:
watermark 清空

Source B 首包:
600000 @ now-3days
```

因为 `first_seen=False`，4 小时 stale 下限不再执行；watermark 又被清空，所以这条 3 天前报价会直接被接受并覆盖 latest。

本轮机制复现结果：

```text
source_a_fresh_admitted        = true
source_b_three_day_old_admitted= true
latest_price                   = 8.0
stale_stats                    = 0
```

这说明“首见陈旧保护”并没有覆盖它最重要的跨源场景。

## 6. 更根本的问题：TIME policy 与自己的 contract 冲突

`source_time_contract.json` 对 Tencent / Sina / Eastmoney 全部写：

```json
"role": "unknown",
"freshness_allowed": false
```

并明文：

> 禁止基于 provider ts 判定新鲜度。

但 Engine 当前又实现：

```python
if first_seen and q_ep < ep - STALE_TOLERANCE_SECONDS:
    return False, q_ep, "stale"
```

这就是用 provider ts 判 freshness。

当前注释把它解释为“保守兜底”，但代码语义仍然是 freshness reject；合同与执行策略已经分叉。

### 建议

在时间角色没有认证前，优先级应是：

```text
provider_ts_raw：保留诊断
received_at：当前 round/current membership 的硬依据
strict ordering：仅在合同明确允许的 source epoch 内使用
freshness reject：只有 freshness_allowed=true 才允许使用 provider ts
```

若三源继续 `role=unknown` / `freshness_allowed=false`，就不应该用 `provider ts age > 4h` 作为硬拒绝条件；可以先记录 `provider_age_seconds`、异常分位和 source 分组，再决定是否升级为可执行 policy。

如果以后拿到官方字段语义并将某 source 标为可判 freshness，再把 stale gate 改成**per source epoch first packet**，而不是全局 `first_seen`。

## 11. 主改造：Observation Truth Contract v4

建议把事实链正式收敛为：

```text
实际 dispatch
    ↓
RawBatchResult(route, requested_codes, provider_objects)
    ↓
per-code provenance
    source / source_epoch / time_role / provider_ts_raw / received_at
    ↓
AdmissionDecision
    accepted_ordering / future / stale / ooo / explicit_unavailable / quality
    ↓
admitted_current
    ↓
business filter
    ↓
rule_eligible
    ├─ current stock view
    ├─ current index view
    ├─ latest cache
    ├─ history / ObservationInterval
    ├─ coverage ledger
    └─ ML feature input
```

### 必须冻结的不变量

```text
actual_requested
= provider_objects + unknown_missing

provider_objects
= admitted_time
+ explicit_unavailable
+ future_rejected
+ provider_stale_rejected
+ out_of_order_rejected
+ quality_rejected

rule_current ⊆ admitted_current

stock/index 各自 route epoch 独立
```
