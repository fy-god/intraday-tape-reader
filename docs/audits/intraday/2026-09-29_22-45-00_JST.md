### 1.1 `IT-P1-SOAK-RAW-PRESENCE-GRADE-GATE-002`【确认 · 已修】

**文件/函数/行号**：`tools/live_session.py` · `evaluate_health()` · 新 `:2812-2900`

**背景**：上一轮（WP08）我把 `raw_presence_known_by_route` 读成了
三态证据等级（`exact` / `mixed` / `not_measured`），并写进 22 条测试。
但**它只呈现、不判定** —— `evaluate_health` 里没有对应检查项。

**机制**：这是 bug 类 **(c)「数据算了、判决层零读者」**，
而且是**我自己上一轮犯的**。本项目已因这个类栽过两次
（`raw_presence_known_by_route` 零读者本身、Eastmoney `truncated` 无赋值）。
我加了字段却没接读者，等于把"修好了"留在测试里。

**影响**：soak 报告里 `unknown_missing` / `rejected_quality` 若是**投影反推**
（`raw_presence_known_by_route[route] is False`），仍会以与精确数据
**同等的权威**参与健康判决。一个"不知道自己证据等级"的会话可以判绿。

**修复**（三档，依据是"**知道 vs 不知道**"，不是"精确 vs 不精确"）：

| 会话状态 | 等级 | 理由 |
|---|---|---|
| 无观测账本（`rounds_with_observation == 0`） | **ok（跳过）** | 本项**不适用**；与既有 16 个 check 一致 |
| 有账本、无 grade 字段（旧版采集） | **warn** | 版本差异，非事故；但**不得**默认成精确 |
| `not_measured` | **warn** | 定义就是"轮样本无等级字段"，是**采集**属性 |
| `projected`（明确知道是投影） | **warn** | 已知降级 + 计数已降为**上界**；判 fail 会惩罚合法的 legacy 用法 |
| **`partial`（某 route 产数据却没登记证据）** | **fail** | **唯一真事故**：bug 类 (e)「证据子集自称全程」 |
| `exact` | **ok** | 全 route 有精确出品证据 |

**⚠ 我写错了两次，是既有测试抓住了我（如实记录）**：

* **第一版**：把"有账本但无 grade 字段"判 **fail** → 当场打红

* **第二版**：把 `not_measured` 也判 fail → 又打红 **9 个**。
* **第三版**才收敛到上表。

防止以后有人为了"更严格"把 warn 又升回 fail。

**我的测试又抓出我自己门禁的一个弱点**：
第一版 fail 消息写 `未登记 route: {ungraded_routes or '未知'}`，

`by_route` 键 ∪ `rounds_seen_by_route` 键 减去已登记的精确/投影 route。
报"未知"等于把可行动信息丢掉 —— 那正是本仓库反复出现的

### 1.2 `IT-P2-CALENDAR-BARE-CONSTRUCT-SILENT-EMPTY-HOLIDAYS-003`【确认 · 已钉住】

**文件/函数/行号**：`src/arad/session.py` · `TradingCalendar`（dataclass 默认值）

**发现经过（一次被我自己纠正的结论）**：

全日仿真 agent 先怀疑 `config/holidays.txt` **缺失**，验证后**撤回**，
结论是"文件存在、正确加载、非缺陷"。

**我独立复核，发现它的撤回本身是错的** —— 但错的不是文件：

```
TradingCalendar()        -> holidays=0  条  2026-10-01 交易日=True   ❌
TradingCalendar.load()   -> holidays=33 条  2026-10-01 交易日=False  ✅
```

`config/holidays.txt` **确实存在**（48 行、33 个假期日，含国庆
2026-10-01～10-07）。agent 对文件的判断**是对的**。
但它用 `TradingCalendar()` 做探针，得到"国庆是交易日"后
把结果归因成"文件没问题所以没缺陷"，**把构造方式的坑漏掉了**。

**机制**：`holidays: set[str] = field(default_factory=set)` ——
**裸构造的默认值是"没有假期"**，即**默认不安全**。
任何新代码 `TradingCalendar()` 都会静默把国庆/春节当交易日，**且不报错**。
这是本仓库反复出现的**假绿出口**形状（bug 类 d 的近亲）。

**严重性分级：潜在陷阱，非当下生产缺陷。** 生产路径**都用** `load()`：

* `src/arad/engine.py:1061` — `self.calendar = calendar or TradingCalendar.load()`
* `src/arad/store.py:51` — 同上
* `src/arad/cli.py:86,112,172,223`、`tools/live_session.py:3789`

而显式 `TradingCalendar(holidays=set())` 的 4 个调用点
（`replay.py:572`、`bench_round.py:73`、`probe_session_boundaries.py:91`、
`shot_index.py:49`）都是**刻意**要空表的工具/回放场景。
**所以今天不会错。**

**处置：钉住陷阱，不改产品语义。**
改默认值会波及 replay/bench 的刻意用法，属于需要版本化的迁移。
本轮加 `tests/test_calendar_holiday_trap.py`（**9 条**）把
**两个构造方式的差别**写成显式合同：

* `test_load_reads_the_holiday_file` / `test_national_day_is_closed`
* `test_normal_trading_day_is_morning`（**阳性对照**，防"全判 CLOSED"）
* `test_bare_construct_yields_empty_holidays`（钉住事实；若哪天改成默认
  `load()`，此测试转红提示复查全部调用点）
* `test_bare_construct_treats_national_day_as_trading`（**陷阱本体**）
* `test_explicit_empty_holidays_is_still_supported`（刻意用法不得被破坏）
* `test_engine_and_store_use_load`（**AST 门禁**：`engine.py` / `store.py`
  出现裸构造即转红；注释无法满足）

我核实了断言的 7 个假期日期（元旦/春节/清明/劳动节/端午/中秋/国庆）
**真的都在表里**，不是我编的。

### 2.3 腾讯指数角色：**诚实降级为"结构对齐，非行为修复"**【降级】

**原判断**：`tencent.py` 的
`idx_set = {sym for sym, explicit in norm if explicit}`
把"调用方**写了**前缀"当成"它**是指数**"（v1 根因，R3），应改成 caller-owned。

**我做了修复**（新增 `index_codes` 类属性 + `_role_set()`，与新浪同调）。

**但回滚牙齿证明这个"修复"对行为几乎无影响 —— 2 颗牙齿没转红。**
根因：`is_index_role`（`tencent.py:323-324`）里 `idx_set` 只是**预过滤**，
成员**还要过** `looks_like_index`。实测：

```
symbol       looks_like_index   在 idx_set 里 -> index_role
sh000001     True               True
sh000905     True               True
sz399001     True               True
sh600000     False              False    <- 被兜底判据否掉，不靠 idx_set
sz000001     False              False
sh000922     False              False    <- 只能靠 route(index_role=True)
```

**结论（如实记录）**：
* 对**能靠代码段/名称判定的**指数（5 个默认指数都在内），
  `idx_set` 收不收它们**不改变结果**；
* 对**判据否掉的**指数（如 `sh000922` 中证红利），`idx_set` **也救不了**，
  唯一出路是 `index_role=True`（route 轴）；
* 而 `snapshots()` 的调用方是引擎、引擎本就在**指数路由**上，
  `index_role=True` **已经覆盖**。

**所以 `index_codes` 是防御性结构对齐，不是行为修复。**
它的价值是让腾讯与新浪共用同一 caller-owned 角色接口，
消除"角色从字符串拼法推断"这个**结构**隐患，而**不是**修一个
当下可复现的错误。我把这个结论**写进了测试文件头**，
并专门加了 `TestHonestScope::test_declaration_does_not_rescue_name_only_index`
防止后人误以为它修好了 `sh000922` 那一类。

**我据此重写了测试**（20 条，分三层：行为不变量 / 判据边界 / 结构对齐），
重做牙齿后 **4/4 behavioral RED，字节级还原**：
`no-attribute` / `role-set-no-declaration` / `publish-first-only` /
`everything-is-index`。
