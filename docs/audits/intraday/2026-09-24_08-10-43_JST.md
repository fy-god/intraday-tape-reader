# 2. 本轮主 P1：股票覆盖率会把“指数路由全断”完全淹没

新稳定 ID：

### `IT-P1-INDEX-ROUTE-HEALTH-MASKED-BY-STOCK-AGGREGATE-001`
**P1 latent（`spirit_index` 启用时用户级功能缺失）。**

固定 `RoundObservationSet` 当前是**整轮聚合对象**：
- `requested` = 股票 + 指数；
- `returned` = 股票 + 指数；
- `admitted` = 股票 + 指数；
- 单独只有 `index_requested` / `index_admitted`；
- **没有 `index_returned`**；
- `coverage()` = `returned/requested`。

`live_session` 的观测字段白名单又只收：
`requested/returned/admitted/coverage/source/...`，
**不收 `index_requested` 或 `index_admitted`**。

而当前观察健康阈值主要看整轮：
- p50 WARN < 0.97；
- p50 FAIL < 0.90；
- p05 WARN < 0.95；
- min WARN < 0.90。

### 固定反例

按项目历史全市场规模 5563 只股票、当前配置 5 个 index codes：

```text
stock:
requested = 5563
returned  = 5563

index:
requested = 5
returned  = 0
```

整轮：

```text
requested = 5568
returned  = 5563

aggregate coverage
= 5563 / 5568
= 99.9102%
```

而指数真实覆盖：

```text
index coverage = 0 / 5 = 0%
```

结果是：
> **整个指数路由 100% 断掉，整轮 coverage 仍是 99.91%，远高于当前所有 aggregate WARN/FAIL 线。**

这不是说整个 health 一定永远绿色——某个 source 自身 health 可能另行转红；准确结论是：

> **当前 Observation Coverage Gate 自身无法发现完整 index-route outage。**

而 `_fetch_indices()` 对指数抓取异常的生产策略是：
- log warning；
- 返回 `[]`；
- 不拖垮股票主循环。

这本来是合理的“指数是加分项”容错，但也意味着：
> 如果没有单独 index-route health，指数整条功能链可以静默消失，而股票 5563 只把总分母完全压住。

### 用户影响边界

`spirit_index` 默认 `enabled=false`，所以出厂默认不会请求指数作为告警信号；本条不是默认就发生的 P1。

但是用户一旦开启该功能：
- `Engine` 会请求指数；
- `spirit_index` 只认 `ctx.current_indices`，因此**不会拿旧指数继续误报**——这一旧坑已经修好；
- 但 index route 0/5 时，两条指数信号“拉升指数/打压指数”会整类不可用，而现有 aggregate coverage 仍可像健康轮。

因此这是**功能启用后的漏报/不可评估盲区**，不是 stale-alert bug。

本轮沙箱产物：
- `route_coverage_masking_matrix.csv`
- `route_coverage_masking_probe.json`

# 3. 新 P2：一轮里股票和指数可以来自不同 Provider，但 RoundObservation 只能写一个 source/capabilities

新稳定 ID：

### `IT-P2-ROUND-ROUTE-PROVENANCE-COLLAPSE-001`
**P2 · 本轮固定 SHA 静态确认。**

这个场景并不需要达到 failover threshold。

同一轮可以非常自然地发生：

```text
股票大请求：
Tencent primary 失败
→ Sina backup 热备成功

指数小请求：
Tencent primary 正常
→ Tencent 服务
```

这种“股票 Sina、指数 Tencent”的同轮 mixed-source 组合正是 SourceManager 分 route `serving_of()` 存在的理由。

EngineState 也已经按 route 开 source epoch。

但最终 `RoundObservationSet` 当前只写：

```python
serving_idx = self.sources.serving_of(ROUTE_STOCKS)
serving_src = ...
caps = capabilities_for(serving_src)

RoundObservationSet(
    source = stock serving source,
    capabilities = stock source capabilities,
    requested = stock + index,
    returned = stock + index,
    admitted = stock + index,
    ...
)
```

因此上面的真实一轮会被序列化成：

```text
source = sina
capabilities = Sina capabilities

但 returned/requested 里
同时混有 Tencent index observations
```

这不是纯文字问题，因为能力差异很大：

```text
Tencent:
turnover/volume_ratio/depth_l1/depth_l5/
outer_inner/float_cap = available

Sina:
turnover=false
volume_ratio=false
depth_l1=true
depth_l5=false
outer_inner=false
float_cap=false
```

当然，当前 `ctx.capabilities` 主要服务股票规则，所以“股票来自 Sina -> 用 Sina caps”这一条本身正确。

错误发生在**把这个 stock-route source/capabilities 同时当作整个 RoundObservation 的 provenance**。

一旦研究层、live-session 或未来影子模型按 observation.source 做 source-switch 分组，它会丢掉指数 route 的真实 provider。

本轮产物：
`mixed_route_provenance_probe.json`。

# 4. 为什么现在才暴露：EngineState 已经是 per-route，RoundObservation 还不是

当前项目其实已经有两层正确的 route separation：

### EngineState 时间状态
`accepted_watermark_by_route[(route, code)]`；
`source_epochs[route]`；
`source_names[route]`。

注释明确写：
> 股票和指数是两个独立数据流，各有自己的 serving source 与切源时机。

### RuleContext
`ctx.current_indices` 明确表示**本轮真正准入的指数**；
`spirit_index` 优先消费它，不再从累计 `state.quotes` 猜 current。

也就是说：
> “当前行情”和“source epoch”都已经按 route 分开。

但最外层可观测账本：

```text
RoundObservationSet
```

仍然是：
> 先把 stocks/index 加总，再挂一个 stock source。

这就是现在最大的架构断层。

WP07 如果只是：
```text
stocks call -> call_detailed
index call  -> call_detailed
```
然后仍旧把两个 outcome 加成旧 RoundObservation 形状，就会**把 source-v4 刚得到的 per-route raw truth 在最后一步再次压扁**。

# 5. 主改造：Per-Route Round Observation Contract v1

下一版建议先引入 route sidecar：

```text
RouteObservation
  route
  source
  capabilities
  provenance
  raw_presence_known

  requested R
  raw_returned P
  usable_returned Q
  admitted

  unknown_missing
  rejected_quality
  future_rejected
  out_of_order_rejected
  unattributed_requested

  raw_return_coverage = P/R
  usable_coverage     = Q/R
```

然后：

```text
RoundObservationSet.routes["stocks"]
RoundObservationSet.routes["index"]
```

作为真正的事实源。

### 向后兼容

旧字段仍可保留，但只能是 projection：

```text
requested = sum(routes.requested)
returned  = sum(routes.raw_returned)
admitted  = sum(routes.admitted)
coverage  = aggregate P/R
```

旧 `source/capabilities` 如果必须兼容，可以继续暂时代表 stock route，但必须标 deprecated，新生产消费者不得再用它解释整个 round。

### Health

整轮 aggregate health 可以继续保留，回答：
> 主扫描系统整体有没有塌。

但是只要：

```text
index_requested > 0
```

就必须单独有：

```text
index_raw_return_coverage
index_source
index missing / quality / time reject
```

股票 99.9% 覆盖不能给 index 0/5 背书。

建议初始策略：

```text
如果 index_requested == 0：
index health = not_measured / not_applicable

如果 index_requested > 0：
index 0 返回 = FAIL
部分返回 = WARN/FAIL 按独立阈值
```

阈值不需要现在拍死；首先要把分母做对。

完整候选：
`per_route_round_observation_contract_v1.json`。

## 最终判断

当前产品已经把 detailed source truth 修到“可以接线”的程度。

现在真正不能再忽略的是：

> **stocks 和 index 已经是两条 route，但 RoundObservation / soak health 仍然主要把它们当成一个分母。**

5563 只股票足以把 5 个指数的完整断流压缩成只有 0.09% 的总 coverage 损失。

所以 WP07 的正确目标不能只是：

```text
call() -> call_detailed()
```

而必须是：

```text
Exact Source Outcome
↓
Per-Route Round Observation
↓
Per-Route Health / Provenance
↓
Compatibility Aggregate
```

完成这层之后，Membership 与 exact soft-empty 才有可靠的在线事实基础，研究模型才值得继续。
