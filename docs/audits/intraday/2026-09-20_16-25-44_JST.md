## 4. `IT-P1-COMPLETE-001` — `complete` 未与 `returned` 挂钩（已修 + 验牙）

> 由**并行子 agent** 完成，本机复核其产出。

### 4.1 机制

`src/arad/sources/eastmoney.py` 上一轮修了 `max_pages` 截断轴，但 `complete`
仍**只**由 `bool(total>0) and not failed and not truncated` 决定，
**从不比较 `len(out)` 与 `expected_total`**。`:383` 的 `"returned": len(out)`
只是诊断字段，**无任何代码消费**。

于是"页数够、但每页缩水"的返回仍 `complete=True`：

```text
total=5913, page_size=100 -> required_pages=60 <= max_pages=80
  每页足额 100 行:  returned=5913→6000   complete=True   <- 正常
  每页只回 10 行:   returned=600        complete=True   <- 缺陷：10.1% 当完整
```

**端到端**：`engine.py` 的 `if not meta.get("complete", True):` 会放行，
引擎把 600 只当成**完整全市场**。这正是"截断轴修了、缩水轴没修"的漏网。

### 4.2 修法

```python
shortfall = 0
if expected_total > 0 and len(out) < expected_total:
    shortfall = expected_total - len(out)
    ...
complete = (bool(total > 0) and not failed and not truncated
            and shortfall == 0)
```

判据是"**不少于**"（`len(out) >= expected_total`），**不是** `==` ——
因为翻页时边界重叠会令 `returned` **略高于** `expected_total`（实测
5913 → 6020），那是正常的。新增 `shortfall` 诊断字段，`reason` 能区分
截断 / 失败页 / 行数缩水三种不完整。

### 4.3 验收测试与验牙

`tests/test_eastmoney_truncation.py` 追加 2 类 7 用例（该文件 13 → **20**）。

回退验牙（`git stash push -- src/arad/sources/eastmoney.py`）：
**5 failed, 15 passed**；`pop` 后 81 passed。

**子 agent 主动如实说明**：另两个边界用例（略多→True、恰好相等→True）在修复前
**也是绿的** —— 它们是**回归保护**而非验牙用例。这一区分很重要，我认可其诚实。

## 7. 三条可证伪的研究想法

### RF-01【程序修复】观测账本字段应有"名实一致"守卫

- **假设**：`stale_rejected` 名实相反能长期存活，是因为**没有东西检查字段名与
  数据来源的语义一致性**。可加守卫：凡 `as_dict()` 导出的字段，其写入侧表达式
  必须能在注释/文档里找到对应说明；或更机械地 —— 字段名中的关键词（stale/future）
  必须与写入侧的 stats 键（`t_reject:future`）匹配。
- **证伪条件**：若守卫报出的全部是误报，或它漏掉 OBS-006 形态，则规则无效。
- **可执行动作**：`tools/check_ledger_names.py` 独立守卫。

### RF-02【任务定义调整】"数据太旧"应当有真实判定，而不是缺席

- **假设**：OBS-006 之所以只能改名不能改数据，是因为**系统压根没有"陈旧拒绝"
  这条路径**。首见码接受数天前的 `ts`（`IT-P1-TIME-ROLE-003`）意味着跨源切换时
  可能把数天前的价格当成新鲜行情。
- **证伪条件**：若加上陈旧下限（如 `ts < now - N 分钟` 即拒）后，在真实语料上
  造成**高于**它挡掉的假信号的漏报（即把正常的集合竞价/停牌复牌数据误杀），
  则该下限应更宽或不做。
- **性质**：这是**任务定义**问题 —— "多旧算陈旧"取决于数据源特性，本轮**未决定**，
  只把"该路径不存在"这一事实写进字段注释。

### RF-03【模型真正增量提升】`decisions` 明细应作为可解释性输入

- **假设**：OBS-007 修完后，逐 (code, field, reason) 的不可评估明细**首次可用**。
  把这些原因分布作为特征（"该标的缺失哪些字段"）输入模型，可能提升真实数据上的
  PR AUC —— 因为"数据可用性"本身与"是否值得告警"相关。
- **证伪条件**：真实语料上相对 base 提升 < 0.005，或缺失模式在 family
  permutation 中重要性排名后 50%。
- **前提**：依赖真实多日语料，当前 `blocked`。
