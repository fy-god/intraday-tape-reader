### 2.1 `IT-P0-002-R2`：平价新鲜观测不推进水位线 —— **已确认错误（三次独立复现）**

> **来源说明（避免误记功）**：该缺陷**最早由 05:30 JST 报告发现并命名**（`2026-09-20_05-30-48_JST.md` §2.1），`08-10-29` 报告「再次复现」，**本轮是第三次独立复现**并补上一条关键新事实。三份报告结论一致，故该条证据强度为**三重独立确认**，非本轮新发现。

**文件/行**：`src/arad/engine.py:157-161`（唯一乱序守卫）与 `:173-174`（追加门）

```python
157  h = self.history.get(q.code)
158  if h and q_ep < h[-1][0]:          # 水位线 = history[-1][0]
159      self.stats["t_reject:out_of_order"] = ... + 1
161      continue
...
173  if prev is None or prev != q.price or not h or h[-1][2] != q.volume_lots:
174      h.append((q_ep, q.price, q.volume_lots))   # 仅价格/量变化才追加
```

**触发条件/反例（本机真实复现）**：R1 `t0 10.0/100` → R2 `t+60 10.0/100` → R3 `t+30 9.8/110`

```text
R1 admitted=1 history=[(t0, 10.0, 100.0)]
R2 admitted=1 history=[(t0, 10.0, 100.0)]      <- 未追加（同价同量）
R3 admitted=1 quotes.price=9.8 last_price=9.8 history=[(t0,10.0,100.0),(t+30,9.8,110.0)]
stats out_of_order = 0
=> R3 被准入 = True ; latest 倒退到 9.8 = True ; ooo = 0
```

**机制**：水位线是**隐式**的 `history[-1][0]`；`history` 只在价格或累计量变化时追加（`:173`）。于是同价同量的新鲜观测虽已通过时间准入、也推进了 `quotes`/`last_price`（`:163`、`:175`），却**不推进水位线**。下一次真实迟到的点因 `q_ep (t+30) >= h[-1][0] (t0)` 而被放行 → 覆盖缓存、时间序列尾部倒挂。

**影响面（给实际计数，非泛述）**：`EngineState.window()`（`:82-85`）按 `p[0]` 过滤与**排序**，故任何经由 `window()`/`price_change()`（`:87-95`）计算的窗口涨跌幅都可能把迟到点当作窗口末点。`last_price` 与 `quotes` 倒退本身又会被 `SpiritOrderRule._drop_stale()` 一类依赖时间戳的规则消费。**本轮未对该影响面做样本级计数**（需回放真实 tick），故不给出受影响比例。

**该报告未说、本轮新增的关键事实**：现有测试**只覆盖 R2 变动价格的情形**。子 agent 的对照实验隔离了这一点（同一 R3，仅改 R2 价格）：

```text
FLAT  R2 (10.0, 同量): 水位线=30s | R3 admitted=True  latest=9.8 ooo=0
MOVED R2 (10.5, 同量): 水位线=60s | R3 admitted=False latest=10.5 ooo=1
```

即守卫在「history 前进」时**工作正常**；空洞恰是平价观测。现有 `31 passed` 全绿也不覆盖该分支——**这是「有测试但没测到」而非「没测试」**。

**修复建议（程序修复）**：引入**独立显式**水位线（如 `accepted_watermark[code]`），在准入成功时无条件推进，不再借用 `history[-1][0]`；`history` 的「仅变化追加」语义保留（它服务的是窗口采样，不应改）。

**验收测试（必须可失败）**：固定 R1 `t0 10.0/100` → R2 `t+60 10.0/100` → R3 `t+30 9.8/110`，断言 R3 **不被准入**、`latest` 仍为 10.0、`t_reject:out_of_order == 1`。**该用例在当前源码上已实测为红**：

### 2.2 `IT-P2-OBS-005`：provider 返回但 `price<=0` 被记为「没返回」 —— **已确认错误**

**文件/行**：`src/arad/engine.py:905-907` 与 `:858`；丢弃点在 `:145-146`

```python
145  if q.price <= 0:
146      continue                      # 不进 admitted
...
858  returned = dict(admitted)         # 于是 returned 不含 price<=0
...
905  unknown_missing=tuple(c for c in self._codes if c not in returned)
```

**反例（本机真实复现）**：provider 实际返回 `600000`(10.0) 与 `600001`(0.0)

```text
provider 实际返回 : ['600000', '600001']
admitted         : ['600000']
unknown_missing  : ['600001']   <- 明明返回了却记 missing
```

**机制**：`returned` 被定义为**准入后**集合（`:858`），而 `unknown_missing` 用 `returned` 做补集（`:906`）。任何**已返回但被 `update()` 内部丢弃**的票（`price<=0`，`:145`；以及被时间准入拒绝的票，`:150-152`、`:158-161`）都会落进 `unknown_missing`。

**影响**：`unknown_missing` 同时表达三种互斥语义——「没返回」「返回了但质量不可用」「返回了但时间不合格」。`capabilities.py:134` 文档已定义 `rejected_quality` 桶，但代码内 `rejected_quality` **零发射点**（`src/`、`tests/`、`tools/` 均无），故该桶实际不存在。于是覆盖率与「缺数据」诊断不可解释。

**实测的跨源差异（决定影响面）**：`sources/tencent.py:294` **刻意保留** `price<=0` 行，而 `sources/sina.py:197`、`sources/eastmoney.py:197` 在解析期就过滤。真实 fixture 中 tencent 出现 `001246` `price=0.0`（1/423）。故**该混算只在 tencent 路径上以「对象已返回」的形态可观察**——这限定了影响面，是本轮新增的量化边界。

**双重计数（同一根因的第二个表现）**：被**时间准入**拒绝的票既计入 `stale_rejected`/`out_of_order_rejected`（`:897-898` 差分），又因不在 `returned` 中而计入 `unknown_missing`。本机实测：远未来票 `admitted=[]`、`t_reject:future=1`，同时落进 `unknown_missing`。

**修复建议（程序修复）**：把 `returned` 改为「provider 原始返回」计数/集合，与 `admitted` 分离；新增 `explicit_unavailable`（质量不可用）与独立的 `future`/`ooo` 桶，使三者互斥。

**验收测试**：provider 返回含 `price<=0` 的票时，断言该 code **不在** `unknown_missing`、而在 `explicit_unavailable`（或 `rejected_quality`）；且时间拒绝的票不同时出现在 `unknown_missing`。

### 2.3 `IT-P1-TIME-ROLE-001`：`ts` 是排序键，跨源语义不同 —— **已确认错误（比原报告更硬）**

**文件/行**：能力表 `src/arad/capabilities.py:89-105`；`_admit_time` `src/arad/engine.py:179-196`

- 三个 provider 的 `provider_time` **全部为 False**（`:93` tencent、`:98` sina、`:103 eastmoney`），且 `provider_time` 在 `src/`、`tools/` 中**零消费者**（仅声明与 `as_dict()` 暴露）。
- 三个 parser **都**填 `ts`：`sources/tencent.py:397`、`sources/sina.py:232`、`sources/eastmoney.py:227`。
- `_admit_time`：`:186` `ts is None` → 接受；`:192` 仅拒绝**远未来**（`> +120s`，`FUTURE_TOLERANCE_SECONDS` 见 `:42`）；`:194` 轻微超前夹到 `now`；`:196` **任何早于 now 的 ts 无条件接受**，无陈旧下限。

**「信任任何非空 ts」的措辞修正**：远未来确被拒、轻微超前被夹，故该子句应为**部分成立**；但「任意偏旧 ts 无条件接受」成立。

**为何是真缺陷而非设计警告（本轮加强）**：`ts` **就是**排序/水位线键——`:158` 用它判乱序、`:174` 存入 `history`、`:82-85` 用 `p[0]` 过滤与排序。同码跨源实测差 **2400 秒**（`000572` tencent 16:14:27 vs eastmoney 15:34:27）与 **2328 秒**（`000001` tencent 16:14:48 vs sina 15:36:00）。**结论**：跨源共享同一个 provider-time 水位线**确定会错**，必须先有 `source_epoch`/`time_role`。`source_epoch`、`time_role`、`round_id`、`observation_ledger`、`ObservationInterval` 在**代码中均零命中**（仅存在于 `docs/audits/intraday/` 提案文本）——本报告不把它们当作既有机制。

## 5. 研究/改进想法（基于本轮证据）

1. **把「平价观测」提升为水位线契约的一等用例。** 本轮证明缺陷只在「同价同量」时出现，而现有 31 项相关测试在**变动**价格路径上全绿。依据：§2.1 的对照实验。建议在水位线重构时，把「平价新鲜观测必须推进水位线」写成**独立可失败断言**，并对每个消费 `window()` 的规则各加一条迟到点回放——这比「修 R2」更能防止同类空洞回归。
2. **`provider_time=False` 与「三 parser 都填 ts」的矛盾应改为机制而非注释。** 依据：§2.3（能力表全 False、`ts` 零消费者、`ts` 却是排序键、跨源差 2400s）。建议引入 `source_epoch`/`time_role` 作为**准入前置**：当 `provider_time=False` 时，`ts` 只允许做**同源**排序，跨源比较必须显式失败。这让当前「静默按 ts 全局排序」变成可检测错误。
3. **`unknown_missing` 的四义混用应以「互斥桶 + 机械对账」收口。** 依据：§2.2（同一票在 `unknown_missing` 与 `stale_rejected` 双计；`rejected_quality` 有文档零实现；tencent 是唯一可观察路径）。建议落 Observation Ledger v2 时同时加一条**恒等式断言**：`requested == hit + evaluated_no_hit + unavailable + rejected_quality + future + ooo + unknown_missing`，任一不成立即失败——这能在 `BLOCKED` 语料状态下用纯软件方式完成。
