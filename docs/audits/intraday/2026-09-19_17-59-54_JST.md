## 1. 已确认错误

### IT-P0-003：累积缓存被包装成"本轮观测"进入规则

- **文件 / 函数 / 行号**：`src/arad/engine.py` → `Engine.poll_once()`，原 L775-789（修复前）。
- **触发条件**：任一快照来源在某轮少返回代码（provider soft-partial、分页截断、
  单只抓取失败、停牌零价），而 `state.quotes` 中仍留有该代码的旧值。
- **机制**：
  1. `EngineState.update()`（`engine.py` L112-113）对 `q.price <= 0` 直接 `continue`，
     不把旧缓存显式标记为"当前不可用"；
  2. `poll_once()` 用 `self.state.quotes`（累计"最近已知值"）构造 `eligible`，
     再把 `eligible` 全量灌进 `Snapshot.quotes`；
  3. 于是**本轮并未返回**的代码带着旧价、旧量进入了规则。
- **影响**（不止"看板显示旧价"）：
  - `SpiritOrderRule._drop_stale()` 依赖"本轮 Snapshot 中不存在"来清理缓存。
    缓存代码每轮都进 Snapshot，**缺席永远看不见**，该保护实质失效
    （规则级测试 `test_stale_code_cache_dropped_between_rounds` 钉住的语义
    与生产 Engine 的实际行为不一致）；
  - `SpiritOrderRule._check_trades()` 先执行
    `self._prev[code] = (outer, inner, amount, volume, now_epoch)` 再判断
    `now_epoch - p_epoch > max_gap`，因此 stale 代码每轮都把 `_prev` 时间
    刷新成当前轮 → **真实长缺口被"洗短"**：
    `10:00:00` 最后一次真实观测，`10:00:05~10:02:55` 持续缺失但缓存每 5 秒进
    Snapshot，`10:03:00` 恢复时真实观测间隔 180 秒，却被看成 5 秒，
    长缺口安全阀（默认 `max_gap_seconds=300`）不生效，可能产出无中生有的
    大笔买入/卖出告警。
- **修复**：把"缓存"与"本轮观测"分层（对应审计报告 WP4）。规则 Snapshot 只消费
  本轮**实际返回且解析成功**的观测：

  ```python
  returned = {q.code: q for q in quotes if q.price > 0}
  eligible = {c: q for c, q in returned.items()
              if self.filters.accept(q, now.date()) and c not in self.ignore}
  watch_cur = {c: returned[c] for c in self.watchlist if c in returned}
  snap = Snapshot(ts=now, seq=self.state.seq, quotes=dict(watch_cur))
  snap.quotes.update(eligible)
  ```

  `state.quotes` 保留为仅供看板/历史的 `latest_cache`（本轮未改动其写入语义，
  以免影响 `spirit_index` 等依赖 `ctx.state.quotes` 的规则）。
  自选股同样必须是本轮返回的，不再用缓存旧值兜底。
- **验收测试**（`tests/test_engine.py`，新增 4 项）：
  | 测试 | 钉住的语义 |
  |---|---|
  | `test_snapshot_excludes_codes_absent_from_this_round` | provider 本轮没返回的代码不得进 Snapshot，即使缓存里还有 |
  | `test_snapshot_is_current_only_even_when_cache_is_large` | 缓存 4 只、本轮只返回 1 只时 Snapshot 必须只有 1 只 |
  | `test_snapshot_excludes_zero_price_that_blocks_cache_update` | 零价必须让该股退出本轮观测，不能拿旧有效值喂规则 |
  | `test_watchlist_codes_absent_this_round_do_not_enter_snapshot` | 自选股缺席时不得用缓存旧值继续喂规则 |

## 5. 研究想法（1-3 条，带证伪条件）

### R1 — 同快照重放：缓存污染的可观测指标（程序修复方向）

- **想法**：在 `Snapshot` 上增加 `admitted` / `stale_dropped` 两个计数，
  把"本轮请求 N、返回 M、准入 K"记入 `state.stats`，并在看板暴露。
- **新意**：现有指标只有告警数与轮次耗时，无法区分"真的没有异动"与
  "数据没回来所以没告警"。这正是 `IT-P0-003` 能长期隐身的原因。
- **实现位置**：`engine.py::poll_once`，`store.py::set_poll_stats`，`server/dashboard.html`。
- **证伪条件**：若在固定 fixture 下 `returned` 与 `admitted` 恒等
  （即粗筛从不拦掉本轮返回的票），则该指标无增量价值，应淘汰。
- **区分**：**程序修复**（可观测性），不是模型增益。

### R2 — 长缺口被洗短的端到端负控制（验收方向）

- **想法**：构造 `180s` 真实缺口 + 每 5 秒缓存刷新的固定剧本，
  断言 `spirit_order` **不**产出告警，并把 `real_gap` 与 `seen_gap` 同时写进
  告警 metrics 以便对账。
- **新意**：本轮只证明了 Snapshot 层已修；规则层"`_prev` 先写后判"的顺序
  本身仍有把缺口洗短的余量（若快照层再次退化）。
- **实现位置**：新增 `tests/test_full_day_simulation.py`（该文件至今 `not_run`）。
- **证伪条件**：若在真实数据上 `max_gap` 门控从未拦下过任何告警
  （即缺口场景不产生假告警），则该实验优先级下降。

### R3 — 三源 requested-vs-returned 完整性合同（任务定义调整）

- **想法**：`Source.snapshots()` 返回 `BatchResult(requested, returned, missing, epoch)`
  而非裸 `list[Quote]`，把"少行"从静默成功变为可判定状态。
- **新意**：当前接口无法表达"我要 5000 只、只拿到 3000 只"，
  这是 `IT-P1-SOURCE-EMPTY-001` 的根因，也是 `IT-P0-003` 的上游。
- **实现位置**：`src/arad/sources/base.py`（Protocol）、三源实现、`SourceManager.call`。
- **证伪条件**：若三源在真实运行中 returned 恒等于 requested
  （即从不发生 soft-partial），则该合同是过度设计，应降级为日志断言。
- **区分**：**任务定义调整**（接口合同变更），会触及全部来源实现，
  需与调度方确认是否接受一次性大改。

**本轮没有"模型真正增量提升"类结论** —— 没有独立真实标注，
Precision/Recall 仍标记为不可用。
