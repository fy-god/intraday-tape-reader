### 050 ·【已确认错误】异动榜 `speed` 按墙钟切窗口，replay 下恒 0

| 项 | 内容 |
|---|---|
| 文件 | `src/arad/store.py` `AlertStore._quote_item`（:459）、新增 `_now_epoch`（:108） |
| 触发 | `serve --replay`（回放模式） |
| 机制 | `_quote_item` 用 **墙钟** `time.time()` 算 `speed_1m/5m`，而 `EngineState.history` 的 `p[0]` 是**事件 ts**（由 `Engine` 的**可注入时钟** clamp）。窗口判据 `cutoff <= p[0] <= now_epoch` —— **两个时点来自不同时间轴**。属本仓库 bug 类 **(b) 同一语义实现两次**：`Engine.now()` 已是"当前时刻"的唯一权威实现（且可注入），store 又自己调了一次墙钟。 |
| 影响 | 回放模式下 `speed_1m`/`speed_5m` **恒 0.0**，而 `speed` 是**异动榜的默认排序键** → 榜单退化成插入序（**假绿出口**：看起来排了，其实没排）。 |
| 修复 | 新增 `AlertStore._now_epoch()`：优先 `engine.now()`，取不到回落 `time.time()`。 |
| 验收 | `tests/test_quote_speed_clock.py`（7 条） |

**实测（真实 replay 链路：`Replay.build_engine` + 真 `AlertStore`）**：

```
引擎时钟（SimClock）now = 2026-09-30 09:30:00
真实墙钟          now = 2026-09-30 12:21:07      <- 差 2h51m
修前 top_quotes(30,'speed') -> speed_1m 非零 0/30，speed_5m 非零 0/30
     且 sort=speed 与 sort=volume_ratio 返回**完全相同且未排序**的序列
```

**修后（同一链路）**：

```
speed_1m 非零 17/20，speed_5m 非零 20/20
sort=speed       序前 8 = ['300702','000858','688703','002594','600708',...]
sort=volume_ratio序前 8 = ['601899','600000','600704','000709','600519',...]
两序不再相同
```

**为什么实盘看不出（重要区分）**：真实盘中 provider 服务端时钟跟着"现在"走，与墙钟近似同步。实测 live 语义（ts == 墙钟，价格每轮真实上涨）：

```

```

**所以这是 replay 专属缺陷** —— 但 replay 正是用户休市时"先看看长什么样"的**唯一入口**（见 `cli.cmd_serve` docstring），退化榜单会直接误导。**不得声称"实盘异动榜也坏了"。**

**为什么回落而不是硬依赖引擎时钟**：`_state()` 在引擎未 attach 时返回 `None`，且 `now_fn` 理论上可能抛异常 —— 那时宁可与修前一致，也不要让看板整页 500。

**回滚验牙 2/2 RED**：T1 退回 `time.time()`（缺陷本体）→ 3 failed；T2 `_now_epoch` 恒返回墙钟（**假修复**）→ 3 failed。两次均字节级还原。

**我自己的一个错误（如实记录）**：第一版断言写成"按**带符号** speed 降序"，被 `-10.12` 排在 `5.68` 前判红。实际排序键是 `-abs(speed_1m)`（异动榜要"波动最大"，急拉急跌同等重要）—— **错的是我的断言，不是产品**。已按真实语义重写。

### 想法 1【程序修复】给每个观测字段加"消费者合同"测试
**可证伪断言**：对 `RoundObservationSet` 的**每个**字段，写一条测试断言"存在至少一个非测试代码路径读取它，且读取结果会改变某个用户可见输出"。预期结果：`observation`、`universe_truth.freshness` 两个字段**没有**这样的消费者（子 agent 已实测 `status()` 里 83.2% 字节从未被前端读取）。
**若断言成立** → 证明 bug 类 (c)「数据算了、判决层零读者」不是偶发，而是**结构性**的：观测层的字段从来没有过消费者契约。这已是**连续第四轮**同一根因（R14 字段零读者 → R15 加读者但没审字段表达力 → R16 被云端审计我 → R17 子 agent 再发现两个零读者字段）。
**若断言不成立**（找到消费者）→ 我的假设错误，应下调为"仅两个字段孤立缺失"。

### 想法 2【任务定义调整】把"绿灯"改成"绿灯 + 必须指出一条真实告警"
**可证伪断言**：当前 `live_session.py` 的 18 项检查**全部可以在 `alerts=0` 时通过**。因此"✓ 健康"与"用户收到了有用预警"**没有任何蕴含关系**。
**验证方式**：在休市时跑 soak，观察是否 exit 0（本轮已观察：是）。**若成立** → 说明健康判据测的是"管道没坏"，不是"盯盘有用"，需要增加一条**端到端告警产生**的判据（例如：注入一条已知必然触发急拉的合成行情，断言告警真的产生、去重、投递、且在看板 API 里可见）。
这条我认为是本轮最有价值的发现：**我们一直在优化一个不衡量目标函数的指标。**

### 想法 3【模型真正增量提升】—— 本轮为 0
本轮没有任何"模型真的变强了"的证据。四个缺陷里：
- 047 靠**真实网络测量**（抖动分布、板块归属）找到，不是靠推理；
- 050 靠**读代码发现两处时钟实现**找到，属常规静态分析；
- 048 靠**跑一次真实 CLI** 找到；
- 049 由**子 agent 用真实浏览器**找到。
四者都是**工具驱动的发现**（跑真实路径、量真实分布），不是模型推理能力的增量。诚实记 0。
