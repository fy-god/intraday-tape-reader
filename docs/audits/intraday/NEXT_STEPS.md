## P0 — 需要**产品确认**才能继续（阻塞中）

这两条不是技术问题，是**语义决策**。不定下来，改任何一边都可能是错的。

### 1. `max_per_round` 是"硬限流"还是"不许丢"？
- **现状**：本轮改成"截断 + 下一轮补报"（不丢，但跨轮积压会逐轮释放）。
- **如果产品意图是硬限流 20 条/轮**：正确修法是让超出的**不写状态**、
  下一轮重新竞争（可能永远报不出来）。
- **如果产品意图是不许丢告警**：当前实现正确。
- **为什么重要**：涨停封板是最高优先级信号，且"多股同时涨停"正是最容易
  触发截断、也最该看到的行情。
- **验收**：定下语义后，`test_truncated_alerts_are_reported_next_round_not_lost`
  要么保留、要么改成断言"超额被丢弃"。

### 2. `limit_board` 封单缩水（300万 → 100万 → 300万）算不算独立事件？
- **现状**：会**重新告警**（状态从 `sealed` 退回 `at_limit_unqualified`，
  再达标即跃迁）。
- **替代定义**：只在"炸板"（价格离开限价）时才重新报，封单缩水不算。
- **为什么重要**：只影响文案与告警频率，但影响用户对"这只票是不是刚又封了"的判断。
- **验收**：定下语义后补一条跨轮用例钉住。

## P1 — 解锁一批缺陷的公共前置

### 3. per-code provenance（code → source / source_epoch / capabilities）
- **解锁**：`IT-P1-CAPABILITY-002`（规则侧只有轮级能力声明）、
  WP07 有界软部分回退。
- **做法**：`Quote` 或 `EngineState` 上记录每个码**本轮由哪个源、哪个 epoch
  提供**；规则可据此判断"这个码的数据源不支持换手率"而不是整轮降级。
- **为什么现在做**：本轮把 route 级 epoch 和账本桶做完了，per-code 是自然下一步，
  再拖下去 WP07 一直无法启动。
- **验收**：一条真验牙用例 —— 同一轮里两个码来自不同源，规则能分别判定能力。
- **注意**：`000001` 同时是平安银行（个股）与上证指数，provenance 的键必须
  **带 route**，否则撞码。本轮已经在 epoch 侧踩过这个坑。

### 4. `IT-P1-WINDOW-001` 窗口跨 epoch 语义
- **位置**：`engine.py:234-241`
- **问题**：窗口（如 300 秒）跨越 source epoch 边界时，两侧数据不可比，
  当前没有处理。
- **做法**：定下"窗口遇到 epoch 边界就截断"还是"标脏"，然后实现 + 用例。
- **验收**：构造一个跨 epoch 的窗口，断言不会把两段不可比数据拼成一个信号。

### 5. `IT-P1-SOURCE-EMPTY-001` 空结果 vs 失败
- **位置**：SourceManager + `eastmoney.snapshots`
- **问题**：provider 返回**空列表**（明确说"没有"）与**抛异常**（不知道）
  当前不可区分，故障转移会误判。
- **做法**：source 协议层区分 `[]`（成功但空）与异常（失败），
  `failover` 只在**失败**时切源。
- **验收**：空结果不得触发切源；异常必须触发。
